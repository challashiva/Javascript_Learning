01 Core Web Vitals — what Google actually measures metrics
LCP — Largest Contentful Paint
Time until the biggest visible element loads
The time from navigation start until the largest visible element (hero image, h1, product photo) is fully rendered. Good: < 2.5s. Poor: > 4s. Fix: server-render above-the-fold content, priority on hero images, eliminate render-blocking resources, use CDN. Your LCP element is almost always an image — optimise that image first.
INP — Interaction to Next Paint
Responsiveness to user interactions
Replaced FID in 2024. Measures the worst interaction delay: tap, click, keyboard input. Good: < 200ms. Poor: > 500ms. Fix: break up long JavaScript tasks, defer non-critical work with setTimeout/requestIdleCallback, avoid heavy synchronous computation on the main thread, use web workers for CPU-intensive work.
CLS — Cumulative Layout Shift
Unexpected content movement
Sum of all unexpected layout shifts during page load. Text jumping when fonts load, images resizing when they load, ads pushing content down. Good: < 0.1. Poor: > 0.25. Fix: always set width and height on images, use font-display: optional or preload fonts, reserve space for dynamic content.
TTFB — Time to First Byte
Server response speed
How long until the first byte of the server response arrives. Not a Core Web Vital but influences everything downstream. Good: < 800ms. Fix: Vercel Edge Network puts your server close to users, Next.js caching avoids repeated DB queries, CDN for static assets, connection pooling (Day 23) for DB access.

04 Next.js caching — four layers, one mental model caching
Next.js 15 caching layers — innermost to outermost
1. Request Memoization
Deduplicates identical fetch() calls within a single render pass. If page.tsx and generateMetadata() both call getProduct(id), the DB is hit once. Lasts for the duration of one request. Automatic — no config needed.
2. Data Cache
Persists fetch results across requests on the server. Controlled by cache: "force-cache" (default, permanent), { next: { revalidate: 60 } } (TTL), or cache: "no-store" (no caching). Invalidated by revalidatePath() or revalidateTag().
3. Full Route Cache
Caches the entire rendered HTML + RSC payload of a route at build time (static routes) or after first render (ISR routes). For dynamic routes (using cookies, headers, or no-store), this layer is skipped. Reduces server work for popular pages to near-zero.
4. Router Cache
In-browser cache of visited RSC payloads. When you navigate back to a page, Next.js serves the cached payload instead of re-fetching. Lasts for 5 minutes (static) or 30 seconds (dynamic). Call router.refresh() to invalidate. Not configurable.
typescriptCaching strategies for different data types — ISR, on-demand, no-cache
// ── Static pages (cache forever, revalidate on change) ────
// app/products/page.tsx — revalidate every hour, or on mutation
export const revalidate = 3600  // ISR: rebuild page every hour

// ── Per-fetch caching control ─────────────────────────────
// Cache product catalog for 1 hour (changes slowly)
const products = await fetch("/api/products", {
  next: { revalidate: 3600, tags: ["products"] }
})

// Never cache user cart (personal, changes frequently)
const cart = await fetch("/api/cart", { cache: "no-store" })

// ── unstable_cache — cache Prisma queries ─────────────────
import { unstable_cache } from "next/cache"
import { cache } from "react"

// Cache expensive DB query for 5 minutes, tag for invalidation
export const getFeaturedProducts = unstable_cache(
  async () => db.product.findMany({ where: { featured: true, published: true } }),
  ["featured-products"],
  { revalidate: 300, tags: ["products"] }
)

// Deduplicate within one request (not persisted)
export const getProduct = cache(async (id: string) =>
  db.product.findUnique({ where: { id } })
)

// ── On-demand revalidation — trigger from Server Actions ──
"use server"
import { revalidatePath, revalidateTag } from "next/cache"

export async function updateProduct(id: string, data: object) {
  await db.product.update({ where: { id }, data })
  revalidateTag("products")          // invalidate all fetches tagged "products"
  revalidatePath(`/products/${id}`)   // specific page
  revalidatePath("/products", "layout") // page + all children
}

// ── Dynamic routes — opt out of caching ──────────────────
// These make the route dynamic (no Full Route Cache):
export const dynamic = "force-dynamic"  // always re-render
// or use: cookies(), headers(), searchParams — these auto-opt out
05 React optimizations — memo, useMemo, profiler react
tsxReact.memo, useMemo, useCallback — when they help and when they hurt
// ── React.memo — prevent re-render when props unchanged ───
// Use when: component renders often, props rarely change, render is expensive
// DON'T use when: component renders rarely, or props change every render anyway

const ProductCard = React.memo(function ProductCard({ product, onAddToCart }: Props) {
  console.log("ProductCard render")  // only runs when product or onAddToCart changes
  return (
    <div className="product-card">
      <h3>{product.name}</h3>
      <button onClick={() => onAddToCart(product.id)}>Add to cart</button>
    </div>
  )
})

// ── useCallback — stable function reference for memoized children ──
// Problem: without useCallback, onAddToCart is a new function every render
// → ProductCard.memo sees new prop → re-renders anyway
function ProductList({ products }: { products: Product[] }) {
  const { addItem } = useCart()

  // ✅ Stable reference — only changes if addItem changes
  const handleAddToCart = useCallback((productId: string) => {
    addItem(productId)
  }, [addItem])

  return (
    <div className="grid grid-cols-3 gap-4">
      {products.map(product => (
        <ProductCard key={product.id} product={product} onAddToCart={handleAddToCart} />
      ))}
    </div>
  )
}

// ── useMemo — cache expensive computation ─────────────────
// Use when: computation is truly expensive (sorting 10,000 items, heavy math)
// DON'T use for: simple operations — the overhead of useMemo itself costs time
function ProductDashboard({ orders }: { orders: Order[] }) {
  // ✅ Only recalculate when orders changes
  const stats = useMemo(() => ({
    total:    orders.reduce((s, o) => s + Number(o.total), 0),
    average:  orders.length ? orders.reduce((s, o) => s + Number(o.total), 0) / orders.length : 0,
    byStatus: Object.groupBy(orders, (o) => o.status),  // expensive grouping
  }), [orders])

  // ❌ Don't do this — not worth the overhead
  const count = useMemo(() => orders.length, [orders])  // just use orders.length!

  return <StatsPanel stats={stats} />
}

06 Database query performance — indexes, N+1, select database
typescriptN+1 problem, select vs include, Prisma indexes, query analysis
// ── The N+1 problem — the most common DB performance issue ─
// Bad: 1 query for orders + N queries for each user
const orders = await db.order.findMany()        // 1 query: "SELECT * FROM orders"
for (const order of orders) {
  order.user = await db.user.findUnique({ where: { id: order.userId } })
  // ^ N queries: "SELECT * FROM users WHERE id = ?" for each order
}
// 1 + N queries total. With 100 orders = 101 queries. SLOW.

// Good: 1 query with JOIN via include
const orders = await db.order.findMany({
  include: { user: { select: { id: true, name: true, email: true } } }
})
// 2 queries: orders + users in one batched query. Always fast.

// ── select: fetch only needed columns ──────────────────────
// Bad: fetch all columns including large description + images array
const products = await db.product.findMany()  // description could be 10KB each

// Good: only what the product card needs
const products = await db.product.findMany({
  select: { id: true, name: true, price: true, slug: true,
             images: true,  // first image only
             rating: true, reviewCount: true },
})

// ── Indexes — add for every column you filter/sort by ─────
// In schema.prisma:
// @@index([categoryId])           ← filter by category
// @@index([published, createdAt]) ← filter published + sort by date
// @@index([userId])               ← fetch user's orders

// Check if query uses index (PostgreSQL):
// db.$queryRaw`EXPLAIN ANALYZE SELECT * FROM products WHERE "categoryId" = 'c1'`
// Look for "Index Scan" vs "Seq Scan" — Seq Scan on large tables = missing index

// ── Parallel queries — don't await sequentially ───────────
// Bad: 3 sequential DB queries (sum of all their latencies)
const user     = await db.user.findUnique({ where: { id } })
const orders   = await db.order.findMany({ where: { userId: id } })
const wishlist = await db.wishlist.findMany({ where: { userId: id } })

// Good: parallel (max of all their latencies)
const [user, orders, wishlist] = await Promise.all([
  db.user.findUnique({ where: { id } }),
  db.order.findMany({ where: { userId: id } }),
  db.wishlist.findMany({ where: { userId: id } }),
])

08 Interview questions + model answers 10 Q&As
Q1What are Core Web Vitals and why do they matter for a React app?▶
model answer
Core Web Vitals are Google's set of user experience metrics that directly affect search ranking. LCP (Largest Contentful Paint) measures how quickly the main content loads — good is under 2.5 seconds. INP (Interaction to Next Paint, replaced FID in 2024) measures responsiveness to clicks and taps — good is under 200ms. CLS (Cumulative Layout Shift) measures unexpected layout movement — good is under 0.1.

For React apps specifically: the biggest LCP threat is client-side rendering — a blank HTML shell that shows a spinner while JavaScript runs. Server Components (Next.js) eliminate this by rendering content on the server. The biggest INP threat is heavy JavaScript on the main thread — large re-renders, complex state calculations, or synchronous work blocking user interactions. The biggest CLS cause is images without dimensions or dynamically injected content that pushes existing content down.

Track these in Google Search Console, Chrome UX Report (real user data), or PageSpeed Insights. Lighthouse gives lab measurements — useful for development but field data tells the real story.
Q2How does next/image improve performance compared to a regular img tag?▶
model answer
Four key improvements. First, format conversion: automatically serves WebP or AVIF (30–50% smaller file sizes than JPEG) to browsers that support them, falling back to JPEG/PNG for older browsers. Second, responsive resizing: generates multiple sizes and sends the correct one based on the user's viewport (via srcset), so a mobile user downloading a 200px thumbnail doesn't get a 1200px image. Third, lazy loading: images below the fold are loaded lazily by default, preventing them from competing with above-the-fold content for bandwidth. Fourth, CLS prevention: the width and height props allow the browser to reserve the correct space before the image loads, eliminating layout shift.

The priority prop is important for LCP images — it triggers a preload link in the document head so the browser starts downloading the image as early as possible. Only use it for the hero image or the primary image above the fold; adding it to everything defeats the purpose.
Q3When should you use React.memo, useMemo, and useCallback? And when shouldn't you?▶
model answer
These are performance optimisations with a cost — the memoisation itself consumes time and memory. Only apply them when you've identified a real performance problem with the React Profiler, not preemptively.

React.memo: wrap a component when it renders frequently but its props rarely change, and when the render is expensive enough to be worth the comparison cost. Don't use it on components that always receive different props — the comparison runs every time and adds overhead for no benefit.

useMemo: cache the result of an expensive computation (sorting 10,000 items, complex aggregate calculations) that would otherwise re-run on every render. Don't use it for simple operations like orders.length — the useMemo itself costs more than just running the expression.

useCallback: required when passing a callback to a memoised child component — without it, the function is recreated each render, breaking memo. Also useful for event handlers in useEffect dependency arrays. Don't use it on callbacks that are only called directly in the component's own JSX without affecting memoised children.

The rule: measure first, memoize second. The React Profiler shows exactly which components are re-rendering and why.
Q4What is the N+1 query problem and how do you fix it in Prisma?▶
model answer
N+1 happens when you run 1 query to fetch a list, then N separate queries to fetch related data for each item. With 100 orders, you'd run 101 queries instead of 2 — each round-trip to the database adds latency, so this is catastrophically slow at scale.

The classic pattern: const orders = await db.order.findMany() followed by a loop that calls db.user.findUnique({ where: { id: order.userId } }) for each order. The fix: use Prisma's include to JOIN the related data in a single query: db.order.findMany({ include: { user: { select: { name: true, email: true } } } }). Prisma batches this into 2 efficient queries regardless of how many orders there are.

Detect N+1 in development by enabling Prisma query logging (log: ["query"] in PrismaClient config) — you'll see the repeated queries in the console. Or use the Prisma query event to count queries per request.
Q5What are the four caching layers in Next.js App Router?▶
model answer
From innermost to outermost: Request Memoization — within a single render, identical fetch() calls are deduplicated automatically. If two Server Components both call getProduct(id), the database is hit once. Clears between requests.

Data Cache — persists fetch results on the server across requests. Controlled by { next: { revalidate: 60 } } for TTL-based invalidation, or revalidatePath()/revalidateTag() for on-demand invalidation. This is where most performance wins come from — popular product pages can be cached for hours.

Full Route Cache — stores the entire rendered HTML and RSC payload at build time (static) or after first render (ISR). Dynamic routes (using cookies, headers, or no-store fetches) bypass this. Essentially free page serving for cached routes.

Router Cache — in-browser cache of RSC payloads from pages you've visited. Enables instant back/forward navigation. Lasts 5 minutes for static routes, 30 seconds for dynamic. Call router.refresh() to invalidate.
In Next.js 15, fetch() is no longer cached by default — you must opt in with { cache: "force-cache" } or { next: { revalidate: n } }. This is a breaking change from Next.js 14.
Q6How do you reduce JavaScript bundle size in a Next.js application?▶
model answer
Five main strategies. First, server components by default: code in Server Components never ships to the browser — the biggest free bundle reduction is keeping as much logic as possible server-side. Prisma client, heavy data transformations, and auth checks all stay on the server.

Second, dynamic imports: use next/dynamic to load heavy components only when needed — charts only on the dashboard page, modal components only when opened, rich text editors only when editing. Third, replace heavy libraries: moment (293KB) → dayjs (2KB), lodash (72KB) → lodash-es with named imports or native JS, axios → native fetch.

Fourth, tree shaking: import specifically (import { format } from "date-fns"), not the entire library. Fifth, analyse the bundle: run ANALYZE=true npm run build with @next/bundle-analyzer to see exactly what's taking space — often one unexpected import from a deep dependency causes most bloat. Target: first-load JS under 100KB, individual page JS under 50KB.
Q7What causes Cumulative Layout Shift and how do you prevent it?▶
model answer
CLS is caused by content moving after initial paint. The three most common causes: images without dimensions — the browser doesn't know how much space to reserve, so the page reflows when the image loads. Fix: always provide width and height props on <Image> (or use the fill prop with a parent container that has an explicit aspect ratio).

Web fonts — FOUT (flash of unstyled text) and FOIT (flash of invisible text) cause layout shifts as fonts swap in. Fix: use Next.js's next/font which preloads fonts and uses size-adjust CSS to match fallback metrics, or set font-display: optional which only uses the custom font if it's already cached.

Dynamically injected content — cookie banners, ads, or notification bars that appear above existing content push everything down. Fix: reserve the space in the layout before JavaScript runs, or inject content below existing content (e.g., sticky bottom bar instead of top banner).

Measure with the Layout Instability API or Chrome DevTools Performance panel — it highlights shifting elements in red.
Q8How does code splitting work in Next.js and when should you manually apply it?▶
model answer
Next.js automatically code-splits at the route level — each page gets its own JavaScript chunk that's only downloaded when the user navigates to that page. The shared runtime and common components are in a separate shared chunk. This happens without any configuration.

Manual code splitting via next/dynamic is needed when: a heavy component (chart library, rich text editor, PDF viewer) is on a page but users don't always interact with it. Instead of loading it with the page, you load it lazily: const Chart = dynamic(() => import("./SalesChart"), { loading: () => <Skeleton />, ssr: false }). The ssr: false option skips server-side rendering entirely — useful for components that use browser APIs.

React's lazy + Suspense achieves the same thing in non-Next.js apps: const Modal = lazy(() => import("./Modal")). The difference is that next/dynamic integrates with Next.js's streaming and SSR capabilities, so the loading fallback can be server-rendered while the component loads.
Q9What is ISR (Incremental Static Regeneration) and when should you use it?▶
model answer
ISR is Next.js's strategy for serving static pages that stay fresh without a full rebuild. After the specified revalidation period, the next visitor triggers a background regeneration of the page. The current visitor still gets the (slightly stale) cached version instantly — subsequent visitors get the fresh version. It's "stale-while-revalidate" for entire pages.

Set it at the page level with export const revalidate = 3600 (seconds), or at the fetch level with { next: { revalidate: 3600 } }. For on-demand invalidation (trigger regeneration when an admin publishes a product), use revalidatePath() or revalidateTag() in a Server Action.

Use ISR for: product pages (update when product changes, not every second), blog posts, category pages, any content that changes less frequently than it's viewed. Don't use ISR for: user-specific pages (cart, orders, dashboard — these must be dynamic), real-time data (live prices, stock levels — use client-side fetching or no-store).
Q10How do you measure and improve Time to First Byte (TTFB) in Next.js?▶
model answer
TTFB is the time from the user making a request to receiving the first byte of the response. It directly affects everything else — a slow TTFB means everything downstream starts later. Measure it in Chrome DevTools Network tab → select the document request → Timing → TTFB.

The main causes and fixes: slow database queries — add indexes to commonly filtered columns, use select instead of fetching all columns, avoid N+1, use connection pooling. Profile with db.$on("query", console.log) to find slow queries. No caching — the biggest win is often simply adding Next.js data cache. A product page hitting the DB on every request vs serving from cache is the difference between 800ms and 50ms TTFB. Server location — Vercel's Edge Network deploys your server globally and routes users to the nearest instance. For server-only routes, the Edge runtime reduces cold start times. Cold starts — serverless functions have cold start latency. Warm them with periodic pings, or use Vercel Pro's minimum instances setting.
