Project: ShopCo AI Suite

🛍️ ShopCo AI Suite — Week 5 Capstone
A production-ready AI layer on top of ShopCo with three integrated features: (1) semantic product search powered by pgvector embeddings, (2) a multi-step shopping agent that can search, compare, and recommend, and (3) full observability with Sentry error tracking and Playwright E2E tests that verify AI responses are relevant and don't hallucinate product data.

🔍 Semantic Search

  • Embed all products on import
  • Vector similarity via pgvector
  • Hybrid search with keyword fallback
  • Search results page with similarity score
  • Re-embed on product update webhook

🤖 Shopping Agent

  • 4 tools: search, stock, reviews, cart
  • Streaming responses via useChat
  • Tool call progress shown in UI
  • Confirmation gate before addToCart
  • maxSteps=5 safety limit

🧪 Test Suite

  • Unit: embed(), cosineSimilarity(), tools
  • Integration: RAG pipeline with MSW mocks
  • E2E: Playwright chat flow tests
  • Agent eval: assert product relevance
  • CI: GitHub Actions on every PR

🔭 Observability

  • Sentry on every API route
  • Breadcrumbs: query → embed → retrieve
  • Custom spans for AI latency tracking
  • Alert if embedding pipeline fails
  • Error rate dashboard per feature
🎯 Week 5 Integration principle: Each system from this week is a layer — Performance is the foundation, Testing ensures correctness, Sentry catches what slips through, and the AI features (SDK → RAG → Agents) build on each other. The agent calls the RAG search tool. The RAG pipeline is monitored by Sentry. The whole flow is tested by Playwright. Everything connects.

import { test, expect } from '@playwright/test'

test.describe('ShopCo AI Chat', () => {
  test('agent finds in-stock product for trail query', async ({ page }) => {
    await page.goto('/chat')

    // User asks for trail shoes
    await page.fill('[data-testid="chat-input"]',
      'Find me trail running shoes under $200')
    await page.keyboard.press('Enter')

    // Wait for agent tool calls to resolve
    await page.waitForSelector('[data-testid="tool-call-done"]')

    // Assert response contains relevant product
    const response = await page.textContent('[data-testid="agent-message"]')
    expect(response).toContain('TrailRunner') // must mention a real product
    expect(response).not.toContain('$500') // must respect $200 budget

    // Verify cart button NOT auto-triggered
    await expect(page.locator('[data-testid="order-confirm"]'))
      .not.toBeVisible()
  })

  test('out-of-stock products are flagged correctly', async ({ page }) => {
    await page.goto('/chat')
    await page.fill('[data-testid="chat-input"]', 'I want SpeedMax Elite')
    await page.keyboard.press('Enter')
    await page.waitForSelector('[data-testid="agent-message"]')
    const resp = await page.textContent('[data-testid="agent-message"]')
    expect(resp.toLowerCase()).toMatch(/out of stock|unavailable|not available/)
  })
})

Interview Q&A — Week 5 Mixed

1. How do you test AI-powered features that produce non-deterministic output?
Use determinism at the boundary: mock the LLM/embedding API in unit and integration tests so results are fixed. For E2E tests, use semantic assertions instead of exact string matching — assert "the response mentions a product from the catalog" rather than an exact phrase. Use eval frameworks (RAGAS, custom scripts) on a golden dataset to measure quality metrics (relevance, faithfulness, groundedness) over time. Set alert thresholds: if average relevance drops below 0.8 in evals, block the deploy.
2. What Core Web Vital is most affected by streaming AI responses?
Primarily Interaction to Next Paint (INP) — if you block the UI waiting for a full AI response, interactions feel sluggish. Use streaming (streamText + useChat) so text renders progressively, keeping INP low. CLS (Cumulative Layout Shift) is also affected if the message container resizes as streaming text arrives — use fixed-height containers or reserve space upfront. LCP is less affected since the chat interface is already loaded before the user interacts.
3. How do you implement rate limiting for an AI agent endpoint?
Three layers: (1) Middleware rate limiting — use Upstash Redis with a sliding window, e.g. 10 agent requests per user per minute; (2) Token budget — track cumulative tokens per user per day in Redis, reject when over limit; (3) maxSteps — cap per-request agent loops at 5 steps to bound per-request token usage. Return 429 with a Retry-After header. Log all rate limit hits to Sentry for capacity planning. Consider separate limits for authenticated users vs anonymous.
4. Explain the difference between Vitest's vi.mock() and MSW for API mocking.
vi.mock() replaces a module's exports at the Node.js import level — ideal for mocking internal functions like prisma.product.findMany(), OpenAI client methods, or utility functions. MSW (Mock Service Worker) intercepts real HTTP requests at the network layer — ideal for testing code that calls fetch() and for ensuring your API client code is correct. Use vi.mock() when you own the called code; use MSW when you're testing through an HTTP boundary. For AI tests: mock the OpenAI SDK with vi.mock() in unit tests, use MSW to mock /api/chat in component tests.
5. How would you debug a RAG system that returns irrelevant products?
Systematic debugging: (1) Inspect embeddings — log the query vector and check if similar products have similar vectors (cosine similarity > 0.8 for clearly related items); (2) Check chunking — are product descriptions comprehensive? Missing category/price/tags reduces relevance; (3) Verify index — run EXPLAIN ANALYZE to confirm the HNSW index is being used; (4) Test retrieval — query pgvector directly with known good inputs and verify top-K results; (5) Check model mismatch — ensure you embed queries and documents with the same model and same preprocessing (trimming, case).
6. What is the testing pyramid and how does it apply to AI features?
The pyramid: many unit tests (fast, cheap) → fewer integration tests → fewest E2E tests (slow, expensive). For AI: Unit — test embedding functions, cosine similarity, chunking, tool definitions, tool executors in isolation. Integration — test the RAG pipeline with mocked embeddings, test the agent loop with a scripted fake LLM. E2E — Playwright tests that exercise the full stack including the real LLM (run nightly, not on every PR, because they're slow and cost money). The key insight: mock the LLM at the lowest possible level to keep most tests fast and deterministic.
7. How do you handle Sentry alert fatigue for AI errors?
Alert fatigue happens when too many low-severity errors trigger alerts. Fix with: (1) Fingerprinting — group similar AI errors (e.g. all "rate limit" errors become one Sentry issue, not thousands); (2) Severity tiers — only alert on errors that affect user experience (agent fails to respond), not transient tool errors the agent recovered from; (3) Error sampling — in production, sample LLM errors at 10% if they're known flaky, 100% for unknown errors; (4) Alert on rate, not count — "error rate > 5% of requests" is more useful than "100 errors in last hour".
8. What's the difference between an AI agent and a simple chatbot?
A chatbot generates text from conversation history — it can only say things, not do things. An agent has tools (functions it can call), memory (the message history grows with each tool result), and autonomy (it decides what to do next based on observations). An agent can search your database, check inventory, compare options, and add items to a cart — all in one conversation turn, without the user specifying each step. The ReAct loop (Reason → Act → Observe → repeat) is what gives agents their autonomous behaviour.
9. How do you measure the ROI of adding AI features to ShopCo?
Key metrics: (1) Conversion lift — A/B test: do users who interact with the AI agent buy more? (2) Search satisfaction — compare click-through rate on semantic search results vs keyword search; (3) Support deflection — how many customer support tickets does the AI answer correctly, reducing human workload? (4) Session depth — do AI users view more products per session? (5) Cost per interaction — track token costs per user session and ensure LTV > CAC + AI cost. Use PostHog or Amplitude to track these. Good AI features show positive ROI within 30–60 days of launch.
10. Summarise Week 5 — what's the most important thing you learned?
Week 5 showed that AI features are just software features — they need the same engineering discipline as any other system: testing (don't skip it because outputs are fuzzy), monitoring (Sentry catches AI failures just like regular bugs), and performance profiling (embedding latency, vector search speed, and LLM time-to-first-token all matter). The key architectural insight: RAG + Agents are complementary — RAG gives the agent accurate, up-to-date knowledge; the agent decides what to do with it. Together they produce a system that actually helps users rather than hallucinating answers.
