01 Event handlers — React's synthetic event system foundation
synthetic events
React wraps native browser events
React uses SyntheticEvent — a cross-browser wrapper around the native DOM event. It has the same API (e.target, e.preventDefault(), e.stopPropagation()) but works identically across all browsers. Under the hood, React uses event delegation — all events are attached to the root container, not individual elements.
naming
camelCase, pass functions not calls
React event props are camelCase: onClick, onChange, onSubmit, onKeyDown. Pass a function reference, not a call — onClick={handleClick} not onClick={handleClick()}. The second form calls the function immediately during render and passes its return value.
closures
Handlers close over current state
Every render creates new handler functions that close over that render's state values. This means a handler always sees the state from when it was created. This is why stale closures happen — and why the functional update form setState(prev => ...) is safer when basing new state on old state.
jsxEvent handler patterns — inline, named, passing data, preventing defaults
// ── Inline vs named handlers ──────────────────────────────
// Inline — fine for simple one-liners
<button onClick={() => setCount(c => c + 1)}>+</button>

// Named — better for anything multi-line or reused
function handleDelete(e) {
  e.stopPropagation()   // prevent bubbling to parent's onClick
  onDelete(task.id)
}
<button onClick={handleDelete}>Delete</button>

// ── Passing data with arrow wrapper ───────────────────────
// When you need to pass an argument to a handler
{tasks.map(task => (
  <li key={task.id}>
    {task.text}
    <button onClick={() => handleDelete(task.id)}>✕</button>
  </li>
))}

// ── Curried handler (avoids new function per render) ──────
const handlePriorityChange = (id) => (e) => {
  updateTask(id, { priority: e.target.value })
}
<select onChange={handlePriorityChange(task.id)}>...</select>

// ── Common event object properties ────────────────────────
function handleKeyDown(e) {
  e.key           // "Enter", "Escape", "a", "ArrowUp"
  e.code          // physical key: "KeyA", "Enter"
  e.target        // element that fired event
  e.target.value  // for inputs
  e.target.name   // input name attribute
  e.target.checked// for checkboxes
  e.shiftKey      // modifier keys
  e.ctrlKey
  e.metaKey       // Cmd on Mac

  if (e.key === "Enter") submitForm()
  if (e.key === "Escape") resetForm()
  if (e.ctrlKey && e.key === "z") undo()
}

// ── Form submit — prevent default is critical ─────────────
function handleSubmit(e) {
  e.preventDefault()  // ALWAYS — stops page reload
  // process form data...
}
<form onSubmit={handleSubmit}>...</form>

// ── Mouse events ──────────────────────────────────────────

  onClick={handleClick}

02 Lifting state up — React's core data flow pattern critical pattern
The one-way data flow rule
data flows down
State is passed to children as props. Children read it but cannot change it directly.
events flow up
Children notify parents of changes by calling callback functions passed as props.
when to lift
When two sibling components need to share or react to the same state, lift it to their nearest common parent.
where to put state
As low as possible — only lift when necessary. Local state is simpler and more isolated.
jsxLifting state — search filter + results sharing the same state
// ── Problem: two siblings need to share state ─────────────
// SearchBar needs to UPDATE the query
// ResultsList needs to READ the query
// Solution: lift query state to their shared parent

function SearchBar({ query, onQueryChange }) {    // receives state + setter as props
  return (
    <input
      type="search"
      value={query}
      onChange={e => onQueryChange(e.target.value)}
      placeholder="Search products..."
    />
  )
}

function ResultsList({ products, query }) {        // reads state via prop
  const filtered = products.filter(p =>
    p.name.toLowerCase().includes(query.toLowerCase())
  )
  return (
    <ul>
      {filtered.length === 0
        ? <li>No results for "{query}"</li>
        : filtered.map(p => <li key={p.id}>{p.name}</li>)
      }
    </ul>
  )
}

// Parent OWNS the state — passes it down as props
function ProductSearch({ products }) {
  const [query, setQuery] = useState("")

  return (
    <div>
      <SearchBar query={query} onQueryChange={setQuery} />  // passes setter down
      <ResultsList products={products} query={query} />    // passes state down
    </div>
  )
}

// ── Callback pattern — child notifies parent ──────────────
function TaskItem({ task, onToggle, onDelete, onEdit }) {
  return (
    <li>
      <input
        type="checkbox"
        checked={task.done}
        onChange={() => onToggle(task.id)}   // calls parent's handler
      />
      <span onDoubleClick={() => onEdit(task.id)}>{task.text}</span>
      <button onClick={() => onDelete(task.id)}>✕</button>
    </li>
  )
}

function TaskList() {
  const [tasks, setTasks] = useState(...)

  const toggle = (id) => setTasks(p => p.map(t => t.id===id ? {...t,done:!t.done} : t))
  const remove = (id) => setTasks(p => p.filter(t => t.id !== id))

  return tasks.map(t =>
    <TaskItem key={t.id} task={t} onToggle={toggle} onDelete={remove} />
  )
}
03 Controlled inputs — every input type daily use
controlled
React owns the value
A controlled input has its value (or checked) driven by React state, and an onChange that updates that state. React is the single source of truth. You can validate, format, or restrict input on every keystroke. The input always displays exactly what state holds.
uncontrolled
DOM owns the value
An uncontrolled input stores its value in the DOM. You read it when needed with a ref. Simpler to set up, but you can't validate as the user types, can't programmatically set the value, and can't derive state from it. Use for file inputs or when you only need the value on submit.
common bug
undefined/null value → uncontrolled warning
If you pass value={undefined} or value={null}, React treats the input as uncontrolled. Then when you set a value later, React warns: "component changing uncontrolled to controlled". Always initialise state with "" for text, false for checkboxes, never undefined.
jsxAll input types — text, checkbox, select, radio, textarea
function AllInputTypes() {
  const [form, setForm] = useState({
    name:        "",           // text — NEVER undefined
    email:       "",
    password:    "",
    bio:         "",           // textarea
    role:        "user",       // select
    newsletter:  false,        // checkbox — NEVER undefined
    theme:       "light",      // radio group
    age:         "",           // number input (store as string, parse on submit)
  })

  // ── Generic onChange — handles ALL input types ─────────
  const handleChange = (e) => {
    const { name, value, type, checked } = e.target
    setForm(prev => ({
      ...prev,
      [name]: type === "checkbox" ? checked : value   // checkboxes use .checked
    }))
  }

  return (
    <form onSubmit={handleSubmit}>

      {/* Text input */}
      <input
        type="text"
        name="name"
        value={form.name}
        onChange={handleChange}
        placeholder="Your name"
      />

      {/* Textarea */}
      <textarea
        name="bio"
        value={form.bio}
        onChange={handleChange}
        rows={4}
      />

      {/* Select dropdown */}
      <select name="role" value={form.role} onChange={handleChange}>
        <option value="user">User</option>
        <option value="admin">Admin</option>
        <option value="editor">Editor</option>
      </select>

      {/* Checkbox */}
      <label>
        <input
          type="checkbox"
          name="newsletter"
          checked={form.newsletter}   // checkboxes use checked, not value
          onChange={handleChange}
        />
        Subscribe to newsletter
      </label>

      {/* Radio group */}
      {["light", "dark", "system"].map(t => (
        <label key={t}>
          <input
            type="radio"
            name="theme"           // same name groups radios
            value={t}
            checked={form.theme === t}  // controlled by comparison
            onChange={handleChange}
          />
          {t}
        </label>
      ))}

      <button type="submit">Save</button>
    </form>
  )
}
04 Form validation — real production patterns real-world
jsxValidation on blur, on submit, field-level errors, touched tracking
function SignupForm() {
  const [values,  setValues]  = useState({ name: "", email: "", password: "" })
  const [errors,  setErrors]  = useState({})
  const [touched, setTouched] = useState({})  // tracks which fields user visited
  const [submitting, setSubmitting] = useState(false)

  // ── Validate a single field ────────────────────────────
  const validateField = (name, value) => {
    switch (name) {
      case "name":
        if (!value.trim())              return "Name is required"
        if (value.length < 2)          return "Name must be at least 2 characters"
        return ""
      case "email":
        if (!value)                     return "Email is required"
        if (!value.includes("@"))     return "Enter a valid email"
        return ""
      case "password":
        if (value.length < 8)         return "Password must be 8+ characters"
        if (!/[A-Z]/.test(value))    return "Include at least one uppercase letter"
        return ""
      default: return ""
    }
  }

  // ── onChange — update value + re-validate if touched ──
  const handleChange = (e) => {
    const { name, value } = e.target
    setValues(prev => ({ ...prev, [name]: value }))
    if (touched[name]) {
      setErrors(prev => ({ ...prev, [name]: validateField(name, value) }))
    }
  }

  // ── onBlur — mark field as touched, validate ──────────
  const handleBlur = (e) => {
    const { name, value } = e.target
    setTouched(prev => ({ ...prev, [name]: true }))
    setErrors(prev  => ({ ...prev, [name]: validateField(name, value) }))
  }

  // ── onSubmit — validate all, block if errors ──────────
  const handleSubmit = async (e) => {
    e.preventDefault()

    // Validate all fields at once
    const allErrors = Object.fromEntries(
      Object.entries(values).map(([k, v]) => [k, validateField(k, v)])
    )
    setErrors(allErrors)
    setTouched({ name: true, email: true, password: true })

    const hasErrors = Object.values(allErrors).some(e => e !== "")
    if (hasErrors) return   // stop if any field invalid

    setSubmitting(true)
    try {
      await createUser(values)
    } finally {
      setSubmitting(false)
    }
  }

  // Derived: form is valid when all touched fields have no errors
  const isValid = Object.keys(values).every(k => !validateField(k, values[k]))

  return (
    <form onSubmit={handleSubmit}>
      <input
        name="email"
        value={values.email}
        onChange={handleChange}
        onBlur={handleBlur}                               // validate when leaving field
        className={touched.email && errors.email ? "error" : ""}
      />
      {touched.email && errors.email && (
        <p className="error-msg">{errors.email}</p>      // only show after touching
      )}
      <button type="submit" disabled={submitting}>
        {submitting ? "Saving..." : "Sign up"}
      </button>
    </form>
  )
}
05 Derived state & useReducer state patterns
derived state
Compute, don't store
If a value can be computed from existing state or props, don't put it in state. Derived state (computed inline during render) is always in sync, never stale, and requires no synchronisation logic. Classic mistakes: storing a filtered list alongside the raw list, storing a total alongside items, storing a boolean "isSelected" that can be derived by comparison.
useReducer
For complex, related state updates
When state has multiple sub-values that change together, or when the next state depends on the previous in complex ways, useReducer is cleaner than multiple useState calls. The reducer is a pure function (state, action) => newState — the same pattern as the Redux store from Week 1 Day 7.
when to choose
useState vs useReducer
Use useState when: state is simple (primitives, small objects), updates are independent, few state variables. Use useReducer when: multiple state values update together, next state depends on previous in complex ways, state update logic is long and worth naming, or you want to extract state logic for testing.
jsxDerived state examples + useReducer for a todo app
// ── Derived state — compute during render ─────────────────
function CartSummary() {
  const [items, setItems] = useState([
    { id: 1, name: "Laptop", price: 999, qty: 1 },
    { id: 2, name: "Mouse",  price: 29,  qty: 2 },
  ])

  // ✓ DERIVED — computed from items, not stored separately
  const total     = items.reduce((s, i) => s + i.price * i.qty, 0)
  const itemCount = items.reduce((s, i) => s + i.qty, 0)
  const isEmpty   = items.length === 0
  const hasDiscount = total > 500                   // derived from total

  // ✗ DON'T do this — creates stale state risk
  // const [total, setTotal] = useState(0)  // redundant!

  return (
    <div>
      <p>{itemCount} items · ${total}</p>
      {hasDiscount && <p>10% discount applied!</p>}
    </div>
  )
}

// ── useReducer — task manager state ──────────────────────
const initialState = { tasks: [], filter: "all", nextId: 1 }

function taskReducer(state, action) {
  switch (action.type) {
    case "ADD":
      return {
        ...state,
        tasks: [...state.tasks, {
          id:       state.nextId,
          text:     action.payload,
          done:     false,
          priority: "medium"
        }],
        nextId: state.nextId + 1
      }
    case "TOGGLE":
      return {
        ...state,
        tasks: state.tasks.map(t =>
          t.id === action.payload ? { ...t, done: !t.done } : t
        )
      }
    case "DELETE":
      return { ...state, tasks: state.tasks.filter(t => t.id !== action.payload) }
    case "SET_FILTER":
      return { ...state, filter: action.payload }
    default:
      return state
  }
}

function TaskApp() {
  const [state, dispatch] = useReducer(taskReducer, initialState)

  // Derived state from reducer state
  const visibleTasks = state.tasks.filter(t => {
    if (state.filter === "done")    return  t.done
    if (state.filter === "active")  return !t.done
    return true
  })

  return (
    <div>
      <input
        onKeyDown={e => {
          if (e.key === "Enter" && e.target.value.trim()) {
            dispatch({ type: "ADD", payload: e.target.value })
            e.target.value = ""
          }
        }}
      />
      {visibleTasks.map(t => (
        <div key={t.id}>
          <input
            type="checkbox"
            checked={t.done}
            onChange={() => dispatch({ type: "TOGGLE", payload: t.id })}
          />
          {t.text}
          <button onClick={() => dispatch({ type: "DELETE", payload: t.id })}>✕</button>
        </div>
      ))}
    </div>
  )
}

07 Interview questions + model answers 10 Q&As
Q1What does "lifting state up" mean and when do you do it?▶
model answer
Lifting state up means moving state from a child component to its parent so that multiple children can share or react to it. You do it when two sibling components need to read the same state, or when a child's action needs to affect another part of the tree.

The pattern: the parent owns the state and passes it down as props. Children receive a callback function (also as a prop) to request state changes — they call it when something happens, and the parent updates the state, triggering re-renders of all affected children.

Put state as low in the tree as possible — only lift when necessary. Lifting too eagerly makes code harder to maintain and causes unnecessary re-renders.
Real example: "In a product search page, I had a SearchBar and a ProductGrid as siblings. The query state lived in SearchBar at first, which meant ProductGrid couldn't access it. Lifting query to the shared parent fixed it — SearchBar calls onQueryChange, the parent updates, ProductGrid re-renders with the new query."
Q2What is a controlled component? Why is it preferred over uncontrolled?▶
model answer
A controlled component is an input whose value is driven by React state. The input's value prop comes from state, and an onChange handler updates that state. React is the single source of truth.

This is preferred because: you can validate or transform the input on every keystroke, you can programmatically set or clear the value, you can derive other UI state from the input (e.g. showing a character count), and the input always reflects exactly what's in state — there's no divergence between DOM state and React state.

Uncontrolled inputs (reading via ref) are fine for simple cases like file inputs or when you only need the value on submit, but for any interactive form — validation, formatting, conditional fields — controlled is the right choice.
Q3What is the difference between onChange and onInput in React? What about onChange and onBlur for validation?▶
model answer
In React, onChange fires on every keystroke — it behaves like the native DOM input event, not the native change event (which only fires when focus leaves). React normalised this because "fires on every keystroke" is almost always what you want for controlled inputs.

For validation timing: onChange validates as the user types — useful for character limits or real-time feedback, but can be annoying if errors appear before the user finishes. onBlur validates when the user leaves the field — better UX for most cases. The best pattern is: show errors on blur (after first visit), then re-validate on change once the field is touched. This is what Formik and React Hook Form do by default.
Q4When would you use useReducer instead of useState?▶
model answer
useReducer is better than multiple useState calls when: state has multiple sub-values that always update together (form with many fields, a pagination object with page/pageSize/total), when the next state depends on the previous in complex ways, or when there are many different ways to update the same state (many action types).

useState is simpler and sufficient for: primitive values, simple objects with independent fields, or when state updates are straightforward.

A good rule of thumb: if you find yourself calling 3+ setState functions in the same handler, consider useReducer. It also makes logic more testable — the reducer is a pure function that you can unit test without rendering anything.
Mental model: useReducer is useState with the update logic extracted into a named function. It also pairs naturally with useContext to create a lightweight global state solution without Redux.
Q5What is derived state? Why is storing it a mistake?▶
model answer
Derived state is any value that can be computed from existing state or props — a filtered list, a total, a boolean "isEmpty", a count. Storing it in state is a mistake because: it creates synchronisation risk (you have to update both the source and the derived value together), it makes code more complex, and it can easily become stale when you forget to update it.

The fix is simple — compute the value inline during render. React re-runs the component on every state change, so derived values are always fresh:
const total = items.reduce((s, i) => s + i.price, 0)

For expensive computations, use useMemo to cache the result and only recompute when dependencies change — but this is an optimisation, not required by default.
Q6How do you handle a form with many fields without writing an onChange for each?▶
model answer
Use a generic handleChange function that reads the input's name attribute and uses it as a computed key to update the corresponding field in the form state object:

const handleChange = (e) => setForm(prev => ({...prev, [e.target.name]: e.target.type === "checkbox" ? e.target.checked : e.target.value}))

Then give every input a name attribute matching its state key. This one function handles all text inputs, textareas, selects, and checkboxes. For radio buttons, the same function works since they also have a name attribute.

This pattern is what React Hook Form uses internally — one handler, many fields.
Q7What is React's one-way data flow? Why is it beneficial?▶
model answer
One-way data flow means data flows in one direction: from parent to child via props. Children cannot directly modify parent state — they request changes via callbacks passed as props. This creates a predictable, unidirectional flow: state lives at a fixed level of the tree, flows down, and changes flow back up through callbacks.

Benefits: it's easier to trace where a bug came from (follow the data up the tree), it's easier to reason about what causes a component to re-render, and it makes components more reusable (a child component is a pure function of its props).

The alternative — two-way data binding (like Angular v1) — makes it hard to trace which component changed what, leading to cascading updates that are difficult to debug.
Q8How do you prevent a form from submitting when there are validation errors?▶
model answer
Three layers: First, always call e.preventDefault() in the onSubmit handler to prevent the browser's default page reload. Second, run all validations synchronously in the submit handler, update the errors state, and return early if any errors exist. Third, optionally disable the submit button when the form is invalid (though this can be frustrating UX — disabled buttons don't explain why they're disabled).

Best practice: validate on submit (shows all errors at once), but also re-validate on change for fields the user has already touched (so errors disappear as soon as they're fixed). Never rely on HTML5 required or pattern attributes alone — they can be bypassed and don't give you control over error message styling.
Q9What is the difference between e.target and e.currentTarget in a React event handler?▶
model answer
e.target is the element the event originated on — the actual element the user clicked or typed in. e.currentTarget is the element the event listener is attached to.

In most single-element event handlers these are the same. They differ when events bubble — if you have a click handler on a <div> and the user clicks a <button> inside it, e.target is the button and e.currentTarget is the div.

In React form handlers, you almost always want e.target — you want to know which actual input was changed, not which parent form the event bubbled to. The generic handleChange pattern uses e.target.name and e.target.value specifically because of this.
Q10Why does React warn about changing a component from uncontrolled to controlled?▶
model answer
This warning means an input switched from having no value prop (uncontrolled — DOM owns the value) to having a value prop (controlled — React owns the value). React flags this because it means the DOM's current value and React's state may be out of sync, which can cause the input to suddenly jump to a different value.

The most common cause: initialising state to undefined or null instead of "". When state is undefined, value={undefined} is treated as no value prop — uncontrolled. When state becomes a string, the input is suddenly controlled.

Fix: always initialise text input state to "", checkbox state to false, select state to a valid option value, never to undefined.
The same warning can happen if you load async data: the input renders with undefined while loading, then switches to controlled when data arrives. Use a loading state or default to empty string: const [name, setName] = useState(""), not useState(undefined).
