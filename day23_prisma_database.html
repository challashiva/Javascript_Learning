01 Why Prisma — the gap between SQL and TypeScript motivation
raw SQL pain
Strings that TypeScript can't check
With raw SQL: db.query("SELECT * FROM users WHERE id = " + userId) — SQL injection risk. No autocomplete. Typo in a column name → runtime error. Return type is any. Refactoring a column means hunting through string literals. Every query is a potential bug.
Prisma solution
Your DB schema becomes TypeScript types
Prisma generates a client from your schema. Every model becomes a TypeScript type. Every query is fully typed — typo in a field name → compile error. Autocomplete on every query parameter. Return types match exactly what you asked for. Refactoring is safe — the compiler guides you.
vs other ORMs
Better DX than Sequelize, TypeORM, Mongoose
Sequelize and TypeORM: class decorators, manual type annotations that drift from schema, complex association setup. Mongoose: JavaScript-only, no compile-time safety. Prisma: schema is the single source of truth, generated client is always in sync, queries are clean JS objects — no decorators, no classes.
the workflow
Schema → generate → migrate → query
Define your data model in schema.prisma. Run prisma generate to update the TypeScript client. Run prisma migrate dev to update the database schema. Write queries with full autocomplete and type safety. This cycle takes seconds and keeps code, types, and database always in sync.
02 The Prisma schema — models, fields, relations schema
prismaComplete React Shop schema — all models, all field types, all relation types
// prisma/schema.prisma

generator client {
  provider = "prisma-client-js"
}

datasource db {
  provider = "postgresql"          // or "sqlite", "mysql", "mongodb"
  url      = env("DATABASE_URL")
}

// ── User model ────────────────────────────────────────────
model User {
  id        String   @id @default(cuid())   // auto-generated collision-resistant ID
  clerkId   String   @unique                  // Clerk's user ID — for auth linkage
  email     String   @unique
  name      String
  imageUrl  String?                           // optional field (can be null)
  role      Role     @default(USER)
  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt               // auto-set on every update

  // Relations
  orders    Order[]                           // one user → many orders
  reviews   Review[]
  cart      CartItem[]

  @@map("users")                              // actual DB table name
}

enum Role { USER  ADMIN  MODERATOR }

// ── Product model ─────────────────────────────────────────
model Product {
  id          String   @id @default(cuid())
  name        String
  slug        String   @unique
  description String
  price       Decimal  @db.Decimal(10, 2)   // precise money — not Float!
  stock       Int      @default(0)
  images      String[]                         // array of image URLs
  published   Boolean  @default(false)
  createdAt   DateTime @default(now())
  updatedAt   DateTime @updatedAt

  categoryId  String
  category    Category @relation(fields: [categoryId], references: [id])

  reviews     Review[]
  orderItems  OrderItem[]
  cartItems   CartItem[]
  tags        Tag[]     @relation("ProductTags")  // many-to-many

  @@index([categoryId])          // create DB index for common queries
  @@index([published, createdAt]) // composite index
}

// ── Order model ───────────────────────────────────────────
model Order {
  id        String      @id @default(cuid())
  status    OrderStatus @default(PENDING)
  total     Decimal     @db.Decimal(10, 2)
  createdAt DateTime    @default(now())

  userId    String
  user      User        @relation(fields: [userId], references: [id], onDelete: CASCADE)
  items     OrderItem[]
}

enum OrderStatus { PENDING  PROCESSING  SHIPPED  DELIVERED  CANCELLED }

// ── Junction table for N:M ───────────────────────────────
model Tag {
  id       String    @id @default(cuid())
  name     String    @unique
  products Product[] @relation("ProductTags")
}

# After editing schema.prisma:

// ── lib/db.ts — singleton to avoid connection pool exhaustion ─
// In development, Next.js hot-reloads files, which would create a
// new PrismaClient on every reload → too many connections.
// The singleton pattern reuses the existing instance.
import { PrismaClient } from "@prisma/client"

const globalForPrisma = globalThis as unknown as { prisma: PrismaClient | undefined }

export const db = globalForPrisma.prisma ?? new PrismaClient({
  log: process.env.NODE_ENV === "development"
    ? ["query", "error", "warn"]  // log all queries in dev
    : ["error"],                   // only errors in prod
})

if (process.env.NODE_ENV !== "production") {
  globalForPrisma.prisma = db
}

// Usage in any Server Component or Server Action:
import { db } from "@/lib/db"
const user = await db.user.findUnique({ where: { id: "..." } })
// user is typed as: User | null   — from your schema!

// ── Generated types you can import ───────────────────────
import type { User, Product, Order, OrderStatus, Prisma } from "@prisma/client"

// Use Prisma namespace for complex types:
type ProductWithCategory = Prisma.ProductGetPayload<{
  include: { category: true }
}>
// → Product & { category: Category }  — exactly what the query returns!

type CreateProductInput = Prisma.ProductCreateInput  // input type for create()
type UpdateProductInput = Prisma.ProductUpdateInput  // input type for update()
04 CRUD queries — every operation you'll use daily queries
typescriptfindMany, findUnique, create, update, upsert, delete — with filtering and pagination
import { db } from "@/lib/db"

// ── findMany — list with filter, sort, pagination ─────────
const products = await db.product.findMany({
  where: {
    published:  true,
    stock:      { gt: 0 },              // gt=greater-than, gte, lt, lte
    price:      { gte: 10, lte: 500 },  // between 10 and 500
    name:       { contains: "Pro", mode: "insensitive" },  // case-insensitive search
    categoryId: "cat_electronics",
    NOT:        { status: "DRAFT" },     // negation
    OR: [                               // logical OR
      { price: { lt: 50 } },
      { tags: { some: { name: "sale" } } }
    ],
  },
  orderBy: [
    { createdAt: "desc" },
    { name: "asc" },               // tie-break
  ],
  skip:  (page - 1) * pageSize,       // offset pagination
  take:  pageSize,
  select: {                           // only fetch these fields (more efficient)
    id: true, name: true, price: true, images: true
  },
})
// products: Array of { id, name, price, images } — exactly what select specified

// ── findUnique — single record by unique field ────────────
const product = await db.product.findUnique({
  where: { id: "prod_123" },   // or { slug: "macbook-pro" }
})
// product: Product | null

// findFirst — first match (non-unique where clause)
const latest = await db.product.findFirst({
  where: { categoryId: "cat_1" },
  orderBy: { createdAt: "desc" },
})

// ── count ─────────────────────────────────────────────────
const total = await db.product.count({ where: { published: true } })

// ── create ────────────────────────────────────────────────
const newProduct = await db.product.create({
  data: {
    name:       "MacBook Pro",
    slug:       "macbook-pro",
    description:"Apple M3 chip",
    price:      1999.99,
    stock:      50,
    category:  { connect: { id: "cat_electronics" } },  // relate to existing
    tags:       { connect: [{ name: "laptop" }, { name: "apple" }] },
  },
})

// ── update ────────────────────────────────────────────────
const updated = await db.product.update({
  where: { id: "prod_123" },
  data:  {
    stock: { decrement: 1 },     // atomic operations: increment, decrement, multiply
    price: 1799.99,
  },
})

// ── upsert — create or update ─────────────────────────────
const user = await db.user.upsert({
  where:  { clerkId: "user_abc" },
  update: { name: "Alice Smith", email: "new@email.com" },
  create: { clerkId: "user_abc", name: "Alice", email: "alice@email.com" },
})

// ── delete ────────────────────────────────────────────────
await db.product.delete({ where: { id: "prod_123" } })
await db.product.deleteMany({ where: { published: false, stock: 0 } })
05 Relations — include, select, nested writes relations
typescriptinclude vs select, nested creates, many-to-many, relationship filtering
// ── include — fetch related records ───────────────────────
const product = await db.product.findUnique({
  where: { id: "prod_123" },
  include: {
    category: true,          // include full Category object
    reviews:  {
      where:   { rating: { gte: 4 } },   // filter related records
      orderBy: { createdAt: "desc" },
      take:    5,
      include: { user: { select: { name: true, imageUrl: true } } },
    },
    tags:     true,
    // _count to count related records without fetching them
    _count: { select: { reviews: true, orderItems: true } }
  },
})
// product.reviews → Review[] (filtered), product.category → Category
// product._count.reviews → number

// ── include vs select — when to use each ─────────────────
// include: Product + extra fields appended
// select: only the fields you specify (can include relations)
const lean = await db.product.findMany({
  select: {
    id: true, name: true, price: true,
    category: { select: { name: true } },   // nested select
  }
})
// lean: { id, name, price, category: { name } }[] — nothing else

// ── Nested create — create related records together ───────
const order = await db.order.create({
  data: {
    userId: "user_123",
    total:  299.99,
    items:  {
      create: [                          // create related OrderItems inline
        { productId: "prod_1", quantity: 2, price: 99.99 },
        { productId: "prod_2", quantity: 1, price: 100.01 },
      ]
    }
  },
  include: { items: { include: { product: true } } }
})

// ── Many-to-many — tags on products ──────────────────────
// Connect existing tags:
await db.product.update({
  where: { id: "prod_123" },
  data: {
    tags: {
      connect:    [{ id: "tag_sale" }],    // add tags
      disconnect: [{ id: "tag_old" }],     // remove tags
      set:        [{ id: "tag_new" }],     // replace all tags
    }
  }
})

// ── Filter by relation ────────────────────────────────────
// Products that HAVE at least one review with rating >= 4
await db.product.findMany({
  where: { reviews: { some: { rating: { gte: 4 } } } }
})

// Products that have NO reviews:
await db.product.findMany({
  where: { reviews: { none: {} } }
})

// Products where ALL reviews have rating >= 3:
await db.product.findMany({
  where: { reviews: { every: { rating: { gte: 3 } } } }
})

# ── Seed script ──────────────────────────────────────────
# package.json: "prisma": { "seed": "ts-node prisma/seed.ts" }
# prisma/seed.ts:
import { db } from "../lib/db"

async function main() {
  await db.category.createMany({
    data: [
      { name: "Electronics", slug: "electronics" },
      { name: "Clothing",     slug: "clothing" },
    ],
    skipDuplicates: true,   // safe to re-run
  })
}
main().catch(console.error).finally(() => db.$disconnect())
# Run: npx prisma db seed

// ── $transaction — atomic operations ──────────────────────
// All succeed or all fail — no partial updates

// Sequential transaction (operations run in order, can use results)
const [order, updatedStock] = await db.$transaction([
  db.order.create({ data: { userId: "u1", total: 99 } }),
  db.product.update({ where: { id: "p1" }, data: { stock: { decrement: 1 } } })
])
// If either fails, both are rolled back

// Interactive transaction (can use results of earlier operations)
await db.$transaction(async (tx) => {
  // Check stock first
  const product = await tx.product.findUnique({ where: { id: "p1" } })

  if (!product || product.stock < 1) {
    throw new Error("Out of stock")   // throws → rolls back the whole transaction
  }

  // Decrement stock and create order atomically
  const order = await tx.order.create({
    data: { userId: "u1", total: product.price }
  })
  await tx.product.update({
    where: { id: "p1" },
    data:  { stock: { decrement: 1 } }
  })
  return order
})
07 Production patterns — pagination, raw SQL, connection pooling production
typescriptCursor pagination, aggregations, raw SQL, Supabase/PlanetScale setup
// ── Cursor-based pagination (better than offset for feeds) ─
async function getProducts({ cursor, take = 20 }: { cursor?: string; take?: number }) {
  const products = await db.product.findMany({
    take:   take + 1,            // fetch one extra to check hasMore
    cursor: cursor ? { id: cursor } : undefined,
    skip:   cursor ? 1 : 0,      // skip the cursor item itself
    orderBy:{ createdAt: "desc" },
  })
  const hasMore  = products.length > take
  const items    = hasMore ? products.slice(0, -1) : products
  const nextCursor = hasMore ? items.at(-1)?.id : undefined
  return { items, hasMore, nextCursor }
}

// ── Aggregations ──────────────────────────────────────────
const stats = await db.order.aggregate({
  _sum: { total: true },        // total revenue
  _avg: { total: true },        // average order value
  _count: { _all: true },      // order count
  _min: { createdAt: true },   // first order date
  where: { status: "DELIVERED" },
})
stats._sum.total    // Decimal | null

// Group by — revenue by category
const byCategory = await db.product.groupBy({
  by: ["categoryId"],
  _sum: { price: true },
  _count: true,
  having: { price: { _avg: { gt: 100 } } }  // filter groups

09 Interview questions + model answers 10 Q&As
Q1What is Prisma and why is it preferred over raw SQL or other ORMs?▶
model answer
Prisma is a next-generation ORM that generates a type-safe client from your schema. The three core advantages over alternatives: type safety — every query is fully typed, typos in field names are compile errors, return types match exactly what you asked for; schema as single source of truth — your schema file defines the database structure and the TypeScript types simultaneously, no drift; developer experience — autocomplete on every query argument, Prisma Studio as a visual browser, clear error messages.

Versus raw SQL: raw SQL strings can't be type-checked, have SQL injection risk if not careful, and require manual TypeScript type annotations. Versus Sequelize/TypeORM: those use class decorators and manual type sync that often drifts from the real schema. Prisma generates the client fresh from your actual schema — it's always accurate.
Q2What is the difference between include and select in Prisma?▶
model answer
include appends relation data to the query result — you get the full model plus the related records. select specifies exactly which fields to return — you only get what you ask for, and it can include relations too.

include: { category: true } returns Product & { category: Category } — all product fields plus the full category. select: { name: true, price: true, category: { select: { name: true } } } returns only those three fields — nothing else, which is more efficient for list views where you don't need every column.

You can't use both include and select at the same level — pick one. For performance: prefer select in list views (only fetch what you render), use include in detail views (fetch the full object and its relations). The _count modifier lets you count relations without fetching them: include: { _count: { select: { reviews: true } } }.
Q3When and why would you use Prisma's $transaction?▶
model answer
Use $transaction when multiple database operations must either all succeed or all fail — partial completion would leave the data in an inconsistent state. The classic example: placing an order requires creating the order record AND decrementing stock. If the order creates but the stock decrement fails (or vice versa), the database is in a bad state.

Two forms: sequential — db.$transaction([op1, op2, op3]) — runs all operations in a single transaction but can't use the result of op1 in op2. Interactive — db.$transaction(async (tx) => { ... }) — you get a transaction-scoped client where you can read then write based on results. If you throw inside the callback, the entire transaction rolls back.

For the stock-check case: read the product inside the transaction, check the stock, then decrement. Because it's all in one transaction, another concurrent request can't deplete the stock between your read and write — preventing overselling.
Q4What is the Prisma singleton pattern and why is it needed in Next.js?▶
model answer
In development, Next.js hot-reloads modules when files change. Without the singleton pattern, every hot-reload creates a new PrismaClient instance, each with its own connection pool. You'd quickly exhaust the database's connection limit (typically 100 for PostgreSQL) with warnings and connection errors.

The singleton stores the instance on globalThis: globalThis.prisma ?? new PrismaClient(). On first load: the instance is created and stored on globalThis. On hot-reload: the module re-runs, but finds the existing instance on globalThis and returns it instead of creating a new one. In production, this doesn't matter because modules aren't re-executed — but you still need the pattern for development.

In serverless environments (Vercel), each function invocation is a fresh Node.js process — the singleton doesn't help there. Use a connection pooler (Supabase pooler, PgBouncer, Prisma Accelerate) to reuse connections across invocations.
Q5Why should you use Decimal instead of Float for money in Prisma?▶
model answer
Floating point numbers in computers can't represent all decimal values exactly — it's a fundamental binary representation issue. 0.1 + 0.2 in JavaScript is 0.30000000000000004, not 0.3. For money, these tiny rounding errors accumulate and can cause discrepancies in totals, taxes, and financial reports.

Prisma's Decimal type maps to the database's NUMERIC or DECIMAL(10, 2) type, which stores exact decimal values without floating-point errors. In TypeScript, Prisma returns Decimal objects that you can convert with .toNumber() or .toString().

Always use Decimal @db.Decimal(10, 2) for prices, totals, tax amounts, and any monetary value. Use Int instead if you store money in cents/pence — an integer for $19.99 stored as 1999 cents avoids both floating-point issues and requires no special type.
Q6What is cursor-based pagination and when is it better than offset pagination?▶
model answer
Offset pagination (skip: 20, take: 10) works by counting rows to skip. This becomes slow on large tables (the database must count through millions of rows to find page 1000), and it's unstable — if a new record is inserted while a user is paginating, they'll see a duplicate or skip a record depending on where it was inserted.

Cursor pagination uses the last seen record's ID (or a timestamp) as a reference point. Instead of "skip 20", it says "give me the 10 records after this specific ID." This is: fast (uses an index, not counting), stable (unaffected by insertions before the cursor), and the natural pattern for infinite scroll feeds.

In Prisma: cursor: { id: lastSeenId }, skip: 1, take: 10 — skip 1 excludes the cursor record itself. Fetch take + 1 to detect whether more pages exist. Return the last fetched ID as the next cursor.

Use offset for traditional numbered pagination (the user can jump to page 37). Use cursor for infinite scroll, feeds, and real-time data streams.
Q7How do Prisma migrations work and what's the difference between migrate dev and migrate deploy?▶
model answer
When you change schema.prisma, Prisma needs to update the actual database structure to match. Migrations are version-controlled SQL files that describe these changes — they're committed to git and applied in order.

prisma migrate dev is for local development: it detects schema changes, generates a migration SQL file, applies it to the development database, and updates the Prisma Client. It can also reset the DB and re-apply all migrations from scratch. It prompts you if there are dangerous changes.

prisma migrate deploy is for production: it applies all pending (unapplied) migrations without generating new ones. It never prompts, never resets data, and should be run in your CI/CD pipeline before deploying new code. The workflow: developer runs migrate dev locally → commits the migration file → CI runs migrate deploy before deploying the new app version.
Q8How do you handle N:M (many-to-many) relationships in Prisma?▶
model answer
Prisma supports two kinds of N:M relations. Implicit: both models reference each other in their schema and Prisma creates a hidden junction table automatically. Simple to write, but you can't add extra fields to the junction table.

Explicit: you create the junction model yourself (e.g., ProductTag), which gives you control to add fields like assignedAt or assignedBy.

For operations, use connect, disconnect, and set in update mutations. connect adds a relation, disconnect removes one, set replaces the entire collection. For filtering: where: { tags: { some: { name: "sale" } } } finds products that have at least one tag named "sale". every finds products where all tags match. none finds products with no matching tags.
Q9How do you handle database connections in serverless Next.js deployments?▶
model answer
Serverless functions (Vercel Edge, AWS Lambda) have cold starts and short lifetimes — they don't maintain persistent connections. Each invocation might open a new connection, and with many concurrent requests you can hit the database's connection limit (typically 100 for PostgreSQL).

The solution is a connection pooler: a proxy that maintains a pool of persistent database connections and routes incoming queries to available ones. Options: Supabase includes a built-in pooler (PgBouncer); Prisma Accelerate is Prisma's official cloud pooler; Neon has serverless connection pooling built in; you can self-host PgBouncer.

Configure two URLs in your schema: url = env("DATABASE_URL") for queries (the pooled URL, usually port 6543) and directUrl = env("DIRECT_URL") for migrations (the direct URL, port 5432 — migrations don't work through PgBouncer in transaction mode). The singleton pattern helps in dev but doesn't solve the serverless problem.
Q10What is Prisma Studio and how do you use it in development?▶

Prisma Studio is a visual browser for your database, accessible at localhost:5555 after running npx prisma studio. It shows all your models as tables, lets you browse and filter records, create/edit/delete rows, and follow relations between models — without writing a single SQL query or needing a separate DB GUI application like TablePlus or pgAdmin.

In development, it's invaluable for: quickly checking whether your queries are writing the right data, inspecting the result of migrations, debugging why a relation isn't working, seeding test data manually, and verifying that webhooks (like Clerk user.created) are correctly creating records in your database.

It connects directly to the database URL from your .env file, respects your Prisma schema for types and relations, and reflects schema changes immediately after prisma generate. Note that it's a development tool only — don't run it in production as it gives direct database access.
