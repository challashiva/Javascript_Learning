01 Why TypeScript — the value proposition for React developers motivation
without TS
Bugs discovered at runtime, in production
Passing a string where a number is expected. Calling a method that doesn't exist. Accessing .name on undefined. Renaming a prop in one component but missing three others that use it. These bugs only surface when someone actually uses the feature — sometimes months later.
with TS
Bugs caught at write-time, in your editor
TypeScript's language server runs in your IDE and highlights mistakes as you type. Rename a prop and TypeScript immediately shows every component that needs updating — red squiggles guide you. Pass the wrong type and you see the error before you even save the file.
living documentation
Props are self-documenting
A typed component's interface tells you everything about it — which props are required, their types, which are optional, what values are accepted. Hover over a component in your IDE and see the full API. No more opening source files to understand how to use a component.
safe refactoring
Rename anything with confidence
Renaming a function, interface, or prop across a 50,000-line codebase is terrifying in JavaScript. In TypeScript it's a three-second IDE operation — every reference updates automatically, and the compiler catches any you missed. This is the feature that converts senior engineers.

02 Core TypeScript types — everything you use in React fundamentals
typescriptPrimitives, arrays, objects, unions, intersections, interfaces vs types
// ── Primitives ────────────────────────────────────────────
let name:     string  = "Alice"
let age:      number  = 30
let active:   boolean = true
let nothing:  null    = null
let undef:    undefined = undefined

// ── Arrays ────────────────────────────────────────────────
const names:   string[]    = ["Alice", "Bob"]
const scores:  number[]    = [95, 87, 100]
const matrix:  number[][]  = [[1,2],[3,4]]
const mixed:   Array<string | number> = ["a", 1]  // generic syntax

// ── Objects: interface vs type ────────────────────────────
// Interface — extendable, good for shapes (objects, classes)
interface User {
  id:        number
  name:      string
  email:     string
  role?:     "admin" | "user"   // optional + literal union
  createdAt: Date
}

// type alias — can represent ANY type (unions, primitives, tuples)
type Status   = "idle" | "loading" | "success" | "error"
type ID       = string | number
type Point    = [number, number]     // tuple
type Callback = (err: Error | null, data: unknown) => void

// ── Union types — one of several types ───────────────────
type Result<T> =
  | { status: "success"; data: T }
  | { status: "error";   error: Error }
  | { status: "loading" }

// ── Intersection types — both at once ────────────────────
type AdminUser = User & { permissions: string[] }

// ── Literal types ─────────────────────────────────────────
type Direction  = "north" | "south" | "east" | "west"
type HttpMethod = "GET" | "POST" | "PUT" | "PATCH" | "DELETE"
type YesNo     = true | false   // same as boolean, but explicit

// ── unknown vs any — prefer unknown ──────────────────────
// any:     bypasses ALL type checking — avoid
// unknown: type-safe alternative — must narrow before use
function processInput(input: unknown) {
  if (typeof input === "string") {
    console.log(input.toUpperCase())   // TS knows it's a string here
  }
  if (input instanceof Error) {
    console.log(input.message)         // TS knows it's an Error here
  }
}

// ── Type narrowing — telling TS what type something is ───
function formatId(id: string | number): string {
  if (typeof id === "number") return `#${id.toString().padStart(6, "0")}`
  return id                               // TS knows it's a string here
}
interface vs type — when to use each
Use interface for…
Object shapes that might be extended. Component props. API response shapes. Anything that other code will extend or implement. React convention in most codebases.
Use type alias for…
Union types ("a" | "b"). Intersection types. Tuple types. Function signatures. Anything that isn't an object shape. Required when the type can't be expressed as an interface.
Key difference
Interfaces support declaration merging — two declarations with the same name merge together. Type aliases don't. This matters for augmenting third-party library types. In day-to-day React work, both are fine for object shapes.
Team convention
Pick one and be consistent. Most React+TS projects use interface for props and API types, type for unions and computed types. The React team's own code uses both. Don't mix within the same file inconsistently.

// Preferred: plain function with interface (NOT React.FC)
function Button({
  label,
  variant  = "primary",   // default value
  size     = "md",
  disabled = false,
  loading  = false,
  onClick,
  className,
  children,
}: ButtonProps) {
  return (
    <button
      className={`btn btn--${variant} btn--${size} ${className ?? ""}`}
      disabled={disabled || loading}
      onClick={onClick}
    >
      {loading ? <Spinner /> : (children ?? label)}
    </button>
  )
}

// ── Extending HTML element props ──────────────────────────
// Spread all native <button> props + your own overrides
interface InputProps extends React.InputHTMLAttributes<HTMLInputElement> {
  label:    string
  error?:   string
  hint?:    string
}

function Input({ label, error, hint, ...rest }: InputProps) {
  return (
    <div>
      <label>{label}</label>
      <input {...rest} aria-invalid={!!error} />  {/* spreads all native props */}
      {error && <p className="error">{error}</p>}
      {hint  && <p className="hint">{hint}</p>}
    </div>
  )
}

// ── useReducer typing ─────────────────────────────────────
interface CartState  { items: CartItem[]; total: number }
type      CartAction =
  | { type: "ADD";    payload: CartItem }
  | { type: "REMOVE"; payload: number }    // id
  | { type: "CLEAR" }

function cartReducer(state: CartState, action: CartAction): CartState {
  switch (action.type) {
    case "ADD":    return { ...state, items: [...state.items, action.payload] }
    case "REMOVE": return { ...state, items: state.items.filter(i => i.id !== action.payload) }
    case "CLEAR":   return { items: [], total: 0 }
    default:       return state
  }
  // TS knows action.payload is CartItem in "ADD", number in "REMOVE", absent in "CLEAR"
}

// ── Typing custom hooks ───────────────────────────────────
function useLocalStorage<T>(key: string, initial: T): [T, (val: T) => void] {
  const [stored, setStored] = useState<T>(() => {
    try { const s = localStorage.getItem(key); return s ? JSON.parse(s) : initial }
    catch { return initial }
  })
  const set = useCallback((val: T) => {
    setStored(val); localStorage.setItem(key, JSON.stringify(val))
  }, [key])
  return [stored, set]
}
// Usage — T inferred automatically:
const [theme, setTheme] = useLocalStorage("theme", "dark")  // T = string
const [cart,  setCart]  = useLocalStorage<CartItem[]>("cart", [])  // T = CartItem[]

// ── Generic components — reusable with any type ───────────
interface ListProps<T> {
  items:       T[]
  renderItem:  (item: T, index: number) => ReactNode
  keyExtractor:(item: T) => string
  emptyState?: ReactNode
}

function List<T>({ items, renderItem, keyExtractor, emptyState }: ListProps<T>) {
  if (items.length === 0) return <>{emptyState}</>
  return (
    <ul>
      {items.map((item, i) => (
        <li key={keyExtractor(item)}>{renderItem(item, i)}</li>
      ))}
    </ul>
  )
}
// TS infers T from the items prop:
<List
  items={users}                    {/* User[] → T inferred as User */}
  renderItem={(user) => user.name}  {/* user is typed as User automatically */}
  keyExtractor={u => u.id.toString()}
/>

// ── Discriminated unions for component variants ───────────
// Pattern: a "type" or "kind" field narrows what other props are available
type AlertProps =
  | { variant: "success"; message: string }
  | { variant: "error";   message: string; code?: string }
  | { variant: "warning"; message: string; action?: () => void }
  | { variant: "info";    children: ReactNode }   // different shape!

function Alert(props: AlertProps) {
  if (props.variant === "error") {
    // TS knows props.code is available here (string | undefined)
    return <div>{props.message} {props.code && `(${props.code})`}</div>
  }
  if (props.variant === "info") {
    // TS knows props.children is ReactNode, props.message doesn't exist here
    return <div>{props.children}</div>
  }
  return <div>{props.message}</div>
}

08 Interview questions + model answers 10 Q&As
Q1Why use TypeScript with React? What specific problems does it solve?▶
model answer
TypeScript solves three concrete problems in React codebases. First, prop mismatches — passing a string where a number is expected, or forgetting a required prop — are caught at write-time in your editor instead of at runtime in the browser (or worse, in production).

Second, refactoring safety: renaming a prop in one component in plain JavaScript means manually searching every file that uses it. With TypeScript, rename it once and the compiler shows every reference that needs updating. For a large codebase this is the difference between confident refactoring and hours of searching.

Third, living documentation: a typed component's interface is always accurate — it can't drift from implementation. Hover over any component in VS Code and see exactly what props it accepts, their types, and which are optional. No need to read source code to understand how to use a component.
Q2How do you type component props? What's the difference between interface and type for props?▶
model answer
Define props as a named interface or type and annotate the component's parameter: function Button({ label, onClick }: ButtonProps). For optional props, add ?: onClick?: () => void. For default values, use JavaScript defaults in destructuring: { variant = "primary" }: ButtonProps.

Both interface and type work for props. The practical differences: interface supports declaration merging (two declarations with the same name merge), while type supports union types directly (type Props = A | B). For simple object shapes either is fine — most React codebases use interface for props by convention.

One important pattern: interface ButtonProps extends React.ButtonHTMLAttributes<HTMLButtonElement> — this makes a wrapper component accept all native button props automatically, which you spread: <button {...rest} />.
Q3When does useState need an explicit generic, and when can you rely on inference?▶
model answer
TypeScript infers the type from the initial value. When the initial value fully represents the type, you don't need an explicit generic: useState(0) → number, useState("") → string, useState(false) → boolean.

Explicit generics are required when: the initial value is null or undefined (useState<User | null>(null)), the initial value is an empty array (useState<Product[]>([]) — otherwise inferred as never[]), or the type is a union (useState<Status>("idle") — otherwise inferred as the literal "idle").

Rule of thumb: if the initial value can hold all possible future values of the state, let TypeScript infer. If the initial value is a stand-in (null, empty array) for something richer, provide the generic explicitly.
Q4What are discriminated unions and why are they useful for React components?▶
model answer
A discriminated union is a union type where each member has a shared field (the "discriminant") with a unique literal value, allowing TypeScript to narrow to the correct member based on that field's value.

For React components, they're used for props that have fundamentally different shapes depending on a variant. For example, a Button that can be a link or a button:

type ButtonProps = { as: "button"; onClick: () => void } | { as: "a"; href: string }

When as === "button", TypeScript knows onClick exists. When as === "a", TypeScript knows href exists and onClick doesn't. This prevents impossible combinations — you can't pass both href and onClick to the same render. Also great for async state: { status: "success"; data: T } | { status: "error"; error: Error } — accessing .data is only allowed after narrowing to success.
Q5How do you type event handlers in React?▶
model answer
The pattern is React.{EventName}Event<HTML{Element}Element>. The most common ones: React.ChangeEvent<HTMLInputElement> for onChange on text inputs (gives e.target.value), React.FormEvent<HTMLFormElement> for form onSubmit (call e.preventDefault()), React.MouseEvent<HTMLButtonElement> for click handlers, React.KeyboardEvent<HTMLInputElement> for key events.

For inline handlers, TypeScript infers the type automatically from context — you only need to annotate when extracting the handler into a separate function. A useful shorthand: React.ChangeEventHandler<HTMLInputElement> is equivalent to (e: React.ChangeEvent<HTMLInputElement>) => void.
If you can never remember the exact type: write the handler inline first, hover over the e parameter in VS Code to see the inferred type, then copy that type to the extracted function.
Q6What's the difference between any and unknown, and when do you use each?▶
model answer
any completely disables TypeScript's type checking for a value — you can do anything with it, and TypeScript won't complain. It's a full opt-out from the type system. Avoid it except when migrating JS to TS incrementally or working with genuinely untyped third-party APIs.

unknown is the type-safe alternative. It represents "we don't know the type yet." Unlike any, TypeScript requires you to narrow an unknown value before you can use it: if (typeof value === "string") { value.toUpperCase() }. This forces you to handle the type uncertainty explicitly rather than ignoring it.

Use unknown for: API responses (before Zod parsing), catch block errors (catch (e: unknown)), or any value whose type is determined at runtime. Use any as a last resort when you truly can't type something and need to move forward.
Q7How do you write a generic component in TypeScript?▶
model answer
Add a type parameter to both the interface and the function: interface ListProps<T> { items: T[]; renderItem: (item: T) => ReactNode }, then function List<T>({ items, renderItem }: ListProps<T>).

TypeScript infers T automatically from the items prop — so <List items={users} renderItem={u => u.name} /> means TypeScript knows u is a User inside renderItem, giving full autocomplete on the callback parameter.

You can constrain generics: T extends { id: string | number } ensures every item has an id. Or provide multiple type params: function Select<TValue, TOption extends { value: TValue; label: string }> for a typed Select component.

In .tsx files, the syntax <T> is ambiguous with JSX. Use <T,> (trailing comma) or <T extends unknown> to disambiguate.
Q8Which utility types do you use most often in React and why?▶
model answer
The four I reach for constantly: Partial<T> for update/PATCH operations where only some fields are sent — form schemas for editing, API calls where you don't send every field. Omit<T, K> for stripping sensitive or auto-generated fields like Omit<User, "password" | "createdAt">. Pick<T, K> for list views that only need a subset of fields — prevents over-fetching concern in types. ReturnType<typeof fn> combined with Awaited to derive types from fetcher functions without duplicating them.

Two less obvious ones: Record<K, V> for lookup maps and status-to-message mappings. NonNullable<T> after guard checks — const users = data.filter((u): u is NonNullable<typeof u> => u != null).
Q9How do you type a Context with useContext and prevent the null check at every usage?▶
model answer
Create the context with null as the initial value: createContext<AuthContextValue | null>(null). Then write a custom hook with an explicit return type annotation that throws if the context is null:

function useAuth(): AuthContextValue { const ctx = useContext(AuthContext); if (!ctx) throw new Error("useAuth must be inside AuthProvider"); return ctx }

The explicit : AuthContextValue return type tells TypeScript that the function always returns a non-null AuthContextValue — after the null check and throw, TypeScript is confident the returned value is not null. Every caller of useAuth() gets AuthContextValue, never AuthContextValue | null, so no optional chaining is needed in consuming components.

This is cleaner than using a non-null assertion (useContext(AuthContext)!) because the runtime error message is descriptive, and the pattern is enforced consistently.
Q10What is a type guard and how do you write a custom one?▶
model answer
A type guard is a function that tells TypeScript "if this function returns true, then the parameter is of type X." The key syntax is the return type: value is User — called a "type predicate."

function isUser(value: unknown): value is User { return typeof value === "object" && value !== null && "id" in value && "email" in value }

After calling if (isUser(data)), TypeScript narrows data from unknown to User inside the if block. Without the type predicate return type, the function would work at runtime but TypeScript would still think data is unknown.

Use type guards when: validating API responses that arrive as unknown, filtering arrays to remove nulls (items.filter((x): x is NonNullable<typeof x> => x != null)), or processing websocket messages that could be any event type. Pair with Zod's safeParse for the most robust approach — it's both a runtime validator and implicitly acts as a type guard.
