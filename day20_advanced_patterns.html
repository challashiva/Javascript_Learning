01 Compound components — flexible, composable UI pattern 1
the problem
Prop explosion — passing everything through the top
A Tabs component with a monolithic API: <Tabs items={[{label, content, icon, disabled}]} activeTab={0} onTabChange={fn} tabStyle="underline" contentPadding={24} />. Every new requirement means a new prop. The API becomes unlearnable and the implementation a mess of conditional rendering.
the pattern
Compose sub-components, share state via Context
Compound components expose a family of related sub-components that share implicit state via Context: <Tabs><Tabs.List><Tabs.Tab>…<Tabs.Panel>. Users compose the UI they need. Adding a badge to one tab doesn't require a new prop — just put it in the JSX. This is how Radix UI, shadcn/ui, and Headless UI work.
real examples
Every major component library uses this
Radix <Select.Root><Select.Trigger><Select.Content>, Headless UI <Disclosure><Disclosure.Button><Disclosure.Panel>, React Router <Routes><Route>. Understanding this pattern means understanding how all your dependencies work.
tsxCompound Tabs component — Context + static sub-components
import { createContext, useContext, useState, type ReactNode } from "react"

// ── Internal context — hidden from consumers ───────────────
interface TabsContextValue {
  active:    string
  setActive: (id: string) => void
}
const TabsCtx = createContext<TabsContextValue | null>(null)
function useTabsCtx() {
  const ctx = useContext(TabsCtx)
  if (!ctx) throw new Error("Must be used inside Tabs")
  return ctx
}

// ── Root component — owns the state ───────────────────────
interface TabsProps { defaultActive?: string; children: ReactNode }
function Tabs({ defaultActive = "", children }: TabsProps) {
  const [active, setActive] = useState(defaultActive)
  return (
    <TabsCtx.Provider value={{ active, setActive }}>
      <div className="tabs">{children}</div>
    </TabsCtx.Provider>
  )
}

// ── Sub-components — read from context ────────────────────
function TabList({ children }: { children: ReactNode }) {
  return <div role="tablist" className="flex border-b border-gray-200">{children}</div>
}

interface TabProps { id: string; children: ReactNode; disabled?: boolean }
function Tab({ id, children, disabled = false }: TabProps) {
  const { active, setActive } = useTabsCtx()
  const isActive = active === id
  return (
    <button
      role="tab"
      aria-selected={isActive}
      disabled={disabled}
      onClick={() => !disabled && setActive(id)}
      className={`px-4 py-2 text-sm font-medium transition-colors
        ${isActive
          ? "text-blue-600 border-b-2 border-blue-600 -mb-px"
          : "text-gray-500 hover:text-gray-700"}
        ${disabled ? "opacity-40 cursor-not-allowed" : ""}`}
    >
      {children}
    </button>
  )
}

function TabPanel({ id, children }: { id: string; children: ReactNode }) {
  const { active } = useTabsCtx()
  if (active !== id) return null
  return <div role="tabpanel" className="p-4">{children}</div>
}

// ── Attach sub-components as static properties ────────────
Tabs.List  = TabList
Tabs.Tab   = Tab
Tabs.Panel = TabPanel

// ── Usage — compose freely ────────────────────────────────
function ProductPage() {
  return (
    <Tabs defaultActive="description">
      <Tabs.List>
        <Tabs.Tab id="description">Description</Tabs.Tab>
        <Tabs.Tab id="reviews">
          Reviews <span className="bg-blue-100 text-blue-700 rounded-full px-2 text-xs">48</span>
        </Tabs.Tab>  {/* badge with zero props changes to Tabs */}
        <Tabs.Tab id="shipping" disabled>Shipping</Tabs.Tab>
      </Tabs.List>
      <Tabs.Panel id="description"><ProductDescription /></Tabs.Panel>
      <Tabs.Panel id="reviews"><ReviewsList /></Tabs.Panel>
    </Tabs>
  )
}
02 Render props — share logic, delegate rendering pattern 2
Render props — pass a function as a prop (or children)
what it is
A component accepts a function as its children (or a named prop). It calls that function with its internal state. The caller decides how to render — the component only handles the logic.
why it matters
Decouples behaviour from presentation. A MouseTracker tracks position — you decide what to render at that position. A DataFetcher handles loading/error — you decide the UI for each state.
vs custom hooks
Custom hooks achieve the same sharing but render props can share multiple render slots simultaneously. Also used when the shared logic needs to influence the component tree structure, not just state values.
in the wild
React Router's <Route render={fn} />, Formik's <Field>, Downshift's <Combobox>, React Table. Most libraries now offer both hook and render-prop APIs for flexibility.
tsxRender props — DataFetcher and Disclosure examples
// ── DataFetcher — logic in component, rendering delegated ─
interface DataFetcherProps<T> {
  url:      string
  children: (state: {
    data:      T | null
    isLoading: boolean
    error:     Error | null
    refetch:   () => void
  }) => ReactNode
}
function DataFetcher<T>({ url, children }: DataFetcherProps<T>) {
  const [data,      setData]      = useState<T | null>(null)
  const [isLoading, setIsLoading] = useState(true)
  const [error,     setError]     = useState<Error | null>(null)
  const [tick,      setTick]      = useState(0)

  useEffect(() => {
    setIsLoading(true); setError(null)
    fetch(url).then(r => r.json()).then(setData).catch(setError)
    .finally(() => setIsLoading(false))
  }, [url, tick])

  return <>{children({ data, isLoading, error, refetch: () => setTick(t => t+1) })}</>
}

// ── Usage — caller decides the rendering ──────────────────
<DataFetcher<User[]> url="/api/users">
  {({ data, isLoading, error, refetch }) => (
    <div>
      {isLoading && <Spinner />}
      {error     && <button onClick={refetch}>Retry</button>}
      {data      && <UserList users={data} />}
    </div>
  )}
</DataFetcher>

// ── Disclosure — toggle open/close pattern ────────────────
interface DisclosureProps {
  children: (state: { isOpen: boolean; toggle: () => void; open: () => void; close: () => void }) => ReactNode
  defaultOpen?: boolean
}
function Disclosure({ children, defaultOpen = false }: DisclosureProps) {
  const [isOpen, setIsOpen] = useState(defaultOpen)
  return <>{children({
    isOpen,
    toggle: () => setIsOpen(v => !v),
    open:   () => setIsOpen(true),
    close:  () => setIsOpen(false),
  })}</>
}

// Usage — caller controls both trigger and content
<Disclosure>
  {({ isOpen, toggle }) => (
    <div className="border rounded-lg">
      <button onClick={toggle} className="w-full flex justify-between p-4">
        FAQ Question <span>{isOpen ? "−" : "+"}</span>
      </button>
      {isOpen && <div className="px-4 pb-4 text-gray-600">Answer here</div>}
    </div>
  )}
</Disclosure>
03 HOCs — higher-order components, when they still win pattern 3
tsxwithAuth, withErrorBoundary, withAnalytics HOCs — cross-cutting concerns
// HOCs are still the right tool when you need to wrap arbitrary
// components in cross-cutting behaviour WITHOUT the consumer knowing.
// Key: HOC = function that takes a component, returns a component.

// ── withAuth — protect any page component ─────────────────
function withAuth<P extends object>(Component: React.ComponentType<P>) {
  function Protected(props: P) {
    const { user } = useAuth()
    if (!user) return <Navigate to="/login" replace />
    return <Component {...props} />
  }
  Protected.displayName = `withAuth(${Component.displayName || Component.name})`
  return Protected
}
const ProtectedDashboard = withAuth(Dashboard)  // use in router

// ── withErrorBoundary — wrap anything in a boundary ───────
function withErrorBoundary<P extends object>(
  Component: React.ComponentType<P>,
  fallback:  ReactNode
) {
  return function WithBoundary(props: P) {
    return (
      <ErrorBoundary fallback={fallback}>
        <Component {...props} />
      </ErrorBoundary>
    )
  }
}

// ── withAnalytics — track page views silently ─────────────
function withAnalytics<P extends { name?: string }>(
  Component: React.ComponentType<P>,
  eventName: string
) {
  return function WithTracking(props: P) {
    useEffect(() => {
      analytics.track(eventName, { component: Component.name })
    }, [])
    return <Component {...props} />
  }
}

// ── When to use HOCs (vs hooks or render props) ────────────
// ✓ Cross-cutting concerns added declaratively in router/config (withAuth)
// ✓ Wrapping third-party components you can't modify
// ✓ Adding class-based lifecycle to function components (rare)
// ✗ Don't use for logic sharing in same codebase — use custom hooks
// ✗ Don't use when render props or compound components are cleaner

// ── Composing HOCs ────────────────────────────────────────
// Bad: deeply nested HOC calls
const Bad = withAuth(withAnalytics(withErrorBoundary(Dashboard, <Error />), "dashboard_view"))

// Good: compose utility
const compose = (...fns) => (x) => fns.reduceRight((v, f) => f(v), x)
const Good = compose(
  withAuth,
  (C) => withAnalytics(C, "dashboard_view"),
  (C) => withErrorBoundary(C, <Error />),
)(Dashboard)
04 State machines — explicit states, predictable transitions pattern 4
tsxState machine with useReducer — typed states, guarded transitions
// State machines make impossible states impossible.
// Instead of booleans: isLoading=true AND isError=true (impossible!)
// You have ONE current state: "loading" | "error" | "success"

// ── Payment state machine ─────────────────────────────────
type PaymentState =
  | { status: "idle" }
  | { status: "validating" }
  | { status: "processing"; amount: number }
  | { status: "success";    transactionId: string }
  | { status: "declined";   reason: string; retryCount: number }
  | { status: "error";     message: string }

type PaymentEvent =
  | { type: "SUBMIT";  amount: number }
  | { type: "APPROVE"; transactionId: string }
  | { type: "DECLINE"; reason: string }
  | { type: "ERROR";   message: string }
  | { type: "RETRY" }
  | { type: "RESET" }

function paymentReducer(state: PaymentState, event: PaymentEvent): PaymentState {
  switch (state.status) {
    case "idle":
      if (event.type === "SUBMIT") return { status: "validating" }
      return state

    case "validating":
      if (event.type === "SUBMIT") return { status: "processing", amount: event.amount }
      if (event.type === "ERROR")   return { status: "error", message: event.message }
      return state

    case "processing":
      if (event.type === "APPROVE")
        return { status: "success", transactionId: event.transactionId }
      if (event.type === "DECLINE")
        return { status: "declined", reason: event.reason, retryCount: 0 }
      if (event.type === "ERROR")
        return { status: "error", message: event.message }
      return state

    case "declined":
      if (event.type === "RETRY" && state.retryCount < 3)
        return { status: "validating" }
      return state

    case "success":
    case "error":
      if (event.type === "RESET") return { status: "idle" }
      return state
  }
}

// ── Usage ─────────────────────────────────────────────────
function PaymentForm() {
  const [state, dispatch] = useReducer(paymentReducer, { status: "idle" })

  const submit = async (amount: number) => {
    dispatch({ type: "SUBMIT", amount })
    // Validate...
    dispatch({ type: "SUBMIT", amount })  // advances to processing
    try {
      const { transactionId } = await processPayment(amount)
      dispatch({ type: "APPROVE", transactionId })
    } catch (e) {
      dispatch({ type: "DECLINE", reason: (e as Error).message })
    }
  }

  return (
    <div>
      {state.status === "idle"       && <form onSubmit={...}>...</form>}
      {state.status === "processing" && <Spinner />}
      {state.status === "success"    && <Success id={state.transactionId} />}
      {state.status === "declined"   && (
        <div>
          <p>{state.reason}</p>
          {state.retryCount < 3 &&
            <button onClick={() => dispatch({ type: "RETRY" })}>Try again</button>}
        </div>
      )}
    </div>
  )
}
05 Portals — render outside the component tree pattern 5
tsxPortals for modals, toasts, tooltips — escaping overflow:hidden
import { createPortal } from "react-dom"
import { useEffect, useRef, type ReactNode } from "react"

// ── Portal — renders into a DOM node outside the tree ─────
// Problem: z-index and overflow:hidden trap modals inside their parent.
// Solution: render into document.body (or a dedicated portal root).

function Modal({ isOpen, onClose, children }: {
  isOpen:   boolean
  onClose:  () => void
  children: ReactNode
}) {
  // Lock body scroll when open
  useEffect(() => {
    if (isOpen) document.body.style.overflow = "hidden"
    return () => { document.body.style.overflow = "" }
  }, [isOpen])

  // Close on Escape key
  useEffect(() => {
    if (!isOpen) return
    const handler = (e: KeyboardEvent) => { if (e.key === "Escape") onClose() }
    document.addEventListener("keydown", handler)
    return () => document.removeEventListener("keydown", handler)
  }, [isOpen, onClose])

  if (!isOpen) return null

  return createPortal(
    <div
      className="fixed inset-0 z-50 flex items-center justify-center"
      role="dialog"
      aria-modal
    >
      {/* Backdrop */}
      <div
        className="absolute inset-0 bg-black/50 backdrop-blur-sm"
        onClick={onClose}
      />
      {/* Content — above backdrop */}
      <div className="relative bg-white rounded-2xl shadow-xl p-6 max-w-lg w-full mx-4 z-10">
        <button
          onClick={onClose}
          className="absolute top-4 right-4 text-gray-400 hover:text-gray-600"
          aria-label="Close"
        >✕</button>
        {children}
      </div>
    </div>,
    document.body   // ← render here, not inside parent DOM node
  )
}

// ── Toast system — portal + queue ────────────────────────
type Toast = { id: string; message: string; type: "success" | "error" | "info" }
const ToastCtx = createContext<{ toast: (msg: string, type?: Toast["type"]) => void }>({ toast: () => {} })

function ToastProvider({ children }: { children: ReactNode }) {
  const [toasts, setToasts] = useState<Toast[]>([])

  const toast = useCallback((message: string, type: Toast["type"] = "info") => {
    const id = crypto.randomUUID()
    setToasts(t => [...t, { id, message, type }])
    setTimeout(() => setToasts(t => t.filter(x => x.id !== id)), 4000)
  }, [])

  return (
    <ToastCtx.Provider value={{ toast }}>
      {children}
      {createPortal(
        <div className="fixed bottom-4 right-4 z-50 flex flex-col gap-2">
          {toasts.map(t => (
            <div key={t.id}
              className={`px-4 py-3 rounded-lg shadow-lg text-white text-sm font-medium
                ${t.type === "success" ? "bg-green-600"
                : t.type === "error"   ? "bg-red-600"
                :                           "bg-gray-800"}`}
            >
              {t.message}
            </div>
          ))}
        </div>,
        document.body
      )}
    </ToastCtx.Provider>
  )
}
export const useToast = () => useContext(ToastCtx)
06 Error boundaries — catch render errors gracefully pattern 6
tsxError boundary class + react-error-boundary + retry pattern
// Error boundaries MUST be class components — no hook equivalent exists.
// They catch errors thrown during render, in lifecycle methods, and in
// constructors of child components. They do NOT catch async errors.

// ── Manual implementation ─────────────────────────────────
class ErrorBoundary extends React.Component<
  { children: ReactNode; fallback?: ReactNode },
  { hasError: boolean; error: Error | null }
> {
  state = { hasError: false, error: null }

  static getDerivedStateFromError(error: Error) {
    return { hasError: true, error }
  }

  componentDidCatch(error: Error, info: React.ErrorInfo) {
    console.error("Boundary caught:", error, info.componentStack)
    logErrorToService(error, info)  // Sentry, LogRocket etc.
  }

  reset() { this.setState({ hasError: false, error: null }) }

  render() {
    if (this.state.hasError) {
      return this.props.fallback ?? (
        <div className="p-8 text-center">
          <h2 className="text-xl font-semibold text-gray-900">Something went wrong</h2>
          <p className="text-gray-600 mt-2">{this.state.error?.message}</p>
          <button onClick={() => this.reset()}>Try again</button>
        </div>
      )
    }
    return this.props.children
  }
}

// ── react-error-boundary (recommended) ────────────────────
// npm install react-error-boundary
import { ErrorBoundary, useErrorBoundary } from "react-error-boundary"

function App() {
  return (
    <ErrorBoundary
      fallbackRender={({ error, resetErrorBoundary }) => (
        <div role="alert" className="p-8 text-center">
          <pre className="text-red-600 text-sm">{error.message}</pre>
          <button onClick={resetErrorBoundary}>Try again</button>
        </div>
      )}
      onReset={() => { /* clear state that caused the error */ }}
    >
      <ProductList />
    </ErrorBoundary>
  )
}

// ── Throw from inside a component to test ─────────────────
function BuggyComponent() {
  const { showBoundary } = useErrorBoundary()  // from react-error-boundary
  // Use showBoundary for async errors (fetch errors etc.)
  useEffect(() => {
    fetchData().catch(showBoundary)  // async error → boundary
  }, [])
  return <div>...</div>
}

08 Interview questions + model answers 10 Q&As
Q1What is the compound component pattern and when would you use it?▶
model answer
Compound components are a family of related sub-components that share implicit state through Context. Rather than passing all options as props to a single component, users compose the UI they need from the parts.

The signature: a parent component owns state in Context, and child components consume it without the user having to wire anything — <Tabs><Tabs.List><Tabs.Tab id="a">…<Tabs.Panel id="a">.

Use it when: a component has multiple distinct parts that need to share state (Tabs, Accordion, Select, Dialog), when users need flexibility to add custom content to individual parts (a badge on one Tab, an icon on another), or when the prop API would otherwise explode with configuration options. This is how Radix UI, shadcn/ui, and Headless UI are designed.
Q2What is the render prop pattern and how does it differ from custom hooks?▶
model answer
A render prop is a function passed as a prop (often children) that a component calls with its internal state, letting the caller decide what to render. The component handles the logic; the caller controls the UI.

Both render props and custom hooks share logic between components. The key difference: custom hooks extract logic into a reusable function that the component calls directly — the component still controls its own rendering. Render props invert this — the component calls the consumer's function, allowing the component to influence where and when the consumer's UI renders.

Render props are better when: you need to expose multiple render slots, when the component itself needs to control the container structure (DataFetcher wrapping with loading/error states), or when working with class component APIs that can't use hooks. In modern React, custom hooks are usually simpler and preferred — render props shine in specific cases.
Q3When should you use a HOC in 2025, and when should you use a hook instead?▶
model answer
HOCs wrap components declaratively at the definition point, without the consumer needing to know. Hooks add logic inside a component explicitly. Both share behaviour — the choice is about where you want the logic to live.

Use HOCs when: the enhancement is applied consistently across many components from outside (protecting all routes with withAuth in the router config), when wrapping third-party components you can't modify (adding error boundaries to library components), or for cross-cutting concerns that shouldn't require code changes in each consumer.

Use hooks instead when: the logic needs to be used inside the same component that benefits from it, when you want explicit opt-in rather than implicit wrapping, or when the logic produces state that the component needs to use directly. In most everyday React code, hooks are simpler and clearer — HOCs are a tool for specific architectural patterns, not a general-purpose logic-sharing mechanism.
Q4What makes state machines better than booleans for managing complex UI state?▶
model answer
With booleans, impossible states become possible. Consider isLoading: true and isError: true simultaneously — this shouldn't happen, but nothing prevents it. As complexity grows, managing combinations of 4-5 booleans becomes error-prone and the number of impossible states explodes.

A state machine has exactly ONE current state from an explicit set. Transitions are defined precisely — you can only move from processing to success or declined, not to validating. This makes impossible states structurally impossible, not just "we try to prevent them."

In React, implement with useReducer where the state is a discriminated union: type State = {status:"idle"} | {status:"loading"} | {status:"success",data:T} | {status:"error",error:Error}. TypeScript then enforces that you only access data when in success state. The result: fewer bugs, clearer code, and easier testing — you test transitions, not combinations.
XState is the library version if state machines get complex. For most React use cases, useReducer with a well-typed state union is sufficient and has zero dependencies.
Q5Why do portals exist and what problems do they solve?▶
model answer
The DOM's stacking context and overflow rules trap child elements inside their parent. A modal inside a card with overflow: hidden gets clipped. A tooltip with z-index: 9999 still appears below a parent with z-index: 10 if the parent creates a new stacking context.

createPortal(children, domNode) renders React children into a DOM node outside the component tree — usually document.body. Crucially, the component is still inside React's virtual tree (events bubble correctly, Context works, refs work) but it renders to a different DOM location. This means modals escape overflow and stacking context issues while maintaining full React behaviour.

Common uses: modals (need to overlay everything), tooltips (need to position relative to viewport), toasts/notifications (fixed positioning at screen edge), dropdown menus (need to escape overflow containers). If you've ever seen a dropdown clipped by a parent with overflow hidden, you needed a portal.
Q6What can error boundaries catch and what can't they catch?▶
model answer
Error boundaries catch JavaScript errors during rendering, in lifecycle methods, and in constructors of any child component below them. They provide a fallback UI and prevent the entire application from unmounting.

They do not catch: errors in event handlers (use try/catch inside the handler), async errors (errors in setTimeout, Promise rejections, fetch failures), server-side rendering errors, or errors in the error boundary itself.

For async errors with React Query's useSuspenseQuery, you need an error boundary above the component — the query throws an error that the boundary catches. The react-error-boundary package's useErrorBoundary hook lets you programmatically pass async errors to the nearest boundary via showBoundary(error), bridging the async gap. Place boundaries strategically — too high and a small error crashes the whole app, too low and you have duplicated fallback UI everywhere.
Q7What is inversion of control in React and how does it improve component APIs?▶
model answer
Inversion of control (IoC) means the component gives control back to the consumer rather than trying to handle every case internally. Instead of the component deciding everything, it provides extension points where the consumer can inject their logic.

In React: a Select component with a filterItems prop (consumer provides filtering logic), a List with a renderItem prop (consumer decides rendering), or a Modal with onClose (consumer decides what closing does). Render props and compound components are both forms of IoC.

The benefit: the component stays simple and general, while consumers get exactly the flexibility they need without the component author anticipating every use case. This is why the best component libraries feel unopinionated — they invert control at the right points. The alternative (the component handles everything via props) leads to prop explosion and a component API that can never satisfy all consumers.
Q8How do you implement a modal that closes on Escape and backdrop click?▶
model answer
Three things are needed: a portal to render at body level, a keyboard event listener for Escape, and a backdrop div that calls onClose on click.

The keyboard listener goes in a useEffect that's active only when the modal is open: document.addEventListener("keydown", handler), cleanup removes it. Add isOpen to the dependency array — the effect re-runs when it changes.

The backdrop is a full-screen div positioned behind the modal content: fixed inset-0 bg-black/50 with an onClick={onClose}. The modal content sits above it with relative z-10. Clicking the backdrop closes the modal, clicking the content does not (because content sits above the backdrop and the click doesn't bubble to the backdrop).

Additional: lock body scroll with document.body.style.overflow = "hidden" while open and restore in cleanup. Set role="dialog" and aria-modal for accessibility. Use focus-trap to keep keyboard focus inside the modal.
Q9How do compound components maintain state between sub-components without prop drilling?▶
model answer
Via React Context scoped to the compound component family. The root component (Tabs) owns the state and wraps its children in a Context Provider. All sub-components (Tab, TabPanel) call useContext to read and update that state — no props needed.

The implementation: create a private context (not exported), create a custom hook with a null check that throws if called outside the root component, and attach sub-components as static properties on the root for the namespaced API.

The key advantage: the user's JSX tree can be any depth — they can wrap Tab in a div, conditionally render panels, or add any custom elements between the compound components. The Context bypasses all intermediate layers automatically. This is what makes the pattern "compound" — the components appear independent in JSX but are coupled through implicit Context.
Q10What's the difference between controlled and uncontrolled compound components?▶
model answer
An uncontrolled compound component owns its state internally (with defaultActive): the consumer doesn't manage it. Good for simple cases where the parent doesn't need to know or control the active state.

A controlled compound component receives its state as a prop (active) and calls a callback to request changes (onActiveChange): <Tabs active={activeTab} onActiveChange={setActiveTab}>. The consumer owns the state. Good when the parent needs to sync the active tab with URL params, analytics, or other state.

The professional approach supports both with a single implementation — detect whether active prop is provided, and if so, use it; otherwise use internal state. This is how Radix and Headless UI work. In code: const isControlled = active !== undefined, then use whichever source of truth is appropriate. When controlled, ignore internal state changes and call onActiveChange instead of setActive.
