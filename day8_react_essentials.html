01 What React is and why it was built foundation
the problem
Keeping UI in sync with data is hard
In vanilla JS, you manually update the DOM every time data changes. With many pieces of state, it becomes easy to forget an update — the UI gets out of sync with your data. The larger the app, the worse this gets. React's core insight: describe what the UI should look like for a given state, and let React handle the actual DOM updates.
the solution
UI = f(state) — declarative, not imperative
React flips the programming model. Instead of imperatively saying "find this element and change it", you declaratively say "when state looks like this, the UI should look like that". React figures out the minimum DOM changes needed. Your component is just a pure function from state to UI description.
virtual DOM
Why the Virtual DOM exists
Real DOM operations are expensive — they trigger layout recalculation. React keeps a lightweight JS object copy of the DOM in memory. When state changes, React re-runs your component, creates a new virtual DOM, diffs it against the old one, and applies only the minimum real DOM changes needed. This is called reconciliation.
week 1 link
React is Week 1 concepts combined
Components are functions (Day 3). State updates use immutable array patterns (Day 2). Hooks use closures (Day 3). The event system uses event delegation (Day 5). JSX compiles to function calls. useEffect cleanup uses the same pattern as removeEventListener (Day 5). Nothing here is truly new.

02 JSX — JavaScript + XML (it's just function calls) syntax
what JSX is
JSX compiles to React.createElement()
JSX is not HTML and not a separate language. It's syntax sugar that compiles to plain JavaScript function calls. <Button color="red">Click</Button> becomes React.createElement(Button, {color:"red"}, "Click"). Modern React uses a JSX transform, so you don't need to import React anymore — but understanding the compilation demystifies every JSX rule.
key rules
Rules that differ from HTML
One root element per return (use <></> Fragment to avoid extra divs). camelCase attributes: className not class, onClick not onclick, htmlFor not for. Self-closing tags must close: <img />. JS expressions in {}. No statements directly (no if, for) — use ternaries or move logic out.
common gotcha
Rendering 0 — the falsy gotcha
JSX renders false, null, undefined as nothing — but renders 0 as the character "0". So {count && <Component />} prints "0" when count is 0. Fix: use {count > 0 && ...} or {!!count && ...}. This is one of the most common React bugs beginners hit.

03 Components & Props — building blocks core
Component mental model
what a component is
A JavaScript function that accepts props and returns JSX. That's it. function Button(props) { return <button>...</button> }
rules
Name must start with a capital letter. Must return JSX (or null). Must be a pure function — same props → same output, no side effects during render.
props
The object passed to a component. Read-only — never modify props directly. Think of them as function arguments.
children
props.children is whatever JSX you put between opening/closing tags: <Card>{children}</Card>. Used for composition.
jsxComponents, props, default props, children, PropTypes pattern
// ── Basic function component ───────────────────────────────
function Greeting({ name, role = "user" }) {    // default prop via destructuring
  return <h2>Welcome, {name} ({role})</h2>
}

// Arrow function component — identical, just different syntax
const Badge = ({ label, color = "blue" }) => (
  <span style={{ background: color }}>{label}</span>
)

// ── Using components ──────────────────────────────────────
function App() {
  return (
    <div>
      <Greeting name="Alice" role="admin" />
      <Greeting name="Bob" />             // role defaults to "user"
      <Badge label="New" color="green" />
    </div>
  )
}

// ── Children prop — composition pattern ──────────────────
function Card({ title, children, footer }) {
  return (
    <div className="card">
      <h3>{title}</h3>

      {footer && <footer>{footer}</footer>}

// ── Why keys matter ────────────────────────────────────────
// React uses keys to identify which items changed, were added, or removed
// Without keys: React re-renders the ENTIRE list on any change
// With keys:    React only re-renders the changed items

// ── Key rules ─────────────────────────────────────────────
// ✓ Stable — same item should always have same key
// ✓ Unique among siblings (not globally)
// ✓ Not a prop — React uses it internally, not passed to component

// ✗ NEVER use array index as key when list can reorder/add/remove
tasks.map((task, i) => <li key={i}>{task.text}</li>) // ← BAD if list changes

// ✓ Use index ONLY for truly static lists that never change
const DAYS = ["Mon", "Tue", "Wed", "Thu", "Fri"]
DAYS.map((d, i) => <li key={i}>{d}</li>)  // ← OK for static list

// ── Extracting list items into a component ─────────────────
function TaskItem({ task }) {
  return (
    <li className={task.done ? "done" : ""}>
      {task.text}
    </li>
  )
}

function TaskList() {
  return (
    <ul>
      {tasks.map(task =>
        <TaskItem key={task.id} task={task} />  // key on TaskItem, not li inside it
      )}
    </ul>
  )
}
05 useState — React's state model in depth critical
what state is
Data that, when changed, causes a re-render
State is React-managed data that lives inside a component. When state changes, React re-runs the component function, produces new JSX, diffs against the previous output, and updates only the changed DOM nodes. Regular variables don't trigger re-renders — only useState (and other hooks) do.
the golden rule
NEVER mutate state directly
React detects changes by comparing object references. If you mutate (state.count++, array.push()), the reference stays the same — React thinks nothing changed and won't re-render. Always create new values: setCount(c + 1), setItems([...items, newItem]). This is Week 1 Day 2 immutability in action.
batching
State updates are batched and asynchronous
Multiple setState calls in one event handler are batched into a single re-render. The new state isn't available immediately after calling setState — the update happens on the next render. To base a new state on the current state, use the functional update form: setState(prev => prev + 1).
jsxuseState — primitives, objects, arrays, functional updates
import { useState } from "react"

// ── Primitive state ───────────────────────────────────────
function Counter() {
  const [count, setCount] = useState(0)   // [currentValue, setter]

  return (
    <div>
      <p>Count: {count}</p>
      <button onClick={() => setCount(count + 1)}>+</button>
      <button onClick={() => setCount(c => c - 1)}>-</button>  // functional update
      <button onClick={() => setCount(0)}>Reset</button>
    </div>
  )
}

// ── Object state — spread to update immutably ─────────────
function UserForm() {
  const [form, setForm] = useState({ name: "", email: "", role: "user" })

  const handleChange = (e) => {
    setForm(prev => ({
      ...prev,                             // keep all other fields
      [e.target.name]: e.target.value     // update only changed field
    }))
  }

  return (
    <form>
      <input name="name"  value={form.name}  onChange={handleChange} />
      <input name="email" value={form.email} onChange={handleChange} />
    </form>
  )
}

// ── Array state — immutable add, remove, update ───────────
function ShoppingCart() {
  const [items, setItems] = useState([])

  const addItem    = (item) => setItems(prev => [...prev, item])
  const removeItem = (id)   => setItems(prev => prev.filter(i => i.id !== id))
  const updateQty  = (id, qty) => setItems(prev =>
    prev.map(i => i.id === id ? { ...i, qty } : i)
  )

  const total = items.reduce((s, i) => s + i.price * i.qty, 0)  // Day 2!

  return (
    <div>
      <p>Total: ${total.toFixed(2)}</p>
      {items.map(item => <CartItem key={item.id} item={item} onRemove={removeItem} />)}
    </div>
  )
}

// ── State batching gotcha ─────────────────────────────────
function BugExample() {
  const [count, setCount] = useState(0)

  const buggy = () => {
    setCount(count + 1)  // uses stale count from closure
    setCount(count + 1)  // still uses SAME stale count — only increments by 1!
  }

  const correct = () => {
    setCount(prev => prev + 1)  // uses latest state
    setCount(prev => prev + 1)  // increments from result of above — adds 2!
  }
}
06 useEffect — side effects & the dependency array critical
The three dependency array behaviours — know these cold
no array — useEffect(fn)
Runs after every render. Rarely what you want — usually causes infinite loops if it updates state.
empty array — useEffect(fn, [])
Runs once after initial mount only. Like componentDidMount. Good for one-time setup: fetch initial data, subscribe to events.
with deps — useEffect(fn, [a, b])
Runs after mount AND whenever a or b change. Most common pattern: re-fetch when a filter/id changes.
cleanup function
Return a function from useEffect to run on unmount or before the next effect. Used to cancel fetches, clear timers, remove event listeners.
jsxuseEffect — fetch data, event listeners, timers, AbortController
import { useState, useEffect } from "react"

// ── Fetch data on mount ────────────────────────────────────
function UserProfile({ userId }) {
  const [user,    setUser]    = useState(null)
  const [loading, setLoading] = useState(true)
  const [error,   setError]   = useState(null)

  useEffect(() => {
    // AbortController — cancel stale requests (Day 3 pattern!)
    const controller = new AbortController()

    async function fetchUser() {
      try {
        setLoading(true)
        setError(null)
        const res  = await fetch(`/api/users/${userId}`, { signal: controller.signal })
        if (!res.ok) throw new Error(`HTTP ${res.status}`)
        const data = await res.json()
        setUser(data)
      } catch (err) {
        if (err.name !== "AbortError") setError(err.message)
      } finally {
        setLoading(false)
      }
    }

    fetchUser()

    // Cleanup — cancel request if userId changes before it finishes
    return () => controller.abort()
  }, [userId])   // re-run when userId changes

  if (loading) return <Spinner />
  if (error)   return <ErrorMessage message={error} />
  return <div>{user?.name}</div>
}

// ── Event listener + cleanup ──────────────────────────────
function WindowSize() {
  const [size, setSize] = useState({ w: window.innerWidth, h: window.innerHeight })

  useEffect(() => {
    const onResize = () => setSize({ w: window.innerWidth, h: window.innerHeight })
    window.addEventListener("resize", onResize)
    return () => window.removeEventListener("resize", onResize) // cleanup!
  }, [])  // mount/unmount only

  return <p>{size.w} × {size.h}</p>
}

// ── Timer + cleanup ───────────────────────────────────────
function Countdown({ seconds }) {
  const [time, setTime] = useState(seconds)

  useEffect(() => {
    if (time === 0) return
    const timer = setTimeout(() => setTime(t => t - 1), 1000)
    return () => clearTimeout(timer)   // clear previous timer before next
  }, [time])

  return <p>{time === 0 ? "Time's up!" : time}</p>
}

function renderToString(element) {
  if (element === null || element === undefined || element === false) return ""
  if (typeof element === "string" || typeof element === "number") return String(element)

  const { type, props } = element

  // Function component — call it and render the result
  if (typeof type === "function") {
    return renderToString(type(props))
  }

  // HTML element — render tag with attributes and children
  const { children = [], ...attrs } = props
  const attrStr = Object.entries(attrs)
    .filter(([, v]) => v !== null && v !== undefined)
    .map(([k, v]) => ` ${k}="${v}"`)
    .join("")
  const childStr = (Array.isArray(children) ? children : [children])
    .map(renderToString).join("")
  return `<${type}${attrStr}>${childStr}type}>`
}

function diff(oldNode, newNode, patches = [], path = "root") {
  if (!oldNode && !newNode) return patches

  if (!oldNode) { patches.push({ op:"CREATE", path, node:newNode }); return patches }
  if (!newNode) { patches.push({ op:"REMOVE", path });              return patches }

  if (typeof oldNode === "string" || typeof newNode === "string") {
    if (oldNode !== newNode) patches.push({ op:"UPDATE", path, oldNode, newNode })
    return patches
  }

  if (oldNode.type !== newNode.type) {
    patches.push({ op:"REPLACE", path, newNode }); return patches
  }

  if (propsChanged(oldNode.props, newNode.props)) {
    patches.push({ op:"UPDATE_PROPS", path, props:newNode.props })
  }

  const len = Math.max((oldNode.children||[]).length, (newNode.children||[]).length)
  for (let i = 0; i < len; i++) {
    diff((oldNode.children||[])[i], (newNode.children||[])[i], patches, `${path}[${i}]`)
  }
  return patches
}

function reconcileByKey(oldList, newList) {
  const updates  = []
  const oldByKey = Object.fromEntries(oldList.map(i => [i.id, i]))
  const newByKey = Object.fromEntries(newList.map(i => [i.id, i]))

  newList.forEach(item => {
    const old = oldByKey[item.id]
    if (!old)                       updates.push({ op:"CREATE", item:item.text })
    else if (old.text !== item.text) updates.push({ op:"UPDATE", from:old.text, to:item.text })
    else                              updates.push({ op:"SKIP",   item:item.text })
  })

  oldList.forEach(item => {
    if (!newByKey[item.id]) updates.push({ op:"REMOVE", item:item.text })
  })

  return updates
}

08 Interview questions + model answers 10 Q&As
Q1What is React and what problem does it solve?▶
model answer
React is a JavaScript library for building user interfaces. It solves the problem of keeping the UI in sync with application state. In vanilla JS, you have to manually update the DOM every time data changes, which becomes error-prone at scale.

React introduces a declarative model: you describe what the UI should look like for a given state (UI = f(state)), and React handles the actual DOM updates efficiently. When state changes, React re-runs your component function, diffs the new virtual DOM output against the previous one, and applies only the minimum real DOM changes — a process called reconciliation.
Strong answer adds: "React is just JavaScript — components are functions, state is managed with closures, and the event system uses delegation under the hood. Understanding JS deeply is what separates developers who truly understand React from those who just copy patterns."
Q2What is JSX? Is it required to use React?▶
model answer
JSX is a syntax extension that lets you write HTML-like syntax inside JavaScript. It's not HTML and not required — it's compiled by tools like Babel or the React JSX transform into React.createElement() calls.

<Button color="red">Click</Button> becomes React.createElement(Button, {color:"red"}, "Click").

JSX is not required — you could write React entirely with React.createElement() calls — but JSX is almost universally used because it makes component structure visually clear. Modern React uses the automatic JSX transform, so you no longer need import React from 'react' at the top of every file.
Q3What is the difference between state and props?▶
model answer
Props are inputs passed to a component from its parent — like function arguments. They are read-only and flow one direction (parent to child). A component cannot change its own props.

State is data managed inside a component. It is mutable via the setter returned by useState. When state changes, React re-renders the component. State is private to the component by default.

The distinction matters for data flow: if data needs to be shared between siblings, "lift it up" to the nearest common parent — the parent holds state and passes it down as props. Props flow down; callbacks (via props) allow data to flow back up.
Common follow-up: "When should something be state vs a regular variable?" — if changing the value should cause a re-render, use state. If it's derived from state/props (computed), don't duplicate it in state — compute it inline. If it's static configuration, use a constant outside the component.
Q4Why shouldn't you mutate state directly in React?▶
model answer
React detects state changes by comparing object references, not deep equality. If you mutate state directly (items.push(x), user.name = "Bob"), the reference to the object stays the same — React's comparison sees no change and doesn't re-render, leaving the UI out of sync with your data.

The fix is always creating a new reference: [...items, x] for arrays, {...user, name: "Bob"} for objects. React then sees a different reference and schedules a re-render.

This is the same immutability concept from Week 1 — the immutable update patterns with spread and filter are used constantly in React state management.
Q5What are the three forms of useEffect's dependency array?▶
model answer
No array (useEffect(fn)): runs after every render. Usually causes problems — if the effect updates state, it triggers another render, which triggers the effect again, creating an infinite loop.

Empty array (useEffect(fn, [])): runs once after the initial mount only. Like componentDidMount. Use for one-time setup: fetch initial data, set up event listeners, initialise third-party libraries.

With dependencies (useEffect(fn, [a, b])): runs after mount AND whenever any value in the dependency array changes (shallow comparison). Use when you need to re-run a side effect in response to state or prop changes — like re-fetching data when a filter changes.

The cleanup function returned from useEffect runs before the next effect run and on unmount — critical for preventing memory leaks and stale requests.
Q6What is the Virtual DOM and how does reconciliation work?▶
model answer
The Virtual DOM is a lightweight JavaScript object tree that mirrors the real DOM. React maintains two versions: the current VDOM and the previous VDOM.

When state changes, React re-runs the component function and creates a new VDOM tree. It then diffs (compares) the new tree against the old tree to find what changed — this is reconciliation. Finally, React applies only the minimum required changes to the real DOM.

Why does this help? Real DOM operations are expensive because they trigger layout recalculation and painting. Diffing two JS objects is much cheaper than querying/updating the real DOM. React batches multiple state updates into a single DOM update pass for further efficiency.
Depth signal: React 18 introduced Concurrent Mode and the Fiber architecture — the reconciler can now pause, prioritise, and resume work. This makes animations and user inputs stay responsive even during expensive re-renders.
Q7Why do we need the key prop when rendering lists?▶
model answer
Keys help React identify which items in a list changed, were added, or removed. Without keys, React matches items by their index position in the array. If you insert an item at the beginning, all subsequent items appear "changed" by position — React unnecessarily re-renders them all.

With stable keys (typically IDs), React matches items across renders by identity. If you prepend a new item, React creates one new node and leaves the existing ones untouched.

Keys should be stable (same item → same key across renders), unique among siblings, and predictable. Using array index as key is only safe for static lists that never reorder — for dynamic lists it causes subtle input/animation bugs because a component gets the new item's data but keeps the old item's DOM state.
Never use Math.random() as a key — this generates a new key on every render, causing React to destroy and recreate the element on every render, which is worse than having no key at all.
Q8What is a controlled component? How does it differ from uncontrolled?▶
model answer
A controlled component has its value driven by React state. The input's value prop is set from state, and an onChange handler updates state when the user types. React is the "single source of truth" for the input's value.

An uncontrolled component manages its own state internally in the DOM. You read the value with a ref (useRef) when needed, rather than tracking it on every keystroke.

Controlled components give you full control — you can validate on every keystroke, format as the user types, and derive computed values from the input. Most React forms use controlled inputs. Uncontrolled is simpler for file inputs and when you only need the value on submit, not during input.
Q9What is the 0 gotcha in JSX conditional rendering? How do you fix it?▶
model answer
In JavaScript, 0 is falsy — so 0 && <Component /> short-circuits and returns 0, not false. React renders false, null, and undefined as nothing, but it renders 0 as the character "0" on screen.

This is a common bug: {items.length && <ItemList />} renders "0" when items is an empty array.

Fixes: use an explicit boolean check (items.length > 0 && ...), double negate (!!items.length && ...), or use a ternary (items.length ? <ItemList /> : null). The ternary is the most explicit and readable choice.
Q10What are React hooks? What are the rules of hooks?▶
model answer
Hooks are functions that let you use React features (state, side effects, context, etc.) inside function components. Before hooks, you needed class components for state. Hooks enable cleaner, more composable code by letting you extract stateful logic into reusable custom hooks.

The two rules of hooks:
1. Only call hooks at the top level — never inside loops, conditionals, or nested functions. Hooks must always be called in the same order on every render (React tracks them by position).
2. Only call hooks from React function components or custom hooks — not from regular JS functions.

The reason for rule 1: React internally stores hook state in an array indexed by call order. If a hook is conditionally skipped, subsequent hooks shift positions and read the wrong state. ESLint's react-hooks/rules-of-hooks plugin enforces these rules automatically.
If you need to conditionally use an effect, put the condition inside the hook, not around it: useEffect(() => { if (!enabled) return; ... }, [enabled])
