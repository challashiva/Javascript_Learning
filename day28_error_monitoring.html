01 Why monitor — production is a different world motivation
the problem
Errors happen that you never see
In development you test the happy path. In production: edge case input from a user in an unexpected locale, a race condition that only manifests under load, a third-party API returning an unexpected shape, a browser extension interfering with your JavaScript. Without monitoring, you learn about these from angry customer emails — hours or days after they started.
Sentry's value
Know the moment something breaks
Sentry captures every unhandled exception with: the exact stack trace (even in minified code via source maps), the user who hit it (email, ID), what they were doing (breadcrumbs — clicks, API calls, navigation), their browser, OS, and screen size. You can reproduce and fix the bug without talking to the user.
what monitoring covers
Frontend + backend + performance
Sentry captures: client-side JavaScript errors (unhandled promise rejections, React render errors), server-side exceptions in Route Handlers and Server Actions, performance problems (slow API routes, slow page renders), and custom events you manually capture (captureException, captureMessage). One dashboard for the whole stack.
vs alternatives
Sentry vs console.log vs Datadog
console.log in production is invisible — the browser console and server stdout go nowhere useful. Datadog is expensive and complex, better for large teams with infra engineers. Sentry is the sweet spot for indie developers and startups: generous free tier (5K errors/month), excellent Next.js integration, minimal setup, immediately actionable alerts.

// sentry.client.config.ts — browser SDK
import * as Sentry from "@sentry/nextjs"

Sentry.init({
  dsn:              process.env.NEXT_PUBLIC_SENTRY_DSN,
  environment:      process.env.NODE_ENV,
  tracesSampleRate: process.env.NODE_ENV === "production" ? 0.1 : 1.0,
  // ↑ sample 10% of traces in prod (performance data), 100% in dev
  replaysSessionSampleRate: 0.1,  // 10% session replay (optional, costs)
  replaysOnErrorSampleRate:  1.0,  // 100% replay on error (essential)
  integrations: [
    Sentry.replayIntegration(),
    Sentry.browserTracingIntegration(),
  ],
  ignoreErrors: [
    "ResizeObserver loop limit exceeded",  // known browser noise
    /Network Error/i,                        // user's connection issues
    "Script error.",                         // cross-origin script errors (no stack)
  ],
  beforeSend(event) {
    // Strip PII before sending to Sentry
    if (event.request?.data) {
      delete event.request.data.password
      delete event.request.data.creditCard
    }
    return event
  },
})

03 Capturing errors — automatic, manual, and boundaries capture

// ── Automatic capture — just install, these work ───────────

// ✓ React error boundaries (via Sentry.withErrorBoundary)

// ── Manual capture — catch and report ─────────────────────
async function createOrder(items: CartItem[]) {
  try {
    const order = await db.order.create({ data: /* ... */ })
    return { success: true, order }
  } catch (error) {
    // Report to Sentry with context
    Sentry.captureException(error, {
      tags: { action: "createOrder", itemCount: items.length.toString() },
      extra: { items: items.map(i => ({ id: i.productId, qty: i.quantity })) }
    })
    return { error: "Failed to create order" }
  }
}

// captureMessage — log events that aren't exceptions
Sentry.captureMessage("Payment processor fallback used", {
  level: "warning",   // "fatal" | "error" | "warning" | "info" | "debug"
  tags:  { processor: "stripe-fallback", reason: "primary-timeout" },
})

      </button>

  )

export async function createOrderAction(prevState: unknown, data: FormData) {
  return await Sentry.withScope(async (scope) => {
    scope.setTag("action", "createOrder")
    scope.setContext("formData", { itemCount: Number(data.get("itemCount")) })
    try {
      return await processOrder(data)
    } catch (e) {
      Sentry.captureException(e)
      return { error: "Order failed" }
    }
  })
}
04 User context + breadcrumbs — who was affected and what did they do context
typescriptsetUser, addBreadcrumb, tags, extra — answering "who and what" for every error
import * as Sentry from "@sentry/nextjs"

// ── setUser — attach who was affected ─────────────────────
// Call after sign-in, in a Providers component or useEffect
"use client"
import { useEffect } from "react"
import { useUser }  from "@clerk/nextjs"

export function SentryUserProvider() {
  const { user } = useUser()

  useEffect(() => {
    if (user) {
      Sentry.setUser({
        id:       user.id,
        email:    user.primaryEmailAddress?.emailAddress,
        username: user.fullName ?? undefined,
        // Don't include: passwords, full addresses, payment info!
      })
    } else {
      Sentry.setUser(null)  // clear on sign-out
    }
  }, [user])

  return null
}

// ── addBreadcrumb — record user journey ───────────────────
// Sentry automatically adds: navigation, clicks, HTTP requests
// Add custom breadcrumbs for important business events:

function handleAddToCart(product: Product) {
  Sentry.addBreadcrumb({
    category: "cart",
    message:  `Added "${product.name}" to cart`,
    level:    "info",
    data:     { productId: product.id, price: product.price },
  })
  // Now if checkout fails, Sentry shows: "Added X to cart → clicked checkout → error"
}

async function processPayment(amount: number) {
  Sentry.addBreadcrumb({
    category: "payment",
    message:  "Initiating payment",
    level:    "info",
    data:     { amount },  // amount OK, not card number!
  })
}

05 Performance monitoring — traces, spans, and slow operations performance
typescriptSentry transactions, custom spans, measuring slow DB queries and API calls
import * as Sentry from "@sentry/nextjs"

// ── Auto-instrumentation — works out of the box ───────────
// ✓ HTTP requests (fetch, axios)
// ✓ Next.js page loads and navigations
// ✓ Server route handler execution time
// ✓ React component render time (with React integration)

// ── Custom span — measure a specific operation ────────────
async function getProductsWithStats() {
  return Sentry.startSpan(
    { name: "db.getProductsWithStats", op: "db.query" },
    async () => {
      const products = await db.product.findMany({
        include: { reviews: true, category: true, _count: true }
      })
      // If this span takes > 1000ms, Sentry flags it as slow
      return products
    }
  )
}

// ── Instrument a checkout flow ────────────────────────────
async function checkout(userId: string, items: CartItem[]) {
  return Sentry.startSpan(
    { name: "checkout.complete", op: "business" },
    async (span) => {
      span.setAttribute("checkout.item_count", items.length)

      // Step 1: validate stock
      await Sentry.startSpan({ name: "checkout.validateStock", op: "db.query" },
        async () => validateStock(items))

      // Step 2: create order
      const order = await Sentry.startSpan({ name: "checkout.createOrder", op: "db.query" },
        async () => createOrderInDB(userId, items))

      // Step 3: send confirmation email
      await Sentry.startSpan({ name: "checkout.sendEmail", op: "email" },
        async () => sendConfirmationEmail(order))

      return order
    }
  )
  // In Sentry Performance: see the full waterfall
  // checkout.complete: 340ms
  // ├─ checkout.validateStock: 45ms
  // ├─ checkout.createOrder: 280ms ← slow! investigate
  // └─ checkout.sendEmail: 12ms
}

06 Structured logging + alert strategy logging + alerts
typescriptStructured logger, log levels, Sentry alert rules, on-call runbook
// ── Structured logger — replace console.log in production ─
// lib/logger.ts
import * as Sentry from "@sentry/nextjs"

type LogLevel = "debug" | "info" | "warn" | "error"
type LogContext = Record<string, unknown>

function log(level: LogLevel, message: string, ctx: LogContext = {}) {
  const entry = {
    level,
    message,
    timestamp: new Date().toISOString(),
    service:   "shopco-api",
    ...ctx
  }
  // Structured JSON logs — parseable by log aggregators (Datadog, Loki)
  console[level === "debug" ? "log" : level](JSON.stringify(entry))

  // Forward warnings and errors to Sentry as breadcrumbs
  if (level === "warn" || level === "error") {
    Sentry.addBreadcrumb({ category: "log", message, level, data: ctx })
  }
}

export const logger = {
  debug: (msg: string, ctx?: LogContext) => log("debug", msg, ctx),
  info:  (msg: string, ctx?: LogContext) => log("info",  msg, ctx),
  warn:  (msg: string, ctx?: LogContext) => log("warn",  msg, ctx),
  error: (msg: string, ctx?: LogContext) => log("error", msg, ctx),
}

// Usage:
logger.info("Order created", { orderId: "ord_123", total: 299, userId: "u_1" })
logger.warn("Stock low",     { productId: "p_1", remaining: 2 })
logger.error("Payment failed", { userId: "u_1", amount: 299, code: "card_declined" })
// Never: logger.error("Payment failed", { card: "4242424242424242" }) ← PII!

// ── Sentry alert rules ────────────────────────────────────

08 Interview questions + model answers 10 Q&As
Q1Why do you need error monitoring if you have tests?▶
model answer
Tests verify behaviour for inputs you anticipated. Production users do things you never tested: a user in an unexpected locale with a special character in their name, a race condition that requires specific timing, a third-party API returning an undocumented error code, a browser extension interfering with your JavaScript, an edge case in your Zod schema you didn't cover. Tests prove the code works for the scenarios you imagined — monitoring tells you what happens in the scenarios you didn't.

Additionally, tests run in a controlled environment with mocked data and predictable timing. Production has real network latency, real database load, real third-party APIs that go down, and real users doing unexpected things. Error monitoring is what bridges the gap between "it passes tests" and "it works in production for everyone."
Q2What is a DSN in Sentry and what does it contain?▶
model answer
DSN stands for Data Source Name — it's a URL that tells the Sentry SDK where to send captured events. Format: https://public_key@host/project_id. It contains the public key (identifies which project events belong to) and the endpoint URL (usually Sentry's cloud or your self-hosted instance).

Important: the DSN is safe to expose on the client side (it's already in your browser's JavaScript). It can only be used to send events to your project — it can't be used to read events or access your account. The secret key (for API operations like source map uploads) should never be exposed client-side. Always use the environment variable NEXT_PUBLIC_SENTRY_DSN for the DSN (public) and SENTRY_AUTH_TOKEN as a build-time secret (never shipped to browser).
Q3What are breadcrumbs in Sentry and why are they valuable?▶
model answer
Breadcrumbs are a chronological trail of events leading up to an error — like the browser's back button history but for what happened in the application. Sentry automatically captures: navigation events (page changes), HTTP requests (what URLs were called), console output, and DOM events (clicks).

You can add custom breadcrumbs for important business events: "User added MacBook Pro to cart", "Payment initiated for $1999", "Stripe API called". When an error occurs, you see the full sequence: user navigated to /checkout → added item → clicked pay → payment failed. Without breadcrumbs, you'd see the exception in isolation without knowing how the user got there. With breadcrumbs, you can often reproduce the bug immediately — just follow the same sequence of actions.
Q4What PII should you never send to Sentry, and how do you prevent it?▶
model answer
Never send: passwords, authentication tokens, API keys, credit card numbers and CVV, SSNs or national ID numbers, full bank account numbers, or passport numbers. These could be exposed in a Sentry data breach (low but non-zero risk) and may violate GDPR, PCI-DSS, or other regulations.

Safe to send: user IDs (anonymous), email addresses (user has consented in ToS), order amounts, product IDs, error codes, browser/OS information, and page URLs (scrubbed of sensitive query params).

Prevention: use beforeSend(event) in your Sentry config to scrub sensitive fields before events leave the browser. This runs client-side before any data is transmitted. Also: don't log passwords or tokens in your structured logger, don't include card details in breadcrumbs, and use the scrubFields config option for automatic scrubbing by field name pattern.
Q5What is tracesSampleRate and how do you choose the right value?▶
model answer
tracesSampleRate controls what fraction of transactions (page loads, API calls) are tracked for performance monitoring. 1.0 = 100% (every transaction traced), 0.1 = 10% (1 in 10 traced). Errors are always captured regardless of this setting.

In development: use 1.0 — you want full visibility while debugging. In production: start with 0.1 (10%). This gives statistically meaningful performance data while keeping your Sentry quota manageable (performance spans count against your monthly limit). For very high traffic apps (millions of requests/day), you might go lower: 0.01 (1%).

The tradeoff: lower sample rate = less accurate tail latency metrics (p95, p99). For most apps under 100k daily users, 10% is sufficient. You can also use tracesSampler (a function) instead of a static rate to always trace important operations like checkout at 100% while sampling less critical pages at 1%.
Q6Why use structured logging instead of console.log?▶
model answer
console.log("Order created for user", userId) in production goes to server stdout where it's unstructured, unsearchable text that disappears into log files or is never seen at all.

Structured logging outputs JSON: { "timestamp": "...", "level": "info", "message": "Order created", "userId": "u123", "orderId": "ord_1", "total": 299 }. Log aggregators (Datadog, Grafana Loki, AWS CloudWatch) ingest this JSON, allowing you to: filter by level:error to see only errors, filter by userId:u123 to trace one user's journey, aggregate by orderId to debug a specific order, create metrics from log data (order volume over time).

Use log levels correctly: debug (development only, verbose), info (normal operations — order created, user signed in), warn (something unexpected but handled — stock running low, retry needed), error (something broke that needs attention — payment failed, DB connection lost). Never log passwords, tokens, or PII at any level.
Q7What are source maps and why are they needed for production debugging?▶
model answer
Next.js (and any bundler) minifies and bundles your JavaScript in production. A stack trace from minified code looks like: TypeError: Cannot read property 'price' of undefined at o (main-abc.js:1:23456) — completely unreadable. You have no idea where in your codebase this is.

Source maps are files that map the minified code back to the original TypeScript source. With source maps, the same error shows: TypeError: Cannot read property 'price' of undefined at ProductCard (app/components/ProductCard.tsx:42:15) — immediately actionable.

The Sentry webpack plugin (configured in next.config.ts) uploads source maps to Sentry's servers during every build. The maps are private — they're never exposed to users. Sentry uses them server-side to transform stack traces before displaying them to you. Important: set hideSourceMaps: true in the Sentry config to prevent the maps from being served to the browser, where malicious users could use them to understand your code.
Q8How do you set up meaningful Sentry alerts without alert fatigue?▶
model answer
Alert fatigue happens when you get so many alerts that you start ignoring them. The fix: alert on things that require human action, not on things the system can handle itself or that happen all the time.

Good alerts: "New error in checkout flow" (P0 — requires immediate action), "Error rate > 10/minute for 5 minutes" (something is systemically broken), "A specific user-facing feature is broken for 3+ users" (meaningful impact). Bad alerts: every single JavaScript error (most are user-side, benign), every single 4xx response (normal — users mistype URLs), the same recurring error you've already decided is acceptable.

Use alert rules with conditions: minimum threshold (1 alert, not 100 for the same event), time window (errors in last hour vs instant), severity levels (only P0/P1 go to PagerDuty for wake-ups, P2/P3 go to Slack). Review your alert history weekly and silence rules that generate noise without action. The goal: every alert you receive should require you to do something.
Q9How does Sentry's session replay help debug hard-to-reproduce bugs?▶
model answer
Session replay captures a pixel-accurate recording of what the user saw and did before the error occurred — clicks, scrolls, typed characters (masked by default), and DOM changes — without actually recording video (it records DOM mutations and replays them). When you open a Sentry error, you can watch exactly what happened in the seconds before the crash.

This is invaluable for bugs that are hard to reproduce: "Add to cart fails sometimes" — watch the replay, see that the user clicked extremely quickly and triggered a race condition. "Form submission fails for some users" — see that a specific browser auto-fill behaviour was injecting unexpected data. "Mobile layout broken" — see the actual mobile viewport and interaction sequence.

Configure with: replaysSessionSampleRate: 0.1 (record 10% of all sessions, for performance data) and replaysOnErrorSampleRate: 1.0 (record 100% of sessions that encounter an error). The error rate one is the important one — you always want a replay when something breaks.
Q10How do you debug a production incident methodically using Sentry?▶
model answer
A systematic approach: first, understand scope — how many users are affected (the Issues list shows this), when it started (the graph shows the spike), and whether it's a new issue or a regression. Check if it correlates with a recent deploy (Releases feature shows issues introduced by each version).

Then, understand the error — open the issue, read the full stack trace with source maps (directly references your code file and line), read the breadcrumbs (user journey leading to the error), check the tags (browser, OS, route, any custom tags you've set). Often you can reproduce it locally within 5 minutes.

If you can't reproduce: watch the session replay, compare the environments (does it only happen on iOS Safari?), look at the extra context fields you attached. Finally fix, deploy, and mark the issue as resolved in Sentry — it will automatically reopen as a regression if the same error occurs again after the fix. Always add a test that covers the fixed bug before closing the issue.
