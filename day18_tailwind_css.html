01 Why utility-first — the CSS at scale problem motivation
traditional CSS problem
CSS grows forever, never shrinks
With BEM or plain CSS, you write a class, use it, then never know if it's safe to delete. Stylesheets grow to hundreds of KB. Naming things is hard — .card-header-title-secondary. Context switching between HTML and CSS files. Style conflicts from specificity. CSS at scale is a maintenance nightmare.
utility-first solution
Compose styles directly in HTML
Tailwind gives you small, single-purpose classes: p-4, text-blue-500, flex, rounded-lg. You compose them directly on elements. The CSS file stays the same small size forever — Tailwind's build tool scans your files and only includes classes you actually use. Dead CSS is impossible.
design constraints
A design system built in
Tailwind ships with a curated design system — a spacing scale (4px base), a colour palette, font sizes, shadows, radii. Every team member uses the same tokens. Design inconsistencies become harder to introduce. You can still customise everything via config, but the defaults give you a beautiful starting point.
the trade-off
HTML gets verbose; CSS becomes clean
A styled button looks like className="px-4 py-2 bg-blue-600 text-white rounded-lg hover:bg-blue-700 transition-colors". More HTML, essentially no CSS. This feels wrong at first — then you realise you never need to name things, switch files, or wonder what broke when you delete CSS. Most developers prefer it after a week.

  plugins: [react(), tailwindcss()],
})

/* src/index.css — one import, that's it */
@import "tailwindcss";

/* Optional: customise your theme with CSS variables */
@theme {
  --color-brand:    #3b82f6;
  --font-sans:      "Inter", sans-serif;
  --radius-card:    12px;
  --spacing-section:80px;
}

  return (
    <div className="bg-white rounded-xl shadow-md p-6 border border-gray-100">
      <h2 className="text-xl font-semibold text-gray-900 mb-4">{title}</h2>
      <div className="text-gray-600 leading-relaxed">{children}</div>
    </div>
  )
}

05 Responsive design — mobile-first breakpoint prefixes responsive
Breakpoint prefixes — mobile-first (min-width)
no prefix
All screens (0px+). Start here — default mobile styles. text-sm always applies.
sm:
≥ 640px. Tablets portrait. sm:text-base kicks in at 640px.
md:
≥ 768px. Tablets landscape / small laptop. Most layout changes happen here.
lg:
≥ 1024px. Desktop. Sidebars, wider grids, larger text.
xl:
≥ 1280px. Large desktop. Fine-tuning for wide screens.
2xl:
≥ 1536px. Ultra-wide. Usually just max-width constraints.

const button = cva(
  "inline-flex items-center justify-center rounded-lg font-medium transition-colors focus:outline-none focus:ring-2 focus:ring-offset-2 disabled:opacity-50",
  {
    variants: {
      variant: {
        primary:   "bg-blue-600 text-white hover:bg-blue-700 focus:ring-blue-500",
        secondary: "bg-gray-100 text-gray-900 hover:bg-gray-200 focus:ring-gray-500",
        ghost:     "text-gray-700 hover:bg-gray-100 focus:ring-gray-500",
        danger:    "bg-red-600 text-white hover:bg-red-700 focus:ring-red-500",
      },
      size: {
        sm: "px-3 py-1.5 text-sm",
        md: "px-4 py-2 text-sm",
        lg: "px-6 py-3 text-base",
      },
    },
    defaultVariants: { variant: "primary", size: "md" },
  }
)

interface ButtonProps
  extends React.ButtonHTMLAttributes<HTMLButtonElement>,
          VariantProps<typeof button> {}

function Button({ variant, size, className, ...props }: ButtonProps) {
  return <button className={button({ variant, size, className })} {...props} />
}

// Usage — TypeScript enforces valid variants:
<Button variant="primary"   size="lg">Save</Button>
<Button variant="secondary" size="sm">Cancel</Button>
<Button variant="danger">Delete</Button>

// ── cn() — merge classes safely ──────────────────────────
// npm install clsx tailwind-merge
import { clsx }         from "clsx"
import { twMerge }      from "tailwind-merge"

export function cn(...inputs: ClassValue[]) {
  return twMerge(clsx(...inputs))
}
// cn merges + deduplicates Tailwind classes safely
// Without twMerge: cn("px-4", "px-6") → "px-4 px-6" (both apply, last wins unpredictably)

cn("p-4 bg-blue-600", isActive && "ring-2 ring-blue-300", className)

09 Interview questions + model answers 10 Q&As
Q1What is utility-first CSS and how does Tailwind implement it?▶
model answer
Utility-first CSS means styling elements with small, single-purpose classes rather than writing custom class names with custom CSS. Instead of .card-header { font-size: 1.25rem; font-weight: 600; color: #111; } you apply text-xl font-semibold text-gray-900 directly in HTML.

Tailwind generates a large set of these utilities — covering every CSS property — and its build tool (PostCSS/Vite plugin) scans your files and only includes utilities you actually use. The resulting CSS file stays tiny regardless of how large your codebase grows.

The key advantage: CSS stops growing. With traditional CSS, every new component adds new CSS. With Tailwind, adding the 100th component adds zero new CSS because all the utilities already exist in the stylesheet. Dead CSS is structurally impossible.
Q2What does "mobile-first" mean in Tailwind's responsive system?▶
model answer
Mobile-first means classes without a breakpoint prefix apply to all screen sizes starting from mobile. Breakpoint prefixes (sm:, md:, lg:) add min-width media queries that override the base styles at larger screens.

So grid-cols-1 md:grid-cols-2 lg:grid-cols-3 means: 1 column on all screens, then 2 columns at ≥768px, then 3 columns at ≥1024px. You build the mobile layout first (no prefix) then progressively enhance for larger screens.

The breakpoints: sm = 640px, md = 768px, lg = 1024px, xl = 1280px, 2xl = 1536px. These are min-width, not max-width — there is no "mobile-only" prefix. To apply something only on mobile, style it with no prefix, then override at sm: or md:.
Q3How does Tailwind handle hover, focus, and other state variants?▶
model answer
Tailwind uses variant prefixes that compile to CSS pseudo-classes and pseudo-elements. hover:bg-blue-700 compiles to .hover\:bg-blue-700:hover { background-color: ... }.

Common variants: hover:, focus:, active:, disabled:, checked:, placeholder:. These stack with breakpoints: md:hover:bg-blue-700 means "on md+ screens, apply bg-blue-700 on hover."

Two powerful variants: group (mark a parent with group, then use group-hover: on children — children respond to the parent being hovered) and peer (mark a sibling with peer, use peer-focus: on the following sibling — floating labels, checkbox-driven UI). These replace complex JavaScript state management for common UI patterns.
Q4How do you implement dark mode in Tailwind?▶
model answer
Tailwind supports two dark mode strategies. Media strategy (default): respects the user's OS preference via prefers-color-scheme: dark. Class strategy (recommended for apps): toggles dark mode by adding/removing the dark class on the <html> element, giving you programmatic control.

With the class strategy, any class prefixed with dark: only applies when an ancestor has the dark class. You write pairs: bg-white dark:bg-gray-900 text-gray-900 dark:text-white. Every colour you set should have a dark twin.

Implementation: store the theme in localStorage, apply the class on page load (before hydration to prevent flash), and toggle with document.documentElement.classList.toggle("dark"). Wrap in a ThemeContext for React.
Q5When should you use @apply, and when should you not?▶
model answer
@apply lets you extract repeated utility combinations into a CSS class. Use it for: truly global base styles (buttons, inputs, links), elements you style from frameworks you can't modify (MDX content, third-party HTML), or design tokens that are repeated dozens of times across a large codebase.

Don't use it as a default escape hatch just because you're uncomfortable with long className strings. The whole point of utility-first is colocation — styles next to the element they apply to. Extracting to @apply brings back the problems Tailwind solves: you lose the ability to see what a component looks like by reading its JSX, and you create abstraction without encapsulation.

The correct abstraction in React is a component, not a CSS class. If a button style is repeated, extract a Button component with the Tailwind classes in it. Use cva for variant systems. Reserve @apply for the rare cases where a component can't be used.
Tailwind's own docs say: "If you find yourself wanting to create an abstract CSS class like .card, just make a card component instead."
Q6What is class-variance-authority (cva) and why use it over template literals?▶
model answer
cva is a library for defining type-safe component variant systems. You define a base class string, then a variants object mapping variant names and values to class strings, plus default variants. It returns a function that accepts variant props and returns the correct class string.

Versus template literals: `${variant === "primary" ? "bg-blue-600" : "bg-gray-100"}` — this works but gets unreadable fast with multiple variants and combinations. With TypeScript, it also provides no autocomplete on variant values.

cva integrates with TypeScript: VariantProps<typeof button> gives you a typed interface for the component's props, so TypeScript will error if you pass an invalid variant. The variant logic stays in one place, the component stays clean, and every caller gets full autocomplete on variant="primary".
Q7What is the cn() function and why is tailwind-merge necessary?▶
model answer
cn() is a helper that combines clsx (conditional class joining) with tailwind-merge (Tailwind-aware class conflict resolution). It's a pattern so common in the React + Tailwind ecosystem that virtually every project has it.

The problem: CSS specificity doesn't help when two Tailwind classes conflict — px-4 px-6 both have the same specificity, so the result depends on which appears later in the stylesheet (which depends on Tailwind's build order, not your class order). tailwind-merge understands Tailwind's class naming conventions and removes earlier conflicting classes: twMerge("px-4 px-6") → "px-6".

Use cn() for component APIs that accept a className prop: cn("base-classes", isActive && "active-classes", className). The external className correctly overrides the defaults rather than conflicting unpredictably.
Q8How do you customise Tailwind's design tokens?▶
model answer
In Tailwind v4, customisation happens in CSS using the @theme directive rather than a JavaScript config file. You define CSS custom properties under @theme and Tailwind generates utilities for them automatically.

@theme { --color-brand: #3b82f6; --font-display: "Cal Sans", sans-serif; --spacing-section: 80px; } — this adds bg-brand, text-brand, font-display, and section-section (or however the naming maps) to your available utilities.

In v3, customisation goes in tailwind.config.js under theme.extend (to add to defaults) or theme (to replace defaults). The design token approach means your entire design system lives in one file, generating both utilities and the underlying CSS variables that components use.
Q9How does Tailwind's build process keep the CSS file small?▶
model answer
Tailwind v4 uses a Vite plugin (or PostCSS plugin) that scans your source files as they're compiled. It uses a content-scanning approach: every string that looks like a Tailwind class name gets included in the final CSS. Classes you don't use are simply not generated.

In development, a broader set of classes is available for DX. In production, the scanner runs over your final build output and only generates the classes that appear. The resulting CSS is typically 5–15KB for a medium-sized app — much smaller than a handwritten CSS file with similar coverage.

Important implication: never dynamically construct class names. bg-${color}-500 won't work — the scanner sees a string template, not a valid class name. Always use full class names: color === "blue" ? "bg-blue-500" : "bg-red-500". Tailwind's scanner matches these full strings correctly.
Don't do: className={`bg-${color}-500`} — the scanner won't find this and the class won't be generated. Always write complete class names.
Q10How do you handle arbitrary values and when should you use them?▶
model answer
Arbitrary values use square bracket notation to pass any valid CSS value to any utility: w-[342px], bg-[#1a1a2e], text-[clamp(1rem,4vw,2rem)], grid-cols-[1fr_2fr_1fr]. Spaces in CSS values use underscores inside brackets.

When to use: pixel-perfect positioning from a design spec, custom brand colours not in the palette, complex grid templates, CSS functions like clamp() or calc(). They're a safety valve for the cases where the design system doesn't have the right value.

When not to use: if you find yourself using the same arbitrary value in 5 places (w-[342px] five times), add it to your theme instead (--width-sidebar: 342px) so it gets a proper utility class. Arbitrary values are for genuinely one-off values, not for circumventing the design system entirely.
