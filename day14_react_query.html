01 Server state vs client state — why they're different problems foundation
client state
Data you own and control
UI state — whether a modal is open, which tab is active, form inputs, dark mode. You own this data — it lives in memory, you create it, you mutate it, you delete it. useState and useReducer handle this perfectly. Nobody else can change it.
server state
Data that lives on a remote server
User profiles, product lists, orders — data that lives on a server you don't control. It can change at any time. It's asynchronous (requires network), potentially stale (your local copy may be outdated), and must be synchronised with the source of truth. useState alone is inadequate here.
the manual pain
What you write without React Query
Loading boolean, error state, data state, AbortController cleanup, refetch on window focus, deduplication of simultaneous requests, cache with expiry, retry logic, background refresh, race condition protection — every single time, in every component that fetches data. React Query solves all of this with one hook call.
what you get for free
React Query's automatic behaviours
Automatic caching by query key, background refetch when window regains focus, deduplication (two components fetching the same key → one request), stale-while-revalidate (show old data while fetching new), configurable retry on failure, request cancellation, and DevTools built-in.

03 useQuery — the core hook in depth daily use
Query lifecycle — every state a query can be in
pending
No data yet, actively fetching. isLoading is true. Show a skeleton or spinner.
success
Fetch succeeded, data is populated. isSuccess is true. Render your UI.
error
Fetch failed (after retries). error is populated. isError is true. Show error state.
stale
Data is older than staleTime. Still shows old data, but will refetch on next trigger.
fetching
isFetching — true during any fetch, including background refetches. Different from isLoading.
paused
Offline or network unavailable — query is waiting. isPaused is true.
jsxuseQuery — all return values, enabled flag, select transform, placeholderData
import { useQuery } from "@tanstack/react-query"

// ── Basic useQuery ─────────────────────────────────────────
function UserProfile({ userId }) {
  const {
    data,           // the resolved value from queryFn
    isLoading,      // true on first fetch (no cached data)
    isFetching,     // true on ANY fetch, including background
    isError,        // true if last fetch failed
    error,          // the thrown Error object
    isSuccess,      // true if last fetch succeeded
    isStale,        // true if data is older than staleTime
    refetch,        // function to manually trigger a refetch
    status,         // "pending" | "error" | "success"
    fetchStatus,    // "fetching" | "paused" | "idle"
  } = useQuery({
    queryKey: ["user", userId],   // unique cache key — array recommended
    queryFn: () => fetch(`/api/users/${userId}`).then(r => {
      if (!r.ok) throw new Error(`HTTP ${r.status}`)
      return r.json()
    }),
    staleTime: 1000 * 60 * 5,  // 5 min override for this query
  })

  if (isLoading) return <Spinner />
  if (isError)   return <p>Error: {error.message}</p>

  return (
    <div>
      {isFetching && <span>Refreshing...</span>}  {/* subtle refresh indicator */}
      <h1>{data.name}</h1>
      <button onClick={() => refetch()}>Refresh</button>
    </div>
  )
}

04 Query keys — the cache addressing system critical
what they are
Unique addresses for cached data
Query keys are how React Query identifies, caches, and invalidates data. Two components using ["user", 42] as their key share the same cache entry — only one network request fires. Change the key (e.g. to ["user", 43]) and React Query fetches fresh data and stores it separately.
structure
Arrays, not strings — hierarchical
Always use arrays. They support hierarchical invalidation — invalidating ["todos"] also invalidates ["todos", 1] and ["todos", { status: "done" }]. React Query serialises arrays for comparison, so ["todos", { a:1, b:2 }] equals ["todos", { b:2, a:1 }] — order inside objects doesn't matter.
best practice
Put all keys in a factory object
Centralise key construction to avoid typos and inconsistencies. A todoKeys factory makes refactoring safe — if you change the key shape, you only update one place. It also makes code self-documenting and enables perfect invalidation patterns.
jsxQuery key patterns — factory pattern, hierarchical invalidation
// ── Query key factory — the recommended pattern ────────────
export const todoKeys = {
  all:     ()              => ["todos"]                          as const,
  lists:   ()              => [...todoKeys.all(), "list"]         as const,
  list:    (filters)       => [...todoKeys.lists(), { ...filters }] as const,
  details: ()              => [...todoKeys.all(), "detail"]       as const,
  detail:  (id: number)   => [...todoKeys.details(), id]          as const,
}

// Usage — no string typos, fully typed
useQuery({ queryKey: todoKeys.list({ status: "done" }) })
// key: ["todos", "list", { status: "done" }]

useQuery({ queryKey: todoKeys.detail(42) })
// key: ["todos", "detail", 42]

// ── Invalidation with hierarchy ────────────────────────────
const queryClient = useQueryClient()

// Invalidate a specific todo
queryClient.invalidateQueries({ queryKey: todoKeys.detail(42) })

// Invalidate ALL todo lists (any filters)
queryClient.invalidateQueries({ queryKey: todoKeys.lists() })

// Invalidate EVERYTHING todo-related
queryClient.invalidateQueries({ queryKey: todoKeys.all() })

// ── Stale time per-query ──────────────────────────────────
// User profile: cache 5 min (changes rarely)
useQuery({ queryKey: ["user", id], queryFn: fetchUser, staleTime: 5 * 60_000 })

// Notifications: always stale (check every focus)
useQuery({ queryKey: ["notifications"], queryFn: fetchNotifs, staleTime: 0 })

// Stock prices: never cache (always fresh)
useQuery({ queryKey: ["stock", ticker], queryFn: fetchPrice, staleTime: Infinity })
05 useMutation — create, update, delete writes
jsxuseMutation — lifecycle callbacks, error handling, mutation state
import { useMutation, useQueryClient } from "@tanstack/react-query"

function NewTodoForm() {
  const queryClient = useQueryClient()

  const createTodo = useMutation({
    mutationFn: (newTodo) =>
      fetch("/api/todos", {
        method:  "POST",
        headers: { "Content-Type": "application/json" },
        body:    JSON.stringify(newTodo),
      }).then(r => r.json()),

    // Runs immediately when mutate() is called (before async)
    onMutate: async (variables) => {
      console.log("Saving...")
    },

    // Runs when mutation succeeds — invalidate to refetch
    onSuccess: (data, variables, context) => {
      queryClient.invalidateQueries({ queryKey: ["todos"] })
      toast.success("Todo created!")
    },

    // Runs when mutation fails
    onError: (error, variables, context) => {
      toast.error(error.message)
    },

    // Runs after either success OR error
    onSettled: () => {
      console.log("Done — success or fail")
    },
  })

  const handleSubmit = (e) => {
    e.preventDefault()
    createTodo.mutate({ text: "New todo", done: false })
    // Or: createTodo.mutateAsync(...) — returns a Promise
  }

  return (
    <form onSubmit={handleSubmit}>
      <button
        type="submit"
        disabled={createTodo.isPending}   {/* true while mutation is running */}
      >
        {createTodo.isPending ? "Saving..." : "Add Todo"}
      </button>
      {createTodo.isError && (
        <p className="error">{createTodo.error.message}</p>
      )}
    </form>
  )
}
06 Cache invalidation & optimistic updates advanced patterns
jsxInvalidation strategies + optimistic update with rollback on error
// ── Invalidation — force a refetch after mutation ─────────
const queryClient = useQueryClient()

// Exact key
queryClient.invalidateQueries({ queryKey: ["todos", 42] })

// All "todos" queries (any key that starts with "todos")
queryClient.invalidateQueries({ queryKey: ["todos"] })

// Invalidate everything in the cache
queryClient.invalidateQueries()

// ── Direct cache write — skip a refetch round trip ────────
// After creating a todo, inject it directly instead of refetching the list
queryClient.setQueryData(["todos"], (old) => [...(old ?? []), newTodo])

// ── Optimistic update — the full pattern ─────────────────
const toggleTodo = useMutation({
  mutationFn: ({ id, done }) =>
    fetch(`/api/todos/${id}`, {
      method: "PATCH",
      body:   JSON.stringify({ done }),
    }),

  // ① Before the request: update cache optimistically
  onMutate: async ({ id, done }) => {
    // Cancel any in-flight refetches that could overwrite our optimistic update
    await queryClient.cancelQueries({ queryKey: ["todos"] })

    // Snapshot the previous value for rollback
    const previous = queryClient.getQueryData(["todos"])

    // Apply optimistic update immediately
    queryClient.setQueryData(["todos"], (old) =>
      (old ?? []).map(t => t.id === id ? { ...t, done } : t)
    )

    // Return context with snapshot — available in onError
    return { previous }
  },

  // ② On error: roll back to snapshot
  onError: (err, variables, context) => {
    if (context?.previous) {
      queryClient.setQueryData(["todos"], context.previous)
    }
  },

  // ③ Always: sync server truth after mutation settles
  onSettled: () => {
    queryClient.invalidateQueries({ queryKey: ["todos"] })
  },
})
After mutation — choose the right update strategy
StrategyHowWhen to use
Invalidate + refetchinvalidateQueries in onSuccessDefault choice. Ensures server truth. Fine for most CRUD operations.
Direct cache writesetQueryData in onSuccessWhen the API returns the new item and you want to skip a round-trip refetch.
Optimistic updatesetQueryData in onMutate + rollback in onErrorHigh-frequency interactions needing instant feedback — toggles, reorders, likes.
Do nothingNo cache updateWhen the mutated data isn't currently shown anywhere in the UI.

}
function invalidate(key) {

    if (k.includes(prefix)) store.delete(k)

async function query(key, fetcher) {
  const k      = serialize(key)
  const cached = cache.get(k)
  const stale  = !cached || (Date.now() - cached.updatedAt) > staleTime

  if (cached && !stale) return cached.data  // fresh — return immediately

  if (cached && stale) {
    // Stale-while-revalidate: return old, background-refetch
    if (!inFlight.has(k)) {
      const p = fetcher().then(d => { cache.set(k,{data:d,updatedAt:Date.now()}); inFlight.delete(k) })
      inFlight.set(k, p)
    }
    return cached.data
  }

  // No cache — deduplicate in-flight
  if (inFlight.has(k)) return inFlight.get(k)

  const promise = fetcher().then(data => {
    cache.set(k, { data, updatedAt: Date.now() })
    inFlight.delete(k)
    return data
  })
  inFlight.set(k, promise)
  return promise
}

async function mutate(variables) {
  state = { isPending:true, isSuccess:false, isError:false, data:null, error:null }; notify()
  const context = await onMutate?.(variables)

  let lastError
  for (let i = 0; i <= retry; i++) {
    try {
      if (i > 0) await new Promise(r => setTimeout(r, 2**i*100))
      const data = await mutationFn(variables)
      state = { isPending:false, isSuccess:true, isError:false, data, error:null }; notify()
      await onSuccess?.(data, variables, context)
      await onSettled?.(data, null, variables, context)
      return
    } catch (e) { lastError = e }
  }
  state = { isPending:false, isSuccess:false, isError:true, data:null, error:lastError }; notify()
  await onError?.(lastError, variables, context)
  await onSettled?.(null, lastError, variables, context)
}

08 Interview questions + model answers 10 Q&As
Q1What is the difference between server state and client state?▶
model answer
Client state is data your application owns and controls — UI toggles, form inputs, dark mode, modal visibility. It lives in memory, only your app changes it, and it's synchronous. useState and useReducer are the right tools.

Server state is data that lives on a remote server — user profiles, products, orders. You don't own it — anyone with API access can change it. It's asynchronous (network required), potentially stale (your copy may be outdated), and needs synchronisation with the real source of truth.

The mistake is treating server state like client state — using useState with manual fetch logic. This leads to writing the same boilerplate (loading, error, abort, retry, cache) in every component. React Query is specifically designed for server state management.
Q2What does React Query give you that useEffect + fetch doesn't?▶
model answer
React Query provides several behaviours you'd have to build manually: automatic caching keyed by query key — the same data isn't refetched if it's still fresh. Request deduplication — if two components mount simultaneously and request the same data, one network request fires and both get the result. Background refetch on window focus — stale data is silently refreshed when the user returns to the tab. Automatic retry on network failures. Stale-while-revalidate — show cached data immediately while refetching, preventing loading spinners on revisits. Race condition protection built in. Plus DevTools for inspecting the cache state.
Strong answer: quantify it — "In our app, switching from manual fetch to React Query removed about 30 lines of boilerplate per data-fetching component and fixed three bugs: a race condition on fast navigation, duplicate requests on re-mount, and stale data after mutations."
Q3What are query keys and why should they be arrays?▶
model answer
Query keys are the unique identifiers for each cached entry. React Query serialises them to match cached data to query calls, decide when to refetch (key changed = new data needed), and target invalidation.

Arrays are recommended over strings because they support hierarchical invalidation. Invalidating ["todos"] automatically invalidates ["todos", "list"], ["todos", 42], and any other key starting with "todos". With plain strings you'd need to manually enumerate every variant.

React Query also does deep comparison of array elements — object order doesn't matter within a key element, so ["todos", { status:"done", page:1 }] equals ["todos", { page:1, status:"done" }]. The best practice is a key factory object that constructs keys consistently to avoid typos.
Q4What is stale-while-revalidate and why does it matter for UX?▶
model answer
Stale-while-revalidate means: show the cached (possibly outdated) data immediately, while simultaneously fetching a fresh version in the background. When the fresh data arrives, the UI updates — often with no visible loading state at all.

The UX impact is significant: users see content instantly on revisit instead of a loading spinner. The trade-off is that they might see momentarily stale data — but for most data (user profiles, product lists), a brief period of stale data is far better than a loading state on every navigation.

React Query implements this via staleTime — data younger than staleTime is "fresh" (no refetch). Data older is "stale" (refetch in background but still return immediately). Setting staleTime: Infinity disables background refetch entirely; staleTime: 0 means always refetch but still show old data while doing so.
Q5What is the difference between isLoading and isFetching?▶
model answer
isLoading (also called isPending in v5) is true only on the first fetch — when there's no cached data yet and the query is in flight. It represents the "blank state" — show a skeleton or spinner here.

isFetching is true during any network request, including background refetches of stale data when there's already cached data to display. Use this for subtle "refreshing" indicators — a small spinner in a corner, a faded overlay — that don't disrupt the existing content.

Pattern: use isLoading for the initial empty skeleton, use isFetching && !isLoading for the background refresh indicator. Treating them the same causes the dreaded "skeleton flash" where a fully-loaded list briefly disappears while silently refreshing.
Q6When would you use useMutation vs just calling fetch directly?▶
model answer
useMutation adds several things on top of a plain fetch call: it manages mutation state (isPending, isSuccess, isError, data, error) so you don't need separate state variables. It provides lifecycle callbacks (onMutate, onSuccess, onError, onSettled) in the right order. And critically, it integrates with the query cache — in onSuccess you call invalidateQueries to trigger refetches of affected queries.

Call fetch directly when the mutation doesn't affect any cached query data and you don't need loading/error state in the UI. useMutation is worth it whenever you need to update the cache, show a loading indicator, handle errors consistently, or implement optimistic updates.
Q7How do you handle dependent queries — fetching B only after A succeeds?▶
model answer
Use the enabled option: pass a boolean that's false until the dependency is available. React Query will not fire the query until enabled becomes true.

const { data: user } = useQuery({ queryKey: ["user", id], queryFn: fetchUser })
const { data: posts } = useQuery({ queryKey: ["posts", user?.id], queryFn: () => fetchPosts(user.id), enabled: !!user })

When user is undefined (first fetch still in progress), enabled: !!user is false — the posts query waits. Once user data arrives, enabled becomes true and the posts query fires automatically. The query key includes user?.id — when it changes (different user), posts automatically refetch for the new user.
Q8What is an optimistic update and when should you use one?▶
model answer
An optimistic update immediately applies a change to the local cache before the server confirms it — making the UI feel instant. If the server succeeds, the optimistic state is confirmed. If it fails, the previous state is restored (rolled back) from a snapshot taken before the update.

The React Query pattern: in onMutate, cancel in-flight queries, save a snapshot with getQueryData, apply the change with setQueryData, and return the snapshot as context. In onError, call setQueryData with the snapshot. In onSettled, invalidate to sync with server truth.

Use optimistic updates for high-frequency, reversible actions — checkbox toggles, like buttons, reordering. Don't use them for destructive or irreversible actions (deleting an account, processing a payment) where a brief loading state is worth the certainty.
Q9What is gcTime (formerly cacheTime) and how does it differ from staleTime?▶
model answer
staleTime controls when data is considered outdated and should be refetched. Data younger than staleTime is "fresh" — no refetch. Older is "stale" — will be refetched on next mount/focus but still returned immediately.

gcTime (garbage collection time) controls how long unused cache entries are kept in memory before being deleted entirely. When the last component subscribed to a query unmounts, a countdown starts. If no component resubscribes within gcTime (default: 5 minutes), the entry is removed from the cache.

Practical difference: staleTime: 60000 means a user navigating back within 1 minute sees instantly-rendered stale data that quietly refetches. gcTime: 0 would throw away the cache the moment they leave — they'd see a loading state on return. Usually gcTime > staleTime is the right configuration.
Q10How does React Query compare to Redux for data fetching?▶
model answer
They solve different problems. Redux is a general-purpose client state manager — it's good for complex UI state, undo/redo, and state that needs to be shared globally across many components. It has no concept of "staleness", caching with expiry, or background refresh.

React Query is specifically designed for server state — async data that lives on a remote server. It handles caching, background updates, deduplication, and synchronisation automatically. It's not a replacement for Redux for client state; it's a replacement for the Redux patterns people used to fetch server data (Redux Thunk, Redux Saga, RTK Query).

The modern recommendation: use React Query for all server state (API calls), and local state/context for client state (UI, auth). This removes 80% of the Redux boilerplate that previously existed just to manage remote data.
Mark Erikson (Redux maintainer) himself recommends using React Query or RTK Query for server state and using Redux only for genuinely complex client state. RTK Query is Redux Toolkit's built-in answer to React Query if you're already using Redux.
