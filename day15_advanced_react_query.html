01 Paginated queries — page numbers & keepPreviousData pagination
the naive problem
Page change → loading flash
With plain useQuery, changing the page number changes the query key, which means no cached data for the new page — the component shows a loading spinner. Every page navigation feels like the first load. This is the wrong UX for a paginated table or grid.
keepPreviousData fix
Show current page while next page loads
Set placeholderData: keepPreviousData. When the page changes, React Query keeps showing the current page's data (slightly faded) while the next page fetches in the background. The UI never flashes a loading state — it just feels fast. Use isPlaceholderData to dim the content or disable the Next button.
prefetch next page
Preload page N+1 while viewing page N
Call queryClient.prefetchQuery for the next page immediately after rendering the current page. When the user clicks Next, the data is already in cache — navigation feels instant. This is how modern data tables achieve zero-loading pagination.
jsxPaginated query — keepPreviousData + prefetch next page
import { useQuery, useQueryClient, keepPreviousData } from "@tanstack/react-query"
import { useState, useEffect } from "react"

async function fetchProducts({ page, pageSize = 20, category }) {
  const params = new URLSearchParams({ page, pageSize, ...category && { category } })
  const res = await fetch(`/api/products?${params}`)
  if (!res.ok) throw new Error("Failed to fetch")
  return res.json()
  // returns: { items: [...], total: 248, page: 2, totalPages: 13 }
}

function ProductsPage() {
  const [page,     setPage]     = useState(1)
  const [category, setCategory] = useState("")
  const queryClient = useQueryClient()

  const { data, isLoading, isPlaceholderData } = useQuery({
    queryKey:        ["products", { page, category }],
    queryFn:         () => fetchProducts({ page, category }),
    placeholderData: keepPreviousData,  // ← no flash on page change
    staleTime:       1000 * 60,
  })

  // Prefetch the NEXT page while showing the current one
  useEffect(() => {
    if (data && page < data.totalPages) {
      queryClient.prefetchQuery({
        queryKey: ["products", { page: page + 1, category }],
        queryFn:  () => fetchProducts({ page: page + 1, category }),
        staleTime: 1000 * 60,
      })
    }
  }, [data, page, category, queryClient])

  if (isLoading) return <Spinner />

  return (
    <div>
      <div
        style={{ opacity: isPlaceholderData ? 0.6 : 1, transition: "opacity 0.2s" }}
      >
        {data.items.map(p => <ProductCard key={p.id} product={p} />)}
      </div>

      <div className="pagination">
        <button
          onClick={() => setPage(p => Math.max(1, p - 1)}
          disabled={page === 1}
        >← Prev</button>

        <span>Page {page} of {data.totalPages}</span>

        <button
          onClick={() => setPage(p => p + 1)}
          {/* Disable while placeholder showing OR on last page */}
          disabled={isPlaceholderData || page === data.totalPages}
        >Next →</button>
      </div>
    </div>
  )
}
02 useInfiniteQuery — infinite scroll feeds infinite scroll
How useInfiniteQuery differs from useQuery
data shape
data.pages is an array of all page results. data.pageParams is the array of params used. You flatten or map over data.pages to render all loaded items.
getNextPageParam
A function that receives the last page's data and returns the next page's cursor/param. Return undefined to signal there are no more pages. React Query calls this to know how to fetch the next page.
fetchNextPage()
Call this to load the next page. React Query uses the result of getNextPageParam as the pageParam argument to your queryFn. Pair with hasNextPage to know when to stop.
IntersectionObserver
The standard way to trigger fetchNextPage — observe a sentinel element at the bottom of the list. When it enters the viewport, call fetchNextPage. No scroll event listeners needed.
jsxuseInfiniteQuery — cursor pagination + IntersectionObserver trigger
import { useInfiniteQuery } from "@tanstack/react-query"
import { useRef, useEffect } from "react"

// API returns: { items: [...], nextCursor: "cursor_xyz" | null }
async function fetchPosts({ pageParam = null }) {
  const url = pageParam
    ? `/api/posts?cursor=${pageParam}`
    : "/api/posts"
  return fetch(url).then(r => r.json())
}

function PostFeed() {
  const sentinelRef = useRef(null)  // invisible div at bottom of list

  const {
    data,
    fetchNextPage,
    hasNextPage,         // true when getNextPageParam returns non-undefined
    isFetchingNextPage,  // true while the next page is loading
    isLoading,
    isError,
    error,
  } = useInfiniteQuery({
    queryKey: ["posts"],
    queryFn:  fetchPosts,                    // receives { pageParam }
    initialPageParam: null,                   // first call pageParam = null
    getNextPageParam: (lastPage) =>
      lastPage.nextCursor ?? undefined,      // undefined = no more pages
  })

  // IntersectionObserver — auto-load when sentinel enters viewport
  useEffect(() => {
    const el = sentinelRef.current
    if (!el) return

    const observer = new IntersectionObserver(([entry]) => {
      if (entry.isIntersecting && hasNextPage && !isFetchingNextPage) {
        fetchNextPage()
      }
    }, { threshold: 0.1 })

    observer.observe(el)
    return () => observer.disconnect()
  }, [hasNextPage, isFetchingNextPage, fetchNextPage])

  if (isLoading) return <Spinner />
  if (isError)   return <p>Error: {error.message}</p>

  // Flatten all pages into one list
  const allPosts = data.pages.flatMap(page => page.items)

  return (
    <div>
      {allPosts.map(post => (
        <PostCard key={post.id} post={post} />
      ))}

      {/* Sentinel — triggers next page fetch when visible */}
      <div ref={sentinelRef} style={{ height: "1px" }} />

      {isFetchingNextPage && <Spinner />}
      {!hasNextPage && <p>You've reached the end!</p>}
    </div>
  )
}

// ── Offset pagination variant ─────────────────────────────
// API returns: { items: [...], total: 248, page: 2, hasMore: true }
useInfiniteQuery({
  queryKey:       ["posts", "feed"],
  queryFn:        ({ pageParam }) => fetchPosts({ page: pageParam }),
  initialPageParam: 1,
  getNextPageParam: (lastPage, allPages) =>
    lastPage.hasMore ? allPages.length + 1 : undefined,
  // allPages.length = pages fetched so far, +1 = next page number
})
03 Prefetching — data before the user asks for it prefetch
on hover
Fetch when mouse enters a link
When a user hovers over a link, there's ~200–400ms before they actually click. Call prefetchQuery on onMouseEnter. By the time they click and navigate, the data is already in cache. The destination page shows content instantly with zero loading state.
on route change
Prefetch in the parent before rendering children
Before a route renders, the parent route component can call prefetchQuery for the data that the child page will need. When the child mounts and calls useQuery, it finds data already in cache. This is the router-level prefetch pattern.
with loaders (future)
React Router v6.4+ loaders + React Query
React Router's new loader function runs before the component renders. You can call queryClient.prefetchQuery inside the loader to guarantee data is in cache when the component mounts — zero loading states, even on first navigation.
jsxPrefetch on hover, on mount, and with React Router loaders
import { useQueryClient } from "@tanstack/react-query"
import { Link }           from "react-router-dom"

// ── Hover prefetch on a list item ─────────────────────────
function ProductLink({ product }) {
  const queryClient = useQueryClient()

  return (
    <Link
      to={`/products/${product.id}`}
      onMouseEnter={() =>
        queryClient.prefetchQuery({
          queryKey: ["products", product.id],
          queryFn:  () => fetchProduct(product.id),
          staleTime: 1000 * 60,  // skip if already fresh
        })
      }
    >
      {product.name}
    </Link>
  )
}

// ── Prefetch on parent component mount ────────────────────
// A list page can prefetch the first N detail pages immediately
function ProductList({ products }) {
  const queryClient = useQueryClient()

  useEffect(() => {
    // Prefetch the first 3 products' detail pages on list mount
    products.slice(0, 3).forEach(p =>
      queryClient.prefetchQuery({
        queryKey: ["products", p.id],
        queryFn:  () => fetchProduct(p.id),
      })
    )
  }, [products, queryClient])

  return products.map(p => <ProductLink key={p.id} product={p} />)
}

// ── React Router v6.4+ loader integration ────────────────
// In router setup (main.jsx):
const router = createBrowserRouter([
  {
    path: "/products/:id",
    element: <ProductDetail />,
    loader: ({ params }) =>
      queryClient.prefetchQuery({
        queryKey: ["products", Number(params.id)],
        queryFn:  () => fetchProduct(Number(params.id)),
      })
    // Data is in cache when ProductDetail mounts → zero loading state
  },
])
04 useQueries, useSuspenseQuery & error boundaries parallel & suspense
jsxuseQueries for parallel dynamic fetches, useSuspenseQuery, error boundaries
import { useQueries, useSuspenseQuery, useSuspenseQueries } from "@tanstack/react-query"

// ── useQueries — N parallel queries with dynamic count ────
// Can't use N separate useQuery calls in a loop (breaks rules of hooks)
// useQueries handles dynamic arrays cleanly
function MultiUserCard({ userIds }) {
  const results = useQueries({
    queries: userIds.map(id => ({
      queryKey: ["users", id],
      queryFn:  () => fetchUser(id),
      staleTime: 1000 * 60,
    }))
  })
  // results: array of useQuery result objects in same order as queries
  const allLoaded = results.every(r => r.isSuccess)
  if (!allLoaded) return <Spinner />
  return results.map(r => <UserCard key={r.data.id} user={r.data} />)
}

// ── combine option — aggregate all results ────────────────
const { data: combinedData, isPending } = useQueries({
  queries: ids.map(id => ({ queryKey: ["items", id], queryFn: () => fetchItem(id) })),
  combine: (results) => ({
    data:      results.map(r => r.data).filter(Boolean),
    isPending: results.some(r => r.isPending),
    isError:   results.some(r => r.isError),
  }),
})

// ── useSuspenseQuery — integrates with React Suspense ──────
// Throws a Promise when loading (Suspense catches it)
// Throws an Error when errored (Error Boundary catches it)
// NEVER returns isLoading / isError — they're always handled above
function UserProfile({ userId }) {
  // data is ALWAYS defined here — no need for isLoading check
  const { data: user } = useSuspenseQuery({
    queryKey: ["users", userId],
    queryFn:  () => fetchUser(userId),
  })
  return <div>{user.name}</div>  // no null checks needed
}

// ── Wrap with Suspense + ErrorBoundary ────────────────────
function App() {
  return (
    <ErrorBoundary fallback={<ErrorPage />}>
      <Suspense fallback={<PageSkeleton />}>
        <UserProfile userId={42} />
      </Suspense>
    </ErrorBoundary>
  )
}

// ── React Query + react-error-boundary package ────────────
// npm install react-error-boundary
import { ErrorBoundary } from "react-error-boundary"

function QueryErrorBoundary({ children }) {
  const queryClient = useQueryClient()
  return (
    <ErrorBoundary
      fallbackRender={({ error, resetErrorBoundary }) => (
        <div>
          <p>Something went wrong: {error.message}</p>
          <button onClick={() => {
            queryClient.resetQueries()    // clear errored query state
            resetErrorBoundary()           // reset the error boundary
          }}>Try again</button>
        </div>
      )}
    >
      {children}
    </ErrorBoundary>
  )
}

jsxGlobal loading indicator, network status, SSR dehydration pattern
import { useIsFetching, useIsMutating } from "@tanstack/react-query"

// ── Global loading indicator (top progress bar) ───────────
// Shows whenever ANY query is fetching — like GitHub's top progress bar
function GlobalLoadingBar() {
  const isFetching  = useIsFetching()   // count of in-flight queries
  const isMutating  = useIsMutating()   // count of in-flight mutations
  const isActive    = isFetching + isMutating > 0

  return (
    <div
      style={{
        position: "fixed", top: 0, left: 0, right: 0, height: "3px",
        background: "#ff4154",
        transform: isActive ? "scaleX(1)" : "scaleX(0)",
        transformOrigin: "left",
        transition: "transform 0.3s",
      }}
    />
  )
}

// ── SSR pattern — dehydrate on server, hydrate on client ──
// Server-side (Next.js, Remix, or Vite SSR):
import { dehydrate, HydrationBoundary } from "@tanstack/react-query"

export async function getServerSideProps() {
  const qc = new QueryClient()
  await qc.prefetchQuery({ queryKey: ["products"], queryFn: fetchProducts })
  return { props: { dehydratedState: dehydrate(qc) } }
}

// Client-side: wrap with HydrationBoundary to reuse server-fetched data
function Page({ dehydratedState }) {
  return (
    <HydrationBoundary state={dehydratedState}>
      <ProductList />  {/* useQuery finds data already in cache — no fetch */}
    </HydrationBoundary>
  )
}

// ── Mutation error handling with toast ────────────────────
const queryClient = new QueryClient({
  mutationCache: new MutationCache({
    onError: (error) => {
      // Global mutation error handler — toast for all mutations
      toast.error(error.message)
    },
  }),
  queryCache: new QueryCache({
    onError: (error, query) => {
      // Only show toast for background refetch errors (data already exists)
      if (query.state.data !== undefined) {
        toast.error(`Failed to refresh: ${error.message}`)
      }
    },
  }),
})

07 Interview questions + model answers 10 Q&As
Q1How does keepPreviousData (placeholderData) improve pagination UX?▶
model answer
Without it: changing the page number changes the query key, there's no cached data for the new page, and the component shows a loading spinner every time. The content area flashes blank on every page navigation — jarring UX.

With placeholderData: keepPreviousData: when the query key changes (page changes), React Query returns the previous page's data immediately while fetching the new page in the background. The isPlaceholderData flag is true during this time — use it to slightly fade the content or disable the Next button to indicate stale data is showing.

The pattern to pair with it: prefetch the next page with queryClient.prefetchQuery as soon as the current page renders. When the user clicks Next, the data is already in cache — navigation feels instant, zero loading states at all.
In React Query v5, keepPreviousData was removed as a boolean option and replaced with placeholderData: keepPreviousData where keepPreviousData is an imported function. Worth mentioning the v4→v5 change.
Q2Explain useInfiniteQuery — what is getNextPageParam and how does the data shape differ from useQuery?▶
model answer
useInfiniteQuery is designed for "load more" / infinite scroll patterns where new data is appended to a growing list rather than replacing it.

Data shape: instead of a single data value, you get data.pages (an array of each page's API response) and data.pageParams (the params used to fetch each page). To render all items, you flatMap the pages: data.pages.flatMap(page => page.items).

getNextPageParam: a function you provide that receives the last page's response and all pages so far, and returns the param for the next fetch. For cursor pagination: (lastPage) => lastPage.nextCursor. Return undefined to signal no more pages — this sets hasNextPage to false.

Call fetchNextPage() to trigger the next load. In practice you call it when a sentinel element at the bottom of the list becomes visible via IntersectionObserver.
Q3When would you use useQueries instead of multiple useQuery calls?▶
model answer
When the number of queries is dynamic — determined at runtime by an array. React's rules of hooks prevent calling hooks inside loops or conditions, so you can't do ids.forEach(id => useQuery(...)).

useQueries({ queries: ids.map(id => ({ queryKey: [...], queryFn: ... })) }) handles this correctly — it accepts an array of query configs and returns an array of results in the same order. The queries run in parallel.

The combine option is particularly powerful: instead of iterating the results array yourself, you provide a function that transforms the results array into any shape you want — like combine: results => ({ users: results.map(r => r.data), isLoading: results.some(r => r.isLoading) }). The component only re-renders when the combined output changes, not on every individual query update.
Q4What is the difference between useQuery and useSuspenseQuery?▶
model answer
With useQuery, loading and error states are returned as flags — the component is responsible for checking isLoading and isError and rendering appropriate UI. data may be undefined.

With useSuspenseQuery, loading throws a Promise (which React's Suspense boundary catches and shows the fallback for), and errors throw an Error (which an ErrorBoundary catches). The component never sees a loading or error state — by the time the component renders, data is guaranteed to be defined. No null checks needed.

The trade-off: you must wrap the component with a Suspense boundary and an ErrorBoundary above it in the tree. But this co-locates the loading/error UI at a single boundary point rather than scattering it across every component. In large apps this is cleaner — components just declare their data needs and the boundaries handle the states.
Q5How do you implement hover prefetching, and what prevents redundant fetches?▶
model answer
Call queryClient.prefetchQuery in the onMouseEnter handler of the link: <Link onMouseEnter={() => queryClient.prefetchQuery({ queryKey, queryFn })}>.

Redundant fetches are prevented in three ways. First, prefetchQuery checks the cache — if data already exists and is fresher than staleTime, it skips the fetch entirely. Second, if a fetch is already in-flight for the same key (another component already started it), React Query deduplicates and returns the same Promise. Third, you can set a generous staleTime on the prefetch so that hovering the same link multiple times within that window only fetches once.

In practice this means: user hovers a link, a fetch starts in ~0ms. By the time they click (~200ms later), the data is in cache. The detail page renders without any loading state — feels instant.
Q6What is isFetchingNextPage and when is it different from isFetching?▶
model answer
In useInfiniteQuery, isFetching is true whenever any fetch is in-flight — including the initial load and any background refetch of existing pages. isFetchingNextPage is specifically true only when fetchNextPage() is in-flight — appending a new page to the list.

Why the distinction matters: when a user scrolls to the bottom and triggers fetchNextPage, you want to show a "Loading more…" spinner at the bottom of the list — not replace the entire list with a loading state. Using isFetchingNextPage for the bottom spinner and ignoring isFetching achieves this.

Similarly there's isFetchingPreviousPage and fetchPreviousPage for bi-directional infinite scroll (like a chat with historical messages).
Q7How do React Query and React Router loaders work together?▶
model answer
React Router v6.4 introduced loaders — async functions that run before a route renders. React Query integrates by calling queryClient.prefetchQuery inside the loader. The loader doesn't need to return the data — it just populates the React Query cache. When the component mounts and calls useQuery, it finds the data already in cache and renders immediately with zero loading state.

The loader pattern: loader: ({ params }) => queryClient.prefetchQuery({ queryKey: ["products", params.id], queryFn: () => fetchProduct(params.id) }). The component then uses useQuery({ queryKey: ["products", id] }) normally — it just always finds data already there.

This is the gold standard for eliminating loading states entirely. Server-rendered apps do the same with dehydrate/HydrationBoundary: the server populates the cache, serialises it, sends it to the client, and the client rehydrates — no client-side fetch needed on first load.
Q8How do you handle errors globally in React Query without wrapping every component in a try/catch?▶
model answer
Two levels of global error handling. First, the QueryCache and MutationCache accept an onError callback in the QueryClient constructor — this fires for every query or mutation error, regardless of which component triggered it. Use it to show toast notifications for background refetch failures:

new QueryClient({ queryCache: new QueryCache({ onError: (error, query) => query.state.data !== undefined && toast.error(error.message) }) })

Second, for the Suspense approach, a single ErrorBoundary component above the query consumers catches all thrown errors from useSuspenseQuery. The boundary provides a retry button that calls queryClient.resetQueries() to clear the error state and re-trigger fetches.

The recommended pattern: global QueryCache onError for background errors, ErrorBoundary for Suspense-mode errors, and per-component isError handling only for cases where each component needs custom error UI.
Q9What is the Suspense query "throw-while-pending" pattern and how does React catch it?▶
model answer
React's Suspense works through a protocol: if a component throws a Promise during render, React catches it, shows the nearest Suspense fallback, and re-renders the component when the Promise resolves. If the component throws an Error, the nearest ErrorBoundary catches it.

useSuspenseQuery implements this: when the query is pending (no data yet), it throws the in-flight Promise. React catches this, shows the Suspense fallback, waits for the Promise, then re-renders the component. This time the data is in cache, the query returns it normally, and the component renders without any loading check.

The elegance is that the component never needs to handle loading state at all — it's as if async data is synchronous from the component's perspective. The component just reads its data and renders. The complexity is pushed to the boundary layer above, which is often exactly where you want it.
Q10How would you implement "load more" vs infinite scroll — what's the difference?▶
model answer
Both use useInfiniteQuery with the same underlying mechanics — the difference is when fetchNextPage() is triggered.

Load more button: render a button that calls fetchNextPage() on click. Show it when hasNextPage is true, disable it when isFetchingNextPage is true. Simplest implementation, gives users full control — useful for content feeds where auto-loading would be disruptive.

Infinite scroll: render an invisible sentinel element at the bottom of the list and observe it with IntersectionObserver. When it becomes visible, call fetchNextPage(). The observer fires automatically as the user scrolls — seamless, no button needed. Must be careful to stop observing when !hasNextPage || isFetchingNextPage to avoid double-fetching.

In practice: social feeds, image galleries → infinite scroll. Search results, data tables → load more button (users want to feel in control).
