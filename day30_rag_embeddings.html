Core Concepts

🧠 Why RAG?

LLMs are trained on public data up to a cutoff date — they know nothing about your products, docs, or business. RAG solves this by retrieving relevant context from your own database and injecting it into the prompt before generation. The LLM answers using your real data, not hallucinations.

📐 What is an Embedding?

An embedding is a list of numbers (e.g. 1536 floats) that represents the semantic meaning of text. "blue running shoes" and "azure sneakers for jogging" produce similar vectors even though no words match. Models like text-embedding-3-small convert any text to these vectors.

🎯 Cosine Similarity

Two vectors are "similar" if they point in the same direction, regardless of magnitude. Cosine similarity = 1 means identical meaning, 0 means unrelated, -1 means opposite. pgvector uses <=> for cosine distance (1 - similarity), so lower = more similar.

✂️ Chunking

You can't embed an entire product catalogue as one vector. Split content into chunks of ~500 tokens with ~50-token overlap so context isn't lost at boundaries. For ShopCo: one chunk per product (name + description + category + reviews summary).

🐘 pgvector

A Postgres extension that adds a vector column type and distance operators. Add it to your Prisma schema with Unsupported("vector(1536)"). Create an HNSW index for fast approximate nearest-neighbour search across millions of rows.

🔀 Hybrid Search

Pure vector search misses exact keyword matches. Pure full-text search misses semantic similarity. Hybrid search combines both using Reciprocal Rank Fusion (RRF) — merge and re-rank results from both systems. Best for e-commerce where users mix product names with descriptions.

// Enable pgvector extension
generator client {
  provider        = "prisma-client-js"
  previewFeatures = ["postgresqlExtensions"]
}

datasource db {
  provider   = "postgresql"
  url        = env("DATABASE_URL")
  extensions = [vector]
}

model Product {
  id          String   @id @default(cuid())
  name        String
  description String
  price       Float
  category    String
  // 1536-dim vector from text-embedding-3-small
  embedding   Unsupported("vector(1536)")?
  createdAt   DateTime @default(now())
}

model ProductChunk {
  id        String               @id @default(cuid())
  productId String
  content   String               // the actual text chunk
  embedding Unsupported("vector(1536)")?
  product   Product              @relation(fields: [productId], references: [id])
}
migration.sql — create HNSW index for fast search
-- Enable extension
CREATE EXTENSION IF NOT EXISTS vector;

-- HNSW index: fast approximate nearest-neighbour
-- m=16 (connections per layer), ef_construction=64 (build quality)
CREATE INDEX product_embedding_idx
  ON "ProductChunk"
  USING hnsw (embedding vector_cosine_ops)
  WITH (m = 16, ef_construction = 64);
lib/embeddings.ts — embed and search products
import OpenAI from 'openai'
import { prisma } from '@/lib/prisma'

const openai = new OpenAI()

// Embed any text into a 1536-dim vector
export async function embed(text: string): Promise<number[]> {
  const { data } = await openai.embeddings.create({
    model: 'text-embedding-3-small',
    input: text.trim().slice(0, 8000), // token limit
  })
  return data[0].embedding
}

// Embed a product and store it
export async function embedProduct(productId: string) {
  const product = await prisma.product.findUniqueOrThrow({
    where: { id: productId }
  })
  const text = `${product.name}. ${product.description}. Category: ${product.category}`
  const vector = await embed(text)
  // Raw SQL needed — Prisma doesn't support vector type natively yet
  await prisma.$executeRaw`
    UPDATE "Product"
    SET embedding = ${JSON.stringify(vector)}::vector
    WHERE id = ${productId}
  `
}

// Semantic search: find top-K products by meaning
export async function searchProducts(query: string, k = 5) {
  const qVector = await embed(query)
  const results = await prisma.$queryRaw`
    SELECT id, name, price,
      1 - (embedding <=> ${JSON.stringify(qVector)}::vector) AS similarity
    FROM "Product"
    WHERE embedding IS NOT NULL
    ORDER BY embedding <=> ${JSON.stringify(qVector)}::vector
    LIMIT ${k}
  `
  return results
}

RAG Pipeline for ShopCo

app/api/chat/route.ts — RAG-powered product assistant
import { streamText } from 'ai'
import { openai } from '@ai-sdk/openai'
import { searchProducts, embed } from '@/lib/embeddings'

export async function POST(req: Request) {
  const { messages } = await req.json()
  const lastMsg = messages[messages.length - 1].content

  // 1. Embed the user's query
  // 2. Retrieve top-5 relevant products
  const products = await searchProducts(lastMsg, 5)

  // 3. Build context from retrieved products
  const context = products
    .map((p: any) =>
      `- ${p.name} ($${p.price}): ${p.description}`)
    .join('\n')

  // 4. Augment: inject context into system prompt
  const systemPrompt = `You are ShopCo's helpful assistant.
Answer questions using ONLY the products below.
If no products match, say so honestly.

AVAILABLE PRODUCTS:
${context}`

  // 5. Generate with context-aware LLM
  const result = await streamText({
    model: openai('gpt-4o-mini'),
    system: systemPrompt,
    messages,
  })
  return result.toDataStreamResponse()
}

Interview Q&A

1. What is RAG and why is it better than fine-tuning for product search?
RAG (Retrieval-Augmented Generation) retrieves relevant documents at query time and injects them into the prompt. Fine-tuning bakes knowledge into model weights. For product search, RAG is better because: products change frequently (fine-tuning is expensive to redo), you get exact prices/stock at query time, and the LLM can cite specific products. Fine-tuning is better for style/behaviour — not dynamic data.
2. Explain cosine similarity vs L2 (Euclidean) distance for embeddings.
Cosine similarity measures the angle between vectors (direction of meaning), ignoring magnitude. L2 distance measures straight-line distance between vector endpoints. For text embeddings, cosine is preferred because the magnitude of a vector often reflects text length, not meaning — "cat" and "the cat sat on the mat" should be similar in direction even if different in magnitude. pgvector uses <=> for cosine distance and <-> for L2.
3. What is the difference between HNSW and IVFFlat indexes in pgvector?
HNSW (Hierarchical Navigable Small World) builds a graph of vectors for navigation — better recall, faster queries, no training needed, but higher memory. IVFFlat divides vectors into clusters (inverted file) then searches nearby clusters — lower memory, requires training with VACUUM ANALYZE, slightly lower recall. For ShopCo with <1M products, HNSW is recommended. IVFFlat for >10M rows where memory is constrained.
4. How do you handle the "lost in the middle" problem in RAG?
LLMs attend better to content at the beginning and end of the context window — the "lost in the middle" problem. Mitigate with: (1) put the most relevant chunks first and last, (2) reduce k (fewer but better chunks), (3) use re-ranking models (cross-encoders) to score each chunk against the query after retrieval, (4) use max_marginal_relevance_search to diversify results and avoid redundancy.
5. What is Reciprocal Rank Fusion (RRF) and when do you use it?
RRF combines multiple ranked result lists into one by scoring each item as sum(1 / (k + rank)) across all lists, where k=60 is a smoothing constant. Use it for hybrid search: combine vector similarity results with BM25 keyword results. The advantage is it's rank-based (not score-based) so you don't need to normalize scores from different systems. Works well in e-commerce where users mix semantic queries with exact product names.
6. How do you decide on chunk size for embeddings?
It's a precision vs context trade-off. Smaller chunks (128–256 tokens): precise retrieval, loses surrounding context. Larger chunks (512–1024 tokens): more context, less precise. Rules of thumb: (1) match chunk size to your query length — a one-line product search needs small chunks, (2) use 10–20% overlap to avoid boundary issues, (3) respect semantic boundaries (sentences, paragraphs), (4) for ShopCo products: one product per chunk is natural and works well.
7. How do you evaluate RAG quality?
Key metrics: Retrieval quality — precision@k (what % of top-k retrieved are relevant), recall@k (what % of relevant items were retrieved). Generation quality — faithfulness (does the answer come from the context?), relevance (does it answer the question?), groundedness (can every claim be traced to a retrieved doc?). Tools: RAGAS framework, LlamaIndex evaluation, manual human review. For ShopCo: test with real customer queries and verify the returned products actually match intent.
8. What is the difference between text-embedding-3-small and text-embedding-3-large?
text-embedding-3-small: 1536 dimensions, ~5× cheaper, great for most use cases. text-embedding-3-large: 3072 dimensions, higher quality on complex tasks, 13× more expensive. For ShopCo product search, small is sufficient — products are short texts with clear keywords. Use large for complex FAQ matching or document analysis. You can also specify dimensions param to reduce output size (e.g. 256-dim) at the cost of some quality.
9. How do you keep embeddings in sync when products change?
Three strategies: (1) On-write: re-embed in a Prisma middleware or after-update hook — synchronous, adds latency to writes. (2) Background job: queue changed product IDs and process them async with a cron job — best for bulk updates. (3) Change data capture: use Postgres logical replication or triggers to detect changes and trigger re-embedding. For ShopCo: use Prisma middleware for individual edits, batch job for catalogue imports. Track an embeddedAt timestamp to detect staleness.
10. How would you implement multi-tenant RAG where each store has isolated product data?
Add a storeId column to your embeddings table and always include WHERE store_id = $1 in vector queries. This ensures Postgres filters rows before doing similarity search. For pgvector, add a partial index: CREATE INDEX ON product_chunks USING hnsw (embedding vector_cosine_ops) WHERE store_id = 'store_123'. Alternatively use separate Postgres schemas per tenant (full isolation, harder to manage). Avoid putting all tenants in one vector space and filtering after — it wastes compute and leaks data if a bug occurs.
