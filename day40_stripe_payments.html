Core Concepts

🛒 Stripe Checkout Sessions

Checkout is Stripe's hosted, pre-built payment page — handles card input, 3D Secure, Apple/Google Pay, and PCI compliance for you. Create a Checkout Session server-side with line items, then redirect the customer to session.url. After payment, Stripe redirects back to your success_url. Never trust the client-side redirect alone — always confirm the order via webhook, since a customer could close the tab before redirecting back.

💳 Payment Intents

A PaymentIntent tracks a payment through its entire lifecycle: requires_payment_method → requires_confirmation → processing → succeeded (or requires_action for 3D Secure, canceled). Checkout Sessions create a PaymentIntent internally. For custom payment UI (Stripe Elements) you create and confirm PaymentIntents directly. Always handle every status, especially requires_action — many EU cards require 3D Secure authentication.

🪝 Why Webhooks Matter

Never mark an order as paid based only on the client redirecting to your success page — the customer's browser could crash, lose connection, or they could manually navigate away. Webhooks are Stripe's server-to-server notification that a payment actually succeeded, sent reliably (with retries) regardless of what happens in the browser. The only trustworthy signal that a payment succeeded is the checkout.session.completed or payment_intent.succeeded webhook event.

🔁 Idempotency Keys

Network failures can cause your client to retry a request that actually succeeded server-side, risking a duplicate charge. Pass an idempotency key (a unique string, e.g. order_${orderId}_attempt_1) to Stripe API calls — if Stripe sees the same key again within 24 hours, it returns the original result instead of creating a new charge. Always generate this key from something stable (your internal order ID), not Date.now(), which changes on every retry.

📅 Subscription Lifecycle

Subscriptions move through statuses: trialing → active → past_due (payment failed, Stripe retries) → canceled or back to active. Use customer.subscription.updated webhooks to sync status to your DB. For plan changes: stripe.subscriptions.update() with proration. For cancellation: prefer cancel_at_period_end: true so the customer keeps access until the period they already paid for ends.

🧾 Stripe Customer Portal

The Customer Portal is a Stripe-hosted page where subscribers manage their own billing: update payment method, view invoices, change plans, cancel subscription. Create a portal session server-side (stripe.billingPortal.sessions.create()) and redirect the customer. This eliminates building your own billing UI — Stripe handles PCI compliance, proration math, and invoice generation.

app/api/checkout/route.ts — create a Checkout Session
import Stripe from 'stripe'
import { requireAuth } from '@/lib/auth'
import { prisma } from '@/lib/prisma'

const stripe = new Stripe(process.env.STRIPE_SECRET_KEY!)

export async function POST(req: Request) {
  const { userId } = await requireAuth()
  const { items, addressId } = await req.json()

  // 1. Create a PENDING order in our DB first (source of truth for line items)
  const order = await prisma.order.create({
    data: { userId, addressId, status: 'PENDING', items: { create: items } },
    include: { items: { include: { variant: { include: { product: true } } } } }
  })

  // 2. Build Stripe line items from OUR order data (never trust client prices)
  const lineItems = order.items.map(item => ({
    price_data: {
      currency: 'usd',
      product_data: { name: item.variant.product.name, images: [item.variant.product.imageUrl] },
      unit_amount: Math.round(Number(item.unitPrice) * 100), // cents
    },
    quantity: item.quantity,
  }))

  // 3. Create Checkout Session with idempotency key
  const session = await stripe.checkout.sessions.create(
    {
      mode: 'payment',
      payment_method_types: ['card'],
      line_items: lineItems,
      metadata: { orderId: order.id },   // retrieve on webhook
      success_url: `${process.env.APP_URL}/orders/${order.id}?success=true`,
      cancel_url:  `${process.env.APP_URL}/checkout?canceled=true`,
      customer_email: req.headers.get('x-user-email') ?? undefined,
    },
    { idempotencyKey: `checkout_${order.id}` }
  )

  return Response.json({ url: session.url })
}

app/api/webhooks/stripe/route.ts — signature verification + event handling
import Stripe from 'stripe'
import { prisma } from '@/lib/prisma'
import { sendOrderConfirmation } from '@/lib/email'

const stripe = new Stripe(process.env.STRIPE_SECRET_KEY!)
const webhookSecret = process.env.STRIPE_WEBHOOK_SECRET!

export async function POST(req: Request) {
  const body = await req.text()  // MUST be raw text, not JSON — signature needs raw bytes
  const signature = req.headers.get('stripe-signature')!

  let event: Stripe.Event
  try {
    // Verify this webhook actually came from Stripe (not a forged request)
    event = stripe.webhooks.constructEvent(body, signature, webhookSecret)
  } catch (err) {
    console.error('Webhook signature verification failed:', err)
    return new Response('Invalid signature', { status: 400 })
  }

  // Idempotency: have we already processed this event?
  const existing = await prisma.processedWebhook.findUnique({ where: { stripeEventId: event.id } })
  if (existing) return Response.json({ received: true, duplicate: true })

  switch (event.type) {
    case 'checkout.session.completed': {
      const session = event.data.object as Stripe.Checkout.Session
      const orderId = session.metadata?.orderId
      if (orderId) {
        await prisma.order.update({
          where: { id: orderId },
          data: { status: 'PAID', stripeSessionId: session.id, paidAt: new Date() }
        })
        await decrementInventory(orderId)
        await sendOrderConfirmation(orderId)
      }
      break
    }
    case 'payment_intent.payment_failed': {
      const pi = event.data.object as Stripe.PaymentIntent
      await markOrderFailed(pi.metadata.orderId)
      break
    }
    case 'customer.subscription.updated': {
      const sub = event.data.object as Stripe.Subscription
      await syncSubscriptionStatus(sub)
      break
    }
    case 'customer.subscription.deleted': {
      const sub = event.data.object as Stripe.Subscription
      await revokePremiumAccess(sub.customer as string)
      break
    }
  }

  // Record we processed this event (idempotency)
  await prisma.processedWebhook.create({ data: { stripeEventId: event.id, type: event.type } })

  return Response.json({ received: true })
}
⚠ Webhook gotchas:
Always use req.text(), never req.json() for the raw body — signature verification needs the exact bytes Stripe sent. Return 200 quickly even if downstream processing is slow (queue heavy work, don't block the response) — Stripe retries with exponential backoff if it doesn't get a fast 2xx. Test locally with stripe listen --forward-to localhost:3000/api/webhooks/stripe. Always verify the signature — an unauthenticated webhook endpoint lets anyone fake a "payment succeeded" event.

Interview Q&A

1. Why shouldn't you mark an order as paid based on the checkout success redirect alone?
The success redirect is a client-side event — the customer's browser could crash, lose internet connection, or the tab could be closed before the redirect completes, even though the payment succeeded on Stripe's servers. Relying on it means some successful payments never get fulfilled. Webhooks are server-to-server, reliably delivered with retries, and represent the actual source of truth for payment state. Best practice: use the redirect purely for UX (showing a "thank you" page), and use the checkout.session.completed webhook as the only trigger for order fulfillment, inventory updates, and confirmation emails.
2. How do you verify a webhook actually came from Stripe?
Stripe signs every webhook payload with an HMAC-SHA256 signature using your webhook signing secret, sent in the Stripe-Signature header. Your server recomputes the signature from the raw request body and compares it. Use stripe.webhooks.constructEvent(rawBody, signature, webhookSecret) — this both verifies the signature and parses the event. Critical: you must read the request body as raw text (not parsed JSON) because signature verification needs the exact bytes Stripe sent — any reformatting (like JSON.stringify(JSON.parse(body))) breaks the signature check.
3. What is an idempotency key and why is it important for payments?
An idempotency key is a unique string you pass with a Stripe API request. If the same key is sent again within 24 hours (e.g., due to a network timeout causing your client to retry), Stripe returns the original result instead of creating a duplicate charge. This is critical for payments — a customer clicking "Pay" twice due to a slow network shouldn't result in being charged twice. Generate the key from something stable and unique to the operation, like `checkout_${orderId}` — never from Date.now(), which changes on every retry and defeats the purpose.
4. Walk through what happens when a subscription payment fails.
Stripe automatically retries failed subscription payments according to your configured retry schedule (e.g., 3 days, 5 days, 7 days later). The subscription status becomes past_due — you'll receive a customer.subscription.updated webhook. Decide your access policy: many apps keep access active during past_due (grace period) to avoid frustrating customers over a temporarily failed card. If all retries fail, the subscription becomes unpaid or is canceled (configurable), and you'll get another webhook to revoke access. Also handle invoice.payment_failed to send the customer an email prompting them to update their card via the Customer Portal.
5. Why should you never trust product prices sent from the client?
Client-side JavaScript can be modified by anyone using browser dev tools — an attacker could intercept the checkout request and change a $189 item to $0.01 before it reaches your server. Always look up the authoritative price from your database using the product/variant ID sent by the client, and build the Stripe line items server-side from that trusted data. Never accept a price field from the client request body for anything that affects the amount charged. The client should only send identifiers (variant IDs, quantities) — never amounts.
6. How do you test Stripe integrations locally before going live?
Use Stripe's test mode (test API keys, prefixed sk_test_ / pk_test_) — no real money moves. Test card numbers like 4242 4242 4242 4242 simulate successful payments; other numbers simulate declines, insufficient funds, or 3D Secure challenges. For webhooks locally, use the Stripe CLI: stripe listen --forward-to localhost:3000/api/webhooks/stripe — this forwards real webhook events to your local server and gives you a temporary webhook secret for testing. Use stripe trigger checkout.session.completed to fire test events on demand without going through a full checkout flow.
7. What's the difference between Stripe Checkout and Stripe Elements?
Checkout is Stripe's fully-hosted payment page — you redirect the customer to a Stripe-controlled URL, they enter payment details there, and get redirected back. Minimal integration work, Stripe handles all UI, PCI compliance, and localization. Elements are embeddable UI components (card input, payment element) that you render directly in your own checkout page — the customer never leaves your site. More design control and a more seamless brand experience, but more integration work and you're responsible for more of the checkout UX. For most projects, start with Checkout — move to Elements only if you need full UI control (e.g., multi-step custom checkout flows).
8. How would you implement a "buy now, pay later" or free trial flow?
For subscriptions: set trial_period_days when creating the subscription — Stripe automatically manages the trial-to-paid transition and won't charge the card until the trial ends. You still collect payment method upfront (via Checkout with mode: 'subscription' and trial settings) so there's no friction converting after the trial. Listen for customer.subscription.trial_will_end (fires 3 days before trial ends) to send a reminder email. If the customer cancels during the trial, you get customer.subscription.deleted before any charge occurs — no refund needed since nothing was charged.
9. How do you handle proration when a customer changes subscription plans?
Stripe automatically calculates proration when you call stripe.subscriptions.update() with a new price ID — by default it credits the unused time on the old plan and charges for the remaining time on the new plan, reflected on the next invoice (or immediately with proration_behavior: 'always_invoice'). For downgrades, you often want proration_behavior: 'none' combined with scheduling the change for the next billing cycle, avoiding an awkward immediate credit. Always test both upgrade and downgrade paths — customers get confused by unexpected mid-cycle charges more than by delayed downgrades.
10. What database schema do you need to support Stripe subscriptions?
Minimum fields on your User/Subscription table: stripeCustomerId (link to Stripe's Customer object, created once per user), stripeSubscriptionId, status (mirrors Stripe's status enum), currentPeriodEnd (for grace period logic), priceId / plan (which tier they're on), and cancelAtPeriodEnd (boolean — true means "canceled but access continues until period end"). Also maintain a ProcessedWebhook table (event ID + processed timestamp) for idempotency. Never store card details yourself — Stripe handles that entirely; you only store references (customer ID, subscription ID) to Stripe's objects.
