Core concepts

Five foundational topics. Read each in full — every word is there because it shows up in interviews or real codebases.

1. Variables — var, let, const
How JavaScript stores and manages data in memory
foundational

A variable is a named container for a value. JavaScript has three ways to declare one — and the differences between them come up in virtually every junior interview.

// const — use by default. Can't be reassigned.
const name = "Alice";
// name = "Bob";  ← TypeError: Assignment to constant variable

// let — use when the value will change.
let score = 0;
score = 10;  // ✓ fine

// var — old way, avoid in modern code.
var age = 25;  // function-scoped, hoisted — causes confusing bugs
The golden rule Default to const. Only use let when you know the variable will be reassigned (like a counter). Never use var — it behaves unexpectedly with scope and hoisting.

The biggest difference between let/const and var is scope. let and const are block-scoped (they live inside the nearest {}). var is function-scoped (it ignores blocks like if and for).

if (true) {
  let x = 10;
  var y = 20;
}
console.log(y);  // 20 — var leaks out of the block!
console.log(x);  // ReferenceError — let stays inside
Real-world use In React, you'll write const [count, setCount] = useState(0) hundreds of times. Understanding why const is used here (the variable binding doesn't change, even though the state does) will help you reason about React code correctly from day one.
2. Data types — primitives vs objects
What kinds of values JavaScript can hold and how they behave
foundational

JavaScript has 7 primitive types. Everything else is an object. This distinction matters because primitives are copied by value, while objects are copied by reference.

// The 7 primitive types
const str    = "hello";          // string
const num    = 42;               // number  (JS has only ONE number type)
const big    = 9007199254740991n; // bigint
const bool   = true;             // boolean
const empty  = null;             // null — intentional empty
const miss   = undefined;        // undefined — not yet assigned
const id     = Symbol("uid");    // symbol — unique identifier

// typeof operator — check a value's type at runtime
console.log(typeof "hello");   // "string"
console.log(typeof 42);        // "number"
console.log(typeof null);      // "object" ← famous JS bug, not fixable
console.log(typeof undefined); // "undefined"
Common gotcha — value vs reference Primitives are copied. Objects are shared. This trips up almost every beginner. 
// Primitive — copy by VALUE
let a = 5;
let b = a;
b = 10;
console.log(a); // 5 — unchanged

// Object — copy by REFERENCE
const obj1 = { x: 1 };
const obj2 = obj1;  // same object in memory!
obj2.x = 99;
console.log(obj1.x); // 99 — obj1 also changed!
Real-world use In React, this is why you never mutate state directly. When you do state.count = 5, React doesn't see the change because it's the same object reference. You must create a new object: setState({ ...state, count: 5 }).
3. Type coercion and equality
How JavaScript converts types automatically — and how to avoid the traps
tricky

JavaScript automatically converts types when you compare or operate on them. This is called implicit coercion and it's the source of some of the language's most infamous quirks.

// == (loose equality) — coerces types before comparing
console.log(0 == "");    // true  ← both coerce to falsy
console.log(1 == "1");   // true  ← string coerced to number
console.log(null == undefined); // true

// === (strict equality) — no coercion, always use this
console.log(1 === "1");   // false
console.log(null === undefined); // false

// Truthy and falsy values
// FALSY: false, 0, "", null, undefined, NaN
// TRUTHY: everything else (including "0", [], {})
console.log(Boolean(""));      // false
console.log(Boolean("0"));     // true  ← non-empty string!
console.log(Boolean([]));      // true  ← empty array is truthy!
Industry rule Always use === and !==. Never use == or !=. ESLint's eqeqeq rule enforces this on every professional codebase.
4. Functions — declarations, expressions, arrow functions
The building block of all JavaScript logic
critical

JavaScript has three main ways to write a function. Each behaves slightly differently, and React uses arrow functions almost exclusively — so understanding the distinctions is essential.

Function declaration

// Hoisted — can call
// before the definition
greet(); // ✓ works

function greet() {
  return "hello";
}

Arrow function (modern)

// Not hoisted, shorter
// syntax, no own 'this'
const greet = () => {
  return "hello";
};

// Implicit return (1 line)
const add = (a, b) => a + b;
// Parameters and default values
const greetUser = (name = "stranger") => {
  return `Hello, ${name}!`;   // template literal
};

console.log(greetUser("Alice")); // "Hello, Alice!"
console.log(greetUser());        // "Hello, stranger!"

// Functions are first-class values in JS
// — you can pass them around like any other value
const numbers = [1, 2, 3, 4];
const doubled = numbers.map(n => n * 2);
console.log(doubled); // [2, 4, 6, 8]
Real-world use In React: onClick={() => handleClick()}, array.map(item => <Card key={item.id} />), and every component is itself a function. Arrow functions are everywhere.
5. Scope and hoisting
Where variables live and how JavaScript processes your code before running it
interview favourite

Scope determines where a variable is accessible. Hoisting is what JavaScript does before running your code — it moves declarations to the top of their scope.

// Global scope — accessible everywhere
const globalVar = "I'm everywhere";

function outer() {
  // Function scope
  const outerVar = "I'm in outer";

  function inner() {
    // Block scope — can see outerVar (closure!)
    console.log(outerVar);   // ✓ "I'm in outer"
    console.log(globalVar);  // ✓ "I'm everywhere"
  }

  inner();
}

// Hoisting — declarations moved to top before execution
console.log(x); // undefined (not ReferenceError!) — var hoisted
var x = 5;

console.log(y); // ReferenceError — let is NOT initialized
let y = 5;
The temporal dead zone (TDZ) let and const are hoisted but not initialized. The period between the start of their scope and their declaration is called the TDZ. Accessing them there throws a ReferenceError. Interviewers love asking about this. 
// Closure — a function that remembers its outer scope
function makeCounter() {
  let count = 0;  // lives in makeCounter's scope
  return () => {
    count++;
    return count;
  };
}

const counter = makeCounter();
console.log(counter()); // 1
console.log(counter()); // 2
console.log(counter()); // 3 — count persists!
Real-world use Closures power React hooks. useState is essentially a closure — the state value persists between renders because the hook "closes over" its own internal storage. Understanding closures makes hooks intuitive rather than magical.

Ex 05 Scope — spot the bug Medium

Read the code, predict the output, then run it to verify. Then fix the bug.

Predict what logs for each console.log. Then fix the code so all three log the correct loop index (0, 1, 2).
// Bug: var i is shared across all iterations
// Prints: 3, 3, 3 (loop finishes before callbacks run)

// Fix: use let — creates new binding each iteration
for (let i = 0; i < 3; i++) {
  setTimeout(() => console.log("let:", i), 0);
}
// Prints: 0, 1, 2 ✓
Ex 06 Closure counter Medium

Build a closure that maintains private state — a classic interview exercise.

Write makeCounter(start = 0) that returns an object with three methods: increment(), decrement(), and reset(). The count should never be directly accessible from outside.
function makeCounter(start = 0) {
  let count = start;
  return {
    increment: () => ++count,
    decrement: () => --count,
    reset: () => { count = start; return count; }
  };
}
Ex 07 Truthy/falsy filter Medium

A practical exercise that shows up in real data cleaning code.

Write compact(arr) — removes all falsy values from an array. Do it in one line using .filter(). Then write compactDeep(arr) that also removes empty strings and zero.
const compact = arr => arr.filter(Boolean);
// Boolean is a function — filter passes each item to it
// Boolean(value) returns true/false based on truthiness

const compactDeep = arr =>
  arr.filter(v => v !== "" && v !== 0 && Boolean(v));
Ex 08 Mini calculator — bringing it all together Challenge

This exercise combines all of today's concepts in one realistic function.

Build calculate(a, operator, b) that handles +, -, *, /, and %. Guard against division by zero. Return a descriptive error string for invalid inputs.
const calculate = (a, operator, b) => {
  if (typeof a !== "number" || typeof b !== "number")
    return "Error: inputs must be numbers";
  if (b === 0 && (operator === "/" || operator === "%"))
    return "Error: division by zero";
  const ops = {
    "+": (a, b) => a + b,
    "-": (a, b) => a - b,
    "*": (a, b) => a * b,
    "/": (a, b) => a / b,
    "%": (a, b) => a % b,
  };
  if (!ops[operator])
    return `Error: unknown operator ${operator}`;
  return ops[operator](a, b);
};
Interview Q&A

10 questions aligned with real junior JavaScript interviews in 2025–26. Click to expand each answer. Study the answer structure — not just the content.

Q1 What is the difference between var, let, and const? Very common ›

var is function-scoped, hoisted and initialized to undefined, and can be redeclared. let and const are block-scoped, hoisted but not initialized (entering the temporal dead zone), and cannot be redeclared in the same scope.

The key difference between let and const is that const prevents reassignment of the variable binding — but it does not make objects or arrays immutable. You can still do const arr = []; arr.push(1).

In modern JavaScript, the rule is simple: use const by default, let only when you need to reassign, and never use var.

const arr = [];
arr.push(1);  // ✓ allowed — mutating, not reassigning
arr = [];    // ✗ TypeError — reassigning the binding
Q2 What is hoisting in JavaScript? Common ›

Hoisting is JavaScript's behaviour of moving declarations to the top of their scope during the compilation phase, before code executes. Function declarations are fully hoisted — both the declaration and definition. var declarations are hoisted and initialized to undefined. let and const are hoisted but not initialized, creating the temporal dead zone.

sayHi();          // "Hi!" — function declaration is fully hoisted
console.log(x);   // undefined — var hoisted, not yet assigned
console.log(y);   // ReferenceError — let in TDZ

function sayHi() { return "Hi!"; }
var x = 10;
let y = 20;
Q3 What is a closure? Give a practical example. Very common ›

A closure is a function that retains access to its outer scope's variables even after that outer function has finished executing. In JavaScript, every function creates a closure over the scope in which it was defined.

A practical use is data privacy — you can create private variables that can only be accessed through controlled methods:

function bankAccount(initialBalance) {
  let balance = initialBalance; // private
  return {
    deposit: amount => { balance += amount; },
    withdraw: amount => { balance -= amount; },
    getBalance: () => balance,
  };
}
const acc = bankAccount(100);
acc.deposit(50);
console.log(acc.getBalance()); // 150
// acc.balance is undefined — it's private

Closures also power React hooks. useState relies on closures to persist state values between renders.

Q4 What is the difference between == and ===? Very common ›

== is loose equality — it performs type coercion before comparing. === is strict equality — it checks both value and type with no coercion. In professional code, always use ===.

console.log(1 == "1");    // true  — "1" coerced to 1
console.log(1 === "1");   // false — different types
console.log(null == undefined);  // true
console.log(null === undefined); // false

The only legitimate use of == today is the null == undefined check — when you want to catch both without caring which one it is.

Q5 What are truthy and falsy values? Name all the falsy values in JavaScript. Common ›

There are exactly 6 falsy values in JavaScript: false, 0, "" (empty string), null, undefined, and NaN. Everything else is truthy — including "0", empty arrays [], and empty objects {}.

// Truthy surprises (common interview traps)
Boolean("0")    // true — non-empty string
Boolean([])     // true — empty array
Boolean({})     // true — empty object
Boolean(" ")    // true — space is a character

This matters in real code: if (user.name) will only run if the name is a non-empty string — silently ignoring name = 0 or name = false. For stricter checks, use user.name !== undefined && user.name !== null or optional chaining.

Q6 What is the difference between a function declaration and a function expression? Common ›

A function declaration uses the function keyword as a statement and is fully hoisted — you can call it before its definition in the file. A function expression assigns a function to a variable and is not hoisted — calling it before the line throws an error.

// Declaration — hoisted
hello();  // ✓ works
function hello() { return "hi"; }

// Expression — NOT hoisted
world();  // TypeError: world is not a function
const world = () => "hi";

In modern JavaScript and React codebases, function expressions (especially arrow functions) are preferred because they make hoisting behaviour explicit and consistent.

Q7 What is the temporal dead zone (TDZ)? Intermediate ›

The temporal dead zone is the period between the start of a block scope and the point where a let or const variable is declared. During this period, the variable exists in scope (it has been hoisted) but is not yet initialized — accessing it throws a ReferenceError.

function example() {
  // TDZ for 'name' starts here
  console.log(name); // ReferenceError — in TDZ
  const name = "Alice"; // TDZ ends here
  console.log(name); // "Alice" — now accessible
}

The TDZ exists to catch programming errors — specifically using a variable before it's been assigned a value. It's one of the reasons let/const are safer than var.

Q8 Explain pass-by-value vs pass-by-reference in JavaScript. Common ›

Primitive values (numbers, strings, booleans, null, undefined, symbol) are passed by value — a copy is made, and the original is unaffected. Objects (including arrays and functions) are passed by reference — both variables point to the same object in memory, so changes affect both.

// Primitive — pass by value
let x = 10;
function change(n) { n = 99; }
change(x);
console.log(x); // 10 — unchanged

// Object — pass by reference
const user = { name: "Alice" };
function rename(obj) { obj.name = "Bob"; }
rename(user);
console.log(user.name); // "Bob" — original mutated!

This is why in React, you never mutate state directly. Mutating an object doesn't create a new reference, so React's shallow equality check doesn't detect the change and won't re-render.

Q9 What does typeof null === "object" mean? Is it a bug? Trivia / culture ›

Yes, it is a bug — one of the most famous in JavaScript history. In the original JavaScript implementation (1995), values were stored with a type tag. The tag for objects was 000. null was represented as the null pointer, which is also all zeros — so it was incorrectly classified as an object.

A proposal to fix it (making typeof null === "null") was rejected because it would break millions of existing websites. So we're stuck with it. The correct way to check for null is strict equality:

const val = null;

// Wrong — typeof null is "object"
if (typeof val === "object") { /* triggered by null! */ }

// Correct
if (val === null) { /* safe */ }

// Or check for non-null objects
if (val !== null && typeof val === "object") { /* true object */ }
Q10 What is the difference between null and undefined? Common ›

undefined means a variable has been declared but not yet assigned a value — it's JavaScript's way of saying "this hasn't been given a value yet." null is an intentional absence of value — a developer explicitly assigns it to mean "this is deliberately empty."

let x;            // undefined — never assigned
let y = null;     // null — intentionally empty

// Function that hasn't returned anything
const doNothing = () => {};
console.log(doNothing()); // undefined

// API response — user not loaded yet vs user doesn't exist
let user = undefined; // loading...
user = null;           // confirmed: no user found

In practice: prefer null over undefined when you want to explicitly represent "no value" — it communicates intent. Let JavaScript assign undefined naturally rather than assigning it yourself.
