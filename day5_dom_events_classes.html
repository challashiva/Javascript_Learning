Part 1 — The DOM
01 The DOM — Document Object Model foundation
what it is
The DOM is a live tree of objects
When the browser parses HTML, it builds the Document Object Model — a tree of JavaScript objects representing every element, attribute, and piece of text. Changing these objects immediately updates what the user sees. React, Vue, and Angular all manipulate the DOM — either directly or via a virtual copy.
node types
Node types in the tree
Element nodes — <div>, <p>, <button> — the ones you interact with most. Text nodes — the text content inside elements. Document node — the root (document). Attribute nodes — element attributes like id, class, href. nodeType === 1 means element, 3 means text.
React link
Why this matters for React
React uses a Virtual DOM — a lightweight copy of the real DOM in memory. When state changes, React diffs the new virtual DOM against the old one, and makes only the minimal real DOM updates needed. Understanding the real DOM tells you what React is optimising and why direct mutation is dangerous.
javascriptDOM navigation and node properties

03 Events — listening, the event object & bubbling core interaction
Event propagation — bubbling & capturing
1. Capture phase
Event travels down from document → target. Rarely used. Opt-in with {capture: true}.
2. Target phase
Event reaches the element that was clicked/interacted with. Handlers on the target fire here.
3. Bubble phase
Event bubbles up from target → document. Most events bubble. This is what event delegation exploits.
stopPropagation
e.stopPropagation() prevents further bubbling. Use sparingly — it can break event delegation.
javascriptaddEventListener, event object, common patterns
// addEventListener(type, handler, options)
const btn = document.querySelector("#submit")

// Basic
btn.addEventListener("click", (event) => {
  console.log(event.type)           // "click"
  console.log(event.target)         // element that was clicked
  console.log(event.currentTarget)  // element the listener is on
  console.log(event.timeStamp)      // ms since page load
})

// once — handler fires only once, then auto-removes
btn.addEventListener("click", handleClick, { once: true })

// Removing a listener — must pass the same function reference!
function handleClick(e) { console.log("clicked") }
btn.addEventListener("click", handleClick)
btn.removeEventListener("click", handleClick)  // same reference = works
// btn.removeEventListener("click", () => {}) // different reference — DOES NOT WORK

04 Event delegation — one listener to rule them all performance pattern
what it is
Why delegation exists
Instead of attaching a listener to every single child element, attach one listener to a parent and use event.target to determine which child was interacted with. Because events bubble up, the parent receives all events from its descendants. This is dramatically more efficient for large lists and dynamic content.
key benefit
Works for dynamic elements
If you add new list items after the page loads, a listener on each item would miss the new ones. A delegated listener on the parent automatically handles future elements because they bubble up to the same parent. This is exactly how React's synthetic event system works internally.
javascriptEvent delegation — the pattern and its practical uses
// ── Without delegation (bad for lists) ────────────────────
document.querySelectorAll(".todo-item button").forEach(btn => {
  btn.addEventListener("click", deleteItem)  // n listeners for n items
})
// New items added later? Won't have listeners!

// ── With delegation (correct pattern) ─────────────────────
const list = document.querySelector("#todo-list")

list.addEventListener("click", (e) => {
  // e.target = exact element clicked (might be inside a button)
  // e.currentTarget = #todo-list (always the listener's element)

  // closest() — walks up the tree to find the matching ancestor
  const deleteBtn = e.target.closest("[data-action='delete']")
  const editBtn   = e.target.closest("[data-action='edit']")
  const item      = e.target.closest(".todo-item")

  if (deleteBtn && item) {
    const id = item.dataset.id
    removeItem(id)
    item.remove()
  }

  if (editBtn && item) {
    startEditing(item)
  }
})

// ── Data attributes for action routing ────────────────────
// <ul id="todo-list">
//   <li class="todo-item" data-id="1">
//     Buy milk
//     <button data-action="edit">Edit</button>
//     <button data-action="delete">Delete</button>
//   </li>
// </ul>

// ── closest() vs matches() ─────────────────────────────────
// closest(selector) — walks UP tree, returns first matching ancestor (or self)
// matches(selector)  — returns true if the element itself matches
e.target.closest(".card")      // find nearest .card ancestor
e.target.matches("button.del") // true if target IS a delete button
Part 2 — ES6 Classes
05 ES6 Classes — syntax, constructor & methods OOP in JS
what classes are
Syntactic sugar over prototypes
ES6 classes are not a new object model — they're clean syntax over JavaScript's existing prototype-based inheritance. Under the hood, class creates a constructor function and assigns methods to its prototype. They make OOP patterns more readable, especially for people coming from other languages.
key difference
Class vs function constructor
Classes are NOT hoisted like function declarations. They're in the TDZ just like let. Classes also always run in strict mode automatically. Methods defined in a class are non-enumerable (won't show up in for...in). Always use new to instantiate — calling without new throws.
React link
Where classes appear in React
Modern React uses function components and hooks almost exclusively. But class components still exist in many codebases, and understanding classes is essential for reading them. Error boundaries in React still require class components. Understanding prototype chains also explains how React hooks work under the hood.
javascriptClass syntax — constructor, instance methods, getters/setters, static, private fields
class BankAccount {
  // Private fields (ES2022) — only accessible inside the class
  #balance
  #transactions = []

  // Static field — belongs to the class, not instances
  static interestRate = 0.03
  static instanceCount = 0

  // Constructor — called when using new BankAccount()
  constructor(owner, initialBalance = 0) {
    this.owner    = owner
    this.#balance = initialBalance
    BankAccount.instanceCount++
  }

  // Instance method — available on every instance via prototype
  deposit(amount) {
    if (amount <= 0) throw new Error("Amount must be positive")
    this.#balance += amount
    this.#transactions.push({ type: "deposit", amount, date: new Date() })
    return this   // enables chaining: acct.deposit(100).deposit(50)
  }

  withdraw(amount) {
    if (amount > this.#balance) throw new Error("Insufficient funds")
    this.#balance -= amount
    this.#transactions.push({ type: "withdrawal", amount, date: new Date() })
    return this
  }

  // Getter — access like a property: acct.balance (no parentheses)
  get balance() { return this.#balance }

  // Getter for computed value
  get summary() {
    return `${this.owner}: $${this.#balance.toFixed(2)}`
  }

  // Static method — called on the class, not an instance
  static fromJSON(json) {
    const { owner, balance } = JSON.parse(json)
    return new BankAccount(owner, balance)
  }

  // toString — called automatically in string contexts
  toString() { return this.summary }
}

// Usage
const acct = new BankAccount("Alice", 1000)
acct.deposit(500).deposit(250).withdraw(100)
console.log(acct.balance)   // 1650 (getter, no ())
// acct.#balance              // SyntaxError — private field!
console.log(BankAccount.interestRate)  // 0.03 (static)
const acct2 = BankAccount.fromJSON('{"owner":"Bob","balance":500}')
06 Inheritance — extends, super & the prototype chain advanced
javascriptextends, super, overriding, instanceof, prototype chain
class Animal {
  constructor(name, sound) {
    this.name  = name
    this.sound = sound
    this.alive = true
  }

  speak() {
    return `${this.name} says ${this.sound}!`
  }

  toString() { return `Animal: ${this.name}` }
}

class Dog extends Animal {
  constructor(name, breed) {
    super(name, "Woof")   // MUST call super() before using 'this' in subclass
    this.breed = breed
    this.tricks = []
  }

  // Override parent method
  speak() {
    return `${super.speak()} (tail wagging)`  // call parent's speak() via super
  }

  // New method in subclass
  learn(trick) {
    this.tricks.push(trick)
    return this
  }

  get profile() {
    return `${this.name} (${this.breed}) knows: ${this.tricks.join(", ")}`
  }
}

class GuideDog extends Dog {
  constructor(name, breed, owner) {
    super(name, breed)    // calls Dog's constructor
    this.owner = owner
  }
}

// Usage
const rex = new Dog("Rex", "German Shepherd")
rex.learn("sit").learn("stay").learn("fetch")
console.log(rex.speak())   // "Rex says Woof! (tail wagging)"
console.log(rex.profile)   // "Rex (German Shepherd) knows: sit, stay, fetch"

// instanceof — checks prototype chain
rex instanceof Dog     // true
rex instanceof Animal  // true — Dog extends Animal
rex instanceof GuideDog // false

// Prototype chain: rex → Dog.prototype → Animal.prototype → Object.prototype → null
Object.getPrototypeOf(rex) === Dog.prototype   // true

// Mixin pattern — add capabilities without inheritance
const Serialisable = (Base) => class extends Base {
  toJSON() { return JSON.stringify(this) }
  static fromJSON(str) { return Object.assign(new this(), JSON.parse(str)) }
}

class SerializableDog extends Serialisable(Dog) {}
const dog2 = new SerializableDog("Buddy", "Poodle")
console.log(dog2.toJSON())

on(event, handler) {
  if (!this.#listeners.has(event)) this.#listeners.set(event, [])
  this.#listeners.get(event).push(handler)
  return this
}

off(event, handler) {
  if (!handler) { this.#listeners.delete(event); return this }
  const list = this.#listeners.get(event) || []
  this.#listeners.set(event, list.filter(h => h !== handler))
  return this
}

emit(event, ...args) {
  (this.#listeners.get(event) || []).forEach(h => h(...args))
  return this
}

once(event, handler) {
  const wrapper = (...args) => {
    handler(...args)
    this.off(event, wrapper)   // closure over wrapper
  }
  return this.on(event, wrapper)
}

append(value) {
  const node = new Node(value)
  if (!this.#head) { this.#head = node; this.#size++; return this }
  let cur = this.#head
  while (cur.next) cur = cur.next
  cur.next = node; this.#size++; return this
}
prepend(value) {
  const node = new Node(value)
  node.next = this.#head; this.#head = node; this.#size++; return this
}
delete(value) {
  if (!this.#head) return this
  if (this.#head.value === value) { this.#head = this.#head.next; this.#size--; return this }
  let cur = this.#head
  while (cur.next && cur.next.value !== value) cur = cur.next
  if (cur.next) { cur.next = cur.next.next; this.#size-- }
  return this
}
find(value) {
  let cur = this.#head
  while (cur) { if (cur.value === value) return cur; cur = cur.next }
  return null
}
toArray() {
  const result = []; let cur = this.#head
  while (cur) { result.push(cur.value); cur = cur.next }
  return result
}
08 Interview questions + model answers 10 Q&As
Q1What is the DOM? How is it different from HTML?▶
model answer
HTML is a text format — it's the file the browser downloads. The DOM is the live, in-memory tree of JavaScript objects the browser builds from parsing that HTML. Changing the DOM immediately updates what the user sees without downloading anything new.

Key differences: the DOM reflects the current state (modified by JS), while HTML is static source. The DOM is language-agnostic (accessible from JS, Python via Selenium, etc.). The DOM can contain nodes that have no HTML equivalent (Text nodes, Comment nodes). The DOM also models malformed HTML — browsers repair invalid markup when building the tree.
React angle: "React's Virtual DOM is a lightweight JS object tree that mirrors the real DOM. React reconciles changes between virtual DOM snapshots rather than querying the real DOM repeatedly — which is expensive because real DOM operations trigger browser layout recalculation."
Q2What is event bubbling? How does event delegation use it?▶
model answer
When an event fires on an element, it first runs that element's handlers, then bubbles up through each ancestor to the document root — each ancestor's handlers also fire. This is event bubbling.

Event delegation exploits bubbling by placing one listener on a parent element instead of individual listeners on each child. The handler uses event.target to identify which child was actually interacted with, and closest() to walk up and match the relevant element.

Benefits: fewer listeners (better memory), works for dynamically added elements, simpler cleanup. React uses this internally — it attaches a single listener to the root element and routes all events from there.
Q3What is the difference between event.target and event.currentTarget?▶
model answer
event.target is the element that was actually clicked — the deepest element that triggered the event. It changes as the event bubbles up.

event.currentTarget is the element the event listener is currently attached to. It stays constant throughout the handler.

In event delegation: if you click a <span> inside a <button> inside a <ul> with the listener, event.target is the span, while event.currentTarget is the ul. This is why closest() is needed — to walk from the actual target up to the meaningful element you care about.
Common follow-up: what does e.stopPropagation() do? It prevents the event from bubbling further. But it can break event delegation if called on inner elements — their events won't reach the delegated parent listener.
Q4What is the difference between textContent, innerHTML, and innerText?▶
model answer
textContent: returns all text content of the element and its descendants, including hidden elements. Setting it escapes HTML — any <> characters become literal text. Safe from XSS. Preferred for setting text.

innerHTML: returns or sets the HTML markup inside the element. Setting it parses HTML. Never use with user-provided content — it's an XSS vector. Useful for injecting trusted HTML templates.

innerText: like textContent but layout-aware — it only returns visible text and respects CSS (hides text in display:none elements). Triggers reflow, making it slower than textContent.

Rule of thumb: use textContent for text, createElement + append for structure, avoid innerHTML with user data.
Q5Are JavaScript classes really classes? What are they under the hood?▶
model answer
ES6 classes are syntactic sugar over prototype-based inheritance — not a new object system. Under the hood, class Foo {} creates a constructor function named Foo, and methods defined in the class body are attached to Foo.prototype.

When you do new Foo(), JS creates a new object, sets its prototype to Foo.prototype, and calls the constructor with this bound to the new object.

Differences from traditional OOP: there is no runtime type system, no true private (until ES2022 # fields), and "inheritance" is prototype delegation, not copying. class B extends A sets B.prototype.__proto__ = A.prototype, which means method lookups walk the chain rather than copying methods.
Q6What does super do in a class? What happens if you forget it in a subclass constructor?▶
model answer
super() in a constructor calls the parent class's constructor. It must be called before accessing this in a derived class. The reason is that the parent constructor initialises the object — without calling it first, the object isn't properly set up and this is in an uninitialised state.

If you forget super() in a subclass constructor, you get a ReferenceError: Must call super constructor in derived class before accessing 'this'.

super.method() calls the parent class's version of a method — useful when overriding a method but still wanting the parent's behaviour plus extra logic.
If a subclass has no constructor, it's implicitly added: constructor(...args) { super(...args) }. So not writing a constructor at all is fine — only if you write one must you call super().
Q7What are static methods and properties? When would you use them?▶
model answer
Static members belong to the class itself, not to instances. They're accessed via ClassName.method(), not instance.method().

Use static methods for: factory methods (User.fromJSON(json)), utility functions that relate to the class but don't need instance data, validation helpers (Email.isValid(str)), and comparison functions.

Use static properties for: configuration constants shared by all instances, counters tracking how many instances were created, caches shared across instances.

Static methods are NOT inherited by instances — new User().fromJSON() would throw because fromJSON doesn't exist on the instance prototype.
Q8How do you remove an event listener? What common mistake prevents it from working?▶
model answer
Use element.removeEventListener(type, handler) — passing the exact same function reference that was used in addEventListener.

The most common mistake is using an anonymous function or arrow function — each time you write () => {}, a new function object is created, so the reference passed to removeEventListener doesn't match the one registered.

Solutions: store the handler in a variable, use a named function declaration (which is always the same reference), or use the { once: true } option to auto-remove after one call. In React, cleanup is handled by returning a function from useEffect.
React analogy: this is exactly why the dependency array in useEffect matters — if you create a new function reference on each render and don't stabilise it with useCallback, cleanup and re-subscription happen unnecessarily.
Q9What is the prototype chain? How does method lookup work?▶
model answer
Every JavaScript object has an internal [[Prototype]] link pointing to another object (or null). When you access a property, JS looks on the object itself first, then walks up the prototype chain until it finds it or reaches null.

For class instances: instance → ClassName.prototype → ParentClass.prototype → Object.prototype → null. Methods defined in a class live on ClassName.prototype, not on each instance — this is why all instances share the same method functions (memory efficient).

Practical implication: when you call rex.speak() on a Dog instance, JS looks for speak on rex (not found), then on Dog.prototype (found — stops here). If Dog extended Animal and didn't override speak, it would continue up to Animal.prototype.
Q10What is the difference between querySelector and getElementById? Which is faster?▶
model answer
getElementById is faster because it uses an internal hash map lookup by ID — O(1). querySelector uses a CSS selector engine which may need to traverse the tree — O(n) in the worst case.

However, the performance difference is negligible in practice for typical page sizes. The more important differences are: querySelector accepts any CSS selector (class, attribute, pseudo-class, descendant combinations), making it far more flexible. getElementById only finds by ID.

querySelectorAll returns a static NodeList (snapshot). getElementsByClassName and getElementsByTagName return live HTMLCollections that update automatically — which can cause infinite loops if you mutate the DOM while iterating them. Prefer querySelectorAll for predictability.
