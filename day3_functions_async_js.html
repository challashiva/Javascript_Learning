Part 1 — Functions deep dive
01 Scope — where variables live and die foundation
global scope
Global scope
Variables declared outside any function or block. Accessible everywhere in your code. In browsers this is window; in Node.js it's global. Avoid polluting global scope — it creates naming conflicts and makes code hard to reason about. Every var at the top level becomes a property of window.
function scope
Function scope
Variables declared inside a function are only accessible within that function and its nested functions. Each function call creates a fresh scope. This is how you create privacy — variables declared inside can't be accessed from outside. var is function-scoped.
block scope
Block scope
Variables declared with let or const inside any {} block — if, for, while, or a plain block — are only accessible within that block. This is the behaviour you almost always want. Block scope was the main reason ES6 introduced let and const.
lexical scope
Lexical scope & scope chain
JS uses lexical scoping — a function's scope is determined by where it is written in the source code, not where it is called. When a variable is not found in the current scope, JS looks in the outer scope, then the next outer, all the way to global. This lookup chain is the scope chain.
javascriptScope chain, variable shadowing, and the loop trap
// Global scope
const appName = "MyApp"  // accessible everywhere

function outer() {
  const x = 10          // function scope of outer()

  function inner() {
    const y = 20        // function scope of inner()
    console.log(x)      // 10 — found in outer scope via scope chain
    console.log(appName)// "MyApp" — found in global scope
  }

  inner()
  // console.log(y)     // ReferenceError — y not in outer's scope
}

// Variable shadowing — inner scope can reuse names
const color = "blue"
function paint() {
  const color = "red"   // shadows outer 'color' — doesn't overwrite it
  console.log(color)   // "red"
}
console.log(color)     // "blue" — outer is unchanged

// The classic loop closure trap with var
for (var i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 100)
}
// Prints: 3, 3, 3  — var leaks out of the loop, all callbacks share i=3

// Fix 1: use let — block-scoped, each iteration gets its own i
for (let i = 0; i < 3; i++) {
  setTimeout(() => console.log(i), 100)
}
// Prints: 0, 1, 2  — each callback closes over its own block-scoped i

// Block scope example — let stays inside {}
{
  let secret = "hidden"
  console.log(secret)  // "hidden"
}
// console.log(secret)  // ReferenceError
02 Hoisting — what moves, what doesn't interview favourite
Hoisting cheatsheet — all 4 cases
var declaration
Hoisted and initialised to undefined. Accessing before declaration gives undefined, not an error.
let / const
Hoisted but NOT initialised. Accessing before declaration throws ReferenceError. This gap is the Temporal Dead Zone (TDZ).
function declaration
Fully hoisted — both name AND body. You can call it before it appears in the file. The entire function moves to the top.
function expression / arrow
The variable is hoisted (TDZ for let/const, undefined for var), but the function body is NOT. Calling it before declaration throws an error.
javascriptHoisting behaviour — all 4 cases demonstrated
// ── Function declaration — fully hoisted ──────────────────
sayHello()                   // "Hello!" — works before declaration
function sayHello() { console.log("Hello!") }

// ── var declaration — hoisted as undefined ────────────────
console.log(score)           // undefined (not an error — hoisted)
var score = 42
console.log(score)           // 42

// What the engine sees after hoisting:
// var score = undefined    ← declaration moved up
// console.log(score)       ← undefined
// score = 42               ← assignment stays in place
// console.log(score)       ← 42

// ── let/const — Temporal Dead Zone ───────────────────────
// console.log(name)        // ReferenceError: Cannot access before init
const name = "Alice"
console.log(name)           // "Alice"

// ── Function expression — variable hoisted, body is NOT ──
// greet()                  // TypeError: greet is not a function
var greet = function() { return "Hi" }

// ── Arrow function — same as expression ──────────────────
// add(1,2)                 // ReferenceError (const) or TypeError (var)

03 Closures — the most powerful concept in JS critical
definition
What is a closure?
A closure is a function that retains access to its outer (enclosing) scope's variables even after the outer function has returned. The inner function "closes over" those variables — they are kept alive in memory as long as the inner function exists. Every function in JS is technically a closure.
why it matters
Where closures appear in practice
React hooks — every useEffect, event handler, and state updater is a closure over state and props. Data privacy — module pattern keeps data private. Memoisation — cache previous results. Debounce/throttle — hold a timer reference. Partial application & currying — pre-fill function arguments.
gotcha
Stale closures — the React bug
A closure can capture an outdated value if the variable it closed over changed since the closure was created. In React this causes "stale state" bugs where an event handler reads an old value. The fix is using the functional update form: setState(prev => prev + 1) instead of setState(count + 1).
javascriptClosures — 6 real patterns used in production
// ── Pattern 1: Data privacy (module pattern) ──────────────
function createBankAccount(initialBalance) {
  let balance = initialBalance    // private — not accessible from outside

  return {
    deposit:  (amt) => { balance += amt; return balance },
    withdraw: (amt) => {
      if (amt > balance) return "Insufficient funds"
      balance -= amt; return balance
    },
    getBalance: () => balance
  }
}
const acct = createBankAccount(1000)
acct.deposit(500)    // 1500
acct.withdraw(200)   // 1300
// acct.balance       // undefined — balance is private!

// ── Pattern 2: Memoisation — cache expensive results ──────
function memoize(fn) {
  const cache = {}                  // private to memoize, lives as long as memo does
  return (...args) => {
    const key = JSON.stringify(args)
    if (cache[key] !== undefined) return cache[key]
    cache[key] = fn(...args)
    return cache[key]
  }
}
const slowDouble = (n) => { /* imagine expensive work */ return n * 2 }
const fastDouble = memoize(slowDouble)
fastDouble(21)   // computed
fastDouble(21)   // returned from cache instantly

// ── Pattern 3: Partial application — pre-fill arguments ───
function multiply(a, b) { return a * b }
function partial(fn, ...presetArgs) {
  return (...laterArgs) => fn(...presetArgs, ...laterArgs)
}
const double  = partial(multiply, 2)
const triple  = partial(multiply, 3)
double(5)   // 10
triple(5)   // 15

// ── Pattern 4: Debounce — delay until user stops typing ───
function debounce(fn, delay) {
  let timer                         // closed over by the returned function
  return (...args) => {
    clearTimeout(timer)
    timer = setTimeout(() => fn(...args), delay)
  }
}
const search         = (query) => console.log("Searching:", query)
const debouncedSearch = debounce(search, 300)
// Only fires 300ms after the last call — used in every search input

// ── Pattern 5: Once — run a function only once ────────────
function once(fn) {
  let called = false, result
  return (...args) => {
    if (called) return result
    called = true
    result = fn(...args)
    return result
  }
}
const initApp = once(() => console.log("App initialised"))
initApp()  // "App initialised"
initApp()  // nothing — already called

Part 2 — Async JavaScript
05 The event loop — JS's secret to async mental model
call stack
Call stack
A LIFO stack that tracks which function is currently running. When you call a function it gets pushed. When it returns it gets popped. JS is single-threaded — only one thing runs at a time. If the stack is busy, nothing else can run — this is why long operations block the UI.
web APIs
Web APIs (browser / Node)
Async tasks like setTimeout, fetch, DOM events are handled outside the JS engine by the browser's Web APIs (or Node's libuv). JS hands off the task and continues. When the task completes, its callback is placed in a queue — not executed immediately.
event loop
Event loop & task queues
The event loop constantly checks: is the call stack empty? If yes, it picks the next task from the queue and pushes it onto the stack. Microtasks (Promises) have a higher-priority queue — they always run before the next macro task (setTimeout, setInterval).
Event loop execution order — know this for interviews
1st — synchronous code
All sync code runs first, top to bottom. The call stack must be empty before anything async runs.
2nd — microtask queue
Promise callbacks (.then, catch, finally) and queueMicrotask. Drains completely before macrotasks.
3rd — macrotask queue
setTimeout, setInterval, I/O callbacks. One runs per event loop tick.
rule of thumb
Promises always resolve before setTimeout(fn, 0) even though both are "async".
javascriptPredict the output — classic event loop interview question
console.log("1 — sync")

setTimeout(() => console.log("2 — setTimeout"), 0)

new Promise((resolve) => {
  console.log("3 — inside Promise constructor (sync!)")
  resolve()
}).then(() => console.log("4 — .then (microtask)"))

console.log("5 — sync")

06 Promises — states, chaining & combinators core async
Promise states — a Promise is always in one of these three states
pending
Initial state. The async operation has not completed yet.
fulfilled
Operation succeeded. resolve(value) was called. .then() handlers run.
rejected
Operation failed. reject(error) was called. .catch() handlers run.
settled
Fulfilled OR rejected. A settled Promise never changes state again.
javascriptCreating promises, chaining, error handling, combinators
// ── Creating a Promise ────────────────────────────────────
const wait = (ms) => new Promise(resolve => setTimeout(resolve, ms))

const fetchUser = (id) => new Promise((resolve, reject) => {
  if (!id) reject(new Error("ID required"))
  setTimeout(() => resolve({ id, name: "Alice" }), 100)
})

// ── Chaining — .then() returns a NEW promise ──────────────
fetchUser(1)
  .then(user => {
    console.log(user.name)       // "Alice"
    return user.id * 10          // pass a value to next .then
  })
  .then(value => console.log(value)) // 10
  .catch(err => console.error(err))  // catches any error in the chain
  .finally(() => console.log("done")) // always runs — good for cleanup

// ── Promise combinators ───────────────────────────────────
const p1 = fetchUser(1)
const p2 = fetchUser(2)
const p3 = fetchUser(3)

// Promise.all — run in parallel, wait for ALL, fail fast on any rejection
Promise.all([p1, p2, p3])
  .then(([u1, u2, u3]) => console.log(u1, u2, u3))
  .catch(err => console.error("One failed:", err))

// Promise.allSettled — run all, collect ALL results (won't fail fast)
Promise.allSettled([p1, p2, p3])
  .then(results => {
    results.forEach((r) => {
      if (r.status === "fulfilled") console.log("ok:",    r.value)
      else                             console.log("error:", r.reason)
    })
  })

// Promise.race — resolves/rejects with the FIRST settled promise
const timeout = (ms) => new Promise((_, reject) =>
  setTimeout(() => reject(new Error("Timeout")), ms)
)
// Request with 5s timeout:
Promise.race([fetchUser(1), timeout(5000)])

// Promise.any — resolves with FIRST fulfilled (ignores rejections)
Promise.any([p1, p2, p3])  // resolves with first to succeed

javascriptComplete fetch patterns — GET, POST, error handling, abort
// ── Basic GET request ─────────────────────────────────────
async function getUsers() {
  const response = await fetch("https://jsonplaceholder.typicode.com/users")

  // fetch only rejects on network error — NOT on 404, 500 etc!
  // You MUST check response.ok manually
  if (!response.ok) {
    throw new Error(`HTTP ${response.status}: ${response.statusText}`)
  }

  const data = await response.json()   // parse JSON body (also a Promise!)
  return data
}

// ── POST request ──────────────────────────────────────────
async function createPost(postData) {
  const response = await fetch("https://jsonplaceholder.typicode.com/posts", {
    method:  "POST",
    headers: { "Content-Type": "application/json" },
    body:    JSON.stringify(postData)
  })
  if (!response.ok) throw new Error("Failed to create post")
  return response.json()
}

// ── Reusable fetch wrapper (what teams use in real apps) ──
async function apiFetch(endpoint, options = {}) {
  const baseURL  = "https://api.example.com"
  const token    = localStorage.getItem("token")

  const response = await fetch(`${baseURL}${endpoint}`, {
    ...options,
    headers: {
      "Content-Type":  "application/json",
      "Authorization": `Bearer ${token}`,
      ...options.headers
    }
  })

  if (response.status === 401) { redirectToLogin(); return }
  if (!response.ok) throw new Error(await response.text())

  return response.json()
}

// ── AbortController — cancel in-flight requests ───────────
async function fetchWithTimeout(url, timeoutMs = 5000) {
  const controller = new AbortController()
  const timer      = setTimeout(() => controller.abort(), timeoutMs)

  try {
    const res = await fetch(url, { signal: controller.signal })
    clearTimeout(timer)
    return res.json()
  } catch (err) {
    if (err.name === "AbortError") throw new Error("Request timed out")
    throw err
  }
}

function debounce(fn, delay, immediate = false) {
  let timer = null

  return (...args) => {
    const callNow = immediate && !timer

    clearTimeout(timer)
    timer = setTimeout(() => {
      timer = null
      if (!immediate) fn(...args)
    }, delay)

    if (callNow) fn(...args)
  }
}

4
Implement Promise.all from scratch
intermediate
Implement myPromiseAll(promises) that behaves exactly like Promise.all: resolves with an array of all results when every promise resolves, and rejects immediately with the first error if any promise rejects.
Create a new Promise. Keep a results array and a counter. When the counter equals promises.length, resolve with results. If any promise rejects, immediately reject the outer promise.
Exercise 4 — runnable
output
Click ▶ Run
function myPromiseAll(promises) {
  return new Promise((resolve, reject) => {
    if (promises.length === 0) return resolve([])

    const results  = new Array(promises.length)
    let   resolved = 0

    promises.forEach((p, i) => {
      Promise.resolve(p)  // handle non-promise values
        .then(val => {
          results[i] = val
          if (++resolved === promises.length) resolve(results)
        })
        .catch(reject)    // first rejection rejects outer
    })
  })
}

async function retry(fn, maxAttempts = 3, baseDelayMs = 100) {
  let lastError

  for (let attempt = 0; attempt < maxAttempts; attempt++) {
    try {
      return await fn()   // success — return immediately
    } catch (err) {
      lastError = err
      if (attempt < maxAttempts - 1) {
        const delay = baseDelayMs * Math.pow(2, attempt)
        console.log(`Retrying in ${delay}ms...`)
        await sleep(delay)
      }
    }
  }

  throw lastError   // all attempts exhausted
}

Q1What is a closure? Can you give a real-world example from React or a production codebase?▶
model answer
A closure is a function that retains access to its outer scope's variables even after the outer function has finished executing. Every function in JavaScript forms a closure over its surrounding scope.

Real React example: every event handler is a closure. When you write const handleClick = () => setCount(count + 1), the arrow function closes over count from the component's scope. If count changes and the component re-renders, a new closure is created capturing the new value.

Production example: debounce — the returned function closes over timer, allowing each call to clear and reset the same timeout reference. Without a closure, timer would be a new variable each call and the debounce wouldn't work.
Depth signal: "Stale closures are one of the most common React bugs — an event handler closing over an old value of state. The fix is using setState's functional update form: setState(prev => prev + 1) instead of setState(count + 1)."
Q2Explain the JavaScript event loop. What is the difference between microtasks and macrotasks?▶
model answer
JavaScript is single-threaded — it has one call stack and can only execute one thing at a time. The event loop enables async behaviour by offloading tasks to browser Web APIs (or Node's libuv) and scheduling their callbacks for later.

Order of execution: synchronous code runs first and empties the call stack. Then the microtask queue drains completely (all .then, .catch, await continuations). Then one macrotask runs (setTimeout, setInterval, I/O). Then microtasks again. This repeats.

Why it matters: Promise.resolve().then(fn) always runs before setTimeout(fn, 0) even though both are "async". This affects rendering — React batches state updates as microtasks, which is why multiple setState calls in one handler cause only one re-render.
Q3What is hoisting? What's the Temporal Dead Zone?▶
model answer
Hoisting is the JavaScript engine's behaviour of processing declarations before executing code. Variable and function declarations are "moved" to the top of their scope conceptually.

var: declaration hoisted and initialised to undefined. Assignment stays in place. Accessing before declaration gives undefined.

let/const: declaration is hoisted but NOT initialised. The period from the start of the scope to the declaration is called the Temporal Dead Zone (TDZ). Accessing a variable in the TDZ throws a ReferenceError. This is intentional — it catches use-before-assignment bugs that var silently hid.

Function declarations: fully hoisted — name and body. Can be called before declaration.
Interviewers love follow-ups: "Why does typeof x return 'undefined' for a let variable in the TDZ instead of throwing?" — technically typeof is special-cased to not throw for undeclared variables, but let variables in TDZ DO throw even with typeof in some engines.
Q4What is the difference between a Promise and async/await? When would you use one over the other?▶
model answer
async/await is syntactic sugar over Promises — it doesn't introduce new async capabilities, it makes Promise-based code look and read like synchronous code.

Use Promise chains when: you need to run multiple things in parallel (Promise.all), use combinators like race or allSettled, or you're working with stream/pipeline patterns where chaining reads naturally.

Use async/await when: you have sequential async operations that depend on each other, complex error handling with try/catch/finally, or anywhere the sequential, imperative style is clearer.

In practice: most teams use async/await as the default for readability, and reach for Promise combinators when parallelism is needed. They mix freely — await Promise.all([...]) is extremely common.
Q5Why doesn't fetch throw on a 404 or 500 status? How do you handle HTTP errors properly?▶
model answer
fetch only rejects (throws) on network failures — no internet, DNS failure, CORS error. It considers any HTTP response, including 404 and 500, a successful network request and resolves the Promise.

To handle HTTP errors, you must check response.ok (true for status 200–299) or check response.status directly, and manually throw an error:

if (!response.ok) throw new Error(`HTTP ${response.status}`)

This is a deliberate design decision — fetch is a low-level primitive. Higher-level libraries like axios throw on non-2xx by default, which is why many teams prefer them.
Common bug: writing const data = await fetch(url).json() — this doesn't work because fetch returns a Promise, not a Response. The correct pattern is always two awaits: one for the network response, one for parsing the body.
Q6What is the difference between Promise.all, Promise.allSettled, Promise.race, and Promise.any?▶
model answer
Promise.all: waits for ALL to fulfill. Rejects immediately if any rejects (fail-fast). Returns array of results in original order. Use when you need all results and a single failure should abort.

Promise.allSettled: waits for ALL to settle (fulfill or reject). Never rejects. Returns array of {status, value|reason}. Use when you want to process all results regardless of partial failures — loading multiple independent dashboard widgets.

Promise.race: resolves or rejects with the FIRST settled promise. Use for timeout patterns — race a fetch against a timeout promise.

Promise.any: resolves with the FIRST fulfilled promise. Only rejects if ALL reject. Use for redundant requests — try multiple servers, use whichever responds first.
Q7What is lexical scope? How does it differ from dynamic scope?▶
model answer
In lexical scope (static scope), a variable's scope is determined by where the function is written in the source code, at parse time. JavaScript uses lexical scope. A function can access variables from the scope where it was defined, regardless of where it is called from.

In dynamic scope, a function's scope is determined by where it is called at runtime. This would mean the same function produces different results depending on the call site's environment.

Why it matters in JS: closures work because of lexical scope — the inner function always has access to the variables in the scope where it was written. Arrow functions also use lexical scope for this binding (inheriting this from where they're defined, not where they're called), which is why they're preferred in React event handlers.
Q8What is a higher-order function? Give 3 examples from JavaScript and explain the pattern.▶
model answer
A higher-order function (HOF) is a function that either accepts a function as an argument or returns a function (or both).

Example 1 — takes a function: array.map(fn), array.filter(fn), setTimeout(fn, ms). The callback is the function argument.

Example 2 — returns a function: debounce(fn, delay) returns a new function. memoize(fn) returns a cached version. React's useMemo and useCallback are HOF patterns.

Example 3 — both: compose and pipe take functions as arguments and return a new composed function.

HOFs are fundamental to functional programming and enable reusable abstractions — instead of duplicating logic, you parameterise it with a function.
Q9How do you handle errors in async/await? What happens to unhandled promise rejections?▶
model answer
In async functions, wrap await calls in try/catch — any rejection becomes a caught exception. finally always runs regardless of outcome, making it ideal for cleanup (hiding loading spinners, closing connections).

Unhandled rejections: in Node.js, unhandled rejections crash the process (with an UnhandledPromiseRejection warning). In browsers, they fire a unhandledrejection event. In both environments, they indicate a bug — a promise was rejected but no .catch() or try/catch handled it.

Best practices: always attach error handling at the top-level caller. For fire-and-forget async operations, at minimum add .catch(console.error). In React, use error boundaries for rendering errors and async error handling in useEffect cleanup.
Show depth: "Wrapping every await in its own try/catch is noisy. A pattern I use is a helper that returns [error, result]: const [err, data] = await to(fetchUser(1)) — the 'to' pattern from the 'await-to-js' library."
Q10Why does forEach not work with await? How do you iterate asynchronously over an array?▶
model answer
forEach calls its callback synchronously and ignores the return value. When you use an async callback inside forEach, each call returns a Promise — but forEach discards it. The loop completes immediately without waiting for any of the promises to resolve.

Solution 1 — sequential: use for...of with await. The await pauses the loop body each iteration.

Solution 2 — parallel: use await Promise.all(array.map(async item => ...)). The map starts all promises simultaneously, and Promise.all awaits all of them.

Choose sequential when order matters or when requests depend on previous results. Choose parallel when requests are independent — it's dramatically faster.
Common follow-up: "What about for...in?" — use for...of for arrays, never for...in (it iterates over all enumerable properties including inherited ones, not just array elements).
