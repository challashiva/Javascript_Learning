Part 1 — ES6 Modules
01 Why modules exist — the problem they solve foundation
before modules
The global scope nightmare
Before ES modules, every JS file shared the same global scope. Variable names collided, load order mattered critically, and there was no way to say "this file depends on that one." Libraries like jQuery littered window with names. Any file could accidentally overwrite any other file's variables. Projects over a few thousand lines became unmaintainable.
what modules give you
Isolated, explicit dependencies
Every ES module has its own scope — nothing leaks to global. You explicitly declare what you export (what others can use) and what you import (what you depend on). The browser/bundler builds a dependency graph and loads files in the right order automatically. Dead code (unused exports) can be eliminated by bundlers.
live bindings
Imports are live, not copies
ES module imports are live bindings — if the exporting module updates the exported value, all importers see the update. This is different from CommonJS (require()) which copies the value at import time. Live bindings matter for things like counters and config that might change after module load.
static analysis
Static structure = tree-shaking
import and export must be at the top level — they can't be inside if blocks or functions. This static structure lets bundlers like Vite and Webpack analyse your code at build time and eliminate exports that are never imported — dramatically reducing bundle size. This is called tree-shaking.
typical React project module structure
src/
├── main.jsx     ← entry point, imports App
├── App.jsx      ← imports components, hooks, utils
├── components/
│   ├── Button.jsx  ← named export: export function Button()
│   ├── Card.jsx    ← default export: export default Card
│   └── index.js   ← barrel: re-exports everything
├── hooks/
│   └── useAuth.js  ← named export: export function useAuth()
└── utils/
    └── format.js   ← named exports: export const formatDate, formatCurrency

Part 2 — Iterators & Generators
04 Iteration protocol — iterable vs iterator protocol
Two interfaces — both are needed to make something iterable
Iterable
An object with a [Symbol.iterator]() method that returns an Iterator. Arrays, strings, Maps, Sets, NodeLists are built-in iterables.
Iterator
An object with a next() method that returns { value, done }. done: true signals the sequence is finished.
What uses iterables
for...of, spread [...iter], destructuring [a, b] = iter, Array.from(), Promise.all(), new Map(iter).
Infinite sequences
Iterators can produce values forever — done never becomes true. Use break in for...of to stop. Generators make this easy.
javascriptThe iteration protocol — implementing Symbol.iterator by hand
// Under the hood of for...of:
const arr      = [10, 20, 30]
const iterator = arr[Symbol.iterator]()  // get the iterator
console.log(iterator.next())  // { value: 10, done: false }
console.log(iterator.next())  // { value: 20, done: false }
console.log(iterator.next())  // { value: 30, done: false }
console.log(iterator.next())  // { value: undefined, done: true }

// ── Make a custom iterable — a Range object ────────────────
class Range {
  constructor(start, end, step = 1) {
    this.start = start
    this.end   = end
    this.step  = step
  }

  // ✦ This method makes Range an iterable
  [Symbol.iterator]() {
    let current = this.start
    const end   = this.end
    const step  = this.step

    // Returns the iterator object
    return {
      next() {
        if (current <= end) {
          const value = current
          current += step
          return { value, done: false }
        }
        return { value: undefined, done: true }
      }
    }
  }
}

const r = new Range(1, 10, 2)

// Works with for...of
for (const n of r) console.log(n)   // 1, 3, 5, 7, 9

// Works with spread
const nums = [...new Range(1, 5)]      // [1, 2, 3, 4, 5]

// Works with destructuring
const [first, second] = new Range(10, 50, 10)  // 10, 20

// Works with Array.from
const arr2 = Array.from(new Range(0, 4))  // [0, 1, 2, 3, 4]
05 Generator functions — pauseable execution powerful
what they are
Functions that pause and resume
A generator is a function declared with function* that can pause its execution at any yield point and resume exactly where it left off when next() is called again. The function body runs lazily — only when you ask for the next value. Calling a generator function returns a Generator object (which is both an iterable AND an iterator).
key uses
Where generators shine
Infinite sequences — IDs, Fibonacci, prime numbers — without ever running out of memory. Lazy evaluation — only compute values when asked. Custom iterators — much cleaner than implementing Symbol.iterator by hand. State machines — each yield is a state. Saga pattern in Redux (used in large apps).
two-way communication
Sending values back in
Generators are two-way — yield sends a value out, and next(value) sends a value back in (the yield expression evaluates to that value). This bidirectional flow makes generators ideal for complex async coordination patterns like Redux-Saga.
javascriptGenerator syntax — yield, yield*, return, two-way, infinite sequences
// ── Basic generator ────────────────────────────────────────
function* count() {
  console.log("start")
  yield 1              // pauses here, returns { value:1, done:false }
  console.log("resumed")
  yield 2              // pauses here, returns { value:2, done:false }
  console.log("last")
  return 3             // returns { value:3, done:true } — generator done
}

const gen = count()    // does NOT run the body yet — returns generator object
gen.next()              // "start"  → { value:1, done:false }
gen.next()              // "resumed"→ { value:2, done:false }
gen.next()              // "last"   → { value:3, done:true  }
gen.next()              // { value:undefined, done:true } — exhausted

// Generators ARE iterables — use for...of directly
for (const v of count()) console.log(v)  // 1, 2 (return value skipped by for...of)

// ── Infinite sequence generator ────────────────────────────
function* idGenerator(prefix = "id") {
  let i = 1
  while (true) {
    yield `${prefix}_${i++}`   // infinite loop is fine — each next() gets one value
  }
}
const nextId = idGenerator("user")
nextId.next().value  // "user_1"
nextId.next().value  // "user_2"
nextId.next().value  // "user_3"

// ── yield* — delegate to another iterable ─────────────────
function* concat(...iterables) {
  for (const it of iterables) yield* it  // yield each value from sub-iterable
}
[...concat([1,2], "abc", [3])]  // [1, 2, "a", "b", "c", 3]

// ── Two-way communication — next(value) sends value in ────
function* calculator() {
  let result = 0
  while (true) {
    const input = yield result  // yield sends result OUT, receives next input IN
    if (input === null) break
    result += input
  }
  return result
}
const calc = calculator()
calc.next()     // start — { value: 0, done: false }
calc.next(10)   // add 10 — { value: 10, done: false }
calc.next(25)   // add 25 — { value: 35, done: false }
calc.next(null) // stop — { value: 35, done: true }

// ── Practical: lazy pipeline ──────────────────────────────
function* take(n, iterable) {
  let count = 0
  for (const item of iterable) {
    if (count++ >= n) break
    yield item
  }
}
function* map(fn, iterable) { for (const x of iterable) yield fn(x) }
function* filter(fn, iterable) { for (const x of iterable) if (fn(x)) yield x }

// Take first 5 even squares from infinite sequence — nothing computed until needed
function* naturals() { let n = 1; while (true) yield n++ }

const pipeline = take(5, filter(n => n % 2 === 0, map(n => n ** 2, naturals())))
console.log([...pipeline])  // [4, 16, 36, 64, 100] — first 5 even squares
06 Async generators & for await…of async iteration
what they are
async function* — yields Promises
An async generator combines async and function*. It can both await Promises and yield values. Calling next() returns a Promise that resolves to { value, done }. Used with for await...of which automatically awaits each value in the loop.
real-world uses
When you actually use async generators
Paginated APIs — yield each page as it arrives, stop when done. File/stream reading — yield each chunk. WebSocket messages — yield each message as it arrives. Server-Sent Events. AI streaming responses — yield tokens as the model produces them. This is how streaming chat UIs work.
javascriptAsync generators — paginated API, streaming, and for await...of
// ── Async generator — paginated API fetcher ────────────────
async function* fetchAllPages(baseUrl) {
  let page = 1
  let hasMore = true

  while (hasMore) {
    const response = await fetch(`${baseUrl}?page=${page}&limit=10`)
    const data     = await response.json()

    yield data.items   // yield this page's items, then pause

    hasMore = data.hasNextPage
    page++
  }
}

// Consume with for await...of — processes each page as it arrives
async function processAll() {
  let total = 0
  for await (const page of fetchAllPages("https://api.example.com/users")) {
    total += page.length
    console.log(`Got ${page.length} items, total: ${total}`)
    if (total > 50) break   // stop early — remaining pages never fetched!
  }
}

// ── Stream AI response tokens ──────────────────────────────
async function* streamTokens(prompt) {
  const response = await fetch("/api/ai", {
    method: "POST",
    body: JSON.stringify({ prompt })
  })

  const reader  = response.body.getReader()
  const decoder = new TextDecoder()

  while (true) {
    const { done, value } = await reader.read()
    if (done) break
    yield decoder.decode(value)  // yield each chunk as it streams
  }
}

// Display tokens as they arrive — this is how ChatGPT streaming works
let fullResponse = ""
for await (const token of streamTokens("Explain closures")) {
  fullResponse += token
  updateUI(fullResponse)   // re-render after each token
}

// ── Collect async iterable to array ───────────────────────
async function collectAsync(asyncIterable) {
  const results = []
  for await (const item of asyncIterable) results.push(item)
  return results
}
// Or simply: Array.fromAsync(asyncIterable)  — newer browsers

08 Interview questions + model answers 10 Q&As
Q1What is the difference between named exports and default exports? When do you use each?▶
model answer
Named exports: a file can have multiple. Imported with the exact same name in curly braces: import { formatDate } from './utils'. You can rename with as. Better for utility modules exporting many functions, and better for tree-shaking since bundlers know exactly which exports are used.

Default export: one per file. Imported without curly braces with any name: import Card from './Card'. Conventional for React components — one component per file.

When to use which: named exports for utility/helper modules with multiple functions. Default export for modules whose primary purpose is one thing — a component, a class, a configuration object. Many teams avoid default exports entirely because they make global renaming and auto-import tools harder.
Depth signal: mention barrel files (index.js that re-exports from multiple modules) and how they affect bundle size — importing from a barrel re-exports file prevents tree-shaking of unused exports in some bundler configurations.
Q2What is tree-shaking and why do ES modules enable it but CommonJS doesn't?▶
model answer
Tree-shaking is the bundler's ability to eliminate unused exports from the final bundle — "shaking the tree" to drop dead leaves.

ES modules enable it because import/export have a static structure — they must be at the top level and can't be inside conditions or functions. The bundler can analyse the entire dependency graph at build time and determine which exports are never imported.

CommonJS (require()) is dynamic — you can require(someVar) or if (condition) { require('./thing') }. The bundler can't know at build time which modules might be required, so it has to include everything. This is why switching a library from CJS to ESM can dramatically reduce bundle sizes.
Q3What is dynamic import()? How is it different from static import?▶
model answer
Static import is evaluated before code runs — the module is always downloaded when the file loads. Dynamic import() is a function call that returns a Promise and loads the module lazily, on demand, at runtime.

Dynamic import is used for code splitting — only downloading code when it's actually needed. React's React.lazy(() => import('./Component')) uses this. Route-based code splitting with React Router loads each page's code only when that page is visited.

Unlike static imports, dynamic imports can appear inside functions, conditionals, and event handlers. They can use dynamic paths. The cost is that the loaded module isn't available immediately — you must await the Promise.
Q4What is the iteration protocol? What makes an object iterable in JavaScript?▶
model answer
The iteration protocol consists of two interfaces: the iterable protocol and the iterator protocol.

An object is iterable if it has a [Symbol.iterator]() method that returns an iterator. An iterator is an object with a next() method that returns { value, done }.

Built-in iterables: arrays, strings, Maps, Sets, NodeLists, arguments, typed arrays. These all have Symbol.iterator built in. You can make any custom object iterable by implementing this method.

What uses iterables: for...of, spread operator [...iterable], destructuring [a, b] = iterable, Array.from(), new Map(iterable), and Promise.all(iterable).
Q5What is a generator function? How does it differ from a regular function?▶
model answer
A generator function (declared with function*) returns a Generator object when called — the body doesn't run yet. The body executes lazily: each call to next() runs until the next yield statement, suspends, and returns { value, done }. The next next() call resumes from exactly where it paused.

Key differences from regular functions: a regular function runs to completion, returning once. A generator suspends and resumes, producing multiple values over time. Generator objects are both iterables (have Symbol.iterator) and iterators (have next()), so they work with all iterable-consuming syntax.

Important: return in a generator sets done: true. The return value is yielded once but for...of and spread skip it.
Q6What does yield* do in a generator?▶
model answer
yield* delegates iteration to another iterable — it yields every value produced by the inner iterable before the outer generator continues.

Without yield*: yield [1, 2, 3] yields the array as a single value. With yield*: yield* [1, 2, 3] yields 1, then 2, then 3 individually.

Practical uses: flattening nested sequences, composing generators, implementing recursive generator algorithms like tree traversal — instead of manually looping and yielding each item from a recursive call, you just yield* recursiveCall(child).

The expression value of yield* is the final return value of the delegated generator (the value from { done: true, value }).
Q7What is an async generator? When would you use one over a regular async function?▶
model answer
An async generator (async function*) combines async/await and generators — it can both await Promises and yield values. Calling next() returns a Promise that resolves to { value, done }. Used with for await...of.

Use an async generator when you have a sequence of async operations producing multiple values over time — where each value is available at a different point and you want to process each one as it arrives rather than waiting for all of them.

Examples: paginated API responses (process each page as it arrives), file streaming (yield each chunk), WebSocket messages, AI token streaming. A regular async function can only return one value when fully done. An async generator can yield many partial results while still doing async work between each one.
Strong answer: "In our React app, we used an async generator to stream AI responses — each yielded token updated the UI immediately, giving the appearance of the AI typing in real time. This would be impossible with a regular async function which only resolves once."
Q8What is the difference between for...of and for...in?▶
model answer
for...of iterates the values of any iterable — arrays, strings, Maps, Sets, generators. It uses the iteration protocol (Symbol.iterator). This is what you should use for collections.

for...in iterates the enumerable property keys of an object — including inherited ones from the prototype chain. It's designed for plain objects but is unreliable for arrays because: it iterates indices as strings ("0", "1"), it includes any enumerable prototype properties, and the order isn't guaranteed in older environments.

Rule: use for...of for iterables (arrays, strings, collections). Use Object.keys()/entries()/values()` + `.forEach()` for plain objects. Avoid for...in for arrays. for...in is rarely useful in modern code.
Common interview gotcha: for...in on an array that has been given extra properties (e.g. arr.myProp = "x") will also iterate "myProp". for...of only iterates the indexed elements.
Q9What are live bindings in ES modules? How do they differ from CommonJS?▶
model answer
In ES modules, imports are live bindings — a read-only view of the exported variable. If the exporting module updates the export, all importers see the new value automatically. The binding is a live reference, not a copy.

In CommonJS, require() gives you a copy of the exported value at the time of the require call. If the exporting module later changes the value, importers don't see the change.

Practical implication: if a module exports a counter and increments it, ESM importers will see the updated count; CJS importers are stuck with the initial value. This matters for configuration objects that are set up asynchronously, counters, and flags.

Note: the live binding is read-only from the importer's perspective — you can't reassign an imported binding. The module that owns it is the only one that can change it.
Q10What is Symbol.iterator and what happens if you spread an object that doesn't have it?▶
model answer
Symbol.iterator is a well-known Symbol used as a property key. Any object with a [Symbol.iterator]() method is iterable. The method must return an iterator (an object with next()). This protocol is how for...of, spread, and destructuring know how to consume any object uniformly.

If you try to spread a plain object that has no Symbol.iterator: [...obj] throws TypeError: obj is not iterable. Plain objects are not iterable by default — they don't have Symbol.iterator.

However, object spread {...obj} works on plain objects — but that's a different operator. It spreads the object's own enumerable properties into a new object, and doesn't use Symbol.iterator at all. Array spread [...obj] uses the iteration protocol; object spread {...obj} uses property enumeration. They look similar but are completely different operations.
Show depth: strings are iterable (they yield characters), so [..."hello"] gives ["h","e","l","l","o"]. But a Number is not: [...42] throws. Maps and Sets are iterable. WeakMaps and WeakSets are NOT iterable — intentionally, to prevent memory leak analysis.
