Week 6 Interview Q&A Recap

1. Walk me through the ShopCo backend architecture end-to-end.
A request enters through Clerk middleware for authentication, then hits either a REST route (public/mobile clients) or a tRPC procedure (internal admin dashboard) — both validated with Zod. Business logic reads/writes through Prisma to PostgreSQL, with soft deletes and audit logging on every mutation. Order status changes trigger two parallel real-time paths: an SSE stream pushes updates to the customer, and a Pusher event notifies the admin dashboard. Product images upload directly to S3 via pre-signed URLs, then get processed by Sharp into WebP variants before URLs are saved to Postgres. Rate limiting via Redis protects all of it from abuse.
2. Why did you choose a monorepo with Turborepo for this project?
A monorepo lets us share TypeScript types, UI components, and validation schemas across the Next.js app, admin dashboard, and any future mobile app — without publishing/versioning internal npm packages. Turborepo adds intelligent caching (skip rebuilding unchanged packages) and parallel task execution, which keeps CI fast even as the codebase grows. The tradeoff is more complex tooling setup initially, but it pays off once you have 3+ apps or packages that need to share code and stay in sync.
3. How does your RBAC system prevent privilege escalation?
Roles are stored server-side in Clerk's session claims (not client-editable), verified on every request via middleware, and checked against a strict hierarchy (customer < staff < admin < super_admin) using index comparison rather than string matching. Every tRPC procedure and REST route explicitly declares its minimum required role — there's no "default allow" path. Role changes go through an audited admin action, not a self-service user setting. Combined with the permission matrix (role × resource × action), this ensures a customer can never reach admin-only mutations even if they tamper with client-side state.
4. How would you scale the real-time order tracking system to 100,000 concurrent users?
Pusher's infrastructure already handles horizontal scaling for WebSocket fan-out — that's the point of using a managed service instead of raw WebSockets. For SSE (customer order tracking), the bottleneck is serverless function concurrency and DB polling load — mitigate by using Redis pub/sub instead of DB polling for status changes, and cap SSE connection duration with keepalives. Rate limit connection attempts per user to prevent one customer opening hundreds of tabs from exhausting resources. Monitor Pusher's per-app connection limits and upgrade plan tiers proactively as usage grows.
5. What was the hardest architectural tradeoff this week and how did you resolve it?
Choosing between REST and tRPC required weighing type safety against API openness. tRPC gives incredible developer velocity for the admin dashboard we fully control, but it can't serve third-party integrations or a future mobile app without a TypeScript client. The resolution was using both: REST for anything that needs to be a stable, documented, external-facing contract, and tRPC for internal tooling where we want maximum type safety and iteration speed. This "boring but correct" solution avoids forcing one technology to do a job it's not suited for.
6. How do soft deletes interact with your audit logging and real-time systems?
When a product is soft-deleted (deletedAt set), the audit log records who deleted it and when, preserving full history. Any active SSE/Pusher subscriptions related to that product should be notified so the UI can react (e.g., remove from admin's live product list) — this requires explicitly emitting a 'product-deleted' event, since soft delete alone doesn't automatically notify connected clients. File cleanup for that product's images is deferred to a background job with a grace period, since the soft-deleted record might be restored. The key lesson: soft delete is a data-layer concept, but its effects ripple into every other system that references that entity.
7. What security review would you do before launching this to production?
Checklist: (1) Verify every tRPC/REST mutation has proper role checks — no accidentally public admin endpoints; (2) confirm S3 bucket blocks public access and pre-signed URLs have short expiries; (3) validate all file uploads server-side by magic bytes, not extension; (4) ensure rate limiting covers all mutation endpoints, not just reads; (5) confirm Zod schemas reject unexpected fields (no mass-assignment vulnerabilities); (6) check that Clerk webhook signatures are verified before processing; (7) audit that Pusher private/presence channels have server-side auth checks, not just client-side channel naming; (8) review CORS policy is restricted to your domains only.
8. How would you test this entire system before shipping a new feature?
Layered testing: unit tests for pure functions (Zod schemas, permission checks, error formatters); integration tests for API routes with a test database (Vitest + Prisma test client); mocked tests for external services (Pusher, S3, UploadThing) to avoid real network calls in CI; E2E tests with Playwright for critical user journeys (place order, admin uploads image, real-time status update appears). The integration test built in Exercise 6 today is exactly this pattern — simulate the full system with in-memory state and assert on the emergent behavior across auth, orders, and real-time events together, not just each piece in isolation.
9. If you had to cut scope for a launch deadline, what would you cut first?
Real-time features are the safest to defer — SSE/Pusher can be replaced with polling or manual refresh initially, and added later without touching the data model. File upload processing (Sharp variants) could ship with just the original image and add WebP optimization in a follow-up. What should NOT be cut: authentication and RBAC (security foundation), core data model with soft deletes and audit logging (hard to retrofit later), and basic API validation with Zod (prevents entire classes of bugs). The rule of thumb: cut features that enhance UX, never cut the data integrity and security foundations.
10. What would you do differently if you rebuilt Week 6's architecture from scratch?
This is a strong interview question to practice answering about your own projects. Good answers show reflection: e.g., "I'd introduce the Zod schemas earlier and derive Prisma-adjacent types from them from day one, rather than defining API shapes separately." Or: "I'd set up the audit log table before building any mutations, since retrofitting audit logging into existing endpoints means touching every mutation twice." Or: "I'd choose Redis pub/sub over Pusher earlier for cost control at scale, accepting more operational complexity for lower per-message cost." The goal is demonstrating you can critically evaluate your own architectural decisions, not just defend them.
