01 useRef — a mutable box that survives renders escape hatch
what it is
A plain object with a .current property
useRef(initialValue) returns { current: initialValue }. That's it. The same object persists across every render — React never replaces it. Changing ref.current does not trigger a re-render. This is the critical difference from state: refs are for values you want to remember but not react to.
use 1 — DOM access
The ref prop attaches to a real DOM node
Pass a ref to a JSX element's ref prop. After the component mounts, ref.current holds the actual DOM element. Use this for: programmatic focus, reading input values without controlling them, triggering animations, scrolling to position, measuring element dimensions.
use 2 — mutable values
Store anything that changes but shouldn't re-render
Timers, interval IDs, WebSocket instances, previous values, render counts, flags like "is this the first render". If you put these in state, you get unnecessary re-renders. If you use a plain variable, it resets every render. A ref persists without triggering anything.
common mistake
Don't read/write refs during render
Reading ref.current during the render phase is unreliable — the DOM hasn't been updated yet. Refs should be read and written inside event handlers and useEffect. During render, use state. React's rules of hooks require this discipline.
jsxuseRef — DOM access, mutable values, previous value, interval cleanup
import { useRef, useEffect, useState } from "react"

// ── Use 1: DOM access ──────────────────────────────────────
function AutoFocusInput() {
  const inputRef = useRef(null)   // null until component mounts

  useEffect(() => {
    inputRef.current?.focus()   // DOM is ready after mount
  }, [])

  return <input ref={inputRef} type="text" placeholder="I focus on mount" />
}

// ── Scroll to bottom of a chat window ─────────────────────
function ChatWindow({ messages }) {
  const bottomRef = useRef(null)

  useEffect(() => {
    bottomRef.current?.scrollIntoView({ behavior: "smooth" })
  }, [messages])  // scroll every time messages change

  return (
    <div className="chat">
      {messages.map(m => <Message key={m.id} msg={m} />)}
      <div ref={bottomRef} />   {/* invisible anchor at bottom */}
    </div>
  )
}

// ── Measure an element's size ─────────────────────────────
function MeasuredBox() {
  const boxRef  = useRef(null)
  const [size, setSize] = useState({ w: 0, h: 0 })

  useEffect(() => {
    const { offsetWidth: w, offsetHeight: h } = boxRef.current
    setSize({ w, h })
  }, [])

  return <div ref={boxRef}>I am {size.w} × {size.h}px</div>
}

// ── Use 2: Store interval ID without re-render ────────────
function Stopwatch() {
  const [elapsed, setElapsed] = useState(0)
  const intervalRef = useRef(null)   // store ID — not state, no re-render

  const start = () => {
    if (intervalRef.current) return
    intervalRef.current = setInterval(() => {
      setElapsed(e => e + 1)
    }, 1000)
  }

  const stop = () => {
    clearInterval(intervalRef.current)
    intervalRef.current = null
  }

  useEffect(() => () => stop(), [])  // cleanup on unmount

  return (
    <div>
      <p>{elapsed}s</p>
      <button onClick={start}>Start</button>
      <button onClick={stop}>Stop</button>
    </div>
  )
}

// ── Use 3: Track previous value ───────────────────────────
function usePrevious(value) {
  const ref = useRef()
  useEffect(() => {
    ref.current = value   // set AFTER render so this render's value becomes "previous"
  })
  return ref.current        // returns value from previous render
}

function PriceTracker({ price }) {
  const prevPrice = usePrevious(price)
  const direction = prevPrice === undefined ? "—"
    : price > prevPrice ? "↑" : price < prevPrice ? "↓" : "→"
  return <p>${price} {direction} (was ${prevPrice})</p>
}
useLayoutEffect vs useEffect — when the timing matters
useEffect (99% of the time)
Fires asynchronously after the browser has painted. Can't block the browser. Use for: data fetching, subscriptions, logging, anything that doesn't need to read DOM layout before paint.
useLayoutEffect (rare)
Fires synchronously after DOM mutations but before the browser paints. Use when you need to read DOM measurements (width, height, scroll position) and then update state before the user sees anything — prevents visual flicker.
when it matters
Tooltips, popovers, dropdowns that need to be positioned relative to a DOM element before showing. If you use useEffect for this, you see a brief flash of the element in the wrong position.
rule of thumb
Start with useEffect. If you see a visual flicker because you're measuring the DOM and then changing something, switch to useLayoutEffect.
02 useMemo — cache expensive computed values performance
what it does
Remembers a computed value between renders
useMemo(fn, deps) calls fn() and caches the result. On subsequent renders it only re-runs fn() if a dependency changed. Otherwise it returns the cached value. Every component function re-runs on every render — useMemo stops expensive computations from re-running unnecessarily.
when to use it
Only for genuinely expensive computations
Don't use useMemo by default. It has overhead — the dependency comparison runs every render. Only use it when: the computation is slow (sorting thousands of items, complex maths), or you need a stable object/array reference to prevent child re-renders via React.memo.
common mistake
Over-memoising simple computations
const x = useMemo(() => a + b, [a, b]) is worse than just const x = a + b. The memo overhead exceeds the savings. Simple filters, sorts, and maths on small arrays don't need memoisation. Profile first, optimise second.
jsxuseMemo — expensive filter, stable references, when NOT to use it
import { useMemo, useState } from "react"

// ── Good use: expensive computation on large data ──────────
function ProductCatalog({ products }) {   // products: 10,000 items
  const [query,    setQuery]    = useState("")
  const [sortBy,   setSortBy]   = useState("name")
  const [darkMode, setDarkMode] = useState(false)

  // Only re-runs when query or sortBy changes — NOT when darkMode changes
  const filteredProducts = useMemo(() => {
    console.log("Filtering...")   // won't log on darkMode toggle
    return products
      .filter(p => p.name.toLowerCase().includes(query.toLowerCase()))
      .sort((a, b) => a[sortBy].localeCompare(b[sortBy]))
  }, [products, query, sortBy])   // deps: only recalculate when these change

  return (
    <div className={darkMode ? "dark" : ""}>
      <input value={query} onChange={e => setQuery(e.target.value)} />
      <p>{filteredProducts.length} results</p>
    </div>
  )
}

// ── Stable reference for child component (with React.memo) ─
const ExpensiveList = React.memo(({ config }) => {
  console.log("ExpensiveList rendered")
  return <div>...expensive rendering...</div>
})

function Parent() {
  const [count, setCount] = useState(0)

  // Without useMemo: new object every render → React.memo can't help
  // const config = { theme: "dark", pageSize: 20 }  // new ref each render!

  // With useMemo: same reference unless deps change → React.memo works
  const config = useMemo(
    () => ({ theme: "dark", pageSize: 20 }),
    []   // never changes — created once
  )

  return (
    <div>
      <button onClick={() => setCount(c => c + 1)}>Count: {count}</button>
      <ExpensiveList config={config} />   {/* won't re-render on count change */}
    </div>
  )
}

// ── DON'T useMemo for simple/cheap operations ─────────────
// BAD: overhead outweighs benefit
const doubled   = useMemo(() => count * 2, [count])           // just write count * 2
const fullName  = useMemo(() => `${first} ${last}`, [first, last]) // just use template literal
const smallList = useMemo(() => items.filter(x => x > 5), [items])  // fine without memo if items.length < 1000
03 useCallback — stable function references performance
what it does
useMemo for functions
useCallback(fn, deps) returns the same function reference between renders unless a dependency changes. Without it, every render creates a brand new function object. This matters when the function is passed as a prop to a React.memo child — a new function reference breaks memoisation.
relationship
useCallback = useMemo returning a function
These are identical: useCallback(fn, deps) and useMemo(() => fn, deps). useCallback is just the convenient shorthand. Both cache by dependency comparison. Both have the same overhead. Both should only be used when the stable reference actually matters — not by default.
stale closures
The hardest useCallback bug
A memoised function closes over the state values from when it was created. If you forget a dependency, the function uses a stale (old) value. The fix is to add it to the deps array — but this means the function gets recreated when that value changes, which may undo the performance benefit.
jsxuseCallback with React.memo, the stale closure problem, and useReducer as a fix
import { useCallback, useState, memo } from "react"

// ── useCallback + React.memo: the pairing that makes sense ─
const TodoItem = memo(({ todo, onToggle, onDelete }) => {
  console.log("TodoItem rendered:", todo.text)
  return (
    <li>
      <input type="checkbox" checked={todo.done} onChange={() => onToggle(todo.id)} />
      {todo.text}
      <button onClick={() => onDelete(todo.id)}>✕</button>
    </li>
  )
})

function TodoList() {
  const [todos,  setTodos]  = useState([...])
  const [filter, setFilter] = useState("all")

  // Without useCallback: new function every render → every TodoItem re-renders
  // even when only filter changed!

  // With useCallback: same reference while todos doesn't change
  const handleToggle = useCallback((id) => {
    setTodos(prev => prev.map(t => t.id === id ? { ...t, done: !t.done } : t))
  }, [])  // empty deps: uses functional setState, never stale!

  const handleDelete = useCallback((id) => {
    setTodos(prev => prev.filter(t => t.id !== id))
  }, [])  // same: functional update, no stale closure

  const visible = useMemo(() =>
    filter === "all" ? todos : todos.filter(t => t.done === (filter === "done"))
  , [todos, filter])

  return (
    <ul>
      {visible.map(t => (
        <TodoItem key={t.id} todo={t} onToggle={handleToggle} onDelete={handleDelete} />
      ))}
    </ul>
  )
}

// ── Stale closure problem with useCallback ────────────────
function BuggyCounter() {
  const [count, setCount] = useState(0)

  // BUGGY: count in closure is always 0 (the initial value)
  const alertCount = useCallback(() => {
    alert(`Count is ${count}`)   // stale! always shows 0
  }, [])   // empty deps — captures count=0 and never updates

  // FIX 1: add count to deps (recreates fn when count changes)
  const fixedAlert1 = useCallback(() => {
    alert(`Count is ${count}`)
  }, [count])   // recreated every time count changes

  // FIX 2: use a ref to always have current value (no recreation)
  const countRef = useRef(count)
  useEffect(() => { countRef.current = count }, [count])

  const fixedAlert2 = useCallback(() => {
    alert(`Count is ${countRef.current}`)   // always current!
  }, [])   // stable — reads from ref, not closure
}
04 Custom hooks — extract and reuse stateful logic composition
what they are
Functions that start with "use" and call hooks
A custom hook is any JavaScript function whose name starts with use and that calls React hooks internally. That's the entire definition. They let you extract stateful logic from components — logic that involves useState, useEffect, etc. — and share it across components without prop drilling or wrapper components.
why they matter
The correct abstraction for React logic
Before hooks, logic reuse required Higher Order Components or Render Props — complex patterns that added wrapper nodes and made component trees hard to read. Custom hooks let you share logic with zero component overhead. Each component that calls a custom hook gets its own independent state — hooks are not singletons.
rule
Must follow all rules of hooks
Custom hooks obey the same rules: only call at the top level (not in conditionals or loops), only call from React function components or other custom hooks. The use prefix is what tells ESLint to apply hooks rules to your custom function. Never name a hook without use.
jsx6 production-ready custom hooks — useFetch, useLocalStorage, useDebounce, useOnClickOutside, useWindowSize, useMediaQuery
// ── useFetch — async data with loading/error/data states ──
function useFetch(url) {
  const [data,    setData]    = useState(null)
  const [loading, setLoading] = useState(true)
  const [error,   setError]   = useState(null)

  useEffect(() => {
    if (!url) return
    const controller = new AbortController()
    setLoading(true); setError(null)
    fetch(url, { signal: controller.signal })
      .then(r => { if (!r.ok) throw new Error(r.status); return r.json() })
      .then(d => { setData(d); setLoading(false) })
      .catch(e => { if (e.name !== "AbortError") { setError(e.message); setLoading(false) } })
    return () => controller.abort()
  }, [url])

  return { data, loading, error }
}
// Usage:
const { data, loading, error } = useFetch(`/api/users/${userId}`)

// ── useLocalStorage — state that persists across refreshes ─
function useLocalStorage(key, initialValue) {
  const [value, setValue] = useState(() => {   // lazy initialiser
    try {
      const item = window.localStorage.getItem(key)
      return item ? JSON.parse(item) : initialValue
    } catch { return initialValue }
  })

  const setStoredValue = useCallback((newValue) => {
    try {
      const val = newValue instanceof Function ? newValue(value) : newValue
      setValue(val)
      window.localStorage.setItem(key, JSON.stringify(val))
    } catch {}
  }, [key, value])

  return [value, setStoredValue]
}

// ── useDebounce — delays a value update ───────────────────
function useDebounce(value, delay = 300) {
  const [debounced, setDebounced] = useState(value)
  useEffect(() => {
    const timer = setTimeout(() => setDebounced(value), delay)
    return () => clearTimeout(timer)
  }, [value, delay])
  return debounced
}
// Usage: only fetch after user stops typing 400ms
const debouncedQuery = useDebounce(query, 400)
useEffect(() => { fetchResults(debouncedQuery) }, [debouncedQuery])

// ── useOnClickOutside — close dropdowns on outside click ──
function useOnClickOutside(ref, handler) {
  useEffect(() => {
    const listener = (e) => {
      if (!ref.current || ref.current.contains(e.target)) return
      handler(e)
    }
    document.addEventListener("mousedown", listener)
    document.addEventListener("touchstart", listener)
    return () => {
      document.removeEventListener("mousedown", listener)
      document.removeEventListener("touchstart", listener)
    }
  }, [ref, handler])
}
// Usage:
const [open, setOpen] = useState(false)
const dropdownRef   = useRef(null)
useOnClickOutside(dropdownRef, () => setOpen(false))

// ── useWindowSize — reactive window dimensions ────────────
function useWindowSize() {
  const [size, setSize] = useState({
    width:  window.innerWidth,
    height: window.innerHeight
  })
  useEffect(() => {
    const fn = () => setSize({ width: window.innerWidth, height: window.innerHeight })
    window.addEventListener("resize", fn)
    return () => window.removeEventListener("resize", fn)
  }, [])
  return size
}

07 Interview questions + model answers 10 Q&As
Q1What is useRef and what are its two main use cases?▶
model answer
useRef returns a plain object { current: initialValue } that persists for the full component lifetime. Mutating .current does not trigger a re-render — this is the key difference from state.

Use case 1 — DOM access: pass the ref to a JSX element's ref prop and after mount ref.current holds the real DOM node. Use for programmatic focus, scrolling, measuring element dimensions, or integrating with third-party libraries that need DOM nodes.

Use case 2 — mutable values without re-render: storing interval/timeout IDs, WebSocket instances, previous state values, render counts, or any flag that changes but shouldn't trigger re-renders. If you used state for these, every mutation would cause an unnecessary render.
Depth signal: "I use the ref+useEffect pattern to always have the latest value in a callback without creating a stale closure — store the value in a ref inside useEffect, then read the ref in the callback with an empty dependency array."
Q2When should you use useMemo? What's the cost of over-using it?▶
model answer
useMemo caches a computed value and only recomputes when dependencies change. Use it when: the computation is genuinely expensive (sorting/filtering thousands of items, complex maths), or when you need a stable object/array reference to prevent React.memo children from re-rendering.

The cost of over-using it: every useMemo call has overhead — React runs the dependency comparison on every render. For cheap operations like simple arithmetic, string formatting, or filtering small arrays, the comparison overhead exceeds the savings. The code also becomes harder to read.

Rule: write the code without useMemo first, profile if there are performance issues, then add memoisation only where the profiler shows it helps.
Q3What is useCallback and why does it require React.memo to actually help?▶
model answer
useCallback returns a memoised function reference — the same function object across renders unless a dependency changes. Without it, every render creates a brand new function object (even if the function body is identical), because functions are objects and () => {} creates a new reference each time.

However, a stable function reference only matters if the child component skips rendering based on reference equality. A regular child component always re-renders when the parent renders, regardless of whether its props changed. React.memo is what makes a child skip rendering when props haven't changed — and without stable references, even React.memo can't help because the function prop appears different every time.

So the pattern is always: useCallback in the parent + React.memo on the child. One without the other is either overhead (useCallback alone) or no benefit (React.memo with unstable props).
Q4What is a stale closure in React and how do you fix it?▶
model answer
A stale closure happens when a function (usually in useCallback or useEffect) captures a state or prop value from when it was created, but that value has since changed. The function still "sees" the old value because closures capture variables by reference at the time of creation.

Three fixes: (1) Add the value to the dependency array — the function gets recreated when it changes, always seeing the latest value. Downside: may break memoisation. (2) Use the functional update form — setState(prev => prev + 1) always receives the current state, never stale. Best for state updates. (3) Use a ref — store the latest value in a ref inside a useEffect, then read the ref inside the callback. The callback can have an empty dep array but always sees current values via the ref.
The most common stale closure bug: useEffect(() => { const id = setInterval(() => console.log(count), 1000) }, []) — count is always 0 because it was captured at mount. Fix: use functional state update inside the interval, or list count in the deps.
Q5What is a custom hook? How is it different from a regular function?▶
model answer
A custom hook is a JavaScript function whose name starts with use and that calls React hooks internally. The use prefix is what tells React's linting tools to enforce the rules of hooks on it.

Differences from a regular function: it can call React hooks (useState, useEffect, etc.), it must follow the rules of hooks (only call at top level, only from components or other hooks), and each component that calls it gets its own independent state — custom hooks are not shared state singletons.

Custom hooks let you extract stateful logic from components and reuse it without adding wrapper components or prop drilling. A useWindowSize hook can be called by 10 components — each gets its own state, all updated by the same resize listener. The abstraction is perfect: zero component overhead, complete logic reuse.
Q6What is React.memo? When should you use it?▶
model answer
React.memo is a higher-order component that wraps a component and makes it skip re-rendering if its props haven't changed (shallow comparison). Without it, a child re-renders every time the parent re-renders, regardless of whether its props changed.

Use it when: a component renders frequently, its renders are expensive, and it receives the same props most of the time. A list item component that renders 100 times in a list is a good candidate — if the parent's other state changes, none of the items need to re-render.

Don't use it blindly — the shallow prop comparison itself has a cost. If a component always receives different props, React.memo adds overhead with no benefit. Profile first. Also remember: React.memo only works for props — if the component uses a context that changes, it still re-renders.
Q7What is the difference between useEffect and useLayoutEffect?▶
model answer
useEffect fires asynchronously after the browser has painted — the user sees the updated UI first, then the effect runs. This is non-blocking and fine for most effects (data fetching, subscriptions, logging).

useLayoutEffect fires synchronously after DOM mutations but before the browser paints. The user doesn't see anything until the effect completes. Use this when you need to read DOM measurements (offsetWidth, getBoundingClientRect) and then update something based on them — if you used useEffect for this, the user would see a brief flash of the element in the wrong position before the correction.

Classic use case: a tooltip that needs to be positioned relative to a trigger element. Read the trigger's position in useLayoutEffect, set the tooltip position, and the user never sees it in the wrong place. With useEffect, there's a visible flicker.
Q8Why can't you call a hook inside a condition or loop?▶
model answer
React tracks hooks by their call order — internally hooks are stored in an array indexed by the order they're called during render. On every render, hooks must be called in exactly the same order so React can correctly match each hook call to its stored state.

If you call a hook inside a condition, it might not be called on some renders. This shifts every subsequent hook's index by one — React assigns the wrong state to the wrong hook. The symptoms range from subtle bugs (wrong state values) to crashes.

The ESLint plugin eslint-plugin-react-hooks enforces this rule automatically. If you need a hook to conditionally do something, put the condition inside the hook: useEffect(() => { if (!enabled) return; ... }, [enabled]).
Q9How do you implement a previous value tracker with useRef?▶
model answer
The pattern uses a ref that's updated in useEffect after each render — so during any given render, the ref holds the value from the previous render:

function usePrevious(value) { const ref = useRef(); useEffect(() => { ref.current = value }); return ref.current }

Why it works: useEffect runs after the component renders and the DOM updates. So when the component renders with a new value, ref.current still holds the old value (updated to the new one only after this render completes). The returned ref.current is read during render, before useEffect fires — so it's one render behind.

This is useful for animations (knowing which direction to animate), comparison displays (price went up/down), and detecting what specifically changed in complex state.
Q10Walk me through building a useDebounce hook.▶
model answer
useDebounce delays updating a value until it has been stable for a set time. The implementation:

Store the debounced value in state initialised to the input value. In a useEffect with the input value and delay as dependencies: set a timeout that updates the debounced state after the delay, and return a cleanup that clears the timeout. This cleanup runs every time the input value changes — clearing the pending timer — which is the debounce behaviour itself.

function useDebounce(value, delay) { const [debounced, setDebounced] = useState(value); useEffect(() => { const t = setTimeout(() => setDebounced(value), delay); return () => clearTimeout(t) }, [value, delay]); return debounced }

Usage: store the raw input in state, pass it to useDebounce, use the debounced value in useEffect's deps for API calls. The API only fires after the user stops typing.
Common follow-up: "Why return the cleanup?" — without the cleanup, if value changes before the timeout fires, you'd have multiple pending timeouts racing. The cleanup ensures only the most recent one fires.
