Core Concepts

🏗️ Why Monorepo?

A monorepo holds multiple projects (web app, API, shared packages, docs) in one repository. Benefits: atomic commits across packages, shared tooling, easy code sharing, one PR for cross-cutting changes. Tradeoff: slower CI if not set up properly — Turborepo caching fixes this. At ShopCo scale, a monorepo with apps/web, apps/api, packages/ui, packages/db is ideal.

⚡ Turborepo Caching

Turborepo hashes each task's inputs (source files, env vars, dependencies). If inputs haven't changed since last run, it replays the cached output instantly — no re-running tests or builds. Remote caching (Vercel's cache server) means your CI machine shares the cache with your local machine. A cold build that takes 3 minutes becomes a 2-second cache hit on the next run.

🔄 CI/CD Philosophy

CI (Continuous Integration): every push runs lint, typecheck, tests automatically. Catches bugs before they reach main. CD (Continuous Deployment): every merge to main automatically deploys to production (or staging first). The goal: make deploying so cheap and fast that you do it dozens of times per day, making each deploy tiny and low-risk.

👁️ Preview Deploys

Every PR automatically gets a unique URL (e.g. shopco-pr-42.vercel.app). Reviewers click the link to test the actual running app — no local setup needed. Vercel connects to your PR via GitHub integration. For database-dependent features, use branch databases (Neon branching or PlanetScale) to give each preview its own isolated data.

🔐 Environment Strategy

Four environments: dev (local, hot reload, mock services), preview (per-PR, real infra, test data), staging (mirrors production, final QA), production (real users, real data). Each needs its own .env file, database, and Sentry project. Never use production credentials in dev — a bad migration can destroy real user data.

📝 ADRs (Architecture Decision Records)

Short documents that record why a technical decision was made: context, options considered, decision, and consequences. Stored as markdown in docs/adr/. Invaluable when a team member asks "why do we use X instead of Y?" six months later. The template: Title, Status, Context, Decision, Consequences.

name: CI

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  ci:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 2  # needed for Turborepo affected detection

      - uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'npm'

      - name: Install dependencies
        run: npm ci

      - name: Setup Turborepo remote cache
        uses: dtinth/setup-github-actions-caching-for-turbo@v1

      - name: Lint
        run: npx turbo lint

      - name: Typecheck
        run: npx turbo typecheck

      - name: Test
        run: npx turbo test
        env:
          DATABASE_URL: ${{ secrets.TEST_DATABASE_URL }}

      - name: Build
        run: npx turbo build
        env:
          TURBO_TOKEN:  ${{ secrets.TURBO_TOKEN }}
          TURBO_TEAM:   ${{ vars.TURBO_TEAM }}

      - name: Upload coverage
        uses: codecov/codecov-action@v4
        if: always()
        with:
          token: ${{ secrets.CODECOV_TOKEN }}
ADR-001: Use Turborepo for monorepo task orchestration
Status: Accepted | Date: 2024-01-15 | Author: @team
Context
ShopCo has grown to include a customer web app, admin dashboard, and several shared packages. Running lint/test/build across all packages sequentially takes 8+ minutes in CI. We need a solution that handles task dependencies and caches results.
Decision
Use Turborepo with remote caching via Vercel. Configure pipeline dependencies so shared packages build before apps. Enable remote cache sharing between CI and local dev machines.
Consequences
✓ CI time reduced from 8min to 45s on cache hits. ✓ Developers get fast feedback locally. ✗ Requires TURBO_TOKEN secret setup. ✗ Learning curve for new team members.
⚠ Environment variable pitfalls:
Never commit .env files. Use .env.example with placeholder values. In Next.js, prefix with NEXT_PUBLIC_ only for values safe to expose to the browser — everything else stays server-side. Rotate secrets immediately if they're accidentally committed — don't just delete the commit, the git history still has it.

Interview Q&A

1. When would you choose a monorepo over separate repositories?
Choose monorepo when: packages share code frequently, teams work across multiple packages simultaneously, you want atomic changes (one PR changes the API contract and updates the consuming app together), or you need consistent tooling/versions. Stick with polyrepo when: teams have very different tech stacks, strict access controls per project are required, or projects are genuinely independent products with no shared code. Most SaaS products with a web app, admin dashboard, and shared types are monorepo candidates.
2. How does Turborepo's caching work and what are its limits?
Turborepo creates a hash from: source files (via glob patterns in inputs), env variables listed in globalEnv or task env, and the task configuration itself. If the hash matches a previous run, it replays the cached stdout/stderr and restores output files. Limits: (1) cache is only valid if your task is deterministic (same inputs → same outputs), (2) you must declare all outputs for file restoration to work, (3) remote cache requires a server (Vercel's is free for hobby, paid for teams), (4) E2E tests that hit real services shouldn't be cached since external state changes.
3. What is an ADR and why is it important?
An Architecture Decision Record documents a significant technical decision: the context (why does this need a decision?), options considered, the decision made, and the consequences (good and bad). They're important because: (1) they prevent relitigating decisions — "why do we use X?" is answered by ADR-003; (2) they help new team members understand the codebase's reasoning, not just its structure; (3) they capture the tradeoffs, so if circumstances change (e.g. a vendor shuts down), you know what to reconsider; (4) they create accountability and thoughtfulness in architectural decisions.
4. What is the difference between CI and CD, and where does the gate go?
CI (Continuous Integration): every code push triggers automated checks (lint, test, build) that integrate code safely. The goal is fast feedback — know within minutes if a change breaks anything. CD (Continuous Deployment): automatically deploying passing code to environments. The gate between CI and CD is typically: (1) all CI checks pass, (2) code review approved (human gate), (3) optionally: staging environment verification. For ShopCo, every PR gets CI + preview deploy; merging to main triggers automatic production deploy. Some teams require a manual "promote to production" button for higher-risk deploys.
5. How do you manage secrets across dev, preview, staging, and production?
Each environment gets its own secret set, never shared. In development: .env.local (git-ignored, shared via secure channel like 1Password). In preview and production: Vercel environment variables per environment scope. In CI: GitHub Actions secrets, referenced as ${{ secrets.NAME }} — never hardcoded. Rotation: use separate API keys per environment so rotating production doesn't affect dev. For team onboarding: maintain a .env.example with all variable names and placeholder values (no real secrets) — commit this file.
6. What is feature-first folder structure and when do you use it?
Feature-first (also called "vertical slices"): group files by the feature they belong to — features/cart/ contains the cart's components, hooks, API calls, and types together. Layer-first: group by technical role — components/, hooks/, api/ at the top level. Feature-first wins for larger apps: related files change together, new developers can understand a feature by looking at one folder, and deleting a feature is clean (delete the folder). Layer-first is fine for small apps. In Next.js App Router, the route structure already nudges you toward feature-first with co-located page.tsx, loading.tsx, and error.tsx per route.
7. How would you set up database branching for preview deployments?
With Neon (serverless Postgres): each PR creates a database branch from main using the Neon API or GitHub Action — neon branches create --parent main --name pr-42. The preview deploy's DATABASE_URL points to the branch. Migrations run against the branch, not main. When the PR merges, the branch is deleted. This gives each preview a real database with production-like schema and test data, without risking main's data. Neon branching is fast (~1s) and copy-on-write, so branches don't duplicate data. The Vercel integration can automate this with the Neon + Vercel integration.
8. What shared packages would you create for a Next.js monorepo?
Essential packages: (1) @shopco/ui — shared React components, used by web and admin apps; (2) @shopco/db — Prisma client and schema, imported wherever DB access is needed; (3) @shopco/types — shared TypeScript types and Zod schemas, shared between frontend and backend; (4) @shopco/config — shared ESLint, TypeScript, and Tailwind configs to avoid duplication; (5) @shopco/utils — pure utility functions (formatting, validation) with no framework dependencies. Key rule: packages should have no circular dependencies and clear ownership.
9. How do you keep CI fast as the codebase grows?
Tactics: (1) Turborepo affected detection — only run tasks in packages that changed or depend on changed packages; (2) Remote caching — share build/test cache across all machines; (3) Parallelise — run lint, typecheck, and unit tests simultaneously; (4) Split slow tests — run unit tests on every commit, E2E only on PRs to main; (5) Matrix builds — GitHub Actions matrix strategy to split a large test suite across multiple runners; (6) Shallow clone — fetch-depth: 2 in checkout action; (7) Cache npm — use actions/setup-node with cache: 'npm' to avoid re-downloading packages.
10. What makes a good project README for a new team member?
A great README answers these questions in order: (1) What is this project? (1–2 sentences); (2) How do I run it locally? (exact commands, not "install dependencies"); (3) What are the key environment variables? (link to .env.example); (4) What's the folder structure and why? (brief explanation of key directories); (5) How do I run tests?; (6) How do I deploy?; (7) Where are the ADRs? (link to docs/adr/). Avoid: outdated info (worse than no docs), explaining what the code does instead of how to use it, and walls of text. Keep it short and link to deeper docs for details.
