01 The prop drilling problem — why context exists motivation
the problem
Passing props through components that don't use them
Prop drilling is when you pass a value through multiple layers of components just to get it to a deeply nested child. Every intermediate component receives and forwards a prop it doesn't actually use — only passing it down. As apps grow, this creates tight coupling, makes refactoring painful, and forces you to modify components that have no interest in the data.
what context solves
A component can subscribe to any ancestor's data
Context creates a named data channel in the component tree. A Provider anywhere above publishes a value. Any descendant component can directly subscribe using useContext — skipping all intermediate layers. No props needed at any level in between.
ideal use cases
Global or near-global data
Context shines for: auth state (current user, logged-in status), theme (dark/light mode, colour scheme), locale/language, feature flags, or any data that many components across the tree need simultaneously. If only a few nearby components need data, props are still cleaner.
jsxProp drilling — the before picture, showing why it's painful
// ── BEFORE: prop drilling — user passed through 4 layers ──
function App() {
  const [user] = useState({ name: "Alice", role: "admin" })
  return <Dashboard user={user} />   // passes user down...
}

function Dashboard({ user }) {           // receives user, doesn't use it
  return <Sidebar user={user} />    // just passes it further down
}

function Sidebar({ user }) {             // receives user, doesn't use it
  return <UserMenu user={user} />   // just passes it further down
}

function UserMenu({ user }) {            // FINALLY uses user
  return <p>Welcome, {user.name}</p>
}
// Problem: Dashboard and Sidebar MUST receive user even though they don't care
// Renaming or removing user means touching 4 files instead of 2

// ── AFTER: with Context — clean and direct ────────────────
const UserContext = createContext(null)

function App() {
  const [user] = useState({ name: "Alice", role: "admin" })
  return (
    <UserContext.Provider value={user}>
      <Dashboard />          {/* no user prop needed */}
    </UserContext.Provider>
  )
}

function Dashboard() { return <Sidebar /> }   // no user prop
function Sidebar()   { return <UserMenu /> }   // no user prop

function UserMenu() {
  const user = useContext(UserContext)   // reads directly from context
  return <p>Welcome, {user.name}</p>
}
02 createContext & useContext — the full API core API
Three parts every context needs
1. createContext(defaultValue)
Creates the context object. The defaultValue is used only when a component calls useContext without a Provider above it. Usually null or a sensible default.
2. <Context.Provider value={...}>
Wraps the subtree that should have access. Any component inside can read the value. When value changes, all consumers re-render.
3. useContext(Context)
Hook that reads the nearest matching Provider's value above in the tree. Re-renders whenever that value changes. Called inside a function component.
Custom hook wrapper
Always wrap useContext in a custom hook like useAuth(). It hides the context object, adds an error if used outside Provider, and gives a cleaner API.
jsxFull context pattern — createContext, Provider, useContext, and the custom hook wrapper
import { createContext, useContext, useState, useCallback } from "react"

// ── Step 1: Create the context ────────────────────────────
// null default → error thrown if used without Provider (good for dev)
const AuthContext = createContext(null)

// ── Step 2: Create the Provider component ─────────────────
// This lives in its own file: contexts/AuthContext.jsx
export function AuthProvider({ children }) {
  const [user, setUser] = useState(null)
  const [loading, setLoading] = useState(false)

  const login = useCallback(async (email, password) => {
    setLoading(true)
    try {
      const data = await authAPI.login({ email, password })
      setUser(data.user)
      localStorage.setItem("token", data.token)
    } finally {
      setLoading(false)
    }
  }, [])

  const logout = useCallback(() => {
    setUser(null)
    localStorage.removeItem("token")
  }, [])

  // What every consumer gets access to
  const value = { user, loading, login, logout, isAuth: !!user }

  return (
    <AuthContext.Provider value={value}>
      {children}
    </AuthContext.Provider>
  )
}

// ── Step 3: Custom hook — the clean consumer API ──────────
export function useAuth() {
  const ctx = useContext(AuthContext)
  if (ctx === null) {
    throw new Error("useAuth must be used inside <AuthProvider>")
  }
  return ctx
}

// ── Step 4: Place the Provider near the root ──────────────
// main.jsx
createRoot(document.getElementById("root")).render(
  <BrowserRouter>
    <AuthProvider>        {/* auth available everywhere */}
      <App />
    </AuthProvider>
  </BrowserRouter>
)

// ── Step 5: Any component reads with the custom hook ──────
function Navbar() {
  const { user, logout, isAuth } = useAuth()
  return (
    <nav>
      {isAuth
        ? <><span>{user.name}</span> <button onClick={logout}>Logout</button></>
        : <Link to="/login">Login</Link>
      }
    </nav>
  )
}

function LoginForm() {
  const { login, loading } = useAuth()   // same hook, different fields
  // ...
}
03 Provider patterns — theme context & multiple contexts patterns
jsxTheme context — toggle, persist, system preference detection
// ── contexts/ThemeContext.jsx ─────────────────────────────
const ThemeContext = createContext(null)

export function ThemeProvider({ children }) {
  const [theme, setTheme] = useState(() => {
    // Lazy init: check localStorage first, then system preference
    const stored = localStorage.getItem("theme")
    if (stored) return stored
    return window.matchMedia("(prefers-color-scheme: dark)").matches
      ? "dark" : "light"
  })

  const toggleTheme = useCallback(() => {
    setTheme(prev => {
      const next = prev === "dark" ? "light" : "dark"
      localStorage.setItem("theme", next)
      return next
    })
  }, [])

  // Apply theme class to document root
  useEffect(() => {
    document.documentElement.className = theme
  }, [theme])

  return (
    <ThemeContext.Provider value={{ theme, toggleTheme, isDark: theme === "dark" }}>
      {children}
    </ThemeContext.Provider>
  )
}

export const useTheme = () => {
  const ctx = useContext(ThemeContext)
  if (!ctx) throw new Error("useTheme must be used inside ThemeProvider")
  return ctx
}

// ── Composing multiple providers ─────────────────────────
// main.jsx — stack providers from outermost (most global) to innermost
createRoot(document.getElementById("root")).render(
  <BrowserRouter>
    <AuthProvider>
      <ThemeProvider>
        <NotificationProvider>
          <App />
        </NotificationProvider>
      </ThemeProvider>
    </AuthProvider>
  </BrowserRouter>
)

// ── Or compose them cleanly with a single AppProviders wrapper ─
function AppProviders({ children }) {
  return (
    <AuthProvider>
      <ThemeProvider>
        <NotificationProvider>
          {children}
        </NotificationProvider>
      </ThemeProvider>
    </AuthProvider>
  )
}
// <AppProviders><App /></AppProviders>
04 Context & performance — the re-render problem critical
the problem
Every consumer re-renders when value changes
When a Provider's value prop changes, every component that calls useContext with that context re-renders — even if the part of the value it uses didn't change. If you put your entire app state in one context, a single state update causes the whole tree to re-render.
fix 1 — split contexts
Separate frequently-changing from stable data
Split one big context into multiple smaller ones. Put stable data (user profile, theme) in one context. Put frequently-changing data (notification count, loading states) in another. Components only subscribe to what they need and only re-render when that specific context changes.
fix 2 — stable references
useMemo the context value object
If the Provider's value is an object created inline — value={{ user, login, logout }} — it's a new object every render, which triggers all consumers to re-render even when nothing changed. Wrap it in useMemo with the actual dependencies to produce a stable reference.
jsxThe re-render problem, splitting contexts, and memoising the value
// ── Problem: inline object = new reference every render ───
function BadProvider({ children }) {
  const [user,  setUser]  = useState(null)
  const [count, setCount] = useState(0)

  // BAD: new object created every render
  // Updating count re-renders ALL consumers even though user didn't change
  return (
    <AppContext.Provider value={{ user, count, setUser, setCount }}>
      {children}
    </AppContext.Provider>
  )
}

// ── Fix 1: Separate contexts for separate concerns ────────
const UserContext  = createContext(null)   // rarely changes
const CountContext = createContext(null)   // changes often

function GoodProvider({ children }) {
  const [user,  setUser]  = useState(null)
  const [count, setCount] = useState(0)

  return (
    <UserContext.Provider value={{ user, setUser }}>
      <CountContext.Provider value={{ count, setCount }}>
        {children}
      </CountContext.Provider>
    </UserContext.Provider>
  )
  // Now: count change only re-renders CountContext consumers
  // UserContext consumers are unaffected
}

// ── Fix 2: useMemo on context value ─────────────────────
function AuthProvider({ children }) {
  const [user, setUser] = useState(null)

  const login  = useCallback(async (creds) => { /* ... */ }, [])
  const logout = useCallback(() => setUser(null), [])

  // Stable reference — only changes when user changes
  const value = useMemo(
    () => ({ user, login, logout, isAuth: !!user }),
    [user, login, logout]
  )

  return (
    <AuthContext.Provider value={value}>
      {children}
    </AuthContext.Provider>
  )
}

// ── Split state and dispatch — the most powerful pattern ──
// State consumers and action dispatchers can now update independently
const StateContext    = createContext(null)
const DispatchContext = createContext(null)

function StoreProvider({ children }) {
  const [state, dispatch] = useReducer(reducer, initialState)

  return (
    <StateContext.Provider value={state}>
      <DispatchContext.Provider value={dispatch}>
        {children}
      </DispatchContext.Provider>
    </StateContext.Provider>
  )
  // dispatch is stable (never changes) — components that only
  // dispatch actions NEVER re-render due to state changes
}
05 Context + useReducer — a full global store global state
jsxComplete shopping cart global store — context + reducer + custom hooks
// ── store/CartContext.jsx — complete cart store ────────────
const CartStateContext    = createContext(null)
const CartDispatchContext = createContext(null)

const initialState = { items: [], isOpen: false }

function cartReducer(state, action) {
  switch (action.type) {
    case "ADD_ITEM": {
      const exists = state.items.find(i => i.id === action.payload.id)
      return {
        ...state,
        items: exists
          ? state.items.map(i => i.id === action.payload.id
              ? { ...i, qty: i.qty + 1 }
              : i)
          : [...state.items, { ...action.payload, qty: 1 }]
      }
    }
    case "REMOVE_ITEM":
      return { ...state, items: state.items.filter(i => i.id !== action.payload) }
    case "UPDATE_QTY":
      return {
        ...state,
        items: action.payload.qty <= 0
          ? state.items.filter(i => i.id !== action.payload.id)
          : state.items.map(i => i.id === action.payload.id
              ? { ...i, qty: action.payload.qty } : i)
      }
    case "CLEAR":     return { ...state, items: [] }
    case "OPEN_CART":  return { ...state, isOpen: true  }
    case "CLOSE_CART": return { ...state, isOpen: false }
    default: return state
  }
}

export function CartProvider({ children }) {
  const [state, dispatch] = useReducer(cartReducer, initialState)

  return (
    <CartStateContext.Provider value={state}>
      <CartDispatchContext.Provider value={dispatch}>
        {children}
      </CartDispatchContext.Provider>
    </CartStateContext.Provider>
  )
}

// ── Custom hooks with action creators ─────────────────────
export function useCartState() {
  const state = useContext(CartStateContext)
  if (!state) throw new Error("useCartState must be used inside CartProvider")

  // Derived state
  const itemCount = state.items.reduce((s, i) => s + i.qty, 0)
  const total     = state.items.reduce((s, i) => s + i.price * i.qty, 0)
  return { ...state, itemCount, total }
}

export function useCartActions() {
  const dispatch = useContext(CartDispatchContext)
  if (!dispatch) throw new Error("useCartActions must be used inside CartProvider")

  return {
    addItem:    (item)       => dispatch({ type: "ADD_ITEM",   payload: item }),
    removeItem: (id)         => dispatch({ type: "REMOVE_ITEM",payload: id   }),
    updateQty:  (id, qty)    => dispatch({ type: "UPDATE_QTY", payload: { id, qty } }),
    clearCart:  ()            => dispatch({ type: "CLEAR"       }),
    openCart:   ()            => dispatch({ type: "OPEN_CART"   }),
    closeCart:  ()            => dispatch({ type: "CLOSE_CART"  }),
  }
}

// ── Consuming the store in any component ──────────────────
function CartIcon() {
  const { itemCount, isOpen } = useCartState()    // re-renders on state changes
  const { openCart }           = useCartActions()   // NEVER re-renders (dispatch is stable)
  return <button onClick={openCart}>Cart ({itemCount})</button>
}

function ProductCard({ product }) {
  const { addItem } = useCartActions()   // only needs dispatch — zero re-renders
  return <button onClick={() => addItem(product)}>Add to cart</button>
}
06 When to use context — and when not to decision guide
Context vs props vs external library — choosing the right tool
SituationBest toolWhy
Data needed by 2–3 nearby components Props + lifting state Simpler, explicit, easier to trace. Context overhead not justified.
Deeply nested component needs data from far above Context Avoids prop drilling through multiple uninvolved layers.
Auth state (current user, token) Context Needed by navbar, protected routes, API calls — truly global.
Theme (dark/light mode) Context Every component in the app may use it.
Server data (products, users from API) React Query / SWR They handle caching, revalidation, background refresh — context doesn't.
Complex client state with many actors Zustand / Jotai / Redux Fine-grained subscriptions — components re-render only for the slice they use.
Form state Local useState or React Hook Form Form state is local to the form — doesn't need to be global.
URL-based state (filters, pagination) useSearchParams Shareable, bookmarkable, free persistence via URL.
THE DECISION FLOWCHART
1. Can I solve it with local state + lifting up? → Do that first. Always.
2. Is it truly needed by many components far apart in the tree? → Consider context.
3. Does it change very frequently (every keystroke)? → Context will cause too many re-renders. Use local state or a library with selectors.
4. Is it server data that needs caching/revalidation? → Use React Query or SWR, not context.
5. Is it large, complex, shared client state? → Consider Zustand or Redux Toolkit.
6. Is it auth, theme, or locale? → Context is the right answer.

08 Interview questions + model answers 10 Q&As
Q1What is prop drilling and how does Context solve it?▶
model answer
Prop drilling is passing a value through multiple component layers just to get it to a deeply nested descendant — every intermediate component receives and forwards a prop it doesn't use. It creates tight coupling, makes components harder to refactor, and forces you to modify components that have no actual interest in the data.

Context solves this by creating a named data channel in the component tree. A Provider anywhere above publishes a value; any descendant can subscribe directly with useContext, bypassing all intermediate layers. The intermediate components don't need to know the data exists at all.

The cost is reduced explicitness — it's harder to trace where a value comes from when it's in context vs a prop. This is why Context should be used selectively, not as a default replacement for all prop passing.
Strong follow-up: "I found prop drilling usually signals a component hierarchy problem — if many layers need the same data, those layers might be too deeply nested. Before reaching for Context, I ask whether the component tree can be flattened or whether component composition (children prop) would solve it more simply."
Q2What are the three parts of the Context API?▶
model answer
createContext(defaultValue) — creates the context object. The default value is only used when a component consumes the context but there's no Provider above it in the tree. Good practice: set it to null so you can detect (and throw an error) when a consumer is accidentally used outside its Provider.

Context.Provider value={...} — a component that wraps a subtree and provides the value. Every component inside can read it. When value changes, all consumers re-render.

useContext(Context) — the hook that reads the nearest matching Provider's current value. Re-renders whenever that value changes. Should be wrapped in a custom hook (like useAuth) that adds error checking and hides the raw context object from consumers.
Q3Why can context cause performance problems? How do you fix them?▶
model answer
When a Provider's value changes, every component calling useContext with that context re-renders — even if the specific data it cares about didn't change. If you put your entire app state in one context, a single counter increment re-renders every consumer in the tree.

Fix 1 — Split contexts: separate frequently-changing data (notification count, loading states) from stable data (user profile, theme). Components only subscribe to the context they need, so a cart update doesn't re-render the navbar.

Fix 2 — Memoize the value object: an inline object value={{ user, login }} creates a new reference every render, triggering all consumers even when nothing changed. Use useMemo to stabilise the reference. Also useCallback for functions in the value.

Fix 3 — Split state and dispatch: put state and dispatch in separate contexts. Components that only dispatch actions (buttons, forms) never re-render from state changes because dispatch is always the same stable reference.
Q4When should you NOT use Context?▶
model answer
Context is often overused. Don't use it for: data that only 2–3 nearby components need (props are cleaner and more explicit), form state (local to the form — useState or React Hook Form), URL-based state like filters and pagination (use useSearchParams instead, it's shareable), server data (use React Query or SWR — they handle caching, background refetch, stale-while-revalidate).

Context is best for: auth (current user across many components), theme, locale, and app-wide configuration that changes rarely. If your context changes on every keystroke, you're using the wrong tool and will hit performance issues.

For complex global client state, also consider Zustand — it provides fine-grained subscriptions where components only re-render for the exact slice they use, which context can't do without manual splitting.
Q5What is the best practice for consuming context — and why?▶
model answer
Always wrap useContext in a custom hook — for example useAuth() instead of calling useContext(AuthContext) directly in every component. This has three benefits:

1. Error guard: the custom hook can throw a descriptive error if called outside the Provider, giving a clear message instead of a confusing "cannot read property of null".

2. Encapsulation: consumers import useAuth, not the raw context object. The context object becomes an implementation detail — you can refactor the internals without changing every consumer.

3. Additional derived state: the hook can compute derived values (isAdmin: user?.role === "admin") that all consumers get automatically, without duplicating that logic everywhere.
Q6How does combining Context with useReducer compare to Redux?▶
model answer
Context + useReducer gives you the same core Redux pattern — a single state object updated through named actions via a pure reducer — without any external dependencies. It works well for medium-complexity apps.

Redux (particularly Redux Toolkit) adds on top of this: DevTools with time-travel debugging, middleware (for async thunks, logging), and crucially — fine-grained subscriptions via useSelector. With useSelector, a component only re-renders when its specific selected slice changes. With Context, you must manually split contexts to achieve the same effect.

For most apps that don't need Redux DevTools or middleware, Context + useReducer is sufficient. Once you have 5+ contexts or start noticing significant re-render issues, Zustand or Redux Toolkit is worth the addition.
Q7What does the defaultValue in createContext() do?▶
model answer
The default value is used only when a component calls useContext without a matching Provider anywhere above it in the tree. It's not the initial value the Provider uses — it's the fallback for when there's no Provider at all.

Best practice: set it to null (not a sensible default), then in your custom hook check for null and throw an error: if (!ctx) throw new Error("useAuth must be inside AuthProvider"). This immediately surfaces the mistake when a developer uses the hook outside its Provider, instead of getting silent wrong values or a confusing "cannot read property" error later.

Using a non-null default might seem helpful for testing, but it hides the bug. A null default + error check makes the problem impossible to miss.
Q8How do you test a component that uses context?▶
model answer
There are two main approaches. The first is to render the component wrapped in the real Provider with controlled test data — straightforward and tests the integration:

render(<AuthProvider><ComponentUnderTest /></AuthProvider>)

The second is to create a test wrapper that provides specific mock values — useful for testing edge cases or error states without going through the full auth flow:

const mockAuth = { user: { name: "Test" }, login: jest.fn(), logout: jest.fn() };
render(<AuthContext.Provider value={mockAuth}><ComponentUnderTest /></AuthContext.Provider>)

React Testing Library recommends creating a custom renderWithProviders helper that wraps the component in all needed providers — this avoids repeating the wrapper setup in every test file.
Q9Can a component consume multiple contexts?▶
model answer
Yes — a component can call useContext (or custom hooks wrapping it) as many times as needed, consuming multiple contexts. Each useContext call subscribes independently to its context — the component re-renders when any of the subscribed contexts change.

For example, a component might call both useAuth() and useTheme(). It re-renders when the auth state changes (user logs in/out) or when the theme changes (dark/light toggle). The subscriptions are separate — there's no concept of combining or batching them.

This is one more reason to split contexts carefully — a component that consumes both auth and a rapidly-changing notification count will re-render very frequently. Keep fast-changing data in a separate context from stable data.
Q10What is component composition and how can it reduce prop drilling without context?▶
model answer
Component composition uses the children prop or slot props to pass already-rendered components rather than passing data down for children to render themselves. This sidesteps prop drilling because the consuming component is rendered at the level that has access to the data.

Instead of: <Layout user={user}><Sidebar user={user} /></Layout>
Use: <Layout sidebar={<Sidebar user={user} />}> ... </Layout>

Here Layout never sees user — it just renders whatever is passed as sidebar. The user is bound at the calling site where it's available. This technique solves a surprising number of "prop drilling" problems without adding any context overhead, and keeps components more reusable and decoupled.

React's official docs suggest trying composition before context for most prop drilling situations.
