Core Concepts

🌐 REST in Next.js App Router

Route handlers live in app/api/[route]/route.ts. Export named functions GET, POST, PATCH, DELETE. Use Request and Response Web APIs — no Express. Parse body with req.json(), validate with Zod, then query Prisma. Always return Response.json(data, { status: 200 }). REST is best for public APIs consumed by third parties or mobile apps.

🔗 What is tRPC?

tRPC gives you RPC-style API calls with full TypeScript safety — no REST conventions, no code generation, no schema files. Define procedures (queries + mutations) in server routers, call them from React with trpc.products.list.useQuery(). TypeScript infers the input and output types automatically. If you rename a field server-side, your editor highlights the client-side usage as broken. The entire stack is one TypeScript project.

✅ Zod Everywhere

Zod validates data at runtime while TypeScript checks it at compile time. Use Zod for: REST request bodies (z.object({...}).parse(await req.json())), tRPC procedure inputs (input: z.object({...})), environment variables (Day 33), and API response shapes. When Zod fails, throw a 400 with the formatted errors. Never trust user input that hasn't been parsed by Zod.

🚨 Structured Error Responses

Every error response should be a consistent JSON shape: { error: string, code: string, details?: any }. Map error types to HTTP status codes: validation → 400, unauthenticated → 401, forbidden → 403, not found → 404, conflict → 409, server error → 500. In tRPC, use new TRPCError({ code: 'NOT_FOUND', message: '...' }). Log 5xx errors to Sentry, not 4xx (those are user errors).

📌 API Versioning

Version APIs from day one even if you don't need it yet. URL versioning (/api/v1/products) is most visible and easy to route. When making breaking changes: create /api/v2/, run both versions concurrently, set a sunset date for v1, communicate via Sunset and Deprecation headers. For internal tRPC, versioning is less critical since you own all clients.

🚦 Rate Limiting

Protect your API from abuse and control costs. Use Upstash Redis with a sliding window algorithm. In Next.js middleware, check before the route handler runs. Limits by tier: anonymous → 20 req/min, authenticated → 100 req/min, premium → 500 req/min. Return 429 Too Many Requests with Retry-After header. Log rate limit hits to detect scraping or DDoS patterns.

🌐 Use REST when...
  • Third-party clients consume your API
  • Mobile apps need a stable contract
  • Public developer API with docs
  • Webhooks (always REST)
  • File uploads (multipart/form-data)
  • CDN caching on GET endpoints
  • OpenAPI/Swagger documentation needed
🔗 Use tRPC when...
  • TypeScript client you control (same repo)
  • Admin dashboard, internal tools
  • Rapid iteration — refactor safely
  • Complex nested queries with relations
  • Real-time subscriptions (tRPC + WS)
  • Shared input validation client + server
  • Auto-generated React Query hooks

app/api/v1/products/route.ts — GET + POST with full validation
import { requireRole, requireAuth } from '@/lib/auth'
import { prisma } from '@/lib/prisma'
import { z } from 'zod'
import { apiError, apiSuccess } from '@/lib/api-response'

const ProductQuerySchema = z.object({
  cursor:     z.string().optional(),
  limit:      z.coerce.number().min(1).max(50).default(20),
  categoryId: z.string().optional(),
  search:     z.string().max(100).optional(),
})

const CreateProductSchema = z.object({
  name:        z.string().min(2).max(120),
  description: z.string().min(10),
  basePrice:   z.number().positive().multipleOf(0.01),
  categoryId:  z.string().cuid(),
})

export async function GET(req: Request) {
  try {
    const url = new URL(req.url)
    const params = ProductQuerySchema.parse(
      Object.fromEntries(url.searchParams)
    )
    const { data, nextCursor, hasNextPage } = await getProducts(params)
    return apiSuccess({ data, nextCursor, hasNextPage })
  } catch (err) {
    return handleApiError(err)
  }
}

export async function POST(req: Request) {
  try {
    await requireRole('admin')
    const body = CreateProductSchema.parse(await req.json())
    const slug = body.name.toLowerCase().replace(/[^a-z0-9]+/g, '-')
    const product = await prisma.product.create({
      data: { ...body, slug, basePrice: body.basePrice.toString() }
    })
    return apiSuccess(product, 201)
  } catch (err) {
    return handleApiError(err)
  }
}
lib/api-response.ts — consistent response helpers
import { ZodError } from 'zod'

export function apiSuccess(data: unknown, status = 200) {
  return Response.json({ success: true, data }, { status })
}

export function apiError(message: string, status: number, details?: unknown) {
  return Response.json({ success: false, error: message, details }, { status })
}

export function handleApiError(err: unknown) {
  if (err instanceof ZodError)
    return apiError('Validation failed', 400, err.flatten().fieldErrors)
  if (err instanceof Error) {
    if (err.message === 'Unauthorized') return apiError('Unauthorized', 401)
    if (err.message.startsWith('Forbidden'))   return apiError('Forbidden', 403)
    if (err.message === 'Not found')    return apiError('Not found', 404)
  }
  console.error('Unhandled API error:', err)
  return apiError('Internal server error', 500)
}

tRPC Setup

server/trpc.ts — tRPC initialisation with context and middleware
import { initTRPC, TRPCError } from '@trpc/server'
import { auth } from '@clerk/nextjs/server'
import { ZodError } from 'zod'

// Context: available in every procedure
export async function createTRPCContext() {
  const { userId, sessionClaims } = await auth()
  return {
    userId,
    role: sessionClaims?.metadata?.role ?? 'customer'
  }
}
type Context = Awaited<ReturnType<typeof createTRPCContext>>

const t = initTRPC.context<Context>().create({
  errorFormatter({ shape, error }) {
    return {
      ...shape,
      data: {
        ...shape.data,
        zodError: error.cause instanceof ZodError
          ? error.cause.flatten() : null,
      },
    }
  },
})

export const router     = t.router
export const publicProc = t.procedure

// isAuthed middleware — requires login
const isAuthed = t.middleware(({ ctx, next }) => {
  if (!ctx.userId) throw new TRPCError({ code: 'UNAUTHORIZED' })
  return next({ ctx: { ...ctx, userId: ctx.userId } })
})

// isAdmin middleware — requires admin role
const HIERARCHY = ['customer','staff','admin','super_admin']
const isAdmin = t.middleware(({ ctx, next }) => {
  if (HIERARCHY.indexOf(ctx.role) < HIERARCHY.indexOf('admin'))
    throw new TRPCError({ code: 'FORBIDDEN' })
  return next({ ctx })
})

export const authedProc = t.procedure.use(isAuthed)
export const adminProc  = t.procedure.use(isAuthed).use(isAdmin)
server/routers/products.ts — tRPC product router
import { router, publicProc, adminProc } from '@/server/trpc'
import { prisma } from '@/lib/prisma'
import { z } from 'zod'
import { TRPCError } from '@trpc/server'

export const productsRouter = router({
  // Public: list products with cursor pagination
  list: publicProc
    .input(z.object({
      cursor:     z.string().optional(),
      limit:      z.number().min(1).max(50).default(20),
      categoryId: z.string().optional(),
    }))
    .query(async ({ input }) => {
      return getProducts(input)
    }),

  // Public: get single product by slug
  bySlug: publicProc
    .input(z.object({ slug: z.string() }))
    .query(async ({ input }) => {
      const product = await prisma.product.findFirst({
        where: { slug: input.slug, deletedAt: null },
        include: { variants: true, reviews: { take: 10 } }
      })
      if (!product) throw new TRPCError({ code: 'NOT_FOUND' })
      return product
    }),

  // Admin: create product
  create: adminProc
    .input(z.object({
      name:        z.string().min(2),
      description: z.string().min(10),
      basePrice:   z.number().positive(),
      categoryId:  z.string(),
    }))
    .mutation(async ({ input, ctx }) => {
      const slug = input.name.toLowerCase().replace(/[^a-z0-9]+/g, '-')
      return prisma.product.create({
        data: { ...input, slug, basePrice: input.basePrice.toString() }
      })
    }),

  // Admin: delete (soft)
  delete: adminProc
    .input(z.object({ id: z.string() }))
    .mutation(async ({ input }) => {
      return prisma.product.update({
        where: { id: input.id },
        data: { deletedAt: new Date() }
      })
    }),
})

export function ProductList() {
  // Fully typed — TypeScript knows the return shape!
  const { data, isLoading, fetchNextPage } =
    trpc.products.list.useInfiniteQuery(
      { limit: 20 },
      { getNextPageParam: (last) => last.nextCursor }
    )

  const createProduct = trpc.products.create.useMutation()

  return (
    <div>
      {isLoading && <p>Loading...</p>}
      {data?.pages.flatMap(p => p.data).map(product => (
        <div key={product.id}>
          <h3>{product.name}</h3>  // ← TypeScript knows product.name exists
        </div>
      ))}
      <button onClick={() => fetchNextPage()}>Load more</button>
    </div>
  )
}

Interview Q&A

1. What is tRPC and how does it achieve end-to-end type safety?
tRPC is a TypeScript RPC framework — you define server-side procedures (queries and mutations) in routers, and call them from the client using a typed proxy. There's no code generation, no schema files, no REST conventions. TypeScript infers the procedure's input and output types at compile time. When you call trpc.products.list.useQuery(), TypeScript knows exactly what fields data contains. If you rename a server-side field, the client immediately shows a type error. This is only possible because both client and server share the same TypeScript project (monorepo).
2. When would you choose REST over tRPC for a new feature?
Choose REST when: third-party clients need to consume the API (tRPC clients must be TypeScript); you need CDN caching on GET endpoints (REST uses standard HTTP, tRPC usually uses POST); you're building a public developer API with OpenAPI docs; you need file uploads (multipart/form-data); or you're building webhooks (always REST). Choose tRPC when: the client is a TypeScript app you control in the same repo; you want React Query hooks auto-generated; you're building internal tools, admin dashboards, or anywhere rapid iteration and refactoring matters most.
3. How does Zod's parse differ from safeParse?
schema.parse(data) throws a ZodError on invalid input — use this in try/catch and convert to a 400 response. schema.safeParse(data) never throws — returns { success: true, data } or { success: false, error: ZodError }. Use safeParse when you want to handle errors inline without try/catch: const result = schema.safeParse(body); if (!result.success) return apiError(...). In tRPC, input validation via .input(schema) uses parse internally and converts ZodErrors to TRPCError({ code: 'BAD_REQUEST' }) automatically.
4. What is the sliding window rate limiting algorithm?
Sliding window tracks the timestamps of each request within a rolling time window. When a new request arrives, remove all timestamps older than windowStart = now - windowMs, then check if the remaining count is below the limit. If yes, add the new timestamp and allow; if no, return 429 with a Retry-After header. Compared to fixed windows (reset every minute), sliding window prevents burst attacks at the window boundary. Upstash Redis implements this efficiently using sorted sets. The key is per-user or per-IP to prevent one user from blocking others.
5. How should you version an API and handle breaking changes?
URL versioning (/api/v1/) is the most practical: easy to route, visible in logs, easy for clients to target. When introducing breaking changes: (1) create /api/v2/ with the new contract; (2) run v1 and v2 concurrently; (3) add Deprecation: Tue, 01 Jan 2025 00:00:00 GMT and Sunset: Mon, 01 Jul 2025 00:00:00 GMT headers to v1 responses; (4) communicate the sunset to clients; (5) remove v1 after the deadline. For tRPC (internal), versioning is less critical — just update the procedure and fix all clients simultaneously (TypeScript shows you everywhere that breaks).
6. What HTTP status codes should every API developer know?
2xx success: 200 (OK), 201 (Created), 204 (No Content — DELETE). 3xx redirect: 301 (permanent), 302 (temporary), 304 (Not Modified — cached). 4xx client errors: 400 (Bad Request — validation failed), 401 (Unauthorized — not authenticated), 403 (Forbidden — authenticated but not permitted), 404 (Not Found), 409 (Conflict — duplicate), 422 (Unprocessable Entity — semantic validation), 429 (Too Many Requests — rate limit). 5xx server errors: 500 (Internal Server Error), 502 (Bad Gateway), 503 (Service Unavailable). Key distinction: 401 means "please authenticate", 403 means "you are authenticated but not allowed".
7. How do you handle N+1 query problems in tRPC?
N+1 happens when you fetch N items then make N additional queries for each item's related data. Solutions: (1) Prisma include — include: { variants: true, reviews: { take: 5 } } does a JOIN in one query; (2) DataLoader — batches multiple individual lookups into one query; (3) Select carefully — don't include relations you don't need (use select instead of include for projections). In tRPC, the procedure is the right place to optimise: write the Prisma query that fetches exactly what the client needs, including all relations, in a single DB round-trip.
8. What should you never expose in an API response?
Fields to always strip: (1) passwords (even hashed — no reason for clients to see this); (2) internal IDs or foreign keys not needed by the client; (3) deletedAt timestamps — soft-deleted records shouldn't be visible; (4) Prisma internal fields, database-specific metadata; (5) server-side secrets or API keys; (6) other users' personal data (PII) — never return full user objects in order lists; (7) full stack traces in production errors — only return an error code and message. Build explicit serialiser/DTO functions that whitelist fields rather than blacklisting — it's safer to add fields than to accidentally expose them.
9. How do tRPC subscriptions work for real-time features?
tRPC supports subscriptions via WebSockets. Define a subscription procedure using publicProc.subscription(() => observable(...)). The client subscribes with trpc.orders.onStatusChange.useSubscription({ orderId }, { onData: (data) => ... }). The server pushes data whenever it emits to the observable. For ShopCo: subscribe to order status changes, live inventory updates, or admin notifications. Requires a WebSocket adapter in Next.js (use a standalone Express server or a custom WS server alongside Next). For simpler real-time needs, Server-Sent Events (SSE) via Vercel's streaming may be sufficient — Day 37 covers this in detail.
10. What is the difference between a query and a mutation in tRPC?
Queries (.query()): read operations, use HTTP GET under the hood, can be cached by React Query, idempotent (calling multiple times gives same result). Mutations (.mutation()): write operations, use HTTP POST, not cached, may have side effects (create/update/delete data, send emails, charge payments). This mirrors REST's GET vs POST/PATCH/DELETE. In React: use useQuery for queries (auto-fetches on mount, refetches on invalidation) and useMutation for mutations (manually triggered with mutate()). Always invalidate related queries after a mutation: utils.products.list.invalidate() to refresh the cache.
