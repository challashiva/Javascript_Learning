01 Why test — the only reasons that matter motivation
confidence to refactor
Change code without fear
The real value of tests isn't catching bugs when you write code — it's letting you change existing code without breaking it silently. Moving a calculation to a utility function, upgrading a dependency, extracting a hook — with tests you know immediately if something breaks. Without tests, every refactor is a gamble.
specification
Tests describe what the code should do
A test suite is executable documentation. it("displays error when stock is insufficient") tells the next developer (or future you) exactly what the behaviour is without reading the implementation. When a test fails, you know what broke, not just that something broke.
CI safety net
Block broken code from reaching users
Tests in CI catch regressions before they deploy. A developer changes an unrelated file, accidentally breaks the cart calculation — tests catch it in 30 seconds instead of a customer reporting it 2 days later. This is worth the time investment for any production application.
the test pyramid
Many unit, some integration, few E2E
Unit tests (utility functions, hooks): fast, cheap, many. Integration tests (components with data): medium speed, medium cost, some. E2E tests (full user journeys): slow, expensive, few. ShopCo target: ~50 unit tests (utilities, server actions), ~20 component tests (key UI), ~5 E2E tests (checkout, auth, search).

  })
})

03 React Testing Library — test behaviour, not implementation components
RTL queries — getBy vs queryBy vs findBy
getBy* — element must exist
Throws immediately if not found. Use when: you expect the element to be present. getByRole("button", { name:"Add to cart" }). Most common for elements that should always be there.
queryBy* — element may not exist
Returns null if not found (no throw). Use when: you're asserting an element is NOT present. expect(queryByRole("alert")).not.toBeInTheDocument().
findBy* — element appears async
Returns a promise, waits up to 1000ms. Use after async actions (API calls, state updates). await findByText("Order placed!"). Built-in waitFor.
query priority order
ByRole (most semantic) → ByLabelText → ByPlaceholderText → ByText → ByDisplayValue → ByAltText → ByTitle → ByTestId (last resort). Prefer role queries — they test accessibility too.
tsxRTL + userEvent — testing AddToCart, form validation, async state
import { render, screen, waitFor } from "@testing-library/react"
import userEvent                    from "@testing-library/user-event"
import { describe, it, expect, vi } from "vitest"
import { AddToCart }               from "./AddToCart"

describe("AddToCart", () => {
  it("shows Add to cart button initially", () => {
    render(<AddToCart productId="p1" stock={5} />)
    // getByRole is preferred — tests accessibility role too
    expect(screen.getByRole("button", { name: /add to cart/i }))
      .toBeInTheDocument()
  })

  it("disables button when out of stock", () => {
    render(<AddToCart productId="p1" stock={0} />)
    expect(screen.getByRole("button")).toBeDisabled()
    expect(screen.getByText(/out of stock/i)).toBeInTheDocument()
  })

  it("calls addItem and shows Added! when clicked", async () => {
    const user      = userEvent.setup()  // recommended over direct userEvent calls
    const mockAdd   = vi.fn()

    render(<AddToCart productId="p1" stock={5} onAdd={mockAdd} />)

    await user.click(screen.getByRole("button", { name: /add to cart/i }))

    expect(mockAdd).toHaveBeenCalledWith("p1")
    expect(screen.getByText(/added/i)).toBeInTheDocument()
  })
})

// ── Testing a form with validation ────────────────────────
describe("CheckoutForm", () => {
  it("shows validation errors on empty submit", async () => {
    const user = userEvent.setup()
    render(<CheckoutForm />)

    await user.click(screen.getByRole("button", { name: /place order/i }))

    expect(screen.getByText(/address is required/i)).toBeInTheDocument()
    expect(screen.getByText(/city is required/i)).toBeInTheDocument()
  })

  it("submits successfully with valid data", async () => {
    const user       = userEvent.setup()
    const mockSubmit = vi.fn()
    render(<CheckoutForm onSubmit={mockSubmit} />)

    await user.type(screen.getByLabelText(/street address/i), "123 Main St")
    await user.type(screen.getByLabelText(/city/i), "London")
    await user.type(screen.getByLabelText(/postcode/i), "EC1A 1BB")
    await user.click(screen.getByRole("button", { name: /place order/i }))

    expect(mockSubmit).toHaveBeenCalledWith({
      address: "123 Main St", city: "London", postcode: "EC1A 1BB"
    })
  })
})

test.use({ storageState: "playwright/.auth/user.json" })

test("complete checkout flow", async ({ page }) => {
  // Browse to product
  await page.goto("/products")
  await page.getByText("MacBook Pro").click()
  await expect(page).toHaveURL(/\/products\/.+/)

  // Add to cart
  await page.getByRole("button", { name: "Add to cart" }).click()
  await expect(page.getByRole("status")).toContainText("Added to cart")

  // Checkout
  await page.getByRole("link", { name: "Cart" }).click()
  await page.getByRole("button", { name: "Checkout" }).click()

  // Fill shipping
  await page.getByLabel("Street address").fill("123 Main Street")
  await page.getByLabel("City").fill("London")
  await page.getByLabel("Postcode").fill("EC1A 1BB")
  await page.getByRole("button", { name: "Place order" }).click()

  await expect(page).toHaveURL(/\/dashboard\/orders\/.+/)
  await expect(page.getByRole("heading")).toContainText("Order confirmed")

08 Interview questions + model answers 10 Q&As
Q1What is the testing pyramid and how does it apply to a Next.js app?▶
model answer
The testing pyramid describes the ideal distribution: many unit tests at the base (fast, cheap, isolated), fewer integration/component tests in the middle (test how pieces fit together), and very few E2E tests at the top (slow, expensive, test real user flows in a browser).

For a Next.js app: Unit tests — utility functions, Zod schemas, data transformations, Prisma query helpers. These run in milliseconds and should be exhaustive. Component tests with RTL — interactive components (AddToCart button, CheckoutForm, ProductCard). Test user behaviour: what happens when they click, type, submit. Mock API calls and auth. E2E with Playwright — the 5–10 most critical user journeys: complete checkout, auth guard, admin publish. Run against a real (test) database and real Clerk test account.

Anti-pattern: testing implementation details (internals of how state is managed) rather than behaviour (what the user sees). Tests tied to implementation break every refactor even when nothing is actually broken.
Q2Why does React Testing Library encourage querying by role over test IDs?▶
model answer
Querying by ARIA role (getByRole("button", { name: "Add to cart" })) tests what the user actually sees and what screen readers announce — it simultaneously validates accessibility and behaviour. If you change the button implementation from <button> to a <div role="button">, the test still works. If you rename the button text from "Add to cart" to something else, the test fails — which is correct, because the UX changed.

Test IDs (data-testid) are a last resort because they're invisible to users, add noise to your HTML, and don't validate accessibility. A test using getByTestId("add-to-cart-btn") would pass even if the button is visually broken, has no accessible label, or is hidden behind another element.

Query priority: ByRole → ByLabelText → ByPlaceholderText → ByText → ByDisplayValue → ByAltText → ByTitle → ByTestId. Use what a user or screen reader would use to find the element.
Q3What is the difference between getBy, queryBy, and findBy in RTL?▶
model answer
getBy*: synchronous, throws immediately if the element isn't found. Use when you expect the element to definitely be in the DOM at query time. If it's missing, the test fails with a helpful error showing what was in the DOM at that moment.

queryBy*: synchronous, returns null instead of throwing if not found. Use specifically when you want to assert that something is not in the DOM: expect(screen.queryByRole("alert")).not.toBeInTheDocument(). Using getBy* for this would throw before you reach the expect.

findBy*: async (returns a Promise), waits up to 1000ms polling for the element to appear. Use after async operations — clicking a button that makes an API call, or triggering a state update. await screen.findByText("Order confirmed") waits until that text appears in the DOM. It's a built-in waitFor wrapper. Always await it.
Q4How do you test a component that makes API calls?▶
model answer
Three approaches. vi.stubGlobal("fetch"): quickest for simple cases. Mock the global fetch to return controlled responses. Works well when you have one or two calls per test. Downside: brittle if the URL format changes.

MSW (Mock Service Worker): recommended for components with multiple API calls. Define handlers that intercept fetch requests by URL pattern and return mock responses. Handlers are reusable across tests, the component doesn't know it's being mocked, and you can test error states easily by overriding handlers per-test. More setup but much more robust.

Mock the module: if the component uses a custom hook (useProducts) instead of calling fetch directly, mock just the hook: vi.mock("./useProducts", () => ({ useProducts: () => ({ data: mockProducts, isLoading: false }) })). This is cleanest for testing UI behaviour independently of data fetching logic. Test the hook separately in its own test file.
The pattern: test the component with mocked data, test the hook with mocked fetch, test the API route handler separately. Never test all three at once in a component test.
Q5What should you test in an E2E suite vs component tests?▶
model answer
E2E tests are for the critical paths where multiple systems must work together correctly, and where a failure would cause immediate, obvious user harm. The checkout flow: if the cart, auth, order creation, stock decrement, and order confirmation page don't all work together, customers can't pay. That's an E2E test. Authentication guard: if the middleware doesn't redirect unauthenticated users to login, protected data is exposed. That's an E2E test.

Component tests are for unit-level behaviour that E2E tests would test too slowly or too indirectly. Testing that a button shows "Added!" after clicking without waiting for a real network round-trip. Testing all the validation error states of a form (you'd need to fill in and submit the form multiple times in E2E — very slow). Testing that a component renders correctly in each loading/error/empty state.

The key distinction: E2E tests verify that the integration works. Component tests verify that each piece works correctly in isolation. Both are necessary; neither replaces the other.
Q6How do you handle authentication in Playwright E2E tests?▶
model answer
The naive approach — sign in at the start of every test — is slow and fragile. Playwright provides a much better approach: sign in once in a setup step, save the browser storage state to a JSON file, then reuse that state across all tests that need auth.

Create an auth.setup.ts file that logs in, waits for redirect to the dashboard, then calls context.storageState({ path: "playwright/.auth/user.json" }). Configure tests that need auth to use test.use({ storageState: "playwright/.auth/user.json" }). The browser loads with cookies and localStorage already set — no login step needed per test.

For tests that need to run as both authenticated and anonymous users, structure your test files: auth-required tests use the storage state, unauthenticated tests don't. For role-based tests (admin vs regular user), create separate storage state files: admin.json and user.json. Use environment variables for credentials — never hardcode passwords in test files that are committed to git.
Q7What is vi.mock() and what are its gotchas?▶
model answer
vi.mock("module-name") replaces the entire module with a mock version for all tests in that file. Vitest hoists vi.mock calls to the top of the file before any imports — this is why they "just work" even when written after import statements.

The main gotcha: vi.mock is hoisted, so you can't reference variables declared with const in the factory function — they haven't been initialised yet. Use vi.fn() directly in the factory, or use vi.importMock for dynamic mocking. Another gotcha: vi.mock mocks the module for the entire file — if you need different behaviour per test, use vi.mocked(fn).mockReturnValue() inside the test to override the default.

Always call vi.clearAllMocks() in beforeEach to reset call histories between tests, otherwise a mock called in test 1 will still show those calls in test 2's assertions.
Q8How do you test Server Actions in Next.js?▶
model answer
Server Actions are plain async functions — they don't require a running Next.js server to test. Import the action directly and call it with test data. Mock the dependencies (Clerk auth, Prisma, revalidatePath) using vi.mock.

Mock Clerk's auth(): vi.mock("@clerk/nextjs/server", () => ({ auth: vi.fn().mockResolvedValue({ userId: "test-user" }) })). Mock Prisma: vi.mock("@/lib/db", () => ({ db: { order: { create: vi.fn().mockResolvedValue({ id:"ord_1" }) }, product: { update: vi.fn() } } })). Mock revalidatePath: vi.mock("next/cache", () => ({ revalidatePath: vi.fn() })).

Test the action for: success (valid input → correct DB call → revalidation triggered), validation failure (invalid input → error returned without DB call), auth failure (no userId → error without DB call), DB error (mock throws → correct error response). This gives you thorough Server Action coverage without a running database.
Q9What is userEvent vs fireEvent in React Testing Library?▶
model answer
fireEvent dispatches a single DOM event directly. fireEvent.click(button) fires exactly one click event — no hover, no focus, no real user simulation. It's synchronous and fast.

userEvent simulates real user interactions, firing multiple events in the same sequence a real user would trigger. userEvent.click(button) fires: pointerover, pointerenter, mouseover, mouseenter, pointermove, mousemove, pointerdown, mousedown, focus, pointerup, mouseup, click — then blur if focus moves away. userEvent.type(input, "hello") fires keydown, keypress, keyup, and input events for every character, including correctly handling backspace, tab navigation, and modifier keys.

Use userEvent for almost everything — it catches bugs that fireEvent misses (like buttons that only respond to hover states, or validation that triggers on blur not change). Use userEvent.setup() (the instance API) instead of calling userEvent.click() directly — it properly handles fake timers and is the recommended modern pattern.
Q10How do you integrate tests into CI/CD with GitHub Actions?▶
model answer
Two jobs: unit tests and E2E tests. Unit tests run first — they're fast (under 30 seconds for most codebases) and block E2E if they fail, saving time. E2E tests only run if unit tests pass.

For unit tests: npm ci → vitest run (single pass, exits with code 1 on failure). For E2E: install Playwright browsers with npx playwright install --with-deps chromium (just chromium to keep CI fast), set environment variables from GitHub Secrets (database URL, Clerk keys, test user credentials), run npx playwright test. Upload the Playwright HTML report as an artifact on failure so you can see what went wrong.

Key decisions: run E2E against a separate test database (not production), use a dedicated test Clerk application, store test credentials in GitHub Secrets. Add retries: 2 in Playwright config for CI to handle flaky network conditions. Target: unit tests under 1 minute, E2E tests under 5 minutes — tests that take longer don't get run.
