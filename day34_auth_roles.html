Core Concepts

🔐 AuthN vs AuthZ

Authentication: verifying identity — "Are you really user@email.com?" Handled by Clerk (passwords, OAuth, magic links, passkeys). Authorization: verifying permission — "Can user@email.com delete this product?" Handled by your RBAC system. Both are required. AuthN without AuthZ means any logged-in user can do anything. AuthZ without AuthN means you can't trust who's making the request.

🏛️ RBAC Concepts

Role-Based Access Control assigns permissions to roles, then assigns roles to users. Benefits: adding a new admin is just assigning the admin role — not reconfiguring 50 permission flags. ShopCo roles: customer (default), staff (manage orders), admin (manage products/users), super_admin (full access including billing). Roles are hierarchical — admin has all staff permissions.

🏢 Clerk Organizations

Orgs allow multi-tenant setups: a user can be a customer in one org and admin in another. For ShopCo: the "ShopCo Admin" org holds staff and admin members. Customers don't need orgs — they're just authenticated users. Use auth().orgRole to read the user's role in the current org. Clerk's organizationMemberships list all orgs a user belongs to.

🏷️ Custom JWT Claims

Clerk lets you add custom data to the session JWT via a JWT template. Add role and permissions fields — now every API request carries the user's role without a database query. Use Clerk's session customization: {{ user.public_metadata.role }}. Critical: set roles in publicMetadata (readable by client) or privateMetadata (server-only) — never let users set their own role.

🛡️ Middleware Guard

Next.js middleware runs at the edge before every request — perfect for auth. Use Clerk's clerkMiddleware() with createRouteMatcher to protect route patterns. The middleware redirects unauthenticated users to sign-in and can also enforce roles — if a non-admin hits /admin/*, redirect to 403. Runs in ~1ms edge compute, no cold starts.

⚙️ Server-Side Auth

In Server Components and API routes, use Clerk's auth() helper. It returns userId, orgRole, sessionClaims (including your custom fields) server-side, reading from the cookie. Never trust data from the client request body for auth decisions — always re-verify server-side. Even if the middleware passed, a Server Action should still call auth() and check permissions.

middleware.ts — Clerk + RBAC at the edge
import { clerkMiddleware, createRouteMatcher } from '@clerk/nextjs/server'
import { NextResponse } from 'next/server'

// Define protected route patterns
const isPublicRoute = createRouteMatcher([
  '/', '/products(.*)', '/sign-in(.*)', '/sign-up(.*)', '/api/webhooks(.*)'
])
const isAdminRoute = createRouteMatcher(['/admin(.*)', '/api/admin(.*)'])
const isStaffRoute = createRouteMatcher(['/dashboard(.*)', '/api/orders/manage(.*)'])

export default clerkMiddleware(async (auth, req) => {
  const { userId, sessionClaims } = await auth()
  const role = sessionClaims?.metadata?.role as string | undefined

  // Public routes — no auth needed
  if (isPublicRoute(req)) return

  // Unauthenticated — redirect to sign-in
  if (!userId) {
    const signInUrl = new URL('/sign-in', req.url)
    signInUrl.searchParams.set('redirect_url', req.url)
    return NextResponse.redirect(signInUrl)
  }

  // Admin routes — require admin or super_admin
  if (isAdminRoute(req) && !hasRole(role, 'admin')) {
    return NextResponse.redirect(new URL('/403', req.url))
  }

  // Staff routes — require staff or above
  if (isStaffRoute(req) && !hasRole(role, 'staff')) {
    return NextResponse.redirect(new URL('/403', req.url))
  }
})

// Hierarchical role check
const ROLE_HIERARCHY = ['customer', 'staff', 'admin', 'super_admin']
function hasRole(userRole: string | undefined, required: string): boolean {
  if (!userRole) return false
  return ROLE_HIERARCHY.indexOf(userRole) >= ROLE_HIERARCHY.indexOf(required)
}

lib/auth.ts — reusable server-side auth helpers
import { auth } from '@clerk/nextjs/server'

export type Role = 'customer' | 'staff' | 'admin' | 'super_admin'
const HIERARCHY: Role[] = ['customer', 'staff', 'admin', 'super_admin']

// Check if userRole meets the minimum required role
export function hasRole(userRole: Role | undefined, required: Role): boolean {
  if (!userRole) return false
  return HIERARCHY.indexOf(userRole) >= HIERARCHY.indexOf(required)
}

// Get current user + role — throws if unauthenticated
export async function requireAuth() {
  const { userId, sessionClaims } = await auth()
  if (!userId) throw new Error('Unauthorized')
  const role = (sessionClaims?.metadata?.role ?? 'customer') as Role
  return { userId, role, sessionClaims }
}

// Get current user + enforce minimum role
export async function requireRole(required: Role) {
  const { userId, role } = await requireAuth()
  if (!hasRole(role, required)) {
    throw new Error(`Forbidden: requires ${required}, got ${role}`)
  }
  return { userId, role }
}

app/api/orders/[id]/status/route.ts — API route with role check
import { requireRole } from '@/lib/auth'
import { prisma } from '@/lib/prisma'
import { z } from 'zod'

const UpdateStatusSchema = z.object({
  status: z.enum(['pending','processing','shipped','delivered','cancelled'])
})

export async function PATCH(req: Request, { params }: { params: { id: string } }) {
  try {
    // Only staff and above can update order status
    await requireRole('staff')
  } catch {
    return Response.json({ error: 'Forbidden' }, { status: 403 })
  }
  const body = await req.json()
  const { status } = UpdateStatusSchema.parse(body)
  const order = await prisma.order.update({
    where: { id: params.id },
    data: { status }
  })
  return Response.json(order)
}
⚠ Critical security rules:
Never read the user's role from the request body or query string — only from auth() / the session token. Always check roles server-side even if middleware already checked — defence in depth. Filter database queries by userId for resource ownership (e.g. WHERE userId = $currentUser) to prevent IDOR (Insecure Direct Object Reference) attacks. Log all auth failures with Sentry for security monitoring.

Interview Q&A

1. What is the difference between authentication and authorization?
Authentication (AuthN) verifies identity: "Are you who you claim to be?" — handled by login flows, OAuth, JWTs. Authorization (AuthZ) verifies permission: "Are you allowed to do this?" — handled by role checks, permission systems. Both are required. A common mistake is only implementing AuthN — any logged-in user can access any resource. In ShopCo: Clerk handles AuthN; our RBAC system handles AuthZ. Every API route must do both: verify the session exists (AuthN) and check the role permits the action (AuthZ).
2. What is RBAC and how does it differ from ABAC?
RBAC (Role-Based Access Control) assigns permissions to roles and roles to users. Simple, predictable, easy to audit. ABAC (Attribute-Based Access Control) checks arbitrary attributes: user attributes (department, clearance), resource attributes (owner, classification), and environment attributes (time of day, IP). ABAC is more flexible but complex. For ShopCo, RBAC covers 95% of needs. We add lightweight ownership checks ("customer can edit own review") which is a hybrid. Pure ABAC is overkill unless you need very fine-grained controls like "user can only access records from their region during business hours."
3. Why use custom JWT claims instead of a database lookup on every request?
Database lookups add 10–50ms latency to every request and create a hot path in your DB. JWT claims are decoded from the cookie/header in microseconds with no I/O. For stable attributes (role, plan, org membership) that don't change often, embedding them in the JWT via Clerk's session customization is ideal. Tradeoff: if you change a user's role, the old token is still valid until it expires (up to 24h). Mitigate with: short token lifetimes (1–2h), token invalidation via Clerk's session revocation API, or a fast cache check (Redis, edge KV) for high-security role changes.
4. What is an IDOR vulnerability and how do you prevent it?
IDOR (Insecure Direct Object Reference): a user accesses a resource they shouldn't by guessing or brute-forcing an ID. Example: GET /api/orders/123 — if the API returns the order without checking that the requesting user owns order 123, any authenticated user can read any order. Prevention: always filter database queries by ownership — WHERE id = $orderId AND userId = $currentUserId. Even if the middleware checked that the user is authenticated, the data layer must also enforce ownership. This is a top-10 OWASP vulnerability.
5. Where should you enforce authorization — middleware, Server Component, or database query?
All three — defence in depth. Middleware: coarse-grained, fast — block entire route segments (e.g. all of /admin) at the edge. Server Component / API handler: fine-grained role check for specific actions — call requireRole('admin') before processing. Database query: ownership filtering — always include WHERE userId = $currentUser for user-scoped resources. Never rely on only one layer: if a middleware bug allows a customer into /admin, the Server Component check catches it. If a Server Component bug skips the role check, the DB query's ownership filter limits the damage.
6. How do Clerk Organizations enable multi-tenant auth?
Clerk Organizations let one user have different roles in different tenants. A user can be customer in Org A and admin in Org B. The active org is set via setActive({ organization: orgId }) — Clerk updates the session to include orgId and orgRole. Your middleware and server-side code read auth().orgRole for the current org context. This is ideal for B2B SaaS where a business subscribes and adds their own team members. For ShopCo: the "ShopCo Staff" org contains employees; customers are just authenticated users without org membership.
7. How do you handle role changes that need to take effect immediately?
JWT-based sessions can be up to 24h old — a user demoted from admin could still have admin claims. Options: (1) Revoke session: Clerk's sessions.revokeSession(sessionId) immediately invalidates the token — user is forced to re-authenticate; (2) Short token lifetime: set Clerk's session token lifetime to 1h — role changes take effect within 1h; (3) Database check: for high-security actions (delete user, billing changes), do a fresh database role lookup to bypass the cached token. In ShopCo, revoke session when promoting/demoting staff or admin roles.
8. What is the difference between publicMetadata and privateMetadata in Clerk?
publicMetadata: set server-side via Clerk Backend API, readable by the client (included in the session token). Use for: role, plan tier, feature flags the frontend needs to know. privateMetadata: set server-side, never sent to the client — server-side only. Use for: internal notes, admin-only flags, fraud scores. unsafeMetadata: set by the client — never trust for security decisions, only use for non-critical UI preferences. Critical rule: never let users write their own role. Role assignment must always go through your backend via Clerk's Management API with your secret key, never through the frontend SDK.
9. How would you implement a "resource ownership" check for ShopCo reviews?
Two-layer approach: (1) API handler: fetch the review from DB and compare review.userId === currentUserId before allowing update/delete. (2) Database: include ownership in the WHERE clause — DELETE FROM reviews WHERE id = $id AND userId = $currentUserId — this way even if the application logic has a bug, the DB won't delete someone else's review. For admins who should bypass ownership: const where = hasRole(role, 'admin') ? { id } : { id, userId }. This pattern — conditional WHERE based on role — keeps your code clean and secure.
10. How do you audit auth events for compliance?
Log every significant auth event: sign-in, sign-out, role change, permission denied, password reset, org membership change. In Next.js: log in middleware for denied requests, in API handlers for successful sensitive operations. Store logs in a separate, append-only system (never delete audit logs) — options: Axiom, Datadog, or a separate Postgres table with no UPDATE/DELETE permissions. Log: timestamp, userId, action, resource, result, IP address, user agent. For compliance (SOC2, GDPR): retain for 90–365 days depending on regulation. Clerk's event webhooks also provide audit events — subscribe and store them.
