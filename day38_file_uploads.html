Core Concepts

📤 Why UploadThing?

UploadThing is a type-safe file upload service for Next.js. You define file routes with TypeScript — allowed types, max size, auth middleware — and get a React hook (useUploadThing) that handles the client side. It uploads directly to UploadThing's CDN (backed by S3), calls your onUploadComplete callback server-side, and gives you the file URL. Zero infrastructure to manage, type-safe from config to callback.

🔑 Pre-signed URLs

A pre-signed URL is a time-limited, signed S3 URL that lets the client upload directly to S3 without going through your server. Flow: client requests upload permission → your server generates pre-signed URL with size/type constraints → client uploads directly to S3 → S3 notifies your server (or client calls your API) on completion. Bypasses your server for large files — no memory pressure, no bandwidth costs on your end.

🛡️ Server-side Validation

Never trust client-side validation for file uploads. Always validate on the server: MIME type (check magic bytes, not just extension), file size, image dimensions. For UploadThing: configure maxFileSize and acceptedFileTypes in the router. After upload, validate the actual file contents before saving the URL to your database. An attacker can rename a .exe to .jpg — check the actual bytes.

🖼️ Sharp Image Processing

Sharp is a Node.js image processing library (bindings to libvips). Use it to: resize to multiple breakpoints (thumb/medium/large), convert to WebP (30–50% smaller than JPEG), strip EXIF metadata (privacy — GPS coordinates in photos), add watermarks. Process images in the onUploadComplete callback. Store multiple sizes in S3 with a consistent naming convention: products/p_abc/hero_800w.webp.

📊 Upload Progress

For large product images (up to 8MB), show progress. XMLHttpRequest has a native upload.onprogress event. Fetch API streams can also track progress via ReadableStream. UploadThing's useUploadThing hook provides an onUploadProgress callback. Show a progress bar, estimated time remaining, and a cancel button for uploads >2s. Always show a loading state — users abandon uploads without feedback.

🗑️ Orphan File Cleanup

When a product is deleted, the S3 files remain — you pay for storage and leak data. Cleanup strategies: (1) Synchronous: delete S3 files in the same transaction — risky if DB succeeds but S3 fails; (2) Webhook queue: on soft delete, push file keys to a queue, worker deletes from S3; (3) Cron job: periodically scan S3 for file keys not referenced in your DB. For ShopCo: record file keys in the ProductImage table, delete from S3 in a background job after soft delete.

React component — product image uploader with drag & drop
'use client'
import { useUploadThing } from '@/lib/uploadthing'
import { useState, useCallback } from 'react'

export function ProductImageUploader({ productId, onComplete }) {
  const [files, setFiles] = useState([])
  const [progress, setProgress] = useState(0)
  const [error, setError] = useState(null)

  const { startUpload, isUploading } = useUploadThing('productImage', {
    onClientUploadComplete(res) {
      onComplete?.call(null, res)
      setFiles([])
      setProgress(0)
    },
    onUploadError(err) { setError(err.message) },
    onUploadProgress(p) { setProgress(p) },
  })

  const onDrop = useCallback((e) => {
    e.preventDefault()
    const dropped = Array.from(e.dataTransfer.files)
    const valid = dropped.filter(f =>
      f.type.startsWith('image/') && f.size <= 8 * 1024 * 1024
    )
    setFiles(valid)
    setError(null)
  }, [])

  return (
    <div>
      <div
        onDrop={onDrop}
        onDragOver={e => e.preventDefault()}
        className="dropzone"
      >
        {files.length ? `${files.length} file(s) ready` : 'Drop images here'}
      </div>
      {isUploading && <progress value={progress} max={100} />}
      {error && <p className="error">{error}</p>}
      <button
        onClick={() => startUpload(files)}
        disabled={!files.length || isUploading}
      >
        {isUploading ? `Uploading ${progress}%` : 'Upload Images'}
      </button>
    </div>
  )
}

Image Processing Pipeline

lib/image-processor.ts — Sharp pipeline for product images
import sharp from 'sharp'
import { S3Client, GetObjectCommand, PutObjectCommand } from '@aws-sdk/client-s3'

const s3 = new S3Client({ region: process.env.AWS_REGION })

const VARIANTS = [
  { suffix: 'thumb',  width: 150, height: 150, fit: 'cover'  as const },
  { suffix: 'sm',     width: 400, height: 400, fit: 'inside' as const },
  { suffix: 'md',     width: 800, height: 800, fit: 'inside' as const },
  { suffix: 'hero',   width: 1200,height: 1200,fit: 'inside' as const },
]

export async function processProductImage(originalKey: string) {
  // 1. Fetch original from S3
  const { Body } = await s3.send(new GetObjectCommand({
    Bucket: process.env.S3_BUCKET!, Key: originalKey
  }))
  const buffer = Buffer.from(await Body.transformToByteArray())

  // 2. Validate: check actual magic bytes (not just extension)
  const meta = await sharp(buffer).metadata()
  if (!['jpeg','png','webp'].includes(meta.format ?? ''))
    throw new Error('Invalid image format')
  if ((meta.width ?? 0) < 400 || (meta.height ?? 0) < 400)
    throw new Error('Image must be at least 400×400px')

  // 3. Process all variants in parallel
  const results = await Promise.all(
    VARIANTS.map(async (v) => {
      const processed = await sharp(buffer)
        .resize(v.width, v.height, { fit: v.fit, withoutEnlargement: true })
        .webp({ quality: 85, effort: 4 })   // WebP: smaller than JPEG
        .withMetadata(false)               // strip EXIF (GPS, camera info)
        .toBuffer()
      const key = originalKey.replace(/\.[^.]+$/, `_${v.suffix}.webp`)
      await s3.send(new PutObjectCommand({
        Bucket: process.env.S3_BUCKET!,
        Key: key, Body: processed,
        ContentType: 'image/webp',
        CacheControl: 'public, max-age=31536000, immutable',
      }))
      return { variant: v.suffix, key, size: processed.length }
    })
  )

  return {
    original: { key: originalKey, width: meta.width, height: meta.height },
    variants: results,
  }
}
⚠ Security essentials for file uploads:
Never trust the file extension or Content-Type header — always check magic bytes (first few bytes of the file). Scan uploaded files with an antivirus service (ClamAV or cloud service) before making them public. Never execute uploaded files — store them in a separate S3 bucket with no public execute permissions. Strip EXIF metadata from images before publishing — product photos contain GPS coordinates and device info. Set Content-Disposition: attachment on non-image file downloads to prevent browser execution.

Interview Q&A

1. Why upload files directly to S3 instead of through your server?
Routing large files through your server wastes bandwidth (you pay twice), consumes server memory, and creates a bottleneck that limits throughput. With pre-signed URLs: the client uploads directly to S3 at full network speed, your server only handles the tiny URL generation request and the completion notification. Benefits: no memory pressure on serverless functions (which have 128MB–1.5GB limits), no bandwidth costs on your API server, uploads can be massive (S3 handles multipart uploads for files up to 5TB), and S3's infrastructure is optimized for high-throughput concurrent uploads.
2. What is a pre-signed URL and how does it work?
A pre-signed URL is a time-limited, credential-embedded URL that grants temporary permission to perform a specific S3 operation (PUT, GET, DELETE). Your server generates it using your AWS credentials: the URL contains the bucket, key, expiry time, allowed content-type, max file size, and an HMAC signature of these parameters. The client uses this URL to upload directly to S3 — S3 verifies the signature and enforces the constraints without consulting your server. Typical expiry: 5–15 minutes. If the URL expires before upload completes, the upload fails — generate fresh URLs for large files or slow connections.
3. How do you validate file types securely — beyond checking the extension?
Extension and Content-Type header are client-controlled — an attacker can name a malicious file exploit.exe as photo.jpg. Secure validation: (1) Magic bytes: check the first 4–8 bytes of the actual file — JPEG starts with FF D8 FF, PNG with 89 50 4E 47. Use the file-type npm package or Sharp's metadata() which checks actual binary content; (2) Post-upload processing: run Sharp on every image — if it's not a valid image, Sharp throws an error; (3) ClamAV or cloud scanning: scan for malware, especially for PDF/document uploads. Never trust the filename or Content-Type header alone.
4. Why use WebP and how much space does it save?
WebP (Google's format) uses more sophisticated compression than JPEG: typically 25–35% smaller at equivalent visual quality for photos, and 26% smaller than PNG for lossless. For ShopCo: a 4MB product JPEG becomes ~1.2MB WebP at comparable quality. Multiply by thousands of products × 4 variants = significant S3 cost savings and faster page loads. Browser support is now universal (Chrome, Safari 14+, Firefox, Edge). Use Sharp to convert: sharp(buffer).webp({ quality: 85 }). Always serve WebP with a JPEG fallback via <picture> element for maximum compatibility.
5. What is EXIF data and why must you strip it from product images?
EXIF (Exchangeable Image File Format) metadata is embedded in photos by cameras and phones. It contains: GPS coordinates (exact location where the photo was taken), device model and serial number, software version, date/time, camera settings. For product photos shot at a warehouse or home, this data exposes your location and equipment — a privacy and security risk. Strip with Sharp's .withMetadata(false) — zero-cost operation during processing. Always strip EXIF before publishing any user-uploaded content, including avatar photos and profile pictures.
6. How do you handle upload failures and partial uploads?
For small files (<5MB): retry the entire upload on network failure — pre-signed URL is still valid. For large files: use S3 multipart upload — upload in 5MB chunks, each chunk independently retried. UploadThing handles this automatically. UI patterns: (1) show error state with "Retry" button; (2) save progress to localStorage and resume if user navigates away; (3) validate pre-signed URL hasn't expired before retrying — if it has, fetch a new one; (4) implement a timeout (if no progress after 30s, assume stuck and restart the chunk). S3 automatically deletes incomplete multipart uploads after the lifecycle rule you set (typically 1–7 days).
7. What is UploadThing and why use it over raw S3 SDK?
UploadThing is a type-safe file upload service for Next.js. Benefits over raw S3: (1) TypeScript all the way — file route definitions are typed, onUploadComplete callback gets typed file metadata; (2) no AWS account setup — zero infrastructure, just an API key; (3) React hook (useUploadThing) with built-in progress, error, and completion callbacks; (4) auth middleware built in — you define who can upload what in the route config; (5) CDN included — files served from UploadThing's CDN, not your S3 bucket. Tradeoff: vendor lock-in, less control over bucket configuration and lifecycle rules. For production ShopCo with custom requirements (image processing pipeline), raw S3 with pre-signed URLs gives more control.
8. How do you handle orphaned files when products are deleted?
Three strategies: (1) Synchronous cleanup: delete S3 files in the same request as DB soft delete — risky if S3 call fails after DB commit; use only if you can tolerate eventual consistency; (2) Queue-based: on soft delete, push the file keys to a queue (Upstash QStash or Redis queue), a background worker deletes from S3 — decoupled, retries on failure; (3) Reconciliation cron: daily job scans S3 for keys not in DB — catches any leaks from bugs in approaches 1 or 2. Best practice: use all three as layers. Store file keys in your DB (ProductImage.s3Key) so you always know what to delete. Add a grace period (1h) before deleting to avoid race conditions with concurrent uploads.
9. What S3 settings should every production bucket have?
Critical settings: (1) Block public access: disable public ACLs, use bucket policy for read, pre-signed URLs for write; (2) Versioning: enable for critical buckets — accidental deletes are recoverable; (3) Lifecycle rules: auto-delete incomplete multipart uploads after 7 days, move old versions to Glacier after 30 days; (4) Server-side encryption: SSE-S3 (free) or SSE-KMS for regulated industries; (5) CORS policy: restrict to your domain for presigned PUT uploads; (6) Access logging: enable for audit trail; (7) Replication: cross-region replication for disaster recovery on critical assets; (8) CloudFront CDN: put CloudFront in front for caching and edge delivery.
10. How do you implement drag-and-drop file upload with preview?
Key events: dragover (prevent default to allow drop), drop (access e.dataTransfer.files). Also handle dragenter/dragleave for visual feedback. For preview: use URL.createObjectURL(file) to create a local blob URL — renders in an <img> instantly without uploading. Clean up with URL.revokeObjectURL(url) when the component unmounts. For multi-file with reordering: store files in state array, implement drag-and-drop between preview items. Show per-file progress with individual progress bars. Validate before showing preview — if the file is invalid, show an error icon instead. The react-dropzone library handles most of this, but understanding the underlying events is important for customization.
