01 Why React Hook Form — the performance argument motivation
controlled inputs (the old way)
Every keystroke re-renders the whole form
With useState controlled inputs, every character typed triggers a state update which re-renders the component. For a form with 20 fields, typing in one field re-renders all 20. As forms get complex — with nested components, validation, and conditional fields — this cascades into noticeable lag.
uncontrolled inputs (RHF way)
DOM manages values, RHF reads on demand
RHF uses uncontrolled inputs — React doesn't manage the input's value, the DOM does. RHF registers inputs with a ref and reads values only when needed (on submit, on validation). Typing doesn't trigger any React re-renders. The form component only re-renders on submit or when errors change.
validation isolation
Schema validation as a first-class citizen
Manual validation in useState forms means writing if (!email.includes("@")) everywhere — mixed into component logic. Zod separates validation into a typed schema that lives outside the component. The same schema validates on the client, on the server, and in tests. One source of truth.
developer experience
Dramatically less boilerplate
A full form with 6 fields, validation, error messages, and submit handling goes from ~100 lines of manual state management to ~30 lines with RHF + Zod. No separate touched/dirty state, no manual error object management, no onChange handlers for every field. It just works.
❌ Before — manual useState form (60+ lines)
function LoginForm() {
  const [email,    setEmail]    = useState("")
  const [password, setPassword] = useState("")
  const [errors,   setErrors]   = useState({})
  const [touched,  setTouched]  = useState({})
  const [loading,  setLoading]  = useState(false)

  const validate = () => {
    const errs = {}
    if (!email) errs.email = "Required"
    else if (!email.includes("@")) errs.email = "Invalid email"
    if (!password) errs.password = "Required"
    else if (password.length < 8) errs.password = "Min 8 chars"
    setErrors(errs)
    return Object.keys(errs).length === 0
  }
  const handleSubmit = async (e) => {
    e.preventDefault()
    if (!validate()) return
    setLoading(true)
    try { await login({ email, password }) }
    finally { setLoading(false) }
  }
  return (
    <form onSubmit={handleSubmit}>
      <input value={email}
        onChange={e=>setEmail(e.target.value)}
        onBlur={()=>setTouched(t=>({...t,email:true}))} />
      {touched.email && errors.email &&
        <span>{errors.email}</span>}
      {/* password field... same pattern again */}
      <button disabled={loading}>Login</button>
    </form>
  )
}

function LoginForm() {

    formState: { errors, isSubmitting }

      <button disabled={isSubmitting}>Login</button>
    </form>
  )
}
02 useForm — register, handleSubmit & formState core API
Everything useForm returns — what you use every day
register(name, options)
Registers an input. Returns { name, ref, onChange, onBlur } — spread onto the input element. The ref connects RHF to the DOM element directly.
handleSubmit(onValid, onInvalid)
Wraps your submit handler. Runs validation first — only calls onValid(data) if the form passes. Prevents default. Catches async errors automatically.
formState
An object with: errors, isSubmitting, isValid, isDirty, dirtyFields, touchedFields, isSubmitSuccessful. Subscribe only to what you destructure.
watch(name?)
Returns live field values. Causes re-render on changes — use sparingly. watch("email") for one field, watch() for all values.
setValue(name, value)
Programmatically set a field's value. Use { shouldValidate: true } to trigger validation. { shouldDirty: true } to mark as dirty.
reset(values?)
Reset form to default values (or provided values). Use after successful submit to clear the form, or when editing — reset(serverData) pre-fills all fields.
jsxuseForm — full registration form with all field types and formState
import { useForm } from "react-hook-form"

  })

  const password = watch("password")   // live value for confirm-password comparison

  const onSubmit = async (data) => {
    // data is fully validated — all fields present and typed correctly
    await registerUser(data)
    reset()   // clear form after success
  }

  return (
    <form onSubmit={handleSubmit(onSubmit)}>

      {/* Text input */}
      <input

          required: "Email required",

        })}
      />
      {errors.email && <p className="error">{errors.email.message}</p>}

      {/* Password */}
      <input type="password" {...register("password", { required: true, minLength: 8 })} />

      <input
        type="password"
        {...register("confirmPassword", {
          validate: (val) => val === password || "Passwords don't match",
        })}
      />
      {errors.confirmPassword && <p className="error">{errors.confirmPassword.message}</p>}

      {/* Select */}
      <select {...register("role")}>
        <option value="user">User</option>
        <option value="admin">Admin</option>
      </select>

      {/* Checkbox */}
      <input type="checkbox" {...register("agree", { required: "You must agree" })} />
      {errors.agree && <p className="error">{errors.agree.message}</p>}

      <button type="submit" disabled={isSubmitting}>
        {isSubmitting ? "Registering..." : "Register"}
      </button>

  )

03 Zod — schema-first validation with TypeScript types zod
what zod is
A TypeScript-first schema declaration library
You define a schema once using Zod's fluent API. Zod then provides: runtime validation, TypeScript types inferred automatically from the schema (z.infer<typeof schema>), and descriptive error messages. The schema is the single source of truth for both validation and types.
parse vs safeParse
Throw vs return errors
schema.parse(data) throws a ZodError if validation fails — use in contexts where you want errors to propagate. schema.safeParse(data) returns { success: true, data } or { success: false, error } — use when you want to handle errors gracefully without try/catch.
type inference
One schema, two benefits
With type FormData = z.infer<typeof schema>, your TypeScript types are always in sync with your validation. Add a field to the schema — the type updates automatically. Change a field to required — TypeScript will catch every place that doesn't provide it.
jsZod — every validator you'll use daily, parse, safeParse, and type inference

z.string().url("Must be a URL")

z.string().nullable()          // string | null
z.string().default("guest")    // fills missing values

z.number().min(0).max(100)
z.number().int()               // must be integer
z.number().positive()
z.number().nonnegative()

z.boolean()
z.date()
z.enum(["admin", "user", "guest"])
z.literal("active")            // exact value

// ── Objects ───────────────────────────────────────────────
const userSchema = z.object({
  name:    z.string().min(2),
  email:   z.string().email(),
  age:     z.number().min(18).optional(),
  role:    z.enum(["admin", "user"]).default("user"),
  address: z.object({          // nested objects work
    street: z.string(),
    city:   z.string(),
    zip:    z.string().regex(/^\d{5}$/),
  }).optional(),
})

// ── Arrays ────────────────────────────────────────────────
z.array(z.string())             // string[]
z.array(z.string()).min(1, "At least one item")
z.array(z.string()).max(10)
z.array(z.string()).nonempty()  // shorthand for min(1)

// ── Cross-field validation with refine ────────────────────
const signupSchema = z.object({
  password:        z.string().min(8),
  confirmPassword: z.string(),
}).refine(
  (data) => data.password === data.confirmPassword,
  { message: "Passwords don't match", path: ["confirmPassword"] }
)

// ── Union and discriminated union ─────────────────────────
const paymentSchema = z.discriminatedUnion("type", [
  z.object({ type: z.literal("card"),   cardNumber: z.string() }),
  z.object({ type: z.literal("paypal"), email:      z.string().email() }),
])

// ── parse vs safeParse ────────────────────────────────────
// Parse — throws ZodError on failure
const user = userSchema.parse({ name: "Alice", email: "alice@test.com" })

// SafeParse — returns result object
const result = userSchema.safeParse({ name: "A", email: "not-an-email" })
if (!result.success) {
  console.log(result.error.flatten().fieldErrors)
  // { name: ["String must contain at least 2 character(s)"], email: ["Invalid email"] }
}

// ── Type inference ────────────────────────────────────────
type User     = z.infer<typeof userSchema>
type Signup   = z.infer<typeof signupSchema>
type Payment  = z.infer<typeof paymentSchema>
// Types are always in sync with schema — no duplication!

// ── LoginForm.tsx ─────────────────────────────────────────
import { useForm }        from "react-hook-form"
import { zodResolver }   from "@hookform/resolvers/zod"
import { loginSchema, type LoginFormData } from "./schemas/auth"
import { useMutation }   from "@tanstack/react-query"

function LoginForm() {
  const {
    register,
    handleSubmit,
    setError,          // set server-side errors onto fields
    formState: { errors, isSubmitting }
  } = useForm<LoginFormData>({
    resolver:      zodResolver(loginSchema),
    defaultValues: { email: "", password: "", remember: false },
    mode:          "onBlur",
  })

  // Pair with React Query mutation for server errors
  const loginMutation = useMutation({
    mutationFn: (data: LoginFormData) => authAPI.login(data),
    onError: (error) => {
      // Map server errors back to form fields
      if (error.code === "INVALID_CREDENTIALS") {
        setError("email", { message: "Invalid email or password" })
        setError("password", { message: "Invalid email or password" })
      }
      if (error.code === "ACCOUNT_LOCKED") {
        setError("root", { message: "Account locked. Please contact support." })
      }
    },
  })

  const onSubmit = (data: LoginFormData) => loginMutation.mutateAsync(data)

  return (
    <form onSubmit={handleSubmit(onSubmit)}>
      {errors.root && <div className="form-error">{errors.root.message}</div>}

      <div>
        <label>Email</label>
        <input type="email" {...register("email")} aria-invalid={!!errors.email} />
        {errors.email && <p role="alert">{errors.email.message}</p>}
      </div>

      <div>
        <label>Password</label>
        <input type="password" {...register("password")} />
        {errors.password && <p role="alert">{errors.password.message}</p>}
      </div>

      <label>
        <input type="checkbox" {...register("remember")} /> Remember me
      </label>

      <button type="submit" disabled={isSubmitting || loginMutation.isPending}>
        {loginMutation.isPending ? "Signing in..." : "Sign in"}
      </button>
    </form>
  )
}

const checkoutSchema = z.object({
  // Step 1 — Contact
  firstName: z.string().min(1),
  lastName:  z.string().min(1),
  email:     z.string().email(),
  // Step 2 — Shipping
  address:   z.string().min(5),
  city:      z.string().min(1),

})

const STEP_FIELDS = [
  ["firstName", "lastName", "email"],    // step 1 fields
  ["address", "city", "zip"],            // step 2 fields
  ["cardNumber", "expiry"],              // step 3 fields
]

function CheckoutForm() {
  const [step, setStep] = useState(0)

  const { register, handleSubmit, trigger, formState: { errors } } =
    useForm({ resolver: zodResolver(checkoutSchema), mode: "onBlur" })

  const nextStep = async () => {
    // Validate ONLY this step's fields before advancing
    const valid = await trigger(STEP_FIELDS[step])
    if (valid) setStep(s => s + 1)
  }

  return (
    <form onSubmit={handleSubmit(placeOrder)}>
      {/* Step indicator */}
      <StepIndicator current={step} total={3} />

      {step === 0 && (
        <div>
          <input {...register("firstName")} placeholder="First name" />
          <input {...register("email")} placeholder="Email" />
          <button type="button" onClick={nextStep}>Next: Shipping</button>
        </div>
      )}
      {step === 1 && (
        <div>
          <input {...register("address")} placeholder="Address" />
          <button type="button" onClick={() => setStep(0)}>Back</button>
          <button type="button" onClick={nextStep}>Next: Payment</button>
        </div>
      )}
      {step === 2 && (
        <div>
          <input {...register("cardNumber")} placeholder="Card number" />
          <button type="submit">Place Order</button>
        </div>
      )}
    </form>
  )
}

function validateField(name, value, rules) {
  const empty = value === null || value === undefined || value === ""
  if (rules.required && empty)    return rules.required
  if (empty) return null   // optional field — skip other checks
  const s = String(value)
  if (rules.minLength && s.length < rules.minLength.value) return rules.minLength.message
  if (rules.maxLength && s.length > rules.maxLength.value) return rules.maxLength.message
  if (rules.email && !/^[^\s@]+@[^\s@]+\.[^\s@]+$/.test(s))    return rules.email
  if (rules.min   && Number(value) < rules.min.value)             return rules.min.message
  if (rules.max   && Number(value) > rules.max.value)             return rules.max.message
  if (rules.validate) { const r = rules.validate(value); if (typeof r === "string") return r }
  return null
}

function swap(a, b) {
  const next = [...fields];
  [next[a], next[b]] = [next[b], next[a]]
  fields = next; notify()
}

08 Interview questions + model answers 10 Q&As
Q1Why does React Hook Form outperform controlled form implementations?▶
model answer
RHF uses uncontrolled inputs — instead of storing input values in React state (which triggers a re-render on every keystroke), RHF attaches refs directly to DOM elements and reads values from the DOM only when needed. Typing in a field doesn't cause any React renders at all.

With controlled inputs and useState, a form with 20 fields re-renders the entire form component on every keystroke, every onChange. For complex forms with nested components, conditional fields, and expensive validation, this cascades into noticeable lag.

RHF components only re-render when: errors change, the form is submitted, or you explicitly use watch() (which opts a field back into controlled behaviour). This makes it vastly more performant for large or complex forms.
Depth signal: "I use the Chrome Performance tab with React DevTools' Profiler to measure render counts. In a 15-field form I benchmarked, switching from useState to RHF reduced renders per character typed from 15 to 0."
Q2What does register() actually return and how does it connect to the input?▶
model answer
register(name) returns an object with four properties: name (the field name), ref (a callback ref that RHF uses to get the DOM element), onChange (runs validation and error updates), and onBlur (runs validation if mode includes blur).

When you spread it onto an input — {...register("email")} — React assigns all four as props. The ref callback fires when the element mounts, giving RHF a direct reference to the DOM node so it can read the value without React state.

For native HTML inputs (text, email, checkbox, select, textarea), spreading register is all you need. For custom components that don't expose a DOM input element, you need Controller instead, which uses React's controlled pattern just for that one component while keeping the rest of the form uncontrolled.
Q3What is Zod and why would you use it over writing validation manually?▶
model answer
Zod is a TypeScript-first schema validation library. You define a schema once and get three things automatically: runtime validation (actual data checking), TypeScript types inferred from the schema via z.infer<typeof schema>, and error messages attached to each rule.

Versus manual validation: manual validation is imperative code mixed into components — hard to reuse, hard to test in isolation, easy to get out of sync with TypeScript types. Zod schemas are declarative, composable, and testable. The same schema can validate on the client, on the server (in API route handlers), and in unit tests — one source of truth.

The TypeScript integration is the killer feature: add a field to the Zod schema and your TypeScript type updates automatically. Forget a required field in your submit handler and TypeScript catches it at compile time. You can't achieve this with manual validation.
Q4What is the difference between watch() and getValues()?▶
model answer
Both read form field values, but they behave differently regarding re-renders.

watch(name) subscribes the component to changes in that field — every time the field value changes, the component re-renders with the new value. This is the "reactive" way to read a value when the UI needs to respond to it — like showing a password strength indicator, or conditionally rendering a field based on another field's value.

getValues(name) reads the current value without subscribing — no re-render occurs. Use this inside event handlers, in useEffect dependencies where you only need the current snapshot, or when computing derived data outside the render cycle. For example, reading the current email value when a button is clicked to check its availability.
Common mistake: using watch() everywhere for performance concerns from the docs, then being confused why some fields don't update reactively. Rule: watch when the UI needs to react to a value change; getValues when you just need a snapshot at a specific moment.
Q5When would you use Controller instead of register?▶
model answer
register works with native HTML input elements — anything that natively exposes ref, onChange, onBlur, and name. Most HTML elements do: input, select, textarea, radio buttons, checkboxes.

Controller is needed when working with components that: don't expose a native input element (custom date pickers, custom sliders, rich text editors), have a non-standard value change API (trigger onChange with the value directly, not an event), or come from a component library that manages its own state (React Select, Ant Design inputs, MUI).

Controller uses the controlled pattern (value prop + onChange) specifically for that wrapped component, while the rest of the form remains uncontrolled. The field object in the render prop provides value, onChange, onBlur, and ref — wire these to whatever props the component expects.
Q6How do you handle server-side validation errors in RHF?▶
model answer
After the API call fails, map the server's error response onto specific form fields using setError(fieldName, { message: "..." }). This puts the error in formState.errors just like a client-side validation error — the same UI renders for both.

For errors attached to a specific field (like "email already taken"), use the field name: setError("email", { message: "Email already registered" }). For non-field-specific errors (like "account locked"), use setError("root", { message: "..." }) and render errors.root?.message at the top of the form.

Pair this with useMutation's onError callback: the mutation fails, the callback runs setError, and the form shows the server error inline without any extra state management. The error clears automatically when the user modifies the field (onChange in RHF deletes the field's error).
Q7How does useFieldArray work and why must you use field.id as the key?▶
model answer
useFieldArray manages a dynamic array of objects in the form — team members, line items, tags, addresses. It provides fields (the current array with stable IDs), append (add an item), remove (remove by index), move, swap, and update.

For input registration in the array: register("members.0.name") — dot notation addresses nested fields. Error access follows the same pattern: errors.members?.[0]?.name?.message.

The field.id requirement: useFieldArray generates a stable unique ID for each item that persists across reorders. If you use the array index as React's key, reordering causes React to think elements are the same and creates subtle bugs — inputs retain old values, animations break. Using field.id (not field.id from your data, but RHF's generated ID) correctly identifies each element across moves.
Q8How do you implement a multi-step form with RHF?▶
model answer
Use a single useForm instance for the entire form — all fields from all steps share the same form state. Track the current step with regular useState.

Each step renders only its own fields. When the user clicks "Next", call trigger(currentStepFields) — this validates only the specified fields and returns a boolean. If true, advance the step; if false, the errors appear for only that step's fields and navigation is blocked.

The final step's submit button uses handleSubmit(onSubmit) normally — Zod/resolver runs the full schema against all accumulated values. Because all fields are registered even when not visible (uncontrolled inputs persist in the DOM until unmounted), the values are available for final validation. If needed, use shouldUnregister: false in useForm to ensure unmounted fields' values are preserved.
Q9What is Zod's .refine() and when do you need it?▶
model answer
.refine(fn, options) adds a custom validation rule that runs after all field-level validations pass. The function receives the entire object and returns a boolean. If false, the error is attached to the field specified by path.

You need it for cross-field validation — rules that depend on multiple fields' values. The most common cases: confirm-password must match password, end date must be after start date, at least one of several optional fields must be provided, a conditional field is required when another field has a specific value.

Field-level validators in Zod (z.string().min(8)) can only see their own value. refine on a z.object() sees all values simultaneously. The path option controls which field shows the error — without it, the error appears on the root object, which RHF can't display on a specific input.
Q10What does handleSubmit do, and what happens if the submitted function throws?▶
model answer
handleSubmit(onValid, onInvalid?) returns an event handler. When the form submits: it calls event.preventDefault(), runs the resolver (Zod or built-in rules) against all field values, and either calls onValid(data) with the validated data or calls onInvalid(errors) if validation fails.

During the onValid call, formState.isSubmitting is true — use this to disable the submit button and show a loading state. After onValid completes (or throws), isSubmitting returns to false.

If the async onValid function throws an error, RHF catches it and sets isSubmitting back to false — the form doesn't get stuck in a loading state. The thrown error is not automatically shown to the user — you need to handle it yourself (catch it and call setError("root", { message }) or show a toast). This is why pairing with useMutation's onError is the cleanest pattern.
