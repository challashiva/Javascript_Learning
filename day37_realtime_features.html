Core Concepts

📡 Server-Sent Events (SSE)

SSE is a one-way HTTP stream — the server pushes data to the client over a persistent connection. The browser's EventSource API handles reconnection automatically. Best for: live feeds, order status updates, notifications. Uses standard HTTP (works through proxies). Limited to server→client direction, text only. Much simpler than WebSockets for read-only real-time data.

🔌 WebSockets

WebSockets upgrade an HTTP connection to a persistent, full-duplex TCP channel. Both client and server can send messages at any time. Best for: chat, collaborative editing, live cursor positions, gaming. Requires a persistent server (doesn't work well with serverless). For ShopCo: use WebSockets for the admin dashboard where staff trigger actions that others see instantly.

⚡ Pusher Channels

Pusher is a managed WebSocket service — you trigger events from your Next.js API, Pusher delivers them to subscribed clients. No persistent server needed — works with Vercel serverless. Three channel types: public (anyone), private (authenticated users only, validated by your server), presence (private + member list). ShopCo uses private channels per order and a presence channel for the admin dashboard.

✨ Optimistic Updates

Don't wait for the server to confirm an action — update the UI immediately, then reconcile with the server response. If the server returns an error, roll back. React Query's useMutation has built-in optimistic update support via onMutate, onError, and onSettled. Example: clicking "Cancel Order" immediately shows "Cancelled" in the UI while the API call happens in the background.

🔄 Reconnection & Resilience

Networks drop. Always handle disconnections: SSE's EventSource auto-reconnects, but track the last event ID (id: field in the stream) so you can resume from where you left off. For WebSockets: implement exponential backoff — retry after 1s, 2s, 4s, 8s, max 30s. Show connection status in the UI so users know if they're seeing stale data. Never silently drop events.

👥 Presence Channels

Pusher's presence channels extend private channels with a member list — you can see who else is subscribed to the same channel. Use for: live user count on a product page, admin seeing which staff are online, collaborative cart editing. Each member authenticates with your server, which adds their metadata (userId, name, role) to the presence data. The client receives pusher:member_added and pusher:member_removed events.

Server-Sent Events in Next.js

app/api/orders/[id]/stream/route.ts — SSE order status stream
import { requireAuth } from '@/lib/auth'
import { prisma } from '@/lib/prisma'

export const runtime = 'edge'  // Edge runtime for streaming

export async function GET(
  req: Request,
  { params }: { params: { id: string } }
) {
  const { userId } = await requireAuth()

  // Verify ownership before streaming
  const order = await prisma.order.findFirst({
    where: { id: params.id, userId }
  })
  if (!order) return new Response('Not found', { status: 404 })

  const stream = new ReadableStream({
    async start(controller) {
      const send = (event: string, data: unknown, id?: string) => {
        const msg = [
          id ? `id: ${id}` : '',
          `event: ${event}`,
          `data: ${JSON.stringify(data)}`,
          '', ''          // blank line ends SSE message
        ].filter(Boolean).join('\n')
        controller.enqueue(new TextEncoder().encode(msg))
      }

      // Send initial state
      send('status', { status: order.status, orderId: order.id }, '0')

      // Poll for status changes every 5s
      let lastStatus = order.status
      let eventId = 1
      const interval = setInterval(async () => {
        const latest = await prisma.order.findUnique({
          where: { id: params.id }, select: { status: true }
        })
        if (latest?.status !== lastStatus) {
          lastStatus = latest.status
          send('status', { status: lastStatus }, String(eventId++))
          if (lastStatus === 'DELIVERED') {
            send('complete', { message: 'Order delivered!' })
            clearInterval(interval)
            controller.close()
          }
        }
      }, 5000)

      // Cleanup on client disconnect
      req.signal.addEventListener('abort', () => clearInterval(interval))
    }
  })

  return new Response(stream, {
    headers: {
      'Content-Type': 'text/event-stream',
      'Cache-Control': 'no-cache',
      'Connection': 'keep-alive',
      'X-Accel-Buffering': 'no',  // disable nginx buffering
    }
  })
}
React hook: useOrderStatus — consuming the SSE stream
'use client'
import { useState, useEffect } from 'react'

export function useOrderStatus(orderId: string) {
  const [status, setStatus] = useState<string>('PENDING')
  const [connected, setConnected] = useState(false)

  useEffect(() => {
    const es = new EventSource(`/api/orders/${orderId}/stream`)
    es.onopen  = () => setConnected(true)
    es.onerror = () => setConnected(false) // EventSource auto-retries

    es.addEventListener('status', (e) => {
      const { status } = JSON.parse(e.data)
      setStatus(status)
    })
    es.addEventListener('complete', () => es.close())

    return () => es.close()  // cleanup on unmount
  }, [orderId])

  return { status, connected }
}

React hook: useAdminDashboard — real-time order stream
'use client'
import { useState, useEffect } from 'react'
import { pusherClient } from '@/lib/pusher'

export function useAdminDashboard() {
  const [liveOrders, setLiveOrders] = useState<Order[]>([])
  const [onlineStaff, setOnlineStaff] = useState(0)

  useEffect(() => {
    // Private channel for order events
    const adminChannel = pusherClient.subscribe('private-admin')
    adminChannel.bind('new-order', (data: NewOrderEvent) => {
      setLiveOrders(prev => [data, ...prev.slice(0, 49)])
    })
    adminChannel.bind('order-status-change', (data) => {
      setLiveOrders(prev =>
        prev.map(o => o.orderId === data.orderId ? { ...o, status: data.status } : o)
      )
    })

    // Presence channel to count online staff
    const presenceChannel = pusherClient.subscribe('presence-staff')
    presenceChannel.bind('pusher:subscription_succeeded', (members) =>
      setOnlineStaff(members.count))
    presenceChannel.bind('pusher:member_added',   () => setOnlineStaff(n => n + 1))
    presenceChannel.bind('pusher:member_removed', () => setOnlineStaff(n => Math.max(0, n - 1)))

    return () => {
      pusherClient.unsubscribe('private-admin')
      pusherClient.unsubscribe('presence-staff')
    }
  }, [])

  return { liveOrders, onlineStaff }
}

Optimistic UI with React Query

Optimistic order cancellation — instant UI, safe rollback
'use client'
import { useQueryClient } from '@tanstack/react-query'
import { trpc } from '@/lib/trpc'

export function OrderCancelButton({ orderId }: { orderId: string }) {
  const utils = trpc.useUtils()

  const cancel = trpc.orders.cancel.useMutation({
    // 1. Optimistically update the cache BEFORE API call
    async onMutate({ orderId }) {
      await utils.orders.list.cancel()
      const previous = utils.orders.list.getData()
      utils.orders.list.setData(undefined, (old) =>
        old?.map(o =>
          o.id === orderId ? { ...o, status: 'CANCELLED' } : o
        )
      )
      return { previous }   // context for rollback
    },
    // 2. On error: roll back to previous state
    onError(err, vars, ctx) {
      if (ctx?.previous)
        utils.orders.list.setData(undefined, ctx.previous)
    },
    // 3. Always refetch to sync with server truth
    onSettled() {
      utils.orders.list.invalidate()
    },
  })

  return (
    <button
      onClick={() => cancel.mutate({ orderId })}
      disabled={cancel.isPending}
    >
      {cancel.isPending ? 'Cancelling...' : 'Cancel Order'}
    </button>
  )
}
⚠ Real-time gotchas in Next.js + Vercel:
SSE connections time out after 10–30s on Vercel's Edge network — use Vercel's Edge Streaming feature or send a keepalive : ping\n\n comment every 25s. WebSockets don't work in Next.js App Router route handlers — use Pusher or a separate WebSocket server. Never store connection state in a module-level variable on serverless — each invocation is isolated. Use Redis pub/sub (Upstash) to fan out events across multiple serverless instances.

Interview Q&A

1. What is the difference between SSE and WebSockets?
SSE (Server-Sent Events) is a one-way HTTP stream — server pushes data to client over a persistent connection. The browser's EventSource API handles reconnection automatically. Works through HTTP/2 multiplexing and most proxies. Best for: notifications, live feeds, order tracking. WebSockets upgrade HTTP to a full-duplex TCP channel — both sides can send at any time. Lower latency for bidirectional communication. Requires a persistent server (not serverless-friendly). Best for: chat, collaborative editing, gaming. For ShopCo: use SSE for customer-facing order updates (read-only), WebSockets (via Pusher) for the admin dashboard where staff interact.
2. Why use Pusher instead of raw WebSockets in a Next.js app?
Raw WebSockets require a persistent server — they can't run in Vercel's serverless functions which terminate after each request. Pusher is a managed WebSocket service: your Next.js API triggers events via HTTP to Pusher's servers, which maintain the persistent WebSocket connections to clients. Benefits: works serverless, scales automatically, built-in auth (private/presence channels), client SDKs for React, automatic reconnection, and a generous free tier. The tradeoff is vendor dependency and slight latency (your API → Pusher servers → client). Alternatives: Ably, Soketi (self-hosted Pusher-compatible).
3. What is optimistic UI and when should you use it?
Optimistic UI updates the interface immediately (assuming success) before the server confirms, then reconciles with the actual server response. Use it when: the action is likely to succeed (low error rate), the latency is noticeable (>200ms), and the rollback UX is acceptable. Good candidates: liking a post, adding to cart, toggling a setting, cancelling an order. Bad candidates: payment processing (always wait for confirmation), irreversible actions, or actions with high failure rates. React Query's onMutate + onError pattern makes this straightforward — snapshot the cache, apply the update, rollback on error.
4. How do you handle SSE in a serverless environment?
Serverless functions time out — on Vercel, Edge functions can stream for longer than serverless functions. Use the Edge runtime: export const runtime = 'edge'. Send SSE keepalive comments (: keepalive\n\n) every 25s to prevent proxy timeouts. For longer-lived connections, use a polling approach server-side within the SSE handler (poll your DB every few seconds). The SSE connection itself stays open — but the Edge function is effectively in a loop. For Vercel's timeout limits, Pusher is more reliable for events that span many minutes (like order tracking over hours).
5. What are Pusher's three channel types and when do you use each?
Public: anyone can subscribe — use for anonymous data like site-wide announcements or stock tickers. Private: subscribers must authenticate via your server (/api/pusher/auth) — use for user-specific data like order updates or personal notifications. Presence: extends private channels with a member list — you can see who else is subscribed. Use for: live user count, "who's viewing this product", admin dashboard online staff count, collaborative features. For ShopCo: private channel per user for order updates, private-admin for staff notifications, presence-staff for the admin dashboard member count.
6. How do you implement exponential backoff for reconnection?
Exponential backoff increases the wait time between retry attempts to avoid hammering a struggling server. Formula: delay = min(base * 2^attempt + jitter, maxDelay). Jitter (random ±0–1s) prevents thundering herd — if many clients reconnect at exactly the same time, they overwhelm the server. Typical values: base=1000ms, max=30000ms. For SSE: the browser's EventSource has built-in retry via the retry: field in the SSE stream. For WebSockets/Pusher: implement manually in the connection manager. Always show a "Reconnecting..." UI so users know the app is aware of the disconnection.
7. How do you fan out real-time events across multiple serverless instances?
Each serverless invocation is isolated — you can't share in-memory state between instances. If instance A handles a new order and instance B handles a WebSocket connection, instance A can't directly push to instance B's connection. Solutions: (1) Pusher/Ably: trigger events via HTTP to Pusher, which handles delivery across all clients regardless of which server instance processed the origin event; (2) Redis pub/sub (Upstash): instance A publishes to Redis, all instances subscribe and forward to their connected clients; (3) Database polling: all SSE handlers poll the same database — simpler but less efficient. For ShopCo, Pusher solves this cleanly.
8. What is the SSE event ID and why is it important?
The SSE id: field in each message tells the browser the ID of the last received event. When the connection drops and the EventSource reconnects, it sends a Last-Event-ID HTTP header with this value. Your server can use this to replay missed events since the disconnect. Without IDs: client misses events during disconnection and gets a stale view. With IDs: seamless reconnection with no gaps. For ShopCo order tracking: store events in Redis or a database keyed by event ID, so a customer who goes offline for 10 minutes catches up when their phone reconnects.
9. When is polling a valid alternative to SSE or WebSockets?
Polling (repeatedly calling a REST endpoint) is valid when: (1) event frequency is low — checking for a daily report is fine, checking for order status once a minute is reasonable; (2) the tech complexity of SSE/WebSockets isn't justified — a simple admin page that refreshes every 30s may be fine; (3) you need to work through restrictive network environments that block long-lived connections; (4) caching is important — polls can be CDN-cached, SSE cannot. Long polling (holding the request open until data is available) is a middle ground. For ShopCo: use polling as a fallback if SSE fails (EventSource onerror after N retries → switch to polling).
10. How would you test real-time features?
Testing real-time is harder than REST because of timing. Approaches: (1) Unit test event formatters — test SSE message formatting, event routing logic, optimistic update reducers in isolation; (2) Integration test with fake time — use vi.useFakeTimers() in Vitest to control timing without real delays; (3) Mock SSE/Pusher — replace EventSource and pusherClient with test doubles that allow triggering events programmatically; (4) E2E with Playwright — test the actual SSE stream end-to-end, triggering a server event and asserting the UI updates; (5) Chaos testing — simulate network drops and verify reconnection behaviour. Most coverage from (1) and (3), E2E for critical user journeys like order tracking.
