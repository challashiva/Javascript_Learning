Closures

Lexical scope, memory capture, the loop bug, and memoization

Q01
What is a closure? Why does the classic loop-with-setTimeout bug happen and how do you fix it?
HARDClosuresScopevar
▾
①
MISCONCEPTION

"A closure is just a function inside another function. Each loop iteration creates its own i, so setTimeout should print 0,1,2,3,4."

②
WHY IT'S WRONG

var is function-scoped, not block-scoped. All five iterations share the same single variable in the enclosing scope. By the time any setTimeout fires, the loop has finished and i === 5. Every callback closes over the same reference — not the value at iteration time.

③
BROKEN CODE
❌ BROKEN — prints 5 five times 
for (var i = 0; i < 5; i++) {
  setTimeout(function() {
    console.log(i); // 5, 5, 5, 5, 5 — NOT 0,1,2,3,4
  }, i * 1000);
}
// When callbacks fire, loop is done: i === 5
// All callbacks share ONE `i` reference, not a copy
④
FIX — THREE APPROACHES
✅ Fix 1: let — creates new binding per iteration 
for (let i = 0; i < 5; i++) {
  setTimeout(() => console.log(i), i * 1000);
}
// ✅ Each iteration has its OWN block-scoped `i` → 0,1,2,3,4
✅ Fix 2: IIFE — captures value in a new scope 
for (var i = 0; i < 5; i++) {
  ((function(j) {
    setTimeout(() => console.log(j), j * 1000);
  })(i)); // j captures current VALUE of i
}
✅ Fix 3: Factory function — most readable 
const makeTimer = n => () => console.log(n);
for (var i = 0; i < 5; i++) {
  setTimeout(makeTimer(i), i * 1000);
}
⑤
DEEP CONCEPT

A closure is a function that retains a live reference to its outer lexical environment — not a snapshot. Think of closures as holding a pointer to a box, not a copy of the value inside. The environment lives as long as any closure references it.

5-KEYWORD SKELETON
function→lexical scope→live reference→not a copy→survives outer
🎒 Memory Peg: A closure is like a backpack. The inner function packs a live wire (pointer) to outer variables — not a photo of their values.
⑥
REAL-WORLD: MEMOIZATION
function memoize(fn) {
  const cache = new Map(); // closed-over — persists between calls
  return function(...args) {
    const key = JSON.stringify(args);
    if (cache.has(key)) return cache.get(key);
    const result = fn.apply(this, args);
    cache.set(key, result);
    return result;
  };
}
const expensiveFn = memoize(n => n * n * n);
expensiveFn(100); // computed
expensiveFn(100); // ✅ cache hit — closure retains `cache`
⑦
PRO TIP / GOTCHA
💡
Memory Leak Gotcha: Closures keep outer scopes alive. A closure capturing a large object or DOM node holds that memory until the closure itself is GC'd. Always remove event listeners when done. Mention three closure examples in interviews: the loop bug, memoization, and React's useState hook.
Q02
Explain closure-based module pattern and private state encapsulation.
MEDIUMClosuresModule PatternEncapsulation
▾
①
MISCONCEPTION

"Private state in JavaScript requires classes with # private fields. Before that, there was no real privacy."

②
WHY IT'S WRONG

The module pattern using closures has provided true data privacy since ES3. A variable in a closure scope is genuinely inaccessible from outside — not by convention, but by the language's scope rules. This pattern powers many production libraries.

④
IMPLEMENTATION
✅ IIFE Module Pattern — true private state 
const Counter = (function() {
  let count = 0; // truly private — no external access
  let step = 1;  // also private

  return {
    increment() { count += step; },
    decrement() { count -= step; },
    setStep(n) { step = n; },
    getCount() { return count; },
    reset() { count = 0; step = 1; }
  };
})();

Counter.increment();
Counter.increment();
Counter.getCount(); // 2
Counter.count;       // undefined — genuinely private

// Factory pattern — creates isolated instances
function createStore(initialState) {
  let state = { ...initialState };
  const listeners = new Set();

  return {
    getState: () => ({ ...state }),
    setState(patch) {
      state = { ...state, ...patch };
      listeners.forEach(fn => fn(state));
    },
    subscribe(fn) { listeners.add(fn); return () => listeners.delete(fn); }
  };
}
const store = createStore({ user: null, theme: 'dark' });
⑦
PRO TIP
💡
ES2022 private fields (#) vs closure privacy: #field is enforced at the language spec level (even in DevTools you can't access it). Closures are private by scope — accessible in theory via prototype manipulation in some edge cases. For modern code, use #; for functional/factory patterns, closures remain idiomatic.

Prototypal Inheritance

The prototype chain, class sugar, Object.create, and mixins

Q03
How does prototypal inheritance differ from classical OOP? Explain the [[Prototype]] chain.
HARDPrototypeOOPclass
▾
①
MISCONCEPTION

"JavaScript class works just like Java/C# classes. When a child class extends a parent, methods are copied into child instances."

②
WHY IT'S WRONG

JS class is syntactic sugar over prototype delegation. Nothing is copied. Objects have a hidden [[Prototype]] link. Property lookup walks the chain — this is delegation, not copying. This distinction matters for performance, memory, and dynamic behavior.

③
BROKEN ASSUMPTION
❌ Wrong mental model 
class Animal { speak() { return '...'; } }
class Dog extends Animal {}
const d = new Dog();

// WRONG: assuming speak is copied onto d
d.hasOwnProperty('speak'); // false — it's NOT on d at all!
// d → Dog.prototype → Animal.prototype → Object.prototype → null
④
HOW THE CHAIN WORKS
✅ Prototype delegation step by step 
const animal = {
  speak() { return `${this.name} speaks`; }
};
const dog = Object.create(animal); // [[Prototype]] = animal
dog.name = 'Rex';
dog.speak(); // "Rex speaks" — found via chain, not own

Object.getPrototypeOf(dog) === animal; // true
dog.hasOwnProperty('speak');         // false
dog.hasOwnProperty('name');          // true

// Own properties SHADOW prototype properties
dog.speak = () => 'Woof!'; // shadows Animal.speak
dog.speak(); // "Woof!" — own property found first
delete dog.speak;
dog.speak(); // "Rex speaks" — chain traversal resumes
⑤
DEEP CONCEPT

Every JS object has [[Prototype]]. Property lookup: check own properties → check [[Prototype]] → repeat until null. class extends wires Child.prototype.[[Prototype]] to Parent.prototype. Memory benefit: methods live once on the prototype, not per instance.

CHAIN LOOKUP
own props→[[Prototype]]→walk up→null terminus→undefined
⑥
REAL-WORLD: MIXIN PATTERN
// Compose behavior without deep inheritance chains
const Serializable = { serialize() { return JSON.stringify(this); } };
const Validatable = { isValid() { return Object.keys(this).length > 0; } };

class User { constructor(n) { this.name = n; } }
Object.assign(User.prototype, Serializable, Validatable);

const u = new User('Alice');
u.isValid();   // true — mixin behavior
u.serialize(); // '{"name":"Alice"}'

// Pure Object.create — no class overhead
const pureHashMap = Object.create(null); // NO prototype at all
// Perfect for dictionaries — no toString/valueOf interference
⑦
PRO TIP / GOTCHA
💡
Never use __proto__ in production — use Object.getPrototypeOf(). Also: instanceof checks the prototype chain, not the constructor. An object from a different realm (iframe window) will fail instanceof Array — use Array.isArray() instead.
Q04
What happens under the hood when you use the `new` keyword?
MEDIUMnew keywordPrototypeConstructor
▾
④
WHAT `new` DOES — 4 STEPS
// `new Foo(args)` does exactly this internally:
function myNew(Constructor, ...args) {
  // 1. Create a fresh object
  const obj = {};

  // 2. Set its [[Prototype]] to Constructor.prototype
  Object.setPrototypeOf(obj, Constructor.prototype);

  // 3. Call constructor with `this` = obj
  const result = Constructor.apply(obj, args);

  // 4. Return result if object, else return obj
  return (result && typeof result === 'object') ? result : obj;
}

function Person(name) { this.name = name; }
Person.prototype.greet = function() { return `Hi, I'm ${this.name}`; };

const p = myNew(Person, 'Alice');
p.greet();           // "Hi, I'm Alice"
p instanceof Person; // true
⑦
PRO TIP
💡
Step 4 gotcha: If a constructor explicitly returns an object, that object is used instead of the newly created one. This is how some patterns intentionally override new behavior — used in singleton patterns and some ORMs.

this Binding

Four binding rules, arrow functions, call/apply/bind

Q05
Explain the four rules of `this` binding and how arrow functions change the picture.
HARDthisArrow Functionscall/bind/apply
▾
①
MISCONCEPTION

"this refers to the object the function is defined inside."

②
WHY IT'S WRONG

this is determined entirely at call time, not definition time. It depends on how the function is invoked. Arrow functions are the only exception — they capture this lexically at definition time because they have no own this.

③
BROKEN CODE
❌ this-loss bug 
const timer = {
  count: 0,
  start() {
    setInterval(function() {
      this.count++; // ❌ this = undefined (strict) or global
    }, 1000);
  }
};
timer.start(); // NaN — this.count doesn't exist

// Also: method extraction loses implicit binding
const { start } = timer;
start(); // ❌ `this` is global/undefined — lost!
④
THE FOUR RULES + PRIORITY
✅ Rule 1: Default — standalone call → global/undefined 
function f() { return this; }
f(); // window (sloppy mode) | undefined (strict mode)
✅ Rule 2: Implicit — object before the dot 
obj.f(); // this === obj
✅ Rule 3: Explicit — call/apply/bind 
fn.call(ctx, arg1);        // this = ctx
fn.apply(ctx, [arg1,arg2]); // this = ctx, spread args
const bound = fn.bind(ctx); // permanently bound, new fn
✅ Rule 4: new — fresh object 
new Foo(); // this = newly created object
✅ Arrow fix — lexical this 
const timer = {
  count: 0,
  start() {
    setInterval(() => {
      this.count++; // ✅ inherits this from start() = timer
    }, 1000);
  }
};
ℹ️
Priority: new > explicit (bind/call/apply) > implicit (obj.method) > default
⑤
DEEP CONCEPT

Arrow functions have no own this — they cannot be used as constructors (new throws TypeError), and .bind() has no effect on their this. They inherit this from the enclosing lexical (non-arrow) context at definition time.

DECISION FLOWCHART
new?→bind/call/apply?→obj.method?→default
⑥
REAL-WORLD: REACT CLASS COMPONENTS
// Why React class components needed bind
class Button extends React.Component {
  constructor(props) {
    super(props);
    this.handleClick = this.handleClick.bind(this);
    // Without bind: React calls handleClick() — default binding
    // → this is undefined in strict mode → crash
  }
  handleClick() { console.log(this.state); }
}

// Modern solution: class field arrow function
class Button extends React.Component {
  handleClick = () => { // arrow — lexical this = instance
    console.log(this.state); // ✅ always correct
  }
}
⑦
PRO TIP
💡
Gotcha — implicit binding loss: const fn = obj.method; fn(); loses implicit binding. setTimeout(obj.method, 0) also loses it. Always use .bind(), arrow wrappers, or class field arrows when passing methods as callbacks.

Scope & Hoisting

TDZ, var/let/const hoisting mechanics, block scope

Q06
What is hoisting? How are var, let, const, and function declarations hoisted differently?
MEDIUMHoistingTDZvar/let/const
▾
①
MISCONCEPTION

"Only var is hoisted. let and const are not hoisted at all. Hoisting means code physically moves to the top."

②
WHY IT'S WRONG

All declarations are hoisted — registered in scope during the parse phase. The difference is initialization. var is initialized to undefined. let/const are hoisted but left uninitialized in the Temporal Dead Zone (TDZ). Accessing them throws ReferenceError.

③
TDZ TRAP
❌ TDZ violation 
console.log(x); // undefined — var initialized at parse time
console.log(y); // ❌ ReferenceError: Cannot access 'y' before init
console.log(z); // ❌ ReferenceError: Cannot access 'z' before init

var x = 10;
let y = 20;
const z = 30;
④
HOW JS ENGINE PROCESSES DECLARATIONS
✅ Two-phase execution model 
// PHASE 1: Parsing (before any code runs)
// → var declarations: registered + initialized to undefined
// → let/const declarations: registered + UNINITIALIZED (TDZ)
// → function declarations: registered + FULLY initialized

foo(); // ✅ works — function declarations fully hoisted
function foo() { return 'hi'; }

var fn = function() {}; // fn is hoisted as undefined, fn() before this → TypeError
const arr = function() {}; // TDZ — cannot access before line

// PHASE 2: Execution
var count = 0; // assignment happens here
const PI = 3.14; // TDZ ends here, PI initialized
PI = 3; // ❌ TypeError: Assignment to constant variable
⑤
DEEP CONCEPT — TDZ PURPOSE

The Temporal Dead Zone is intentional: it forces you to declare before using, eliminating a class of bugs that var's undefined initialization silently created. TDZ exists in the time between entering a block scope and reaching the let/const declaration line.

ℹ️
Scope: var = function-scoped. let/const = block-scoped ({}, loops, if, try/catch). This is why let in a for loop creates a new binding per iteration — each iteration is its own block.
📦 Memory Peg: TDZ is like a reserved parking spot with a "Not yet available" sign. The spot exists — but you can't use it until the car arrives (initialization).
⑥
REAL-WORLD GOTCHA
// Subtle TDZ in class fields
class Config {
  host = this.getDefault(); // ✅ class fields run in declaration order
  port = 8080;
  getDefault() { return 'localhost'; }
}

// Circular ESM imports can cause TDZ at runtime!
// moduleA.js imports from moduleB.js
// moduleB.js imports from moduleA.js
// One of them gets an uninitialized binding → ReferenceError
⑦
PRO TIP
💡
Rule of thumb: Always use const by default. Use let only when reassignment is needed. Never use var in modern code. ESLint's no-var rule enforces this automatically.

Event Loop & Microtask Queue

Call stack, macrotasks, microtasks, and render timing

Q07
How does the JavaScript event loop work? What's the difference between microtask and macrotask queues?
HARDEvent LoopMicrotaskssetTimeout
▾
①
MISCONCEPTION

"setTimeout(fn, 0) runs immediately after the current code. Promises and setTimeout callbacks go into the same queue."

②
WHY IT'S WRONG

There are two separate queues. The microtask queue is always fully drained before the event loop picks the next macrotask. Promises use microtasks, setTimeout uses macrotasks — so Promise callbacks always run before setTimeout, even if both are ready.

③
THE CLASSIC PUZZLE
⚡ Predict the output — frequent senior interview question 
console.log('1');

setTimeout(() => console.log('2'), 0);

Promise.resolve().then(() => console.log('3'));

queueMicrotask(() => console.log('4'));

console.log('5');

// Output: 1, 5, 3, 4, 2
// Sync:      1, 5  (call stack)
// Microtask: 3, 4  (fully drained before macrotask)
// Macrotask: 2     (setTimeout)
④
EVENT LOOP ALGORITHM
✅ Pseudocode of the event loop 
while (true) {
  // 1. Execute ALL synchronous code on call stack
  executeSyncCode();

  // 2. Drain ENTIRE microtask queue (including newly added!)
  while (microtaskQueue.length) {
    microtaskQueue.shift()();
  }

  // 3. Pick ONE macrotask and execute it
  if (macrotaskQueue.length) macrotaskQueue.shift()();

  // 4. Render (if browser needs repaint/reflow)
  renderIfNeeded();
}
⚠️
Danger: An infinite microtask loop (Promise always resolves, schedules another Promise) starves the macrotask queue. The page freezes — no rendering, no setTimeout callbacks, no user input handled.
⑤
DEEP CONCEPT

Macrotasks: setTimeout, setInterval, setImmediate (Node), I/O callbacks, UI events, postMessage
Microtasks: Promise .then/.catch/.finally, queueMicrotask(), MutationObserver, async/await continuations

MENTAL MODEL
call stack clears→drain microtasks→one macrotask→render→repeat
🚦 Memory Peg: Microtasks are the VIP lane — ALL of them go through before the next regular customer (macrotask) steps up. No exceptions.
⑥
REAL-WORLD: UI RENDERING WINDOW
async function loadData() {
  showSpinner(); // sync — immediate

  const data = await fetch('/api/data');
  // ↑ await yields to event loop — browser CAN render here!
  // Spinner appears before data loads ✅

  hideSpinner(); // runs when microtask resumes
  render(await data.json());
}

// Without await, the spinner never renders before data arrives:
function badLoad() {
  showSpinner();
  const data = fetchSync(); // blocks entire thread — spinner never shows
  hideSpinner();
}
⑦
PRO TIP
💡
Interview Gold: Each await creates a microtask checkpoint. queueMicrotask() is useful when you need something to run after sync code but before I/O — without the overhead of a resolved Promise chain. Also useful for batching multiple synchronous state updates before a single render.

Promises & Async/Await

Internals, error handling, combinators, and implementation

Q08
What are Promise's internal states? How does error propagation work through chains?
HARDPromisesError HandlingCombinators
▾
①
MISCONCEPTION

"A .catch() at the end of a chain catches everything. try/catch around async functions catches all errors including unhandled rejections."

②
WHY IT'S WRONG

Each Promise chain is independent. An un-awaited Promise that rejects isn't caught by another chain's .catch() or a try/catch. Errors thrown inside .then() create new rejected Promises — they don't bubble synchronously.

③
BROKEN PATTERNS
❌ Silent swallowing — un-awaited promise 
async function getData() {
  const a = fetch('/api/a'); // NOT awaited — fire and forget
  const b = await fetch('/api/b');
  // If `a` rejects → unhandledRejection → crashes Node 15+!
}

// ❌ .catch() in wrong position
fetchUser()
  .then(u => fetchPosts(u.id))
  .catch(e => log(e))   // catches fetchUser errors
  .then(p => process(p)); // ❌ errors here are UNCAUGHT
④
CORRECT PATTERNS
✅ States: pending → fulfilled | rejected (immutable once settled) 
// Terminal .catch() catches ALL prior errors
fetchUser()
  .then(u => fetchPosts(u.id))
  .then(p => process(p))
  .catch(e => handleError(e))  // ✅ catches ALL above
  .finally(() => hideSpinner()); // ✅ always runs

// Parallel with per-request fallback
const [users, posts] = await Promise.all([
  fetchUsers().catch(() => []),
  fetchPosts().catch(() => []),
]);

// allSettled — never rejects, inspect each result
const results = await Promise.allSettled([p1, p2, p3]);
results.forEach(r => {
  if (r.status === 'fulfilled') use(r.value);
  else logError(r.reason);
});
⑤
PROMISE COMBINATORS
ℹ️
Promise.all — rejects immediately if ANY rejects (fail-fast)
Promise.allSettled — waits for all, returns status objects
Promise.race — resolves/rejects with FIRST settled
Promise.any — resolves with FIRST fulfilled; rejects only if ALL reject (AggregateError)
⑥
REAL-WORLD: RETRY WITH BACKOFF
async function fetchWithRetry(url, retries = 3, delay = 500) {
  for (let i = 0; i < retries; i++) {
    try {
      return await fetch(url).then(r => r.json());
    } catch (e) {
      if (i === retries - 1) throw e; // last attempt — rethrow
      await new Promise(r => setTimeout(r, delay * 2 ** i));
    }
  }
}
⑦
PRO TIP
💡
await in forEach: await inside Array.forEach does NOT work — forEach ignores returned Promises. Use for...of for sequential async iteration, or Promise.all(array.map(async item => ...)) for parallel.
Q09
Implement a Promise from scratch. How does .then() chaining work internally?
HARDPromise InternalsImplementation
▾
⑤
FULL IMPLEMENTATION
class MyPromise {
  constructor(executor) {
    this.state = 'pending';
    this.value = undefined;
    this.handlers = [];

    const resolve = value => {
      if (this.state !== 'pending') return; // immutable once settled
      this.state = 'fulfilled';
      this.value = value;
      this.handlers.forEach(h => h.onFulfilled(value));
    };
    const reject = reason => {
      if (this.state !== 'pending') return;
      this.state = 'rejected';
      this.value = reason;
      this.handlers.forEach(h => h.onRejected(reason));
    };
    try { executor(resolve, reject); }
    catch(e) { reject(e); }
  }

  then(onFulfilled, onRejected) {
    return new MyPromise((resolve, reject) => {
      const handle = (fn, val) => {
        queueMicrotask(() => { // spec: callbacks are async
          try { resolve(fn(val)); }
          catch(e) { reject(e); }
        });
      };
      if (this.state === 'fulfilled')
        handle(onFulfilled, this.value);
      else if (this.state === 'rejected')
        handle(onRejected ?? (e => { throw e; }), this.value);
      else
        this.handlers.push({
          onFulfilled: v => handle(onFulfilled, v),
          onRejected:  v => handle(onRejected ?? (e => { throw e; }), v)
        });
    });
  }

  catch(fn) { return this.then(undefined, fn); }
  finally(fn) {
    return this.then(
      v => { fn(); return v; },
      e => { fn(); throw e; }
    );
  }
}
// Key insight: each .then() returns a NEW promise
// The return value of onFulfilled becomes the next promise's value
// This is the chain mechanism — not mutation of original promise

Generators & Iterators

Lazy evaluation, infinite sequences, and async generators

Q10
What are generators and iterators? When would you use them over async/await?
HARDGeneratorsSymbol.iteratorLazy Evaluation
▾
①
MISCONCEPTION

"Generators are just an old way to write async code. Now that async/await exists, generators are obsolete."

②
WHY IT'S WRONG

Generators solve a different problem: lazy, on-demand value production and custom iteration protocols. They pause and resume on demand, producing values one at a time. Async/await handles time-based waiting. Generators handle value-sequence-based pausing. They're still used heavily in Redux-Saga, infinite sequences, and streaming.

④
GENERATORS IN ACTION
✅ Infinite sequence — impossible with arrays 
function* naturals(start = 1) {
  while (true) yield start++;
}
const gen = naturals();
gen.next().value; // 1
gen.next().value; // 2 — computes on demand, no memory overhead

// Custom iterable with Symbol.iterator
class Range {
  constructor(start, end) { this.start = start; this.end = end; }
  [Symbol.iterator]() {
    let cur = this.start;
    const end = this.end;
    return {
      next: () => cur <= end
        ? { value: cur++, done: false }
        : { value: undefined, done: true }
    };
  }
}
[...new Range(1, 5)]; // [1, 2, 3, 4, 5]

// Simpler with generator
function* range(start, end) {
  for (let i = start; i <= end; i++) yield i;
}
✅ Async generator — streaming paginated data 
async function* streamPages(url) {
  let page = 1;
  while (true) {
    const data = await fetch(`${url}?page=${page}`).then(r => r.json());
    if (!data.length) break;
    yield data;
    page++;
  }
}
for await (const page of streamPages('/api/items')) {
  render(page); // process each page as it arrives — memory efficient
}
⑤
DEEP CONCEPT

Generators implement the Iterator protocol: an object with a next() method returning { value, done }. Generator functions (function*) automatically return iterators. yield suspends execution and returns the value. next(val) resumes with val replacing the yield expression — enabling two-way communication.

ℹ️
for...of, spread (...), destructuring, Array.from(), and Promise.all() all consume the Symbol.iterator protocol. Making your class iterable makes it work with all these natively.
⑦
PRO TIP
💡
Redux-Saga uses generators for side effect management — showing they're alive in production. Also: async generators are perfect for consuming ReadableStream data from the Fetch API — more memory efficient than buffering the entire response.

Memory Management & Garbage Collection

Mark-and-sweep, generational GC, leak patterns

Q11
How does JavaScript garbage collection work? What are the most common memory leak patterns?
HARDGCMemory LeaksMark-and-Sweep
▾
①
MISCONCEPTION

"JavaScript manages memory automatically. I never need to think about memory leaks."

②
WHY IT'S WRONG

GC only collects objects with no reachable references. If your code accidentally retains references (closures, event listeners, global variables, detached DOM), memory grows until the tab crashes. SPAs running for hours are especially susceptible.

③
FOUR CLASSIC LEAK PATTERNS
❌ Leak 1: Forgotten event listeners 
function setup() {
  const bigData = new Array(100000).fill({ value: 42 });
  document.addEventListener('click', () => {
    console.log(bigData); // closure keeps bigData alive FOREVER
  });
} // bigData never GC'd — listener holds it
❌ Leak 2: Detached DOM nodes 
let ref;
function createLeak() {
  const div = document.createElement('div');
  ref = div; // JS reference keeps it alive
  document.body.appendChild(div);
  document.body.removeChild(div); // removed from DOM but NOT GC'd
}
❌ Leak 3: Growing cache without eviction 
const cache = {}; // grows forever
requests.forEach(id => { cache[id] = process(id); });
❌ Leak 4: setInterval not cleared 
function startPolling() {
  setInterval(() => syncData(), 5000); // never cleared → runs forever
}
④
THE FIXES
✅ Return cleanup, use WeakMap, bound cache size 
// Fix 1: Store reference, remove when done
const handler = () => doWork();
element.addEventListener('click', handler);
return () => element.removeEventListener('click', handler);

// Fix 2: WeakMap for DOM-associated data
const meta = new WeakMap();
meta.set(element, { visited: true });
// When element is removed, WeakMap entry is auto-collected

// Fix 3: LRU Cache with max size
class LRUCache {
  constructor(max) { this.max = max; this.map = new Map(); }
  get(k) {
    if (!this.map.has(k)) return undefined;
    const v = this.map.get(k);
    this.map.delete(k); this.map.set(k, v); // move to end (most recent)
    return v;
  }
  set(k, v) {
    if (this.map.size >= this.max)
      this.map.delete(this.map.keys().next().value); // evict oldest
    this.map.set(k, v);
  }
}

// Fix 4: React useEffect cleanup
useEffect(() => {
  const id = setInterval(() => sync(), 5000);
  return () => clearInterval(id); // ✅ cleaned up on unmount
}, []);
⑤
DEEP CONCEPT — V8 GENERATIONAL GC

V8 uses Mark-and-Sweep: starting from "roots" (globals, call stack), mark all reachable objects; collect the rest. V8 optimizes with generational GC:

Young generation (nursery): most objects born here. Collected frequently via "scavenging" — fast, parallel, only touches young objects.
Old generation: objects that survive 1-2 scavenges are promoted. Collected less often via "major GC" — slower, full mark-and-sweep.

🗑️ Memory Peg: GC is like a janitor who only picks up trash nobody is pointing at. As long as your code holds any pointer — even indirectly through a closure — the janitor leaves it alone forever.
⑦
PRO TIP
💡
Profiling: Chrome DevTools → Memory tab → "Take Heap Snapshot" before and after suspected leak. Filter for "Detached HTMLElement." In React apps, the most common leaks are: forgotten useEffect subscriptions, timers not cleared on unmount, and closures over stale component state.

WeakMap & WeakRef

Weak references, memory-safe associations, FinalizationRegistry

Q12
When should you use WeakMap vs Map? What is WeakRef and FinalizationRegistry?
HARDWeakMapWeakRefMemory
▾
①
MISCONCEPTION

"WeakMap is just a Map with less features. There's no practical reason to use it."

②
WHY IT'S WRONG

WeakMap's weak references mean entries are automatically removed when the key object is GC'd — preventing memory leaks entirely. This is essential when you want to associate data with objects whose lifecycle you don't control (DOM nodes, component instances, third-party objects).

④
ALL WEAK REFERENCE PATTERNS
✅ WeakMap for private class data 
const _private = new WeakMap();

class BankAccount {
  constructor(balance) {
    _private.set(this, { balance, txLog: [] });
  }
  deposit(amt) {
    const d = _private.get(this);
    d.balance += amt;
    d.txLog.push({ type: 'deposit', amt, ts: Date.now() });
  }
  getBalance() { return _private.get(this).balance; }
}
// When BankAccount instance is GC'd → _private entry auto-removed
// No size() or forEach — WeakMap is intentionally non-enumerable
✅ WeakRef — optional cache that doesn't prevent GC 
class OptionalCache {
  constructor() { this.map = new Map(); }
  set(key, value) {
    this.map.set(key, new WeakRef(value));
  }
  get(key) {
    const ref = this.map.get(key);
    const val = ref?.deref(); // returns undefined if GC'd
    if (!val) this.map.delete(key); // clean up stale entry
    return val;
  }
}

// FinalizationRegistry — callback after GC
const registry = new FinalizationRegistry(id => {
  console.log(`${id} was garbage collected`);
  cleanupExternalResource(id);
});
registry.register(myHeavyObject, 'my-heavy-object');
⑤
WHEN TO USE WHICH
ℹ️
Map: need to enumerate keys, count entries, store primitive keys, full lifecycle control
WeakMap: associate data with objects you don't own, want auto-cleanup when object dies
WeakRef: optional caching — GC may collect value, code must handle undefined
FinalizationRegistry: run cleanup callbacks after GC (non-deterministic timing!)
⑦
PRO TIP
💡
React and Vue use WeakMap-like patterns internally to associate component state with DOM nodes without memory leaks. The new WeakSet is useful for tracking "has this object been processed" without preventing GC — perfect for cycle detection in traversal algorithms.

Design Patterns

Observer, Factory, Proxy/Reflect, Singleton, Decorator

Q14
Implement the Observer pattern. How does Proxy enable meta-programming in JavaScript?
MEDIUMObserverProxyReflect
▾
④
OBSERVER PATTERN + REACTIVE SYSTEM
✅ EventEmitter — foundation of reactive systems 
class EventEmitter {
  constructor() { this.events = new Map(); }

  on(event, listener) {
    if (!this.events.has(event)) this.events.set(event, new Set());
    this.events.get(event).add(listener);
    return () => this.off(event, listener); // returns unsubscribe fn
  }
  off(event, fn) { this.events.get(event)?.delete(fn); }
  emit(event, data) { this.events.get(event)?.forEach(fn => fn(data)); }
  once(event, fn) {
    const wrap = d => { fn(d); this.off(event, wrap); };
    return this.on(event, wrap);
  }
}

// Proxy-based reactive state (Vue-like)
function reactive(target) {
  const listeners = new Map();
  return new Proxy(target, {
    set(obj, key, value) {
      Reflect.set(obj, key, value); // use Reflect for correctness
      listeners.get(key)?.forEach(fn => fn(value));
      return true;
    },
    get(obj, key) {
      if (key === '$watch') return (k, fn) => {
        if (!listeners.has(k)) listeners.set(k, new Set());
        listeners.get(k).add(fn);
        return () => listeners.get(k)?.delete(fn);
      };
      return Reflect.get(obj, key);
    }
  });
}

const state = reactive({ count: 0, user: null });
state.$watch('count', v => console.log('count:', v));
state.count = 1; // triggers: "count: 1"
⑥
PROXY USE CASES
// Validation proxy
const validated = new Proxy({}, {
  set(obj, key, value) {
    if (key === 'age' && (typeof value !== 'number' || value < 0))
      throw new TypeError('age must be a positive number');
    return Reflect.set(obj, key, value);
  }
});

// Logging proxy — intercept all property access
const createLogger = target => new Proxy(target, {
  get(obj, key) {
    console.log(`accessed: ${String(key)}`);
    return Reflect.get(obj, key);
  }
});
⑦
PRO TIP
💡
Always pair Proxy with Reflect — Reflect methods mirror Proxy traps and handle edge cases correctly (receiver binding, inheritance). Using obj[key] = value inside a set trap can miss prototype setter calls — Reflect.set(obj, key, value, receiver) handles it correctly.

Performance Optimization

Debounce, throttle, rAF, lazy loading, and profiling

Q15
Implement debounce and throttle from scratch. When would you use requestAnimationFrame instead?
MEDIUMDebounceThrottlerAF
▾
①
MISCONCEPTION

"Debounce and throttle do the same thing — they limit how often a function runs."

②
WHY IT'S WRONG

Debounce: fires ONLY after input stops for a specified delay. Throttle: fires at most once per time window regardless of input frequency. Wrong choice causes UX bugs: debouncing a scroll handler means it fires only after scrolling STOPS — terrible. Throttling a search box means queries fire mid-typing — wasteful.

④
CLEAN IMPLEMENTATIONS
✅ Debounce — waits for inactivity 
function debounce(fn, delay) {
  let timer;
  return function(...args) {
    clearTimeout(timer);
    timer = setTimeout(() => fn.apply(this, args), delay);
  };
}
// User types "react" → fires once, 300ms after last keystroke
const search = debounce(query => fetchResults(query), 300);
input.addEventListener('input', e => search(e.target.value));
✅ Throttle — fires at most once per interval 
function throttle(fn, interval) {
  let last = 0;
  return function(...args) {
    const now = Date.now();
    if (now - last >= interval) {
      last = now;
      return fn.apply(this, args);
    }
  };
}
// Scroll fires 100x/sec → handler runs max every 100ms
const onScroll = throttle(() => updateStickyHeader(), 100);
window.addEventListener('scroll', onScroll, { passive: true });
✅ rAF throttle — syncs with browser paint cycle 
function rafThrottle(fn) {
  let pending = false;
  return function(...args) {
    if (pending) return;
    pending = true;
    requestAnimationFrame(() => {
      fn.apply(this, args);
      pending = false;
    });
  };
}
// Perfect for: scroll position updates, canvas drawing, animations
// rAF auto-pauses when tab is hidden → no wasted CPU
⑤
WHEN TO USE EACH
ℹ️
Debounce: search input, window resize (final layout), autocomplete, form validation
Throttle: scroll listeners (show/hide), mousemove tracking, real-time collaboration cursors
rAF: visual updates, canvas rendering, animations — needs to sync with 60fps paint cycle
⑥
REAL-WORLD: ADVANCED DEBOUNCE WITH CANCEL
function debounce(fn, delay, { leading = false } = {}) {
  let timer, result;
  const debounced = function(...args) {
    const callNow = leading && !timer;
    clearTimeout(timer);
    timer = setTimeout(() => {
      timer = null;
      if (!leading) result = fn.apply(this, args);
    }, delay);
    if (callNow) result = fn.apply(this, args);
    return result;
  };
  debounced.cancel = () => { clearTimeout(timer); timer = null; };
  debounced.flush = (...args) => { debounced.cancel(); return fn.apply(this, args); };
  return debounced;
}
⑦
PRO TIP
💡
In React, use useCallback to memoize the debounced/throttled function reference — otherwise a new function is created on every render and the timer is lost. Or use useRef to persist the function instance across renders without triggering re-renders.

V8 Engine Internals

JIT compilation, hidden classes, Ignition and TurboFan

Q16
How does V8's JIT compiler work? What are hidden classes and how do you write V8-friendly code?
HARDV8JITHidden ClassesTurboFan
▾
⑤
DEEP CONCEPT — V8 PIPELINE

V8 uses a two-tier JIT pipeline:

Ignition (interpreter): parses JS → bytecode → executes immediately. Fast startup, lower peak performance.

TurboFan (optimizing compiler): detects "hot" code paths, compiles to optimized machine code using type feedback collected by Ignition. Assumes types stay consistent.

Deoptimization: if TurboFan's assumptions are violated (type changes), it "bails out" back to Ignition — expensive operation.

❌ Hidden class transitions — forces deoptimization 
function makePoint(x, y) {
  const pt = {};
  pt.x = x; // hidden class A → B (transition!)
  pt.y = y; // hidden class B → C (transition!)
  if (x > 0) pt.label = 'positive'; // sometimes C → D
  // V8 sees MULTIPLE shapes — can't optimize property access
  return pt;
}

delete point.x; // ❌ kills hidden class — never delete, set null instead
✅ V8-friendly code patterns 
// Always initialize all properties in constructor, same order
function makePoint(x, y, label = null) {
  return { x, y, label }; // consistent shape — one hidden class
}

// Monomorphic functions (same arg types) stay TurboFan-optimized
function add(a, b) { return a + b; }
add(1, 2);     // V8 infers number + number → optimized
add(3, 4);     // same types → fast path
add('a', 'b'); // ❌ type change → deoptimize (megamorphic)

// Arrays: keep homogeneous types — V8 uses specialized array kinds
const nums = [1, 2, 3];    // PACKED_SMI_ELEMENTS (fastest)
nums.push(1.5);            // PACKED_DOUBLE_ELEMENTS
nums.push('a');            // PACKED_ELEMENTS (boxed, slowest)
// Transitions are one-way — can't go back to faster kind
⑦
PRO TIP
💡
Interview gold: Mentioning hidden classes and monomorphic functions signals senior-level understanding. Also: V8's Orinoco GC uses incremental marking, parallel scavenging, and concurrent marking to minimize main thread pauses — this is why modern JS can achieve sub-millisecond GC pauses in production.

Web Workers & SharedArrayBuffer

True parallelism, Atomics, structured clone, and Transferables

Q17
What are Web Workers? When would you use SharedArrayBuffer and Atomics for true parallel processing?
HARDWeb WorkersSharedArrayBufferAtomics
▾
①
MISCONCEPTION

"JavaScript is single-threaded — it can't do real parallel processing in the browser."

②
WHY IT'S WRONG

The main thread is single-threaded. But Web Workers run in separate OS threads — actual parallelism. They can't access the DOM, but can do CPU-intensive work concurrently. SharedArrayBuffer provides shared memory between threads for zero-copy data sharing.

④
WORKERS IN PRACTICE
✅ Offload heavy CPU work 
// main.js — UI thread
const worker = new Worker('./worker.js');
worker.postMessage({ pixels: imageData }); // structured clone
worker.onmessage = ({ data }) => displayResult(data);
worker.onerror = e => console.error('Worker error:', e);

// worker.js — background thread (no DOM access!)
self.onmessage = ({ data: { pixels } }) => {
  const processed = applyGrayscale(pixels); // heavy computation
  self.postMessage({ result: processed }, [processed.buffer]); // transfer!
};
✅ SharedArrayBuffer — zero-copy shared memory 
// main.js
const sab = new SharedArrayBuffer(4); // 4 bytes shared
const view = new Int32Array(sab);
worker.postMessage({ sab }); // same memory — no copy!

// In worker: both see the SAME memory
// Problem: race conditions without synchronization

// Atomics — thread-safe operations
Atomics.add(view, 0, 1);                  // atomic increment
Atomics.load(view, 0);                   // safe read
Atomics.compareExchange(view, 0, 0, 1);  // CAS — lock-free sync
Atomics.wait(view, 0, 0);                // block until value changes
Atomics.notify(view, 0, 1);              // wake 1 waiting worker
⑤
TRANSFERABLES VS STRUCTURED CLONE
// Structured Clone: copies data (default postMessage)
// Works with: objects, arrays, Maps, Sets, ArrayBuffers, etc.
// Cost: proportional to data size

// Transferable: moves data — main thread loses access (zero-copy!)
const bigBuffer = new ArrayBuffer(1024 * 1024 * 100); // 100MB
worker.postMessage(bigBuffer, [bigBuffer]); // ✅ zero-copy transfer
console.log(bigBuffer.byteLength); // 0 — main thread lost it

// Transferable types: ArrayBuffer, MessagePort, ImageBitmap,
// OffscreenCanvas, ReadableStream, TransformStream, WritableStream
⚠️
SharedArrayBuffer requires COOP/COEP headers: Cross-Origin-Opener-Policy: same-origin and Cross-Origin-Embedder-Policy: require-corp must be set on the server to enable SharedArrayBuffer.
⑥
REAL-WORLD USE CASES
✅
Perfect for Workers: Image/video processing, large CSV/Excel parsing, cryptography, WASM computation, physics simulations, syntax highlighting (Monaco Editor), spell checking, compression (zip), neural network inference (TensorFlow.js), PDF rendering.
⑦
PRO TIP
💡
Worker pool pattern: Creating/destroying workers is expensive. Use a pool of N workers (usually navigator.hardwareConcurrency) and queue tasks to them. Libraries like comlink abstract the postMessage API into regular async function calls — much cleaner DX.
