Core Concepts

🔗 Relation Design Principles

Choose relations based on cardinality and ownership. 1:1 (User → Profile): separate table when optional or large. 1:N (Product → Reviews): foreign key on the "many" side. M:N (Order → Products): always use an explicit junction table (OrderItem) with extra fields (quantity, price at time of purchase). Never store arrays of IDs in a column — that's a sign you need a M:N relation.

🗑️ Soft Deletes

Instead of DELETE FROM products WHERE id = $1, set deletedAt = NOW(). Benefits: audit trail, undo capability, referential integrity (orders still reference the deleted product). Always add WHERE deletedAt IS NULL to every query — use Prisma middleware to do this automatically. Add a partial index: CREATE INDEX ON products WHERE deleted_at IS NULL to keep queries fast.

📋 Audit Trail

Record every significant change: who (userId), what (table + recordId + field), when (timestamp), old value, new value. Two approaches: (1) Application-level: Prisma middleware writes to an AuditLog table before/after every mutation; (2) Database-level: Postgres triggers + temporal tables. Application-level is more portable and lets you add context (userId from session). Critical for GDPR compliance and debugging production incidents.

⚡ Index Strategy

Indexes speed up reads but slow writes — add only what your queries need. Always index: foreign keys, columns in WHERE clauses, columns in ORDER BY. Composite indexes: order matters — (userId, createdAt) helps WHERE userId = ? ORDER BY createdAt but not WHERE createdAt = ?. Partial indexes for filtered queries: WHERE deletedAt IS NULL. Use EXPLAIN ANALYZE to verify index usage.

🚀 Expand/Contract Pattern

Zero-downtime schema changes in 3 phases: (1) Expand: add new column as nullable, deploy code that writes to both old and new column; (2) Backfill: migrate existing data to new column; (3) Contract: make new column required, drop old column, deploy code that only uses new column. Never make a breaking migration (rename/delete column) in a single deploy — old code still running will crash.

📄 Cursor vs Offset Pagination

Offset (SKIP 100 TAKE 20) is unstable — inserting a row shifts everything, causing duplicates or missed items. Slow on large tables: DB must count 100 rows to skip. Cursor pagination: encode the last item's ID (or composite key) as a cursor, then WHERE id > $cursor ORDER BY id TAKE 20. Stable, uses index efficiently, works at any scale. Tradeoff: no jumping to arbitrary pages.

model ProductVariant {
  id            String   @id @default(cuid())
  productId     String
  product       Product  @relation(fields:[productId], references:[id])
  sku           String   @unique
  size          String?
  colour        String?
  priceModifier Decimal  @default(0) @db.Decimal(10,2)
  stock         Int      @default(0)
  orderItems    OrderItem[]

  @@unique([productId, size, colour])  // no duplicate variant combinations
  @@index([productId])
}

  status      OrderStatus @default(PENDING)
  totalAmount Decimal     @db.Decimal(10,2)
  addressId   String
  address     Address     @relation(fields:[addressId], references:[id])
  items       OrderItem[]
  createdAt   DateTime    @default(now())

  @@index([status])
}

  orderId   String
  order     Order          @relation(fields:[orderId], references:[id])
  variantId String
  variant   ProductVariant @relation(fields:[variantId], references:[id])
  quantity  Int
  unitPrice Decimal        @db.Decimal(10,2) // price AT TIME OF PURCHASE

  @@unique([orderId, variantId])
}

model Review {
  id        String   @id @default(cuid())
  productId String
  product   Product  @relation(fields:[productId], references:[id])
  userId    String
  rating    Int      // 1-5, enforced at app layer
  comment   String?
  verified  Boolean  @default(false) // verified purchase
  createdAt DateTime @default(now())

  @@unique([productId, userId])  // one review per user per product
  @@index([productId, rating])
}

model AuditLog {
  id        String   @id @default(cuid())
  userId    String
  action    String   // CREATE | UPDATE | DELETE
  table     String
  recordId  String
  changes   Json     // { field: { before, after } }
  createdAt DateTime @default(now())

  @@index([table, recordId])
  @@index([userId, createdAt])
}

lib/prisma-middleware.ts — automatic soft delete + audit log
import { PrismaClient } from '@prisma/client'

const prisma = new PrismaClient()

// Middleware 1: Auto-filter soft-deleted records
prisma.$use(async (params, next) => {
  const softDeleteModels = ['Product']
  if (softDeleteModels.includes(params.model ?? '')) {
    if (params.action === 'findMany' || params.action === 'findFirst') {
      params.args.where ??= {}
      params.args.where.deletedAt = null // auto-exclude deleted
    }
    if (params.action === 'delete') {
      params.action = 'update'          // intercept DELETE
      params.args.data = { deletedAt: new Date() } // set soft delete
    }
  }
  return next(params)
})

// Middleware 2: Audit log for mutations
prisma.$use(async (params, next) => {
  const auditActions = ['create', 'update', 'delete']
  const auditModels  = ['Product', 'Order', 'Review']
  if (auditModels.includes(params.model ?? '') &&
      auditActions.includes(params.action)) {
    const result = await next(params)
    // Write audit log after successful mutation
    await prisma.auditLog.create({
      data: {
        userId:   (params.args?.data?.userId ?? 'system') as string,
        action:   params.action.toUpperCase(),
        table:    params.model ?? 'unknown',
        recordId: result?.id ?? 'unknown',
        changes:  params.args.data ?? {},
      }
    })
    return result
  }
  return next(params)
})
Cursor-based pagination for products
export async function getProducts({
  cursor, limit = 20, categoryId, search
}: {
  cursor?: string
  limit?: number
  categoryId?: string
  search?: string
}) {
  const items = await prisma.product.findMany({
    take: limit + 1,          // fetch one extra to detect hasNextPage
    cursor: cursor ? { id: cursor } : undefined,
    skip: cursor ? 1 : 0,    // skip the cursor itself
    where: {
      deletedAt: null,
      categoryId,
      name: search ? { contains: search, mode: 'insensitive' } : undefined
    },
    orderBy: { createdAt: 'desc' },
    include: { variants: true, images: { take: 1 } }
  })

  const hasNextPage = items.length > limit
  const data = hasNextPage ? items.slice(0, -1) : items
  const nextCursor = hasNextPage ? data[data.length - 1].id : null

  return { data, nextCursor, hasNextPage }
}
⚠ Schema pitfalls to avoid:
Never store price in Float — use Decimal(10,2) to avoid floating point rounding errors on money. Always store prices at time of purchase in OrderItem.unitPrice — if the product price changes, historical orders must show the original price. Never use offset pagination on tables with >100k rows. Interview Q&A

1. Why should you never store price as a Float in a database?
Floating-point numbers cannot represent most decimal fractions exactly in binary — 0.1 + 0.2 = 0.30000000000000004 in IEEE 754. For money this causes rounding errors that compound across calculations: a $199.99 item multiplied by tax and discounts can produce $200.001 or $199.998. Always use DECIMAL(10,2) (or NUMERIC) in PostgreSQL — it stores exact decimal values. In JavaScript, use a library like decimal.js for arithmetic rather than native floats. Prisma's Decimal type maps to this correctly.
2. What is a soft delete and when should you use it?
Soft delete sets a deletedAt timestamp instead of removing the row. Use it when: (1) referential integrity matters — orders reference products, deleting the product physically would orphan orders; (2) audit requirements — regulations require keeping data for 7 years; (3) undo capability — users might want to recover deleted items. Don't use it when: data must be physically removed for GDPR "right to be forgotten" (use anonymisation instead of soft delete in that case), or when the table grows so large that filtering WHERE deletedAt IS NULL becomes a bottleneck. Add a partial index to maintain performance.
3. Why use an explicit junction table (OrderItem) instead of a M:N relation?
Prisma's implicit M:N creates a hidden junction table with only the two foreign keys. An explicit OrderItem table lets you add extra fields: quantity, unitPrice (price at time of purchase), discount, notes. These fields can't exist on either the Order or the Product — they belong to the relationship between them. Rule of thumb: use implicit M:N only when the relationship itself has no data. Any time you need to store "how much?" or "when?" on the relationship, use an explicit junction table.
4. Explain cursor pagination vs offset pagination.
Offset (SKIP n TAKE m): simple but unstable and slow on large tables. If a row is inserted before your current page, all offsets shift — you get duplicates or skip items. The DB must count n rows to skip, which is O(n). Cursor pagination: use the last item's stable ID (or composite key) as the cursor. WHERE id > $cursor ORDER BY id LIMIT m — uses the index, O(log n), and is stable because the cursor is a specific position, not a count. Tradeoff: can't jump to page 5 of 100 — only next/previous. For e-commerce product lists and feed-style UIs, cursor pagination is almost always correct.
5. What is the expand/contract pattern and why is it needed?
When you deploy schema changes and application code simultaneously, there's a window where old code and new code run concurrently (during rolling deploy). If your migration renames a column, old code (reading the old column) breaks instantly. The expand/contract pattern avoids this: (1) Expand — add new column alongside old (safe); (2) Backfill — populate new column for existing rows; (3) Contract — remove old column only after all running code uses the new column. Each phase can be deployed independently with zero downtime. Most Prisma migrations are already safe (adding nullable columns), but renames always need this pattern.
6. How do composite indexes work and what order do columns go in?
A composite index on (userId, createdAt) creates a B-tree sorted by userId first, then createdAt within each userId. This index can serve: WHERE userId = ? (leftmost prefix), WHERE userId = ? ORDER BY createdAt (full use), but NOT WHERE createdAt = ? alone (no leftmost prefix). Rule: put the most selective column (highest cardinality) first for equality filters, and the range/sort column last. For ShopCo orders: (userId, createdAt DESC) perfectly serves "get user's orders newest first". The index selector always matches from left to right.
7. How do you model product variants (size/colour) in a relational database?
Three approaches: (1) Separate columns (ShopCo's approach): ProductVariant table with size and colour columns, a unique constraint on (productId, size, colour), and its own stock and sku. Simple and queryable. (2) JSON column: attributes JSON — flexible but hard to query/index. (3) EAV (Entity-Attribute-Value): a VariantOption table with (variantId, attributeName, attributeValue) — maximum flexibility, maximum complexity. For ShopCo with known attribute types, separate columns is cleanest and most performant.
8. Why store unitPrice on OrderItem instead of reading from Product?
Prices change over time. If you stored only the productId on OrderItem and read the price from the Product table, a product price change would retroactively change the order total — which is incorrect and potentially illegal. OrderItem.unitPrice is the price at the time of purchase — immutable historical fact. This is standard in e-commerce: order receipts must show what was charged, not what the product currently costs. Same principle applies to tax rates, discount amounts, and shipping costs — all should be stored on the order, not computed from current configuration.
9. What is Prisma middleware and how do you use it for cross-cutting concerns?
Prisma middleware intercepts every database operation — like an Express middleware but for Prisma. Use prisma.$use(async (params, next) => {...}). params contains the model, action, and args; next(params) executes the actual query. Common uses: (1) soft delete — intercept delete actions and convert to update; (2) auto-filter deleted — add deletedAt: null to all find queries; (3) audit logging — call next() and then log the result; (4) performance logging — time queries and log slow ones. Important: middleware runs in registration order and stacks, so order matters.
10. How do you handle database migrations safely in a CI/CD pipeline?
Never run prisma migrate deploy automatically on production without checks. Safe pipeline: (1) generate migration in dev with prisma migrate dev, commit the migration file; (2) in CI: run prisma migrate deploy against the preview database (Neon branch); (3) run integration tests against the migrated preview DB; (4) on merge to main: run prisma migrate deploy in a pre-deploy step before the new app version starts; (5) if migration fails, rollback the deploy (but NOT the migration — migrations are additive, not reversible). For risky migrations (large tables, dropping columns), run manually with monitoring and a rollback plan.
