01 REST principles — what REST actually means foundations
stateless
Each request contains all necessary information
The server stores no session state between requests. Every request must include everything needed — auth token, required parameters, body data. This makes APIs horizontally scalable (any server can handle any request) and predictable (the same request always produces the same outcome).
uniform interface
Consistent rules applied everywhere
Resources are identified by URLs. Representations (JSON) are separate from resources (database records). Actions are performed via HTTP methods — GET to read, POST to create, PUT/PATCH to update, DELETE to remove. No custom verbs in URLs like /getUserById or /deleteProduct.
resource-oriented
Think in nouns, not verbs
REST APIs expose resources (things), not operations (actions). /products is a resource. /products/42 is a specific resource. The HTTP method expresses the action. Bad: POST /createProduct. Good: POST /products. Bad: GET /getUser?id=5. Good: GET /users/5.
client-server separation
Frontend and backend evolve independently
The API contract (routes, request/response shapes) is the only coupling between client and server. The React frontend can be rewritten without touching the API. A mobile app can consume the same API. The database can be replaced. This separation is what makes REST APIs reusable across multiple clients.

03 HTTP status codes — the right code for every response status codes
200
OK
Successful GET, PATCH, DELETE. Body contains requested data or updated resource.
201
Created
Successful POST — resource created. Include Location header with new resource URL.
204
No Content
Successful DELETE or action with no response body. Empty response — no JSON.
400
Bad Request
Invalid input — missing fields, wrong types, validation failure. Return which fields failed.
401
Unauthorized
Not authenticated — no token or expired token. Misleadingly named (it's really "unauthenticated").
403
Forbidden
Authenticated but not authorised — wrong role, not the resource owner.
404
Not Found
Resource doesn't exist. Don't return 403 when you mean 404 (privacy leak).
409
Conflict
Duplicate resource — email already exists, unique constraint violated.
422
Unprocessable
Well-formed request but semantically invalid — e.g., end date before start date.
429
Too Many Requests
Rate limit exceeded. Include Retry-After header with seconds to wait.
500
Internal Server Error
Unexpected server error. Never expose stack traces. Log internally, return generic message.
503
Service Unavailable
Server overloaded or down for maintenance. Include Retry-After header.
04 Route Handlers — production-grade Next.js API endpoints implementation
typescriptComplete products API — GET list, GET one, POST, PATCH, DELETE with auth + validation
// app/api/products/route.ts — Collection endpoint
import { NextResponse, type NextRequest } from "next/server"
import { auth }         from "@clerk/nextjs/server"
import { db }           from "@/lib/db"
import { z }           from "zod"
import { apiError, apiSuccess } from "@/lib/api"

const listSchema = z.object({
  page:     z.coerce.number().int().positive().default(1),
  limit:    z.coerce.number().int().min(1).max(100).default(20),
  category: z.string().optional(),
  q:        z.string().optional(),
  sort:     z.enum(["price", "name", "createdAt", "rating"]).default("createdAt"),
  order:    z.enum(["asc", "desc"]).default("desc"),
})

export async function GET(req: NextRequest) {
  try {
    const params = Object.fromEntries(new URL(req.url).searchParams)
    const parsed = listSchema.safeParse(params)
    if (!parsed.success) return apiError(400, "Invalid query parameters", parsed.error.flatten())

    const { page, limit, category, q, sort, order } = parsed.data

    const [items, total] = await Promise.all([
      db.product.findMany({
        where: {
          published: true,
          ...category && { categoryId: category },
          ...q        && { name: { contains: q, mode: "insensitive" } },
        },
        orderBy: { [sort]: order },
        skip:    (page - 1) * limit,
        take:    limit,
        select:  { id: true, name: true, price: true, images: true, rating: true },
      }),
      db.product.count({ where: { published: true } }),
    ])

    return apiSuccess({
      items, total, page,
      totalPages: Math.ceil(total / limit),
      hasMore:    page * limit < total,
    })
  } catch (err) {
    console.error("[GET /api/products]", err)
    return apiError(500, "Failed to fetch products")
  }
}

const createSchema = z.object({
  name:       z.string().min(1).max(255),
  price:      z.number().positive(),
  categoryId: z.string().cuid(),
  description:z.string().min(10),
})

export async function POST(req: NextRequest) {
  try {
    const { userId, sessionClaims } = await auth()
    if (!userId)                             return apiError(401, "Unauthorized")
    if (sessionClaims?.metadata?.role !== "admin") return apiError(403, "Forbidden")

    const body   = await req.json()
    const parsed = createSchema.safeParse(body)
    if (!parsed.success) return apiError(400, "Validation failed", parsed.error.flatten())

    const product = await db.product.create({ data: { ...parsed.data, slug: slugify(parsed.data.name) } })

    return NextResponse.json({ data: product }, {
      status:  201,
      headers: { "Location": `/api/products/${product.id}` }
    })
  } catch (err: unknown) {
    if (isPrismaUniqueError(err)) return apiError(409, "Product with this slug already exists")
    return apiError(500, "Failed to create product")
  }
}
05 Validation & consistent error responses validation
typescriptlib/api.ts — helper functions for consistent API responses and error handling
// lib/api.ts — centralise all response shaping
import { NextResponse } from "next/server"
import { Prisma }      from "@prisma/client"
import { ZodError }   from "zod"

// ── Standard response shapes ──────────────────────────────
// Success: { data: T, meta?: object }
// Error:   { error: string, details?: object, code?: string }

export function apiSuccess<T>(data: T, meta?: object, status = 200) {
  return NextResponse.json({ data, ...meta && { meta } }, { status })
}

export function apiError(status: number, message: string, details?: unknown) {
  return NextResponse.json(
    { error: message, ...details && { details } },
    { status }
  )
}

// ── Global error handler — wrap every route in this ───────
export function withErrorHandler(
  handler: (req: NextRequest) => Promise<Response>
) {
  return async (req: NextRequest) => {
    try {
      return await handler(req)
    } catch (err) {
      // Zod validation error
      if (err instanceof ZodError) {
        return apiError(400, "Validation failed", err.flatten())
      }
      // Prisma unique constraint
      if (err instanceof Prisma.PrismaClientKnownRequestError) {
        if (err.code === "P2002") return apiError(409, "Resource already exists")
        if (err.code === "P2025") return apiError(404, "Resource not found")
      }
      // Unknown — log and return generic error
      console.error("[API Error]", err)
      return apiError(500, "Internal server error")
    }
  }
}

// ── Standard error response bodies ────────────────────────
// 400 Validation:
// { "error": "Validation failed",
//   "details": { "fieldErrors": { "name": ["Required"], "price": ["Must be positive"] } } }

// 401 Unauthorized:
// { "error": "Unauthorized" }

// 404 Not Found:
// { "error": "Product not found" }

// 409 Conflict:
// { "error": "Email already registered" }

// 500 Server Error:
// { "error": "Internal server error" }  ← never expose details in prod!

// ── Usage — cleaner routes with the wrapper ────────────────
export const GET = withErrorHandler(async (req) => {
  const { userId } = await auth()
  if (!userId) return apiError(401, "Unauthorized")

  const products = await db.product.findMany()   // throws → caught by wrapper
  return apiSuccess(products)
})
06 Rate limiting, CORS & versioning strategies production
typescriptRate limiting headers, CORS setup, and API versioning approaches
// ── Rate limiting — headers-based approach ────────────────
// npm install @upstash/ratelimit @upstash/redis
import { Ratelimit } from "@upstash/ratelimit"
import { Redis }     from "@upstash/redis"

const ratelimit = new Ratelimit({
  redis:     Redis.fromEnv(),
  limiter:   Ratelimit.slidingWindow(100, "1 m"),  // 100 req/min
  analytics: true,
})

export async function GET(req: NextRequest) {
  const ip  = req.headers.get("x-forwarded-for") ?? "anonymous"
  const { success, limit, remaining, reset } = await ratelimit.limit(ip)

  const rateLimitHeaders = {
    "X-RateLimit-Limit":     String(limit),
    "X-RateLimit-Remaining": String(remaining),
    "X-RateLimit-Reset":     String(reset),
  }

  if (!success) {
    return NextResponse.json(
      { error: "Too many requests", retryAfter: Math.ceil((reset - Date.now()) / 1000) },
      { status: 429, headers: { ...rateLimitHeaders, "Retry-After": String(Math.ceil((reset-Date.now())/1000)) } }
    )
  }

  // Proceed with request, add rate limit headers to response
  const response = await handleRequest(req)
  Object.entries(rateLimitHeaders).forEach(([k,v]) => response.headers.set(k,v))
  return response
}

// ── CORS — for APIs consumed by external clients ──────────
// next.config.js — add CORS headers globally:
const nextConfig = {
  async headers() {
    return [{ source: "/api/:path*", headers: [
      { key: "Access-Control-Allow-Origin",  value: "https://yourapp.com" },
      { key: "Access-Control-Allow-Methods", value: "GET,POST,PATCH,DELETE,OPTIONS" },
      { key: "Access-Control-Allow-Headers", value: "Content-Type,Authorization" },
    ]}]
  }
}
// Handle OPTIONS preflight in route handlers:
export function OPTIONS() {
  return new Response(null, { status: 204, headers: { "Access-Control-Allow-Origin": "*" } })
}

// ── API Versioning ────────────────────────────────────────
// Option A: URL versioning (most common, most explicit)
// app/api/v1/products/route.ts → /api/v1/products
// app/api/v2/products/route.ts → /api/v2/products

// Option B: Header versioning
// GET /api/products   Accept: application/vnd.shopco.v2+json
export async function GET(req: NextRequest) {
  const version = req.headers.get("API-Version") ?? "1"
  if (version === "2") return handleV2(req)
  return handleV1(req)
}

// Deprecation: add Deprecation header to old version responses
return NextResponse.json(data, {

08 Interview questions + model answers 10 Q&As
Q1What are the key principles of RESTful API design?▶
model answer
REST has six guiding constraints. The most practically important are: statelessness — each request contains all the information needed; the server stores no session state between requests, enabling horizontal scaling. Uniform interface — resources are identified by URLs, HTTP methods express the action (GET reads, POST creates, PUT/PATCH updates, DELETE removes), and responses use a consistent shape. Client-server separation — the API contract is the only coupling; frontend and backend evolve independently.

In practice, this means: use nouns in URLs (not verbs), use plural nouns for collections, use HTTP methods correctly, use standard status codes semantically, and keep your response shape consistent across all endpoints. The "REST" label is overloaded — most "REST APIs" are actually REST-ish, which is fine as long as they're consistent.
Q2What's the difference between 401 and 403? Between 400 and 422?▶
model answer
401 vs 403: 401 (Unauthorized, confusingly named) means "you haven't identified yourself yet" — there's no valid token, or the token has expired. The user should log in. 403 (Forbidden) means "I know who you are but you don't have permission" — the user is authenticated but lacks the required role or doesn't own the resource. Don't return 403 when you mean 404 — that leaks information about the existence of resources.

400 vs 422: 400 (Bad Request) means the request is malformed — missing required fields, wrong data types, invalid JSON. 422 (Unprocessable Entity) means the request is syntactically valid but semantically invalid — the data makes sense structurally but fails business logic validation (e.g., an end date that precedes the start date, or a negative price). In practice, many APIs use 400 for both and reserve 422 only for complex cross-field validation errors.
Q3How do you design a consistent error response shape?▶
model answer
The most important thing is consistency — every error in your API should have the same top-level shape. A good pattern: { "error": "human-readable message", "code": "MACHINE_READABLE_CODE", "details": { ... } }.

The error field is the user-facing message. The code is a string constant your frontend can programmatically check (like "INSUFFICIENT_STOCK" or "EMAIL_TAKEN") to show tailored UI. The details object carries context-specific information — for validation errors, it should contain { "fieldErrors": { "email": ["Invalid format"], "price": ["Must be positive"] } }.

Never expose stack traces in production — that's a security vulnerability. Log the full error internally, return only a generic message. Never invent your own status codes — use the 4xx/5xx range semantically. The investment in a consistent error shape pays off when every error boundary and React Query onError handler can process errors identically.
Q4What is idempotency and which HTTP methods are idempotent?▶
model answer
An idempotent operation produces the same result when executed once or multiple times. If a network error causes a client to retry a request, an idempotent endpoint produces the same outcome — no duplicate data, no double charges.

Idempotent: GET (read-only, always same data), PUT (replace entire resource — same request = same result), DELETE (delete twice = resource still deleted), HEAD, OPTIONS. Not idempotent: POST (each call creates a new resource — two POST calls create two products). PATCH can be idempotent if it sets absolute values ({ price: 1999 }) but not if it uses relative operations ({ stock: { increment: 1 } } twice = incremented twice).

Practical implication: when building retry logic (like React Query's automatic retries), only retry idempotent requests automatically. For POST, require the user to explicitly retry to avoid duplicates. Alternatively, implement idempotency keys for POST — the client sends a unique key, the server stores it, and duplicate requests with the same key return the same response without re-executing.
Q5How do you implement rate limiting in a Next.js API?▶
model answer
Rate limiting requires a shared store across serverless function invocations — an in-memory Map doesn't work because each invocation may be on a different server instance. The standard solution is Redis, which maintains state across all instances.

For Next.js: use Upstash Redis (serverless-friendly, HTTP-based) with the @upstash/ratelimit package. Configure a sliding window limiter (100 requests per minute per IP, for example). In each Route Handler, check the rate limit before processing. If exceeded, return 429 with the appropriate headers: X-RateLimit-Limit (total limit), X-RateLimit-Remaining (left in current window), X-RateLimit-Reset (epoch when window resets), and Retry-After (seconds until retry is allowed).

Different limits for different endpoints: public endpoints can be generous (1000/min), authenticated endpoints moderate (100/min), write operations strict (10/min for POST, 5/min for payment endpoints). Use user ID for authenticated users, IP for anonymous — per-IP for anonymous helps prevent bot scraping.
Q6What is CORS and when do you need to handle it?▶
model answer
CORS (Cross-Origin Resource Sharing) is a browser security mechanism that blocks JavaScript from making requests to a different origin (domain/port/protocol) than the page that loaded it. The browser sends an OPTIONS preflight request first, and the server must respond with the appropriate Access-Control-Allow-* headers for the actual request to proceed.

When do you need it: when your API is consumed by a browser-based client from a different origin. If your Next.js frontend and API are on the same domain (e.g., both on shopco.vercel.app), you don't need CORS — same-origin requests are always allowed. You do need CORS if: a React Native app or external website calls your API, you build a public API that others can use, or you serve your API from a different subdomain than your frontend.

In Next.js: add the Access-Control-Allow-Origin header to your Route Handlers (or globally in next.config.js), and add an OPTIONS export that returns 204 for the preflight. Be specific about the allowed origins — * allows any site, which may not be what you want for authenticated endpoints.
Q7What are the different API versioning strategies and which do you prefer?▶
model answer
Three common approaches. URL versioning (/api/v1/products, /api/v2/products) is the most explicit and cacheable — clients can bookmark exact versions, and old versions continue to work after new ones are deployed. Downside: URL proliferation, maintaining multiple code paths.

Header versioning (Accept: application/vnd.shopco.v2+json or API-Version: 2) keeps URLs clean but is invisible in browser history and harder to test without tooling. Preferred by API purists for following REST principles more closely.

Query parameter versioning (/api/products?v=2) is easy to test but breaks caching and looks messy.

My preference: URL versioning for public APIs (explicit, debuggable, cacheable). For internal APIs between your own services or frontend, I prefer no versioning at all — use Server Actions or tRPC where the client and server types are always in sync by definition, eliminating versioning concerns entirely.
Q8How do you validate request bodies in Next.js Route Handlers?▶
model answer
Use Zod for all input validation — it handles both runtime validation and TypeScript type inference simultaneously. The pattern: define a schema, call safeParse(body) on the parsed request body, check result.success, and return 400 with the flattened errors if it fails.

const body = await req.json(); const result = schema.safeParse(body); if (!result.success) return NextResponse.json({ error: "Validation failed", details: result.error.flatten() }, { status: 400 })

For query parameters (which arrive as strings from the URL), use z.coerce.number(), z.coerce.boolean() etc. to automatically convert strings to the right types. Use .default() to provide fallbacks.

Centralise the error handling in a wrapper function so every route handler gets automatic Zod error → 400 mapping without repeating the check. Also catch Prisma's P2002 (unique constraint) error and return 409, and P2025 (not found) → 404.
Q9When should you use Server Actions vs Route Handlers?▶
model answer
Server Actions are for mutations triggered by your own React UI. They're called directly from components — no fetch needed, no API endpoint to design, and they work with progressive enhancement (native form POST works without JS). They handle authentication automatically through Clerk's auth() and can revalidate the React Query or Next.js cache. Use them for: form submissions, cart operations, user profile updates, any write operation triggered by your own frontend.

Route Handlers (route.ts) are for building an actual HTTP API — when you need the endpoint to be consumed by external clients: a mobile app, a third-party webhook, another service, or a public API that other developers can use. Also use them for: webhooks from external services (like Clerk or Stripe), CORS-sensitive endpoints, cases where you need explicit control over HTTP headers and status codes.

Rule of thumb: if only your own Next.js UI calls it, use a Server Action. If anything outside your Next.js app calls it, use a Route Handler.
Q10How do you document an API and what tools do you use?▶
model answer
The best API documentation is generated from the code itself — never maintained separately. Three approaches depending on the stack. TypeScript + tRPC or Server Actions: the type system IS the documentation. Consumers see exact input/output types in their IDE with zero manual effort. Zod schemas: since schemas define validation and types simultaneously, tools like zod-to-json-schema and swagger-jsdoc can generate OpenAPI specs from them automatically. OpenAPI/Swagger: for public REST APIs, write an OpenAPI spec (YAML) and use Swagger UI to serve interactive documentation — clients can try endpoints directly from the docs.

At minimum, any public API should document: all endpoints with their URL and method, all request parameters with types and validation rules, all response shapes with examples (both success and error), authentication requirements, rate limits, and changelog. Keep docs in the same repo as the code and treat documentation failures as bugs — stale docs are worse than no docs because they actively mislead consumers.
For Next.js internal APIs, consider switching to Server Actions or tRPC — they eliminate the documentation problem by making the TypeScript types the documentation, auto-synced with the implementation.
