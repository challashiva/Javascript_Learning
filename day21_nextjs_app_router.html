01 Why Next.js — what vanilla React can't do motivation
SPA limitations
Vite + React ships a blank HTML shell
A pure React SPA sends an empty <div id="root"> to the browser. JavaScript downloads, parses, executes, fetches data, then renders. The user sees a blank screen or spinner for 2–4 seconds. Bots and search engines see nothing crawlable. Every route change triggers another fetch waterfall.
Next.js solution
HTML arrives pre-rendered with real content
Next.js runs React on the server, fetches data there, and sends HTML with actual content to the browser. First paint is near-instant. Search engines index real text. Subsequent navigation uses JavaScript for smooth SPA-style transitions. You get both SEO and interactivity.
full-stack in one repo
API routes, DB queries, auth — all co-located
Next.js lets you write server-side code (database queries, secret API keys, auth logic) right next to your components. No separate Express server needed. Route Handlers replace REST API files. Server Actions replace manual POST endpoints. One TypeScript codebase handles everything.
the ecosystem
Vercel, shadcn/ui, Prisma — built for Next.js
The entire modern React ecosystem converged on Next.js. Vercel deploys it with zero config. shadcn/ui components are Next.js first. Prisma's connection pooling integrates seamlessly. Clerk's auth SDK wraps the App Router. Choosing Next.js means choosing the path of least resistance.

// app/products/page.tsx

export default async function ProductsPage() {

          {/* Pass Client Component as child — composition pattern */}
          <AddToCart productId={product.id} price={product.price} />
        </ProductCard>
      ))}
    </div>
  )

// ── Key rule: "use client" propagates DOWN the tree ──────
// If a component is "use client", ALL its imports are also client.
// If a component has NO directive, it's a Server Component.
// The boundary is one-way: server can render client, not vice versa.
// Exception: server components can be passed as children/props to client components.
04 Client components — when and how to use them client
When to add "use client"
✅ Always use "use client" for
Components that use useState, useEffect, useRef, useContext, or any other hook. Event handlers (onClick, onChange). Browser APIs (localStorage, navigator, window). Third-party libraries that use these.
❌ Don't use "use client" for
Components that only receive props and render HTML. Data fetching components (fetch from DB on server instead). Static UI like Footer, Navbar links, prose content. Anything that doesn't need interactivity.
Push "use client" down
Keep the client boundary as low as possible in the tree. A page should be a Server Component; only the interactive button inside needs "use client". This minimises JS bundle and maximises server rendering.
The children pattern
Server Components can be passed as children to Client Components. <ClientShell><ServerContent /></ClientShell> works because ServerContent is already rendered on the server before being passed as a prop.

// ── Providers must be Client Components ─────────────────
// app/providers.tsx
"use client"

import { QueryClient, QueryClientProvider } from "@tanstack/react-query"
import { useState }                          from "react"

export function Providers({ children }: { children: React.ReactNode }) {
  // useState prevents QueryClient from being shared across requests on the server
  const [queryClient] = useState(() => new QueryClient())

  return (
    <QueryClientProvider client={queryClient}>
      {children}  {/* children can be Server Components! */}
    </QueryClientProvider>
  )
}

        {children}     {/* Server Components — passed as children */}
      </Providers>
    </body></html>
  )
}

// ── useRouter, usePathname, useSearchParams ───────────────
// app/components/SearchBar.tsx
"use client"

import { useRouter, useSearchParams, usePathname } from "next/navigation"

export function SearchBar() {
  const router       = useRouter()
  const pathname     = usePathname()      // /products
  const searchParams = useSearchParams()  // ?q=laptop&category=electronics

  function handleSearch(q: string) {
    const params = new URLSearchParams(searchParams.toString())
    if (q) params.set("q", q)
    else params.delete("q")
    router.replace(`${pathname}?${params}`)  // updates URL without full page reload
  }

  return <input
    defaultValue={searchParams.get("q") ?? ""}
    onChange={e => handleSearch(e.target.value)}
  />
}
05 Data fetching — fetch(), cache, revalidate data
tsxServer-side data fetching — fetch options, cache(), unstable_cache, parallel
// Next.js extends the native fetch() API with caching options.
// All fetch() calls in Server Components are automatically deduped.

// ── fetch() caching options ───────────────────────────────
// Default: cached forever until manually revalidated (ISR)
const data = await fetch("https://api.example.com/products")

// Revalidate every 60 seconds (ISR — Incremental Static Regeneration)
const data = await fetch("https://api.example.com/products", {
  next: { revalidate: 60 }
})

// Never cache — always fetch fresh (equivalent to getServerSideProps)
const data = await fetch("https://api.example.com/cart", {
  cache: "no-store"
})

// ── cache() — deduplicate expensive operations ────────────
import { cache } from "react"

// Memoized for the duration of a single request — safe to call in multiple components
export const getProduct = cache(async (id: string) => {
  return db.product.findUnique({ where: { id } })
})
// Called in page.tsx AND generateMetadata() — DB only hit once!

// ── unstable_cache — persistent cache with tags ───────────
import { unstable_cache } from "next/cache"

export const getCachedProduct = unstable_cache(
  async (id: string) => db.product.findUnique({ where: { id } }),
  ["product"],              // cache key prefix
  { tags: ["products"], revalidate: 3600 }
)
// Invalidate with: revalidateTag("products") in a Server Action

// ── Parallel data fetching — don't await sequentially ────
export default async function ProductPage({ params }: Props) {
  const { id } = await params

  // ❌ Sequential — slow (each awaits previous)
  const product  = await getProduct(id)
  const reviews  = await getReviews(id)
  const related  = await getRelated(id)

  // ✅ Parallel — fast (all fire at once)
  const [product, reviews, related] = await Promise.all([
    getProduct(id),
    getReviews(id),
    getRelated(id),
  ])

  return <ProductDetail product={product} reviews={reviews} related={related} />
}
06 Server Actions — mutations without an API layer mutations
tsxServer Actions — form submission, revalidation, progressive enhancement
// Server Actions are async functions that run on the server.
// They're called directly from components — no fetch("/api/...") needed.
// Progressive enhancement: work without JavaScript (native form POST).

// ── Define in a server action file ────────────────────────
// app/actions/products.ts
"use server"   // marks this module as server-only

import { revalidatePath, revalidateTag } from "next/cache"
import { redirect }                       from "next/navigation"
import { z }                              from "zod"

const createProductSchema = z.object({
  name:  z.string().min(1),
  price: z.coerce.number().positive(),  // coerce: form values are strings
})

export async function createProduct(prevState: unknown, formData: FormData) {
  // Validate with Zod
  const parsed = createProductSchema.safeParse({
    name:  formData.get("name"),
    price: formData.get("price"),
  })
  if (!parsed.success) {
    return { errors: parsed.error.flatten().fieldErrors }
  }

  // Direct DB write — no API route needed
  const product = await db.product.create({ data: parsed.data })

  // Revalidate — next visit to /products will fetch fresh data
  revalidatePath("/products")
  revalidateTag("products")

  // Redirect to new product page
  redirect(`/products/${product.id}`)
}

}

// ── Route Handler — REST API in Next.js ───────────────────
// app/api/products/route.ts
import { NextResponse, type NextRequest } from "next/server"

export async function GET(request: NextRequest) {
  const { searchParams } = new URL(request.url)
  const page     = searchParams.get("page") ?? "1"
  const products = await db.product.findMany({ take: 20, skip: (+page-1)*20 })
  return NextResponse.json({ products, page: +page })
}

export async function POST(request: NextRequest) {
  const body    = await request.json()
  const session = await getSession()
  if (!session) return NextResponse.json({ error: "Unauthorized" }, { status: 401 })
  const product = await db.product.create({ data: body })
  return NextResponse.json(product, { status: 201 })
}

// ── Middleware — auth guard, A/B tests, redirects ─────────
// middleware.ts (at root, next to app/)
import { NextResponse, type NextRequest } from "next/server"
import { getSessionFromCookie }          from "@/lib/auth"

export async function middleware(request: NextRequest) {
  const isProtected = request.nextUrl.pathname.startsWith("/dashboard")
  if (isProtected) {
    const session = await getSessionFromCookie(request.cookies)
    if (!session) {
      return NextResponse.redirect(new URL("/login", request.url))
    }
  }
  return NextResponse.next()
}

09 Interview questions + model answers 10 Q&As
Q1What problems does Next.js App Router solve that plain React/Vite can't?▶
model answer
Three concrete problems. First, SEO and performance: a Vite React SPA sends an empty HTML shell — bots see nothing and users wait for JS to execute before seeing content. Next.js renders on the server and sends real HTML, making first-paint near-instant and making every page crawlable.

Second, data fetch waterfalls: in a SPA, data fetching starts only after the JS executes and components mount. Next.js fetches data during server rendering — by the time HTML arrives at the browser, the data is already embedded in it. No loading spinners for initial page loads.

Third, full-stack in one project: Next.js lets you write server-side logic (DB queries, auth checks, API keys) co-located with your components. Server Actions and Route Handlers eliminate the need for a separate API server. One TypeScript codebase handles frontend and backend with shared types.
Q2What is a Server Component and how does it differ from a Client Component?▶
model answer
Server Components run only on the server — they're never sent to the browser as JavaScript. They can be async, use await, access databases directly, use secret environment variables, and produce zero JS bundle. They cannot use hooks, event handlers, or browser APIs.

Client Components are marked with "use client". They run on the server for the initial HTML (server-side rendering), then the JavaScript is sent to the browser for hydration and interactivity. They can use all React hooks, browser APIs, and event handlers — but cannot access the database or secrets directly.

In the App Router, everything is a Server Component by default. You opt in to Client Components only when you need interactivity. The design goal: push the "use client" boundary as low as possible in the tree to minimise JavaScript sent to the browser.
Q3How does file-based routing work in the App Router?▶
model answer
The app/ directory structure maps directly to URL routes. A page.tsx file defines a route — app/products/page.tsx → /products. Dynamic segments use brackets: app/products/[id]/page.tsx → /products/:id, with the ID available via params.id. Catch-all segments use spread: [...slug] → matches any number of segments.

Special files: layout.tsx wraps a route and its children, persisting across navigation (like a shell); loading.tsx is an automatic Suspense fallback shown while the page fetches; error.tsx is an error boundary; not-found.tsx renders when notFound() is called.

Route groups use parentheses — (marketing)/about/page.tsx routes to /about. The group name doesn't appear in the URL. This lets you apply different layouts to different sections without affecting URLs.
Q4What are Server Actions and how do they work?▶
model answer
Server Actions are async functions marked with "use server" that run on the server. They're called directly from components — no fetch("/api/...") needed. When a form's action prop is set to a Server Action, submitting the form POSTs to the server, the action runs, and the response is returned — this even works without JavaScript (progressive enhancement).

The lifecycle: function receives FormData → validate with Zod → write to database → call revalidatePath() or revalidateTag() to invalidate cache → optionally redirect() or return state.

For rich client-side feedback, pair with useActionState in a Client Component: it provides the pending state, the returned state, and the form action function. The action still runs on the server — the client just gets status updates and can show loading/error UI.
Server Actions replace what you'd previously do with an API route handler + fetch + useState(loading/error). They collapse 4 files into 1 function.
Q5How does Next.js caching work — what are the different caching layers?▶
model answer
Next.js has multiple caching layers. The fetch cache is the most important: Next.js extends the native fetch() API — by default requests are cached indefinitely (equivalent to ISR). You opt into revalidation with { next: { revalidate: 60 } } (revalidate every 60s) or opt out with { cache: "no-store" } (always fresh).

Within a single request, request memoization deduplicates identical fetch calls. If generateMetadata and page.tsx both call getProduct(id), the database is only hit once. The React cache() function makes this explicit for non-fetch operations like direct DB calls.

Revalidation: call revalidatePath("/products") in a Server Action after a mutation to mark that path's cache as stale. revalidateTag("products") invalidates all fetches tagged with "products", regardless of URL. On next request, Next.js regenerates the page.
Q6How do you pass data from a Server Component to a Client Component?▶
model answer
Pass data as props — the same as always. The Server Component fetches data, then passes it to the Client Component via props. The key constraint: the props must be serialisable (no functions, no class instances, no circular references) because they cross the server-client boundary.

async function ProductPage() { const product = await db.product.findUnique({...}); return <AddToCart productId={product.id} price={product.price} /> }

For more complex sharing, Server Components can be passed as children to Client Components. A Client Component provider can wrap Server Component pages: the server-rendered HTML is passed as children already rendered, so it doesn't re-render when the Client Component state changes. This is the pattern for wrapping with QueryClient, ThemeProvider, etc.
Q7What is streaming and how does loading.tsx enable it?▶
model answer
Streaming lets Next.js send HTML to the browser in chunks as each part of the page becomes ready, rather than waiting for all data to be fetched before sending anything. The browser can display fast sections immediately while slower sections load.

loading.tsx creates an automatic Suspense boundary around the page. While the page.tsx Server Component is fetching data, Next.js streams the layout + loading skeleton to the browser instantly. When the page data is ready, the next chunk streams in, replacing the skeleton. The user sees content immediately — no blank page.

For finer control, use manual <Suspense> boundaries inside a page. Wrap slow sections — reviews, related products — with their own Suspense and fallback. Fast sections (product name, price) render immediately; slow sections stream in as they complete, each replacing its skeleton independently.
Q8What is middleware in Next.js and what can you use it for?▶
model answer
Middleware runs before every request, before the route is matched and before caching is applied. It runs at the Edge (close to the user, not the full Node.js runtime), so it's extremely fast but has limited APIs — no database access, no heavy computation.

Common uses: auth guards (redirect unauthenticated users to login before they see the page), A/B testing (read a cookie, rewrite to different variants), internationalisation (detect locale from headers, redirect to /en or /fr), rate limiting (count requests in Edge KV), custom headers (add security headers to all responses).

Configure which routes middleware runs on with the matcher export. Without a matcher, middleware runs on every route — including static files — which is slow. Be specific: matcher: ["/dashboard/:path*", "/api/:path*"].
Q9How do Route Handlers differ from Server Actions and when do you use each?▶
model answer
Route Handlers (route.ts) are REST API endpoints — they handle arbitrary HTTP methods and are accessible from anywhere (browser, mobile apps, third-party services, cron jobs). They return a Response or NextResponse and are consumed with fetch().

Server Actions are called directly from React components — no manual fetch needed. They're tightly coupled to your UI and work with progressive enhancement (native form POST). They return state consumed by useActionState and can redirect or revalidate cache.

Use Route Handlers when: you're building an API consumed by external clients (mobile app, third-party webhooks, cron jobs), you need explicit control over HTTP status codes and headers, or you're building a REST API for other teams. Use Server Actions when: the mutation is triggered by your own UI, you want type safety and no manual fetch, or you want progressive enhancement for forms.
Q10How do you handle SEO and metadata in Next.js App Router?▶
model answer
The App Router has a built-in Metadata API. Export a metadata object from any page.tsx or layout.tsx: export const metadata: Metadata = { title: "Products", description: "..." }. For dynamic metadata, export an async generateMetadata function that receives params and searchParams.

The root layout uses a title.template to add the site name automatically: { template: "%s | ShopCo", default: "ShopCo" } — every page's title automatically gets " | ShopCo" appended without the page needing to know about it.

Open Graph and Twitter card metadata is also handled: openGraph: { images: [{ url: product.image }], type: "product" }. Next.js generates the correct <meta> tags and handles the generateMetadata call in parallel with page.tsx rendering — the fetch is deduplicated so the database is only hit once even if both functions call getProduct(id).
